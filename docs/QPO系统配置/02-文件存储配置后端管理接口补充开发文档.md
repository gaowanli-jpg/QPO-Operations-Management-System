# File Storage Config Backend API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 补齐“系统配置 > 文件存储”前端页面依赖的后端管理接口，让 LOCAL / MINIO 配置可以查询、保存、测试、激活和停用，形成完整可用闭环。

**Architecture:** 继续沿用阶段 1-6 已落地的表结构、权限点、存储抽象和部署配置，不新增新的存储表。新增一层后端管理服务负责 DTO、字段校验、密钥保留/脱敏、测试状态落库、激活互斥和操作审计，再由 Controller 暴露 `/api/system/storage-configs` 接口给阶段 5 前端页面调用。

**Tech Stack:** Spring Boot 3.2、MyBatis Plus、PostgreSQL JSONB、现有 `@RequirePermission`、现有 `AuditService`、现有 `FileStorageConfigService` / `FileStorageTestService` / `FileStorageProvider`。

## 原文档缺口说明

阶段 5 写了前端系统配置页和 API service，阶段 6 写了部署配置与 MinIO 验证，但原 `01-文件存储配置与MinIO切换开发文档.md` 没有把“后端配置管理 Controller + 保存/测试/激活服务”拆成独立阶段。

这会导致一个实际问题：

- 前端已调用 `GET /api/system/storage-configs` 等接口。
- 后端已有存储底层能力，但没有接收这些前端请求的 Controller。
- 因此页面会出现接口 404 或功能无法真正操作配置。

本补充文档作为新增阶段 7 执行，目标是补齐这个中间层。

## Global Constraints

- 不改 `drawingUrl` 业务字段语义，仍保存 `/uploads/...` 稳定路径。
- 不新增 `common:*` 权限，继续复用阶段 1 已新增的 `system:config:*` 权限。
- 不把 `accessSecret`、`ERP_MINIO_SECRET_KEY`、token、Authorization header 写入响应、操作日志、文件日志或异常 message。
- 不让前端直接管理 `system_file_object`，文件对象元数据只由文件保存/读取链路维护。
- 本阶段不做历史图纸迁移，不修改 RFQ/订单/议价提单文件保存流程。
- 本阶段不要求创建 MinIO bucket 策略；测试逻辑只验证 bucket 可访问、可写、可读、可删。
- 本地开发默认 LOCAL；MINIO 仅在配置页新增并测试激活后影响新上传文件。

## API 合同

### 1. 查询配置列表

```http
GET /api/system/storage-configs
Permission: system:config:view
```

响应直接返回数组，保持和 `SystemUserController.listUsers()` 等系统接口风格一致：

```json
[
  {
    "id": 1,
    "name": "Default local upload storage",
    "storageType": "LOCAL",
    "active": true,
    "enabled": true,
    "rootDir": "/data/uploads",
    "endpoint": null,
    "bucket": null,
    "accessKey": null,
    "accessSecret": null,
    "region": null,
    "pathStyle": true,
    "publicReadEnabled": false,
    "publicBaseUrl": null,
    "remark": "Default LOCAL storage",
    "lastTestStatus": "SUCCESS",
    "lastTestMessage": "Local storage test completed",
    "lastTestAt": "2026-07-30T12:00:00",
    "createdAt": "2026-07-30T12:00:00",
    "updatedAt": "2026-07-30T12:00:00"
  }
]
```

### 2. 查询当前激活配置

```http
GET /api/system/storage-configs/active
Permission: system:config:view
```

响应为单个 `SystemStorageConfigDTO`。如果历史异常导致没有激活配置，返回 `null`，不要抛 500；同时记录 WARN，提示管理员检查初始化数据。

### 3. 新增配置

```http
POST /api/system/storage-configs
Permission: system:config:storage:update
Content-Type: application/json
```

请求：

```json
{
  "name": "测试 MinIO",
  "storageType": "MINIO",
  "rootDir": null,
  "endpoint": "http://127.0.0.1:9000",
  "bucket": "qpo-drawings",
  "accessKey": "qpo-service",
  "accessSecret": "secret-value",
  "region": "us-east-1",
  "pathStyle": true,
  "publicReadEnabled": true,
  "publicBaseUrl": "http://127.0.0.1:9000/qpo-drawings",
  "remark": "本地验证 MinIO"
}
```

响应：

```json
{
  "success": true,
  "message": "文件存储配置已保存",
  "data": {
    "id": 2,
    "name": "测试 MinIO",
    "storageType": "MINIO",
    "active": false,
    "enabled": true,
    "endpoint": "http://127.0.0.1:9000",
    "bucket": "qpo-drawings",
    "accessKey": "qpo-service",
    "accessSecret": "******"
  }
}
```

### 4. 编辑配置

```http
PUT /api/system/storage-configs/{id}
Permission: system:config:storage:update
```

规则：

- `storageType` 不允许编辑后改变。
- MINIO 编辑时 `accessSecret` 为空表示沿用旧密钥。
- MINIO 编辑时 `accessSecret` 非空表示覆盖旧密钥。
- 已激活配置允许编辑非关键说明字段，但编辑 endpoint/bucket/accessKey/accessSecret/rootDir 后必须把 `lastTestStatus` 重置为 `null`，避免旧测试结果误导激活判断。

### 5. 测试配置

```http
POST /api/system/storage-configs/{id}/test
Permission: system:config:storage:test
```

行为：

- LOCAL：创建临时测试文件、读取、删除。
- MINIO：确认 bucket 可访问；如 bucket 不存在，由现有 `MinioFileStorageProvider.test(...)` 当前逻辑尝试创建；然后上传临时对象、读取或 stat、删除。
- 成功时更新 `last_test_status='SUCCESS'`、`last_test_message`、`last_test_at`。
- 失败时更新 `last_test_status='FAILED'`、脱敏后的失败摘要、`last_test_at`，接口返回失败 message，不回传堆栈和 secret。

### 6. 激活配置

```http
PUT /api/system/storage-configs/{id}/activate
Permission: system:config:storage:activate
```

规则：

- 配置必须存在且 `enabled=true`。
- 配置必须最近一次测试成功：`last_test_status='SUCCESS'`。
- 一个事务内先将其他配置 `active=false`，再将目标配置 `active=true`。
- 激活只影响之后上传的新文件，历史文件仍由 `system_file_object.storage_type + storage_config_id` 读取。

### 7. 停用配置

```http
PUT /api/system/storage-configs/{id}/disable
Permission: system:config:storage:update
```

规则：

- 已激活配置不能停用。
- 停用使用 `enabled=false`，不物理删除。
- 停用后配置不参与激活，也不参与新文件写入。

public Map<String, Object> testConfig(Long id) {
    SystemFileStorageConfig entity = requireConfig(id);
    try {
        StorageTestResult result = testService.test(configService.toDomain(entity));
        updateTestResult(entity.getId(), result.success() ? "SUCCESS" : "FAILED", sanitizeMessage(result.message()));
        auditService.record(result.success() ? "SYSTEM_STORAGE_CONFIG_TEST" : "SYSTEM_STORAGE_CONFIG_TEST_FAILED",
                "system_file_storage_config", id, null, testSummary(entity, result));
        return Map.of("success", result.success(), "message", sanitizeMessage(result.message()), "data", result);
    } catch (RuntimeException e) {
        String message = sanitizeMessage(e.getMessage());
        updateTestResult(entity.getId(), "FAILED", message);
        auditService.record("SYSTEM_STORAGE_CONFIG_TEST_FAILED", "system_file_storage_config", id, null,
                Map.of("id", id, "storageType", entity.getStorageType(), "message", message),
                "SYSTEM", "FAILED", "文件存储配置测试失败", message);
        log.warn("Storage config test failed configId={} storageType={} message={}", id, entity.getStorageType(), message);
        return Map.of("success", false, "message", message);
    }
}

## 验收标准

- 系统配置页打开后可以成功查询配置列表和当前激活配置。
- 新增 LOCAL 配置后可测试成功，但不自动激活。
- 新增 MINIO 配置后可测试成功，并在激活后成为唯一激活配置。
- 激活 MINIO 后新上传文件走当前激活配置；历史本地文件仍能通过 `/uploads/**` 兜底读取。
- 停用非激活配置成功；停用激活配置被拒绝。
- 编辑 MINIO 时不回显明文 `accessSecret`；留空提交沿用旧密钥。
- 所有响应、操作日志和后端日志不包含明文 secret。
- 未授权用户不能调用保存、测试、激活、停用接口；后端 `@RequirePermission` 是最终边界。
