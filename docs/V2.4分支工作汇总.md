## 0. 一句话概括

V2.4 是一条**纯 MES 对接深化 + 待产零件流程自动化**的迭代分支。没有新模块、没有 UI 改版，
全部工作围绕一个核心矛盾展开：**MES 的物料准备任务按「图号+版本+材质」全局唯一，而 QPO 的
下发/回调/重试链路在多轮迭代后才真正对齐这个契约**。中间穿插列表可用性（创建时间、排序、
大分页）、权限父节点数据修复、以及打包部署的工程化修补。

发布节奏：`v2.4.1-20261027` → `v2.4.2` → `v2.4.3` → `v2.4.4` → `v2.4.5-20261029`
→ `v2.4.6/v2.4.7-20261030`（后两个标签指向同一个提交 `0a945c8`）。

## 1. 主线一：待产零件每日定时自动下发 MES

**提交**：`c974f4f`(主体) → `d0be98e`(熔断修正) → `ee3c336`(环境变量) → `0340394`(构建修复)
**规模**：新增后端 10 个文件约 1100 行 + 前端 300 行 + 迁移 V66 + 规划文档 532 行

### 业务目标
每天 17:00 把当时所有待下发行一次下发完，不设每日总量上限、不顺延到次日；
只靠「小批次 + 批间隔 + 串行执行」控制瞬时负载，避免影响其他在线用户。

### 实现要点
| 层 | 内容 |
|---|---|
| 配置表 | `production_item_auto_dispatch_config`（单行配置）：`enabled`(默认关)、`daily_run_time`(17:00)、`batch_size`(200)、`batch_interval_ms`(3000)、`max_rounds`(50)、`failure_breaker`(3)、`warn_duration_ms`(1h)、`include_failed`(预留) + 一整套 `last_*` 执行快照字段 |
| 调度 | `ProductionItemAutoDispatchScheduler` `@Scheduled` 轮询 + `last_run_date` **CAS 认领**，多实例部署不会重复跑 |
| 执行 | `ProductionItemAutoDispatchService` 循环取候选到空；独立**单线程池**（`ProductionAutoDispatchExecutorConfig`），不挤占手动下发的线程 |
| 候选 SQL | 按销售订单排序，**切批不跨订单**，减少对数据中心的请求次数；两处 `EXISTS` 追加 `source_order_id` 一致性校验，把会被上下文加载器判 error 的错位行在 SQL 层就排除 |
| 接口 | `GET/PUT auto-dispatch/config`、`POST auto-dispatch/run-now` |
| 权限 | V66 新增 **239 `market:production-item:mes-production-schedule`**「待产零件定时下发策略」 |
| 审计 | `PRODUCTION_ITEM_MES_PRODUCTION_AUTO_SUBMIT`、`PRODUCTION_ITEM_AUTO_DISPATCH_CONFIG_UPDATE` |
| 前端 | 待产零件页顶部「定时下发策略」按钮 + 策略弹窗（高级参数折叠、上次执行状态、立即执行一次） |
| 环境变量 | `ERP_PRODUCTION_AUTO_DISPATCH_CHECK_MS`、`..._QUEUE_CAPACITY` 补进 `docker-compose.yml` |

### 部署前核验发现的两个缺陷（`d0be98e`）
1. **熔断永不触发**：原条件「成功=0 且 跳过=0」。但被跳过的行不回写 `mes_production_status`，
   下一轮候选查询还会返回它们 → 纯跳过批次永远不熔断，一路空转到 `max_rounds`，
   并且按固定排序把后面真正可下发的行挡住。改为**连续 `failure_breaker` 批没有任何一行成功即熔断**，
   最坏约 10 秒收手；日志补 `roundsWithoutSuccess / lastRoundSize / lastRoundSkipped`。
2. **迁移版本门禁硬编码 65**：V66 一引入 `SalesOrderLinkedChangeNoticeMigrationTest` 必然失败，改为 66。

### 附带的一次事故（`0340394`）
`908fbc7` 插入「刷新料号」代码时把两行 `const` 声明错误合并成一行且无分号：
`const autoDispatchDialogVisible = ref(false)const autoDispatchConfigLoading = ref(false)`，
导致 `vite:vue` 编译报 `Missing semicolon`，`docker build` 阶段 `npm run build` 失败。
**教训已落文档**：`productionItemManage.test.js` 用 `readFileSync` 做纯文本断言、不解析 SFC，
23 个用例全绿也发现不了这类语法错误 → 前端改动必须额外跑一次 `vite build`。

## 2. 主线二：待产零件「刷新料号」异常修复通道

**提交**：`908fbc7`（+1658 行）、后续 `f8c483e`、`eef6994`、`8c7f9a7` 持续加固

### 为什么需要
MES 侧删除旧料号重建（或人工填错料号后更正）时，QPO 已确认的 `material_no` 被三道锁保护
（提单行已确认、批次行 SUCCESS、请求在途），生产下发会持续报「以下料号不存在」。
这是**异常修复**场景，与正常「批量获取物料号」分离授权。

### 实现要点
| 组件 | 职责 |
|---|---|
| `ProductionItemMaterialNoRefreshService` | 异步任务编排（走 `SystemTaskService`），按图号+版本重新解析料号；按提单去重避免同提单新旧料号并存；料号未变化直接判失败 |
| `ProductionItemMaterialNoRefreshWriter` | **独立 Bean 承载真 `@Transactional`**（避开同类自调用失效）；事务内 `FOR UPDATE` 重校验（无 SUCCESS/PROCESSING/SUBMITTING/RESULT_UNKNOWN）后写回四张表；来源标记 `MES_REFRESH`，留痕旧号→新号 |
| 接口 | `POST production-items/material-no-refresh`（`OrderDeliveryController`） |
| 权限 | V67 新增 **240 `market:production-item:material-no-refresh`**「待产零件刷新料号」，仅授 SUPER_ADMIN / MARKET_MANAGER，含 ID/编码冲突预检与 `setval` |
| 审计 | `_SUBMIT` / `_SUCCESS` / `_FAILED` / `_RESULT_UNKNOWN` / `_RETRY_AFTER_UNKNOWN` 五个动作 |
| 前端 | 工具栏 + 行内入口，确认弹窗必填原因，结果面板展示「旧号 → 新号」 |

### 补的坑（`f8c483e`）
MES 对同一「图号+版本+材质」只允许一个物料准备任务，重复解析返回 `success=false`
「已存在物料准备任务：MPxxxx」。该分支原先在 `validateResponse` 抛异常，而调用点没有
`try/catch` → `order_delivery_ticket_mes_request` 的流水**永远停在 PROCESSING、`response_message` 为空**，
事后完全查不到 MES 的拒绝原因。改为先按 FAILED 落库（含 MES 原文与 `externalTraceId`）再抛出。

## 3. 主线三：MES 物料号同步的契约对齐（本分支最重的一块）

**提交**：`1af0baf` → `26e7d09` → `b3cccfa` → `0d54469` → `eef6994` → `8c7f9a7`
**规模**：`MesMaterialSyncService` 单文件净增 1000+ 行，迁移 V70 / V71

这一块是**一串线上问题倒逼出来的**，按时间顺序还原因果链最清楚：

### 3.1 起点：响应多一个字段就整条调用失败（`1af0baf`）
正式环境刷新料号报
`Error while extracting response for type [MesMaterialResolveResp]`。
HTTP 是 2xx、返回确实是 JSON，但无法映射到 DTO → 业务代码根本没执行。

根因：`DataCenterIntegrationClient` 构造 `RestTemplate` 时只 `disable(WRITE_DATES_AS_TIMESTAMPS)`，
Jackson 默认 `FAIL_ON_UNKNOWN_PROPERTIES` 仍为 true。MES 多返回一个 `traceId/timestamp/path`
之类未声明字段，整条调用就抛 `UnrecognizedPropertyException`。
**该客户端是 U9/WMS/MES 全部对接共用的**，影响面远大于刷新料号一个功能。

修改：关闭 `FAIL_ON_UNKNOWN_PROPERTIES`；解析失败时把**最深一层 cause** 拼进错误信息
（原来只有 Spring 外层文案，线上无法定位到具体字段）；`MesMaterialResolveResp` 加
`@JsonIgnoreProperties`；`data` 改由 `LenientDataDeserializer` 处理（`[]`/`""`/`0` 降级为 null，
让上层读到 MES 真实 `msg`）；`taskId/productId` 由 `Long` 改 `String`。

### 3.2 死锁一：失败后成功回调被拒收（`26e7d09`）
MES 报 409 `MES material callback cannot overwrite a failed terminal result`。
批次行已判 FAILED（超时 / 解析失败 / 被「已存在任务」拒绝），MES 后续仍产出料号并发来成功回调，
QPO 拒收 → **双向死锁**：重新解析被 MES 去重挡住，成功回调又被拒收，料号再也拿不回来。

改为允许成功回调把 FAILED 提升为 SUCCESS（`BatchCallbackDisposition.reviveResult()`）。
安全性依据：进分支前已校验「批次行属本批次 + 提单行未确认料号 + `lineRequestId` 仍是当前值 +
`taskNo` 一致」，不可能是旧请求串行覆盖。额外记审计 `DELIVERY_MES_MATERIAL_CALLBACK_REVIVE`。
边界保护：提单行已写入**另一个**料号时仍返回 409。

### 3.3 死锁二：`mes_request_id` 单值被覆盖导致回调 409（`0d54469`）
MES 报 409 `Stale MES material callback cannot overwrite the current request`。
根因是 `order_delivery_ticket.mes_request_id` 是**单值字段**，同一张提单重新下发时会被新批次行的
`lineRequestId` 覆盖。而 MES 只允许一个物料准备任务 → 重发必被拒 → 「A 失败 → 重发 B 被拒 →
A 的成功回调到达」**必然 409**，料号永久丢失。

处理：**删去 `lineRequestId` 相等比对**，只保留 `taskNo` 比对（不一致仍 409）——
`taskNo` 才是真正防串行的证据。命中「迟到但合法」打 INFO `accepted for superseded line request`。

### 3.4 引入 `RESULT_UNKNOWN` 状态（`eef6994`，V70）
核心洞察：**「MES 明确说没成」和「不知道成没成」是两回事**，对账口径完全不同。

- 只有 MES **明确拒绝**才记 `FAILED`；
- 超时、5xx、解析失败、`bizId` 缺失或不匹配、明细缺行/重复行 → `RESULT_UNKNOWN`（页面「结果待核对」）
- V70 把 `RESULT_UNKNOWN` 写进 `chk_delivery_mes_request_status` 约束，
  并纳入 `uk_delivery_mes_request_active_dedup` 活动去重索引（即它**占去重位**，避免撞「已存在任务」）
- 覆盖范围：物料号同步、刷新料号、生产下发三条链路
- 操作日志补「MES物料号结果待核对」「MES生产下发结果待核对」

### 3.5 物料身份从两字段升到三字段（`8c7f9a7`，V71）
MES 的物料准备任务按「**图号 + 版本 + 材质**」创建，同图号版本换材质要重新建号。
只按「图号+版本」去重会把材质不同的零件并成 follower，后者**永远拿不到自己的料号**。

- V71：三处去重键列 220 → **512**（长度前缀编码最坏 236 字符，有充分余量，不降级摘要）；
  在途台账行、提单行、等待行全部回填成三字段键，避免切代码后被当新请求重复提交
- Java 与 SQL **统一按码点计数**（`varchar` 按字符而非字节），加 ASCII/长度闸门
- 新增 `docs/ops/mes-material-identity-preflight.sql`（257 行）部署前只读核对脚本
- **材质不做归一化**（先人工校对），`null` 与空串等价；MES 会 trim 图号/版本首尾空格；
  **版本不可为空**（打包阶段 `required` 单行拦截，避免整批被 MES 400 退回）

### 3.6 两层契约与错误码（`8c7f9a7`）
MES 确认物料接口是两层契约，这是后续所有判定的基础：

| 层 | 表现 | QPO 处理 |
|---|---|---|
| **行级** | `code=0`，`items` 与请求严格一一对应 | `EXISTING_PRODUCT` 取 `productCode` 写回；`PENDING_CREATE` 等回调；一行已存在不影响同批其它行 |
| **批级回滚** | 非 0 `code` + `data=null`，`@Transactional` 整包回滚 | **一条都没建** → 一律记 `FAILED`（可重试、不占去重位），不是 `RESULT_UNKNOWN` |

错误码：`1030900008` 某行待建料（提示必须写「去 MES 处理」，不会自动出料号）、
`1030900011` 包内图号+版本+材质重复（QPO 分包 bug）、`1030900012` 图纸转存失败。
**比较前必须去掉非数字**（`1_030_900_002` / `1030900002` 两种写法都有），
入口 `isMesMaterialUncertainCode / isMesMaterialRolledBack / mesMaterialRollbackMessage`。

### 3.7 响应映射与料号覆盖
- `items` **按下标对齐**：行数相等才按位置映射 + 图号/版本交叉校验，对不上记 `RESULT_UNKNOWN`；
  行数不等退回按图号+版本匹配
- **料号以最后一次获取为准，允许覆盖**：同步响应写 `DELIVERY_MES_MATERIAL_SYNC_OVERWRITE`，
  回调写 `..._CALLBACK_OVERWRITE`，都带 `previousMaterialNo`

### 3.8 回调超时兜底（`8c7f9a7`）
**MES 只在成功时回调，失败不回调**（MES 明确）。等不到的回调由
`MesMaterialCallbackTimeoutService` + `MesMaterialCallbackTimeoutScheduler` 兜底：
超阈值（默认 4h）把 `CALLBACK_PENDING` 收口成 **`RESULT_UNKNOWN`（不是 FAILED）**——
因为 MES 可能已建料，判 FAILED 会诱导重试造重复任务。先条件更新台账行，
命中 0 行说明回调抢先成功就放弃。审计 `DELIVERY_MES_MATERIAL_CALLBACK_TIMEOUT`。

### 3.9 结果待核对可重试（`8c7f9a7`）
因为 MES 按「图号+版本+材质」**全局唯一**（与 `bizId` 无关），换新 `bizId` 重发不会建第二个任务，
只会回 `EXISTING_PRODUCT`（带料号）/ `1030900008` / `PENDING_CREATE`。
**所以未知结果靠重试一次就能拿到明确答案，不设次数上限。**

重试前必须 `MesMaterialDedupService.retireUnresolvedRequests` 把旧行
`RESULT_UNKNOWN → STALE`（条件更新，回调抢先成功就跳过）释放 `uk_..._active_dedup` 占位，
否则新行插不进去。`assertCanStart` 不再拦 `RESULT_UNKNOWN`，批量入口不再短路。
审计 `..._SYNC_RETRY_AFTER_UNKNOWN` / `..._NO_REFRESH_RETRY_AFTER_UNKNOWN`。

## 4. 主线四：列表可用性（创建时间 / 排序 / 大分页）

**提交**：`03b3122`（锁库）、`40103a5`（已提 + 待产，V68）、`eef6994`（排序 + 1000 行）

### 创建时间列
- **锁库零件**原本就有（`alloc.created_at`），`03b3122` 只是补进「物料号」与「零件类型」之间
- **待产零件**后端 `selectLockedItems` 早已返回 `alloc.created_at`，只缺前端列
- **已提零件**是真缺口：`order_delivery_ticket` 只有业务日期（`start_date` 订单日期、
  `delivery_date` 交货日期），没有落库创建时间；提单行在物料号确认前**还没有分配行**，
  无法复用 `allocation.created_at` → **V68 补 `created_at` 列**
  - 回填优先级：该提单最早一条分配行 `MIN(created_at)` → `mes_synced_at` → 迁移执行时间
  - 最后置 `NOT NULL + DEFAULT CURRENT_TIMESTAMP`

### 排序与大分页（`eef6994`）
- 单页上限提到 **1000**（前端三个页面的 `page-sizes` 都加了 1000；后端 `normalizeListPageSize` 上限 1000；
  客户下拉等辅助分页仍是 100，**别混用同一个 normalize 方法**）
- 服务端排序：`sortBy` + `sortOrder=ASC|DESC`，白名单
  `salesOrderDate / deliveryDate / createdAt / discardedAt`（delivered 无 `salesOrderDate`）
- Mapper 用 `<choose>` 映射到输出别名 + `NULLS LAST`，**禁止 `${sortBy}` 拼 SQL**；不传 `sortBy` 保持原 `id DESC`
- 前端 `sortable="custom"` + `:sort-orders="['descending','ascending']"`，默认不排序；
  `route.query.ticketId` 分支是本地分页，另走 `sortRowsLocally`

## 5. 主线五：权限父节点数据修复（V69，`eef6994`）

**这是本分支唯一一次「修历史数据错误」，值得单独记住。**

V57 的 `market:sales-order:wms-allocate` 用 `parent_id = 190`，V66/V67 的两个待产零件按钮用
`parent_id = 199`。这些 id 取自 `PermissionService.FALLBACK_CATALOG`，而**真实数据库由 V2 基线种子生成**：
父权限实际 id 是 `market:sales-order:view = 150`、`market:production-item:view = 159`，
**199 在库中根本不存在**。

后果：角色一旦勾选这些权限，`SystemRoleService.addPermissionWithParents` 查不到父权限就抛
`Parent permission does not exist` → **整份角色授权保存直接失败**，表现为「勾选后保存不生效」。

V69 统一**按 `permission_code` 重解析父权限**并清理悬空值，不再依赖任何写死的 id。
（`SystemRoleService` 同步改了 10 行。）

> **规则**：今后权限点迁移**禁止写死 `parent_id`**，必须用子查询按 `permission_code` 解析（参照 V52）。

## 12. 遗留风险与待办

1. **`order_delivery_ticket.mes_request_id` 单值承载三种语义**（批次行 `QPO-MATL-` / 刷新 `QPO-MATR-` / 主请求），

## A.2 场景一｜定时下发策略（最值得演示的功能）

**页面**：左侧菜单 `订单` → `待产零件`（`/production-items`）

**演示操作**
1. 页面顶部工具栏，右侧「**定时下发策略**」按钮（灰色 plain，需权限 `market:production-item:mes-production-schedule`）
2. 弹窗标题「**待产零件定时下发策略**」，宽 640px
3. 顶部蓝色提示条：**「当天所有待下发行会全部处理完，不做每日数量限制；分批下发只为避免单批过重影响其他用户。」**
4. 主表单四项：`开启每日自动下发`（开关，开/关）、`每天执行时间`（默认 17:00）、`单批行数`（100~1000，默认 200）、`批间隔`（1000~60000 毫秒，默认 3000）、`连续失败熔断`（1~10 批，默认 3）
5. 点开「**高级参数**」折叠区：`最大轮次`（仅防死循环）、`慢执行告警`（分钟，只告警不中断）

7. 底部三个按钮：**立即执行一次** / 取消 / **保存**
8. 点「立即执行一次」→ 右上角绿色提示「**定时下发任务已提交，任务ID：xxxx**」

**屏幕上要指给听众看的**
- 「**不做每日数量限制**」这句话 —— 业务最关心的是「今天没跑完怎么办」，答案是「当天一定跑完，不会拖到明天」
- `上次执行状态` 四个字段 —— 运维第二天早上第一眼看这里就知道昨晚跑没跑
- `连续失败熔断` —— 防止 MES 挂了以后系统空转一整天

**一句话价值**
> 以前待产零件靠人下班前手动勾选下发，漏一天就积压一天；现在每天 17:00 自动跑完，失败的行不自动重发（避免重复建任务），第二天在列表里筛「下发失败」人工处理。

**对应改动**：`c974f4f`（V66 + 权限 239）、`d0be98e`（熔断修正）、`ee3c336`（环境变量）

**如果被问「跑一半系统重启了怎么办」**：配置表有 `last_run_date` 做 CAS 认领，重启后不会重复跑当天；没跑完的行仍在候选里，第二天继续。

## A.4 场景三｜结果待核对（本次最核心的口径变化）

**页面**：`订单` → `已提零件`（`/delivered-items`）

**演示操作**
1. 点「高级筛选」→ `MES状态` 下拉，把选项念一遍：**未处理 / 处理中 / 待MES回调 / 结果待核对 / 本地写入待修复 / 成功 / 失败**
2. 选「**结果待核对**」→ 列表只剩这些行
3. 勾选 → 点工具栏「**批量获取物料号**」（绿色 plain）
4. 页面上方出现「**MES批量获取结果**」面板：统计条（成功/失败/待核对数量）+ 逐行 `bizId` / `requestId` / 状态标签 / MES 原文消息
5. 切到 `订单` → `待产零件`，同样筛「结果待核对」，下发结果面板里每行有「**核对结果**」按钮

**屏幕上要指给听众看的**
- 状态筛选里「**失败**」和「**结果待核对**」是**两个不同选项** —— 这是本分支最重要的业务口径
- 面板里每行的 `bizId` —— 运维拿这个去 MES 对数

**一句话价值**
> 以前只有「成功/失败」两种结果，超时、MES 返回 5xx、返回内容解析不了，全都记成「失败」。
> 但 MES 那边可能已经把料建好了 —— 判失败就会诱导重试，重试又被 MES 以「已存在任务」拒绝，料号就永远拿不回来。
> 现在这三种情况单独记「结果待核对」：不判死、占住去重位、页面明确提示「先去核对，不要直接重复下发」。

**对应改动**：`eef6994`（V70）、`8c7f9a7`（可重试 + 回调超时兜底）

**如果被问「一直待核对会不会卡死」**：
- 不会。MES 只在成功时回调，超过 4 小时仍「待MES回调」的，系统自动转成「结果待核对」（不转失败，因为怕重复建料）
- 「结果待核对」可以重新获取：系统先把旧台账行收口成 `STALE` 释放占位再重发，不设次数上限。因为 MES 按「图号+版本+材质」全局唯一，重发不会建出第二个任务，只会回明确答案

1. 点「废弃」→ 确认弹窗文案已改为：
   **「…系统只调整销售订单头和零件状态，不清空价格、数量、交期、图纸、提单快照或物料号；同时会同步撤销该订单已下发到 MES 的需求任务，撤销失败的行请在待产零件页筛选「撤销失败」处理。」**
2. 确认后回 `待产零件`，`生产下发状态` 下拉新增两项：**已撤销 / 撤销失败**
3. 筛「撤销失败」→ 这些行的需求任务在 MES 侧已提交审核、删不掉，需要业务去 MES 处理

**一句话价值**
> 订单废弃了但 MES 那边的需求任务还在排产 —— 这是数据不一致的源头。现在废弃订单会同步撤销，**但要说实话**：MES 只允许删「开立」状态的任务，订单废弃往往发生在下发几小时甚至几天后，**大部分行删不掉**，所以方案重点不是「一定删成功」，而是把「哪些删不掉」显式暴露出来。

## A.7 场景六｜角色权限（讲「修了一个数据 bug」，30 秒）

**页面**：`系统` → `角色权限`（`/roles`）

**演示操作**
1. 选一个角色 → 点「授权」→ 在市场/订单分组下找到两个新按钮权限：
   - **待产零件定时下发策略**（`market:production-item:mes-production-schedule`）
   - **待产零件刷新料号**（`market:production-item:material-no-refresh`）
2. 勾上 → 保存 → 绿色提示「保存成功」
3. 退出重新登录该角色账号 → 待产零件页出现「定时下发策略」「刷新料号」两个按钮

**屏幕上要指给听众看的**
- 保存成功的提示 —— 因为**这个动作以前是会整份失败的**

**一句话价值**
> 这不是新功能，是修了一个隐蔽的数据 bug：历史迁移把权限的「父节点 id」写成了代码里的常量（199/190），而真实库里父权限 id 是 159/150，**199 在库里根本不存在**。结果角色一旦勾选这些权限，保存时查不到父节点就抛异常，整份授权直接失败 —— 用户看到的现象是「勾了、保存了、但没生效」。
> 现在统一改成按权限编码去找父节点，不再依赖任何写死的 id。

**对应改动**：`eef6994`（V69）

## A.9 页面上看不到、需要口头补的三件事

汇报时容易被追问「除了界面还做了什么」，这三条按价值排序：

1. **数据中心客户端容错（影响面最大）**
   `1af0baf` 之前，MES 只要在响应里多返回一个字段（`traceId`/`timestamp` 之类），整条调用就抛解析异常、业务代码根本不执行。
   这个客户端是 **U9 / WMS / MES 全部对接共用**的，所以修的不是「刷新料号一个功能」，是整条对外集成链路。
   现在关闭了未知字段报错，并且解析失败时会把**最深一层原因**拼进错误信息 —— 原来线上只看到 Spring 的外层文案，根本定位不到是哪个字段。

2. **物料身份从两字段升到三字段（V71）**
   MES 的物料准备任务按「图号 + 版本 + **材质**」唯一。原来 QPO 只按「图号+版本」去重，
   同图号同版本换材质的零件会被并成一个，**后一个永远拿不到自己的料号**。
   V71 把三处去重键从 220 扩到 512，并把在途数据全部回填 —— 这一步必须部署前用
   `docs/ops/mes-material-identity-preflight.sql` 先核对，否则切代码后在途请求会被当新请求重复提交。

3. **回调超时兜底**
   MES **只在成功时回调，失败不回调**。所以「等回调」是个可能永远等不到的状态。
   系统超过 4 小时（可配）自动把「待MES回调」收口成「结果待核对」——
   **不是失败**，因为 MES 可能已经建好料了，判失败会诱导重试造重复任务。

## A.10 预判提问与标准答案

| 提问 | 回答要点 |
|---|---|
| 定时下发会不会把 MES 打崩？ | 单批 200 行、批间隔 3 秒、独立单线程池串行跑，不挤占手动下发；连续 3 批零成功自动熔断，最坏 10 秒收手 |
| 为什么失败的行不自动重试？ | MES 对同一「图号+版本+材质」只允许一个任务，盲目重试必被「已存在任务」拒绝，还会把真实结果盖掉。失败交给人工看原因 |
| 「结果待核对」到底该谁处理？ | 先看 MES 原文（面板里有 `bizId`），能确认已建料就等回调；确认没建就重新获取（系统会释放占位再重发） |
| 撤销需求任务为什么这么多失败？ | MES 只允许删「开立」状态，提交审核后一律返回 `1030700006`。废弃多发生在下发数天后，删不掉是正常的，所以要暴露而不是掩盖 |
| 这次改了多少？ | 20 个提交、103 个文件、+11012/-371 行；6 个数据库迁移（V66~V71）；2 个新权限点；13 个新审计动作；后端测试 1714 例、前端 858 例全绿 |
| 上线风险在哪？ | V67 上线前要确认权限点 240 没被占用；V71 要复跑身份核对脚本。两个迁移都不是简单回滚型 |
