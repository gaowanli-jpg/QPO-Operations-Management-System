# QPO 企业级权限用户体系开发文档

## 1. 背景与目标

QPO 当前权限体系已经具备基础账号、登录、强制改密、账号锁定、操作日志和前后端角色拦截能力，但整体仍是“单角色 + 静态权限”模型：

- 用户表为 `erp_user`，用户只保存一个 `role` 字段。
- 后端接口通过 `@RequireRole({"ADMIN", "MARKET", "ENGINEER"})` 判断角色。
- 前端路由通过 `meta.roles` 判断可访问角色。
- 左侧菜单通过 `authStore.hasRole()` 控制显示。
- 当前角色固定为 `ADMIN`、`MARKET`、`ENGINEER`。

企业完整版目标是升级为：

> 用户管理管“谁能登录系统”，角色管理管“登录后能做什么、能看哪些数据”，权限点管“页面、按钮和接口的最小操作能力”，数据权限管“同一个功能下能看到哪些业务数据”。

最终权限模型：

```text
用户 -> 用户角色 -> 角色 -> 角色权限 -> 菜单 / 按钮 / 接口权限
                       |
                       -> 数据权限范围 -> 订单 / 客户 / 操作日志 / 字典等业务数据过滤
```

## 2. 建设原则

### 2.1 后端安全优先

前端隐藏菜单和按钮只是用户体验，不能作为安全边界。所有关键接口必须由后端权限注解和数据权限过滤兜底。

### 2.2 权限点稳定命名

权限编码一旦进入角色配置和审计日志，后续要尽量保持稳定。命名采用：

```text
模块:资源:动作
```

示例：

- `market:rfq:import`
- `engineer:quote:save`
- `delivery:ticket:create`
- `system:user:update`
- `system:audit:export`

### 2.3 不用角色名写业务逻辑

目标状态下业务代码不再判断 `MARKET`、`ENGINEER` 是否有权限，而是判断权限点，例如：

```java
@RequirePermission("market:rfq:import")
```

角色只是权限集合，可以由管理员配置。

### 2.4 数据权限独立于功能权限

有功能权限只代表“能进入这个功能”，不代表“能看全部数据”。例如市场人员可以有订单管理权限，但只能看自己负责客户或自己创建的 RFQ。

### 2.5 保留超级管理员兜底

超级管理员角色内置 `super_admin = true`，拥有所有菜单、按钮、接口和全部数据权限，但它的行为仍要进入操作日志。

### 2.6 平滑迁移但目标结构完整

这次按企业完整版设计，但落地时要保护现有登录、强制改密、401/428、操作日志、菜单、Docker 部署和测试体系。

## 3. 当前系统权限现状

### 3.1 后端现状

| 能力 | 当前实现 | 问题 |
| --- | --- | --- |
| 用户主体 | `erp_user` | 表名和字段偏旧，缺少部门、岗位、手机号、邮箱等企业字段 |
| 角色 | `erp_user.role` 单字段 | 不能一个用户多个角色，角色不可配置 |
| 接口权限 | `@RequireRole` | 粒度粗，只能按角色拦截 |
| 超级管理员 | `ADMIN` 在拦截器中直接放行 | 可以保留，但应变成角色属性 |
| 数据权限 | 无统一机制 | 用户有功能权限后通常可以看全部相关数据 |
| 操作日志 | 已较完整 | 权限变更需要补充专门审计动作 |

关键文件：

- `quote-system/src/main/java/com/machining/quote/entity/ErpUser.java`
- `quote-system/src/main/java/com/machining/quote/service/UserAdminService.java`
- `quote-system/src/main/java/com/machining/quote/config/AuthInterceptor.java`
- `quote-system/src/main/java/com/machining/quote/config/RequireRole.java`

### 3.2 前端现状

| 能力 | 当前实现 | 问题 |
| --- | --- | --- |
| 登录状态 | `authStore` 保存 token/user | 可复用，但需要增加 roles/permissions/menus/dataScopes |
| 路由权限 | `meta.roles` | 需要改成 `meta.permission` 或 `meta.anyPermissions` |
| 菜单权限 | `App.vue` 写死角色 | 需要菜单配置 + 权限过滤 |
| 按钮权限 | 少量组件用 `hasRole` | 需要统一 `hasPermission` |
| 用户管理 | `UserManage.vue` 管账号和单角色 | 需要拆出角色管理、部门管理、权限分配 |

关键文件：

- `quote-frontend/src/stores/authStore.js`
- `quote-frontend/src/router/index.js`
- `quote-frontend/src/App.vue`
- `quote-frontend/src/components/UserManage.vue`

## 4. 目标模块

企业完整版拆为 7 个管理模块：

| 模块 | 作用 | 推荐菜单位置 |
| --- | --- | --- |
| 用户管理 | 管账号主体、登录状态、安全状态 | 系统 |
| 角色管理 | 管角色、角色权限、数据范围 | 系统 |
| 部门管理 | 管组织结构、部门负责人、启停 | 系统 |
| 岗位管理 | 管岗位字典，用于用户档案和后续流程 | 系统 |
| 菜单权限管理 | 管菜单、按钮、接口权限点 | 系统 |
| 数据权限策略 | 管角色可见数据范围 | 系统 / 角色详情内 |
| 权限审计 | 查询用户、角色、权限变更日志 | 操作日志中增强 |

第一版 UI 可把“菜单权限”和“数据权限”做在角色管理详情内，不一定单独放一个页面。

## 6. 数据权限设计

### 6.1 数据范围枚举

| 编码 | 名称 | 说明 |
| --- | --- | --- |
| `ALL` | 全部数据 | 超级管理员、总经理等 |
| `DEPT` | 本部门数据 | 用户所属部门 |
| `DEPT_AND_CHILD` | 本部门及子部门 | 部门主管 |
| `SELF` | 本人数据 | 用户创建或负责的数据 |
| `CUSTOMER` | 指定客户 | 只看配置客户 |
| `CUSTOM` | 指定部门 | 按角色配置部门集合 |
| `NONE` | 无业务数据 | 只允许看系统配置或空列表 |

### 6.2 QPO 业务数据归属建议

当前部分业务表没有 `created_by`、`owner_user_id`、`dept_id`。企业级数据权限需要补齐归属字段。

建议新增或逐步补齐：

| 表 | 建议字段 | 用途 |
| --- | --- | --- |
| `order_rfq` | `created_by`, `owner_user_id`, `owner_dept_id` | 新单、订单、报价、提单数据权限 |
| `item_quote_version` | 继承 `rfq_id` | 通过订单过滤 |
| `order_delivery_ticket` | 继承 `rfq_id` | 通过订单过滤 |
| `order_process_sheet` | 继承 `rfq_id` | 通过订单过滤 |
| `audit_log` | `user_id`, `role`, `module` 已有部分字段 | 审计查询权限 |
| 字典表 | 可不加数据权限 | 通常按功能权限控制 |

### 6.3 各模块默认数据权限策略

| 模块 | 默认建议 |
| --- | --- |
| 新单导入 | 创建人可以看自己导入的订单；市场主管看市场部订单 |
| 零件核价 | 工程人员看工程可处理订单；工程主管看工程部全部 |
| 报价处理 | 市场人员看自己负责客户/订单；市场主管看市场部全部 |
| 议价提单 | 与报价处理一致 |
| 订单管理 | 按角色数据范围过滤 |
| 历史订单 | 按角色数据范围过滤 |
| 材料与工艺管理 | 功能权限控制，不做行级数据权限 |
| 报价模板 | 功能权限控制，不做行级数据权限 |
| 操作日志 | 默认仅 `SUPER_ADMIN` 和 `AUDITOR` 可看；非超级管理员不能看超级管理员日志 |
| 用户/角色/部门 | 系统权限控制，不按业务数据范围过滤 |

### 8.4 权限注解设计

保留 `@RequireRole` 作为迁移兼容，但目标新增：

```java
@RequirePermission("market:rfq:import")
@RequireAnyPermission({"market:order:view", "engineer:pricing:view"})
@RequireSuperAdmin
```

拦截逻辑：

1. 解析 token。
2. 加载当前用户。
3. 检查账号启用、锁定、强制改密。
4. 加载用户角色和权限集合。
5. 超级管理员直接通过功能权限。
6. 检查方法或类上的权限注解。
7. 设置 `AuthContext`，包括 `userId`、`username`、`roles`、`permissions`、`deptId`、`dataScopes`。

### 8.5 数据权限实现

初期不建议直接做全局 SQL 插件，因为现有业务查询使用 MyBatis Plus `QueryWrapper` 和多个 service 手写查询混合，直接插件化风险高。

推荐第一阶段做服务层数据权限：

```java
DataScopeCondition condition = dataScopeService.currentOrderScope();
orderPermissionHelper.applyOrderScope(queryWrapper, condition);
```

订单相关查询统一进入：

- `OrderManagementService`
- `MarketController / MarketService`
- `EngineerService`
- `QuoteProcessService`
- `DeliveryService`
- `InternalTargetLeadTimeService`
- `AuditLogQueryService`

后续稳定后，再评估是否抽成 MyBatis 拦截器。

### 8.6 权限缓存

权限信息登录后返回给前端，但后端每次校验也需要可靠。

建议：

- 第一版不引入 Redis。
- 使用 JVM 本地缓存，按 `userId` 缓存权限快照 1-5 分钟。
- 用户角色或角色权限变更后主动失效对应缓存。
- 如果后续多实例部署，再考虑 Redis 或版本号校验。

### 8.7 Token 设计

JWT 中建议只保留稳定身份字段：

- `userId`
- `username`
- `tokenVersion`

不要把完整权限点长期写入 JWT，避免角色修改后旧 token 权限不更新。

登录和 `/api/auth/me` 返回完整权限信息。

### 9.2 路由权限升级

当前：

```js
meta: { roles: ['MARKET', 'ADMIN'] }
```

目标：

```js
meta: { permission: 'market:rfq:view' }
```

或：

```js
meta: { anyPermissions: ['market:order:view', 'engineer:pricing:view'] }
```

路由守卫逻辑：

1. 未登录跳 `/login?redirect=...`。
2. token 存在但未验证时调用 `verifyAuth()`。
3. 权限未加载时调用 `loadPermissionInfo()`。
4. 根据 `meta.permission` 或 `meta.anyPermissions` 判断访问。
5. 无权限跳转到用户有权限的第一个菜单，或显示 403 页面。

### 9.3 菜单渲染升级

当前 `App.vue` 写死菜单和 `canSee()`。

目标：

- 后端返回菜单树。
- 前端根据菜单树渲染左侧菜单。
- 本地保留 route/component 映射，避免后端直接控制任意组件路径。

示例：

```js
const componentRegistry = {
  MarketDashboard: () => import('../components/MarketDashboard.vue'),
  GlobalSetup: () => import('../components/GlobalSetup.vue')
}
```

### 9.4 按钮权限统一

const canImportRfq = computed(() => authStore.hasPermission('market:rfq:import'))

## 11. 迁移策略

### 11.1 数据迁移

新增 Flyway 迁移：

1. 创建 `system_user`、`system_role`、`system_dept`、`system_post`、`system_permission` 等表。
2. 插入默认部门、岗位、角色、权限点。
3. 从 `erp_user` 复制到 `system_user`。
4. 根据旧 `role` 写入 `system_user_role`：
   - `ADMIN` -> `SUPER_ADMIN`
   - `MARKET` -> `MARKET_USER`
   - `ENGINEER` -> `ENGINEER_USER`
5. 保留 `erp_user` 一段时间作为回滚备份。

### 11.2 代码迁移

1. 新增新权限体系，不立即删除旧 `@RequireRole`。
2. 登录改为返回 `roles/permissions/menus`。
3. 前端 `authStore` 兼容旧字段和新字段。
4. 业务接口逐步从 `@RequireRole` 改为 `@RequirePermission`。
5. 所有接口迁移完成后，删除旧角色判断。

### 11.3 回滚策略

- Flyway 迁移不删除 `erp_user`。
- 第一阶段保留旧 `role` 字段读取兼容。
- 如果新权限异常，可以临时启用旧 `@RequireRole` 兼容逻辑。
- 超级管理员账号必须保留，避免权限配置错误导致全系统锁死。
