# QPO 用户组织身份体系完善开发文档

## 1. 背景与目标

当前 QPO 权限体系已经完成了角色、权限点、模块树授权、客户数据范围和操作日志治理，但“用户是谁、属于哪个组织、担任什么岗位”还没有完整闭环。数据库中已经有 `system_dept`、`system_post`、`system_user.dept_id`、`system_user.post_id` 等基础结构，用户管理接口也已经透传 `deptId` / `postId`，但系统缺少完整的部门、岗位维护页面和配套后端 CRUD。

本阶段目标是补齐用户组织身份体系，让用户管理从“散账号列表”升级为“账号 + 组织归属 + 岗位身份 + 多角色授权 + 数据范围”的企业级账号档案。

核心边界：

- 部门和岗位是用户身份属性，用于组织档案、账号归属、日志展示、后续统计和审批扩展。
- 角色是功能授权来源，决定用户能看哪些模块、能点哪些按钮、能调用哪些接口。
- 数据范围仍然只保留 `ALL`、`CUSTOMER`、`SELF`、`NONE`，不重新启用部门数据范围。
- QPO 订单跨市场、工程、系统管理连续流转，不按部门切开订单主流程。
- 本阶段不改变报价、核价、提单、APS 同步等业务逻辑。

## 2. 最终用户档案模型

一个完整用户在 QPO 中应具备以下信息：

| 类别 | 字段 / 来源 | 说明 |
| --- | --- | --- |
| 登录身份 | `username`、`password_hash` | 谁能登录系统。 |
| 展示信息 | `display_name`、`real_name`、`phone`、`email` | 页面展示、联系人信息、审计辅助信息。 |
| 组织归属 | `dept_id` -> `system_dept` | 用户属于哪个部门或组织节点。 |
| 岗位身份 | `post_id` -> `system_post` | 用户在组织里的职位或身份标签。 |
| 账号状态 | `enabled`、`locked_until` | 是否可登录、是否锁定。 |
| 安全信息 | `failed_login_attempts`、`last_login_at`、`password_changed_at` | 登录安全和账号治理。 |
| 功能授权 | `system_user_role` -> `system_role` -> `system_permission` | 用户能进入哪些模块、执行哪些动作。 |
| 数据范围 | 角色上的 `data_scope` + 客户范围 | 用户有功能权限后能看到哪些订单、客户、日志。 |
| 审计追踪 | 操作日志中的 actor、module、result、requestId | 谁在什么时候改了账号、角色、组织资料。 |

一句话口径：

```text
部门 = 用户属于哪个组织
岗位 = 用户在组织里的职位/身份
角色 = 用户在系统里能做什么
数据范围 = 用户能看哪些业务数据
```

## 3. 方案对比与推荐

### 方案 A：把部门和岗位直接塞进用户管理页

做法：`UserManage.vue` 增加多个标签页，用户、部门、岗位都在一个页面里维护。

优点：

- 入口少，改动较小。
- 管理员能在一个页面处理账号和组织属性。

缺点：

- 用户管理页面会继续膨胀。
- `system:user:view`、`system:dept:view`、`system:post:view` 的页面边界会混在一起。
- 后续如果增加组织树、负责人、岗位统计，页面会变得拥挤。

### 方案 B：新增“组织档案”入口，用户管理消费组织字典（推荐）

做法：

- 系统菜单下新增四字入口：`组织档案`。
- `组织档案` 页面包含 `部门管理`、`岗位管理` 两个标签。
- `用户管理` 页面继续维护账号，但新增部门、岗位选择和展示。
- `角色权限` 保持授权职责，不承担组织字典维护。

优点：

- 职责最清楚：账号、组织、角色三件事不混。
- 后续可自然扩展部门负责人、组织排序、岗位状态、人员统计。
- 权限树更符合企业后台直觉：组织资料有自己的 `MENU` 和维护按钮权限。
- 不会把部门重新带回订单数据范围。

缺点：

- 会新增一个系统菜单入口和一组路由、测试、文档同步工作。

### 方案 C：暂不做岗位管理，只做部门管理

做法：先实现部门树和用户部门归属，岗位字段继续保留但不开放页面。

优点：

- 最小化本阶段范围。
- 避免岗位和角色在管理员认知上混淆。

缺点：

- 用户档案仍不完整。
- 已存在的 `system_post`、`postId`、`system:post:*` 权限继续处于“预留但不可用”状态。

推荐采用方案 B。部门和岗位都做，但明确它们只是用户组织身份，不参与订单数据隔离；这样既完整，又不会破坏已经收口的数据范围设计。

## 4. 权限设计

### 4.1 菜单与权限点

建议新增或调整为以下权限结构：

| 权限编码 | 类型 | 名称 | 说明 |
| --- | --- | --- | --- |
| `system:org:view` | `MENU` | 组织档案 | 系统左侧入口，四字模块名。 |
| `system:dept:view` | `MENU` / `TAB` | 查看部门 | 组织档案内部门管理标签可见。 |
| `system:dept:manage` | `BUTTON` | 维护部门 | 新增、编辑、启停、删除部门。 |
| `system:post:view` | `MENU` / `TAB` | 查看岗位 | 组织档案内岗位管理标签可见。 |
| `system:post:manage` | `BUTTON` | 维护岗位 | 新增、编辑、启停、删除岗位。 |

说明：

- `system:dept:view`、`system:post:view` 目前已经存在，可以继续使用。
- `system:org:view` 是新增的左侧可点击入口；保存权限时后端自动补齐父模块权限。
- 不新增 `common:*` 权限。
- 不恢复 `DEPT`、`DEPT_AND_CHILD`、`CUSTOM` 数据范围。

授权树中建议展示为：


## 5. 数据模型

### 5.1 部门表：`system_dept`

现有字段可继续使用：

| 字段 | 说明 |
| --- | --- |
| `id` | 部门 ID。 |
| `parent_id` | 上级部门，根节点可为 `0` 或 `NULL`，实现时统一口径。 |
| `dept_code` | 部门编码，唯一。 |
| `dept_name` | 部门名称。 |
| `leader_user_id` | 部门负责人，预留并可选配置。 |
| `sort_order` | 排序。 |
| `enabled` | 启用状态。 |
| `deleted` | 软删除标记。 |

删除规则：

- 有子部门时不允许删除。
- 有用户归属该部门时不允许删除。
- 删除采用软删除，保留历史引用可追溯。

### 5.2 岗位表：`system_post`

现有字段可继续使用：

| 字段 | 说明 |
| --- | --- |
| `id` | 岗位 ID。 |
| `post_code` | 岗位编码，唯一。 |
| `post_name` | 岗位名称。 |
| `sort_order` | 排序。 |
| `enabled` | 启用状态。 |
| `deleted` | 软删除标记。 |

删除规则：

- 有用户使用该岗位时不允许删除。
- 删除采用软删除。

### 5.3 用户表：`system_user`

本阶段应把以下字段真正展示和维护起来：

| 字段 | 页面行为 |
| --- | --- |
| `real_name` | 用户真实姓名，可选。 |
| `phone` | 手机号，可选，做格式轻校验。 |
| `email` | 邮箱，可选，做格式轻校验。 |
| `dept_id` | 从启用部门中选择。 |
| `post_id` | 从启用岗位中选择。 |

注意：

- `system_user` 继续与历史 `erp_user` 保持兼容同步，不在本阶段删除 `erp_user`。
- 用户的最终功能权限仍来自 `system_user_role`。
- 用户的最终数据范围仍来自其绑定角色的数据范围并集。

## 6. 后端接口设计

### 6.1 部门接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/api/system/departments/tree` | `system:dept:view` | 查询部门树。 |
| `GET` | `/api/system/departments/options` | `system:user:view` | 用户管理选择部门，只返回启用项。 |
| `POST` | `/api/system/departments` | `system:dept:manage` | 新增部门。 |
| `PUT` | `/api/system/departments/{id}` | `system:dept:manage` | 编辑部门。 |
| `PUT` | `/api/system/departments/{id}/status` | `system:dept:manage` | 启停部门。 |
| `DELETE` | `/api/system/departments/{id}` | `system:dept:manage` | 软删除部门。 |

### 6.2 岗位接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/api/system/posts` | `system:post:view` | 查询岗位列表。 |
| `GET` | `/api/system/posts/options` | `system:user:view` | 用户管理选择岗位，只返回启用项。 |
| `POST` | `/api/system/posts` | `system:post:manage` | 新增岗位。 |
| `PUT` | `/api/system/posts/{id}` | `system:post:manage` | 编辑岗位。 |
| `PUT` | `/api/system/posts/{id}/status` | `system:post:manage` | 启停岗位。 |
| `DELETE` | `/api/system/posts/{id}` | `system:post:manage` | 软删除岗位。 |

### 6.3 用户接口增强

现有 `/api/system/users` 保持不变，增强返回字段：

- `deptId`
- `deptName`
- `postId`
- `postName`
- `realName`
- `phone`
- `email`

保存用户时支持：

- 新增 / 编辑用户选择部门、岗位。
- 已禁用或已删除部门、岗位不允许新绑定。
- 编辑历史用户时，如果原部门/岗位已禁用，可以展示但提示；保存时要求重新选择启用项或清空。

## 8. 日志与审计

本阶段属于系统治理能力，必须同步操作日志和后端文件日志。

### 8.1 操作日志动作

| 动作 | 说明 |
| --- | --- |
| `SYSTEM_DEPT_CREATE` | 新增部门。 |
| `SYSTEM_DEPT_UPDATE` | 修改部门。 |
| `SYSTEM_DEPT_ENABLE` | 启用部门。 |
| `SYSTEM_DEPT_DISABLE` | 禁用部门。 |
| `SYSTEM_DEPT_DELETE` | 删除部门。 |
| `SYSTEM_POST_CREATE` | 新增岗位。 |
| `SYSTEM_POST_UPDATE` | 修改岗位。 |
| `SYSTEM_POST_ENABLE` | 启用岗位。 |
| `SYSTEM_POST_DISABLE` | 禁用岗位。 |
| `SYSTEM_POST_DELETE` | 删除岗位。 |
| `SYSTEM_USER_ORG_UPDATE` | 用户部门/岗位变更摘要，可并入 `SYSTEM_USER_UPDATE` 的 before/after。 |

### 8.2 文件日志口径

INFO：

- Department created/updated/deleted.
- Post created/updated/deleted.
- User organization updated.

WARN：

- 删除部门时存在子部门或用户。
- 删除岗位时存在用户。
- 保存用户时绑定了不存在、禁用或已删除的部门/岗位。

ERROR：

- 未预期异常由全局异常处理写入 `qpo-error.log`。

禁止：

- 不为用户列表、部门选项、岗位选项等普通读取增加高频 INFO。

- 新增 `SystemDeptController`、`SystemPostController`。
- 新增 `SystemDeptService`、`SystemPostService`。

## 10. 完成标准

- 用户管理不再只是账号列表，而是能展示并维护用户组织身份。
- 部门和岗位可以由管理员在系统内维护。
- 角色仍然是功能权限和数据范围的唯一配置入口。
- 数据范围仍然只有 `ALL`、`CUSTOMER`、`SELF`、`NONE`。
- QPO 订单主流程不按部门隔离。
- 新增组织能力有权限、有日志、有测试、有管理员说明。
- 旧兼容表和字段不被误删，`erp_user` 等兼容标识继续保留。
