# QPO 权限体系部署与管理员使用说明

版本：Stage 7 收尾版

本文用于记录企业级权限用户体系完成后的部署检查、管理员使用方式、数据权限规则和权限编码清单维护要求。

## 1. 部署检查

### 1.1 数据库迁移

后端启动时 Flyway 会自动执行权限体系相关迁移，包括：

- 企业权限基础表：`system_user`、`system_role`、`system_permission`、`system_user_role`、`system_role_permission`、`system_dept`、`system_post` 等。
- 数据范围表：`system_role_data_scope_dept`、`system_role_data_scope_customer`。
- 订单归属字段：`order_rfq.created_by`、`order_rfq.owner_user_id`、`order_rfq.owner_dept_id`。

部署后建议检查：

```sql
SELECT COUNT(*) FROM system_user;
SELECT COUNT(*) FROM system_role;
SELECT COUNT(*) FROM system_permission;
SELECT created_by, owner_user_id, owner_dept_id FROM order_rfq LIMIT 5;
```

### 1.2 兼容说明

- `erp_user` 作为历史账号来源和备份保留，不作为新的权限配置主表。
- 新权限以 `system_user` + `system_user_role` + `system_role_permission` 为准。
- 后端主代码已移除旧 `@RequireRole` 注解，接口安全边界统一由 `@RequirePermission` 驱动。
- 前端业务页面不再依赖 `meta.roles`，菜单和路由访问由权限点驱动。

### 1.3 验证命令

```powershell
cd D:\Code\quote-system
.\mvnw.cmd test

cd D:\Code\quote-frontend
npm test
npm run build
```

## 2. 管理员使用手册

### 2.1 用户管理

用户管理负责维护“谁可以登录系统”：

- 新增或编辑账号基础信息。
- 设置账号启用/禁用。
- 重置密码。
- 给用户分配一个或多个角色。

注意：用户本身不直接配置菜单、按钮和接口权限，权限来自角色。

### 2.2 角色管理

角色管理负责维护“这个人登录后能做什么、能看哪些数据”：

- 角色基础信息：角色编码、角色名称、说明、启用状态。
- 功能授权：勾选菜单、按钮和接口权限点。
- 数据范围：配置角色可见的业务数据。

禁用角色后，该角色不会再给用户贡献功能权限或数据权限。

### 2.3 数据范围配置

角色支持以下数据范围：

| 编码 | 含义 | 适用场景 |
| --- | --- | --- |
| `ALL` | 全部数据 | 超级管理员、总经理等 |
| `DEPT` | 本部门数据 | 部门普通主管 |
| `DEPT_AND_CHILD` | 本部门及子部门数据 | 多层组织主管 |
| `SELF` | 本人创建或负责的数据 | 市场专员 |
| `CUSTOMER` | 指定客户数据 | 大客户负责人 |
| `CUSTOM` | 指定部门数据 | 跨部门授权 |
| `NONE` | 无业务数据 | 只允许看系统配置或空列表 |

角色管理的数据范围抽屉中：

- 指定部门使用部门树勾选。
- 指定客户使用客户下拉多选。
- 多角色用户的数据范围取并集。
- 超级管理员角色默认拥有全部功能和全部数据。

## 3. 数据权限落地范围

当前数据权限已接入以下关键业务边界：

- 订单列表、历史订单、订单详情、订单选择。
- 新单导入后的订单归属写入。
- 零件核价订单进入、保存全局设定、逐件核价、组合件选择。
- 报价处理、报价交期、内部目标交期。
- 议价提单、已生成提单行、已生成工艺表行。
- 报价单导出、模板报价导出、异步刷新/导出任务提交。
- 操作日志列表、详情、导出和筛选项。

无数据权限时，列表应返回空结果；直接访问无权限订单或日志详情时，后端拒绝访问。

## 4. 权限编码维护要求

权限编码采用：

```text
模块:资源:动作
```

示例：

- `market:rfq:import`
- `market:quote-process:export`
- `engineer:pricing:save-item`
- `system:role:assign-data-scope`

维护规则：

- 新增接口必须先确定权限编码。
- 后端 Controller 必须使用 `@RequirePermission`。
- 前端路由使用 `meta.permission` 或 `meta.anyPermissions`。
- 按钮使用 `v-permission` 或 `authStore.hasPermission()`。
- 权限编码不得重复；新增编码后同步更新 `02-权限点清单与现有角色映射.md` 和测试清单。

## 5. 常用排查

### 5.1 用户看不到菜单

检查顺序：

1. 用户是否启用。
2. 用户是否绑定至少一个启用角色。
3. 角色是否拥有对应菜单权限点。
4. 登录后 `/api/auth/permission-info` 是否返回该权限点。
5. 前端路由 `meta.permission` 是否与权限点一致。

### 5.2 用户能进页面但列表为空

检查顺序：

1. 角色数据范围是否为 `NONE`。
2. `SELF` 范围下订单是否有 `created_by` 或 `owner_user_id`。
3. `DEPT` / `DEPT_AND_CHILD` 范围下用户是否有部门，订单是否有 `owner_dept_id`。
4. `CUSTOMER` 范围下角色是否配置了客户名称。
5. 超级管理员是否能看到同一批数据，用于排除业务数据不存在。

### 5.3 接口返回 403

检查顺序：

1. 当前用户权限集合是否包含接口需要的权限点。
2. 角色是否被禁用。
3. 是否刚修改权限但前端还未刷新权限信息。
4. 后端 Controller 上的 `@RequirePermission` 是否与前端权限编码一致。

## 6. 收尾状态

- 旧 `@RequireRole` 主代码已删除。
- 旧单角色入口不再作为业务安全边界。
- `authStore.hasRole()` 仅保留兼容/超级管理员判断，不作为业务页面直接授权依据。
- `meta.roles` 已从前端业务路由移除。
- 权限体系目标状态为：用户绑定角色，角色配置功能权限和数据权限，前端负责体验隐藏，后端负责最终安全校验。
