# QPO 个人入口与我的资料优化开发文档

## 1. 背景与目标

QPO 已经完成企业级用户组织身份体系：用户具备账号、展示信息、手机号、邮箱、部门、岗位、多角色和数据范围等属性。但当前系统右上角仍是旧式 header 展示：头像、用户名、角色、修改密码、退出全部直接铺在顶部区域。

随着用户属性变多，这种展示方式会带来三个问题：

- 顶部区域信息密度变高，和业务页面标题、侧边栏折叠按钮争夺空间。
- 用户无法在一个入口查看自己的完整身份信息，例如部门、岗位、角色、手机号、邮箱。
- 修改密码和退出按钮过于外露，后续再增加“我的资料”会让 header 更杂乱。

本阶段目标是把右上角升级为企业后台常见的“个人入口”：

- header 右上角只保留一个轻量用户入口。
- 点击入口后展示个人资料面板。
- 本人可以维护手机号、邮箱和密码。
- 部门、岗位、角色等治理属性只读展示，由管理员在用户管理 / 组织档案中维护。

## 2. 当前项目状态

### 2.1 前端现状

当前主要逻辑在：

```text
quote-frontend/src/App.vue
quote-frontend/src/stores/authStore.js
quote-frontend/src/services/authApi.js
```

`App.vue` 中右上角存在：

- `user-card`：展示头像、用户名、角色。
- `修改密码` 按钮：打开当前密码弹窗。
- `退出` 按钮：调用 `authStore.logout()`。

修改密码入口已经存在：

- 用户可从右上角个人入口手动打开改密弹窗。
- QPO 不再设置登录后自动改密阻断；账号启用且权限配置完成后即可使用。
- 个人入口不能弱化现有密码修改能力。

### 2.2 后端现状

当前主要逻辑在：

```text
quote-backend/src/main/java/com/machining/quote/controller/AuthController.java
quote-backend/src/main/java/com/machining/quote/service/AuthService.java
quote-backend/src/main/java/com/machining/quote/service/UserAdminService.java
quote-backend/src/main/java/com/machining/quote/config/AuthInterceptor.java
```

现有接口：

| 接口 | 现状 |
| --- | --- |
| `GET /api/auth/me` | 返回当前用户身份、组织、角色和联系方式。 |
| `GET /api/auth/permission-info` | 返回角色、权限集合和菜单树。 |
| `POST /api/auth/change-password` | 当前用户修改密码。 |

`UserAdminService.publicUser()` 已经能组装较完整用户资料，包括：

- `realName`
- `phone`
- `email`
- `deptId`
- `deptName`
- `postId`
- `postName`
- `roleCodes`
- `roleNames`
- `lastLoginAt`
- `passwordChangedAt`

但这些字段目前主要服务于管理员用户管理列表，`/api/auth/me` 尚未对当前用户返回完整资料。

## 3. 产品边界

### 3.1 本人可维护

个人入口中本人可维护：

| 字段 | 行为 |
| --- | --- |
| `phone` | 可新增、修改、清空。 |
| `email` | 可新增、修改、清空。 |
| 密码 | 沿用现有修改密码弹窗和接口。 |

### 3.2 本人只读

个人入口中本人只能查看：

| 字段 | 原因 |
| --- | --- |
| `username` | 登录账号，不允许本人修改。 |
| `displayName` / `realName` | 企业身份展示字段，暂由管理员维护，避免姓名治理混乱。 |
| `deptName` | 部门是组织身份属性，由组织档案 / 用户管理维护。 |
| `postName` | 岗位是组织身份属性，由组织档案 / 用户管理维护。 |
| `roleNames` | 角色是功能授权来源，由角色权限和用户管理维护。 |
| 数据范围 | 属于角色治理，不在个人入口展示或配置。 |

### 3.3 不做范围

本阶段不做：

- 不新增左侧菜单。
- 不新增可分配权限点。
- 不让用户自行修改部门、岗位、角色、数据范围。
- 不引入头像上传。
- 不做站内消息、通知中心、主题切换。
- 不改变 401、路由权限、Pinia 权限数据流。

## 4. 接口设计

用户明确选择“扩展接口”，因此本阶段优先扩展现有认证接口，而不是新建管理员式资料模块。

### 4.1 扩展当前用户接口

接口：

```text
GET /api/auth/me
```

返回字段扩展为：

| 字段 | 说明 |
| --- | --- |
| `id` | 旧兼容用户 ID，即 `erp_user.id`。 |
| `systemUserId` | 新权限体系用户 ID，即 `system_user.id`。 |
| `username` | 登录账号。 |
| `displayName` | 展示名。 |
| `realName` | 真实姓名。 |
| `phone` | 手机号。 |
| `email` | 邮箱。 |
| `deptId` | 部门 ID。 |
| `deptName` | 部门名称。 |
| `postId` | 岗位 ID。 |
| `postName` | 岗位名称。 |
| `role` | 旧兼容角色字段。 |
| `roles` / `roleCodes` | 当前用户角色编码集合。 |
| `roleNames` | 当前用户角色名称集合。 |
| `lastLoginAt` | 最近登录时间。 |
| `passwordChangedAt` | 最近改密时间。 |

建议响应结构保持现状：

```json
{
  "success": true,
  "data": {
    "id": 1,
    "systemUserId": 1,
    "username": "admin",
    "displayName": "管理员",
    "realName": "张三",
    "phone": "13800000000",
    "email": "admin@example.com",
    "deptId": 1,
    "deptName": "系统管理",
    "postId": 1,
    "postName": "管理员",
    "role": "ADMIN",
    "roles": ["SUPER_ADMIN"],
    "roleCodes": ["SUPER_ADMIN"],
    "roleNames": ["超级管理员"],
    "lastLoginAt": "2026-07-20T10:00:00",
    "passwordChangedAt": "2026-07-18T09:00:00"
  }
}
```

实现建议：

- 复用或下沉 `UserAdminService.publicUser()` 的资料组装逻辑。
- 避免在 `AuthController.me()` 中手工拼少量字段，防止后续字段漂移。
- 如果历史用户还没有 `system_user` 记录，继续通过兼容同步逻辑补齐或返回可用的旧字段。

### 4.2 新增本人资料更新接口

接口：

```text
PUT /api/auth/me/profile
```

请求 DTO：

```text
quote-backend/src/main/java/com/machining/quote/dto/MyProfileUpdateReq.java
```

字段：

| 字段 | 规则 |
| --- | --- |
| `phone` | 可为空；非空时只允许数字、空格、`+`、`-`、括号，长度 6 到 30。 |
| `email` | 可为空；非空时必须符合基础邮箱格式，长度不超过 120。 |

请求示例：

```json
{
  "phone": "13800000000",
  "email": "user@example.com"
}
```

清空示例：

```json
{
  "phone": "",
  "email": ""
}
```

响应：

```json
{
  "success": true,
  "message": "个人资料已更新",
  "data": {
    "id": 1,
    "systemUserId": 1,
    "username": "admin",
    "phone": "13800000000",
    "email": "user@example.com",
    "deptName": "系统管理",
    "postName": "管理员"
  }
}
```

安全规则：

- 只能更新当前登录用户自己的 `phone`、`email`。
- 请求体中即使传入 `role`、`roleCodes`、`deptId`、`postId`、`enabled` 等字段，也必须忽略或拒绝。
- 不需要 `system:user:update` 权限，因为这是本人资料维护，不是管理员维护用户。
- 仍然需要登录态；未登录返回 401。
- QPO 不再设置登录后改密阻断；资料编辑只按普通登录态和当前用户边界校验。

## 5. 前端设计

### 5.1 组件边界

建议新增组件：

```text
quote-frontend/src/components/UserProfilePopover.vue
```

职责：

- 作为 App Shell 右上角个人入口。
- 展示用户头像、姓名、账号、部门、岗位、角色、手机号、邮箱。
- 提供“编辑联系方式”“修改密码”“退出登录”三个动作入口。
- 修改密码弹窗仍由 `App.vue` 统一承载。

修改：

```text
quote-frontend/src/App.vue
quote-frontend/src/stores/authStore.js
quote-frontend/src/services/authApi.js
```

`App.vue` 只保留：

- 侧边栏。
- 顶部标题。
- `UserProfilePopover`。
- 现有手动修改密码弹窗。

这样避免 `App.vue` 继续膨胀。

### 5.2 右上角视觉结构

header 右侧建议为：

```text
[圆形头像] [显示名] [下拉箭头]
```

要求：

- 高度与 header 对齐。
- 使用现有 ERP token，不新增 UI 库。
- 用户名过长时省略号，鼠标悬浮显示完整内容。
- 移动端或窄屏下可只显示头像和下拉箭头。

### 5.3 Popover 内容

建议面板结构：

```text
头像 / 显示名
账号：username
角色：roleNames

组织信息
部门：deptName
岗位：postName

联系方式
手机：phone
邮箱：email

[编辑联系方式] [修改密码] [退出登录]
```

交互规则：

- 部门、岗位、角色只读。
- 手机号、邮箱为空时显示 `未填写`。
- 编辑联系方式打开小弹窗，不在 popover 内塞复杂表单。
- 保存成功后调用 `authStore.updateUser(response.data)`，并同步 localStorage 中的 `erp_user`。

### 5.4 编辑联系方式弹窗

字段：

- 手机号。
- 邮箱。

前端校验：

- 手机号：为空允许；非空使用 `/^[0-9+\-\s()]{6,30}$/`。
- 邮箱：为空允许；非空使用 `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`。

按钮：

- 取消。
- 保存。

保存体验：

- 保存中按钮 loading。
- 成功后关闭弹窗并刷新 popover。
- 失败使用 Element Plus message 展示后端错误。

## 6. Pinia 与本地缓存

`authStore` 调整：

- `verifyAuth()` 调用扩展后的 `GET /api/auth/me` 后，写入完整用户资料。
- 新增 action：`updateMyProfile(payload)`，调用 `PUT /api/auth/me/profile`。
- `displayName` getter 保持兼容：优先 `displayName`，其次 `realName`，再其次 `username`。
- `roleName` getter 可以继续兼容旧 `role`，但个人入口优先展示 `roleNames`。
- 保留 `erp_user` localStorage key，不改兼容标识。

`authApi.js` 调整：

```js
export const updateMyProfile = (payload) => request('/api/auth/me/profile', {
  method: 'PUT',
  data: payload
})
```

## 7. 权限、日志与审计

### 7.1 权限

本阶段不新增可分配权限点。

原因：

- 个人资料查看和本人联系方式更新是登录用户的基础自助能力。
- 它不是左侧模块，也不是管理员操作。
- 后端安全边界是“只能更新当前登录用户自己的手机号和邮箱”。

需要检查：

- `AuthInterceptor` 仍然对 `/api/auth/me/profile` 做登录校验。
- 不要给该接口加 `@RequirePermission("system:user:update")`。
- 不要新增 `common:*` 权限。

### 7.2 操作日志

新增动作：

| 动作 | 模块 | 说明 |
| --- | --- | --- |
| `USER_PROFILE_UPDATE` | `SYSTEM` | 当前用户更新自己的手机号、邮箱。 |

记录内容：

- `targetType`: `system_user`
- `targetId`: 当前用户 `system_user.id`，找不到时使用旧 `erp_user.id`
- `before`: `{ phone, email }`
- `after`: `{ phone, email }`
- 不记录密码、token、Authorization header、Cookie。

修改密码继续使用现有：

| 动作 | 说明 |
| --- | --- |
| `USER_CHANGE_PASSWORD` | 当前用户修改密码。 |

### 7.3 文件日志

建议 INFO：

```text
User profile updated userId={} systemUserId={}
```

建议 WARN：

```text
User profile update rejected userId={} reason={}
```

不记录完整手机号、邮箱；如需排查，操作日志 before/after 已足够。

## 10. 完成标准

- 右上角不再堆叠多个裸按钮，而是统一为个人入口。
- 用户可以在个人入口查看账号、部门、岗位、角色、手机号、邮箱。
- 用户可以自助维护手机号、邮箱和密码。
- 用户不能自助修改部门、岗位、角色、数据范围。
- `GET /api/auth/me` 成为当前用户资料展示的稳定接口。
- `PUT /api/auth/me/profile` 只更新当前用户联系方式。
- 操作日志能查询 `USER_PROFILE_UPDATE` 和 `USER_CHANGE_PASSWORD`。
- 登录态、401、权限菜单行为不被破坏。
- 不新增 UI 库，不新增左侧模块，不新增可分配权限点。
