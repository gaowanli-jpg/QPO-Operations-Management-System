# QPO 角色管理数据范围优化开发文档

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 优化角色管理模块的数据范围功能，让 QPO 订单主流程按“功能权限 + 客户范围”治理，避免部门数据范围误伤跨部门订单流转。

**Architecture:** 后端保留现有数据范围底层能力，前端角色管理将常用范围简化为“全部数据 / 指定客户 / 仅本人 / 无数据”，部门类范围降级为高级兼容配置。订单列表和订单详情仍由后端 `DataScopeService` 做最终安全过滤，前端只负责降低管理员误配概率。

**Tech Stack:** Spring Boot、MyBatis Plus、Flyway、Vue 3、Pinia、Element Plus、Vitest、JUnit。

## Global Constraints

- QPO 订单是跨部门流转对象，不默认按部门隔离。
- 功能权限决定用户能进入哪些模块、能执行哪些动作。
- 客户范围是 QPO 订单数据隔离的主推荐方式。
- 部门字段保留为组织属性、日志展示、未来统计和兼容能力。
- 仅本人当前产品口径为“当前用户导入/创建的订单”；`owner_user_id` 作为未来负责人机制预留字段，不在 UI 文案中强调。
- 多角色数据范围取并集，不做交集收窄。
- 不新增可分配的 `common:*` 权限。
- 本次只优化角色管理模块的数据范围体验，不重构完整订单负责人体系。

## 1. 背景与问题

当前角色管理的数据范围抽屉同时展示：

- 范围类型
- 指定部门树
- 指定客户多选

这会造成两个误解：

1. 管理员选择 `SELF` 仅本人时，下面仍能选择客户，容易误以为是“本人 AND 指定客户”，但当前后端实际是多范围并集。
2. 管理员选择部门范围时，容易把 QPO 订单理解成“部门资产”，但 QPO 的订单实际会跨市场、工程、系统多个部门流转。

QPO 的真实业务逻辑是：

```text
市场导入订单
  -> 工程核价同一订单
  -> 市场报价处理同一订单
  -> 市场议价提单同一订单
  -> 系统/审计追踪同一订单
```

因此，订单主流程不适合默认使用 `DEPT`、`DEPT_AND_CHILD` 或 `CUSTOM` 做部门隔离。更自然的治理方式是：

- 功能权限：控制“能不能进入模块 / 能不能点击动作”。
- 订单状态：控制“当前阶段由谁处理”。
- 客户范围：控制“这个人能看哪些客户的订单”。

## 2. 目标设计

### 2.1 常用数据范围

角色管理默认展示以下 4 个常用范围：

| 范围类型 | 编码 | 推荐用途 | 配置项 |
| --- | --- | --- | --- |
| 全部数据 | `ALL` | 超级管理员、总经理、跨部门业务负责人 | 无 |
| 指定客户 | `CUSTOMER` | 市场人员、大客户负责人、只负责部分客户的用户 | 客户多选 |
| 仅本人 | `SELF` | 临时账号、试用人员、只看自己导入订单的人员 | 无 |
| 无数据 | `NONE` | 只做系统配置、账号管理、不看业务订单的角色 | 无 |

### 2.2 高级兼容数据范围

部门类范围保留底层能力，但在角色管理 UI 中降级为“高级/兼容配置”：

| 范围类型 | 编码 | 说明 |
| --- | --- | --- |
| 本部门 | `DEPT` | 不推荐用于 QPO 订单主流程，可能导致工程看不到市场导入的待核价订单。 |
| 本部门及子部门 | `DEPT_AND_CHILD` | 同上，仅适合未来非订单类部门资产或特殊组织管控。 |
| 指定部门 | `CUSTOM` | 跨部门兼容授权，需明确知道影响后再配置。 |

### 2.3 仅本人口径

产品文案统一为：

> 仅本人：仅查看当前用户导入/创建的订单。

当前系统有两个相关字段：

- `order_rfq.created_by`：订单创建/导入人。
- `order_rfq.owner_user_id`：未来订单负责人机制预留字段。

目标口径：

- 短期 UI 和文档只表达“导入/创建人”。
- 不在角色管理页面展示“负责人”概念。
- 后端可分阶段决定是否把 `SELF` 查询从 `created_by OR owner_user_id` 收紧为 `created_by`；如果收紧，必须先加测试护栏。

### 2.4 多角色叠加规则

多角色数据范围继续取并集：

```text
角色 A：指定客户 = 客户甲
角色 B：指定客户 = 客户乙
最终可见 = 客户甲 OR 客户乙
```

不做交集，因为交集会造成“角色越多权限越窄”，不符合企业权限管理直觉。

### 阶段 2：保存 payload 规范化

**目标:** 避免隐藏字段被误保存，形成脏配置。

**修改文件:**

- `quote-frontend/src/components/SystemRoleManage.vue`
- `quote-system/src/main/java/com/machining/quote/service/SystemRoleService.java`

**前端规则:**

保存数据范围时按类型清理无关字段：

| dataScope | deptIds | customerNames |
| --- | --- | --- |
| `ALL` | `[]` | `[]` |
| `SELF` | `[]` | `[]` |
| `NONE` | `[]` | `[]` |
| `CUSTOMER` | `[]` | 已选客户 |
| `CUSTOM` | 已选部门 | `[]` |
| `DEPT` | `[]` | `[]` |
| `DEPT_AND_CHILD` | `[]` | `[]` |

**后端兜底规则:**

即使前端传了无关字段，后端也应按 `dataScope` 清理：

- `CUSTOMER` 只保存 `customerNames`。
- `CUSTOM` 只保存 `deptIds`。
- 其他类型清空 `deptIds` 和 `customerNames`。

**验收:**

- 从 `CUSTOMER` 切换到 `SELF` 保存后，再打开抽屉，客户不再残留。
- 从 `CUSTOM` 切换到 `ALL` 保存后，再打开抽屉，部门不再残留。
- 旧角色已有残留配置时，重新保存会清理无关字段。

### 阶段 3：SELF 口径决策与实现

**目标:** 让“仅本人”的产品文案和后端行为一致。

**推荐方案 A：先不改后端，只改文案**

- `SELF` 后端继续使用 `created_by OR owner_user_id`。
- 文案写“导入/创建”，不强调负责人。
- 适合短期最小风险。

**方案 B：同步收紧为 created_by**

- `DataScopeService.currentOrderScopeSql()` 中 `SELF` 条件改为：

```sql
created_by = 当前用户
```

- `DataScopeService.matchesOrder()` 中 `SELF` 只判断 `created_by`。
- `owner_user_id` 保留字段，不参与当前 `SELF`。
- 文档明确：负责人机制未启用前，`owner_user_id` 仅预留。

**推荐:** 采用方案 B，但单独作为一个小阶段执行。这样产品口径最干净；如果担心历史订单兼容，可先用方案 A。

**验收:**

- 选择 `SELF` 的用户只能看到自己导入/创建的订单。
- 非本人导入但 `owner_user_id` 指向自己的历史测试数据，如果采用方案 B，不再可见。
- 测试明确体现选择的方案。
