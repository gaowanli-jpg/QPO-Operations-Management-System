# QPO 角色授权模块树企业级开发文档

## 1. 背景

QPO 当前已经完成企业级权限体系主体建设：

- 用户支持多角色。
- 角色绑定权限点。
- 前端路由使用 `meta.permission`。
- 按钮使用 `v-permission`。
- 后端接口使用权限点兜底。
- 数据权限已经接入订单、日志等关键查询。

但角色授权界面目前仍是扁平 checkbox 列表：

```vue
<el-checkbox-group v-model="permissionCodes">
  <el-checkbox v-for="permission in permissions" :label="permission.permissionCode">
    {{ permission.permissionName }}
  </el-checkbox>
</el-checkbox-group>
```

这会带来三个问题：

1. 管理员不知道某个权限属于哪个业务模块。
2. 想关闭整个模块时，需要逐个取消按钮权限，容易漏选。
3. 左侧菜单、路由权限、按钮权限、接口权限之间的关系不直观。

最近“历史订单不见”的问题也说明了同一个根因：

- 前端有 `/history-orders` 左侧入口。
- 该入口和 `/orders` 共用 `market:order:view`。
- 后端权限菜单没有单独建模 `/history-orders`。
- 动态菜单按后端 path 白名单渲染时，历史订单被过滤掉。

短期修复是前端允许“同权限的本地伴随菜单”显示；企业级根治则是让每个真正可点击的左侧入口都能在权限目录中被清晰表达。

```text
业务分组
```

## 3. 核心原则

### 3.1 左侧可点击入口就是授权模块

左侧真正可点击的菜单项应当对应一个 `MENU` 权限点。

当前左侧分组“市场 / 工程 / 订单 / 系统”只是视觉分组，不是可点击页面，不作为后端安全权限点。

| 左侧层级 | 是否权限点 | 说明 |
| --- | --- | --- |
| 市场 / 工程 / 订单 / 系统 | 否 | UI 分组，可用于授权树分组，但不作为接口安全边界 |
| 新单导入 / 报价处理 / 议价提单 | 是 | 可点击模块，必须有 `MENU` 权限 |
| 具体按钮 | 是 | 必须有 `BUTTON` 或 `API` 权限 |
| 逐件核价 | 是 | 虽然不在左侧显示，但属于隐藏业务路由，仍需要权限 |

### 3.2 模块取消勾选表示整个模块不可用

如果取消勾选模块节点：

- 对应左侧菜单不显示。
- 直接访问路由返回前端无权限页或跳到可访问首页。
- 后端相关接口返回 403。
- 模块下按钮和接口权限一并取消。

### 3.3 子权限选中时必须自动包含查看权限

如果管理员只勾选“导出报价单”，系统保存时必须自动带上 `market:quote-process:view`。

原因：

- 没有查看权限，用户进不了报价处理页面。
- 有按钮权限但没有页面权限，会形成“权限配置看似成功但用户无法使用”的无效状态。

保存时规范化规则：

```text
任一模块子权限被选中 -> 自动加入该模块 MENU 权限
模块 MENU 权限被取消 -> 删除该模块所有子权限
```

### 3.4 前端体验不是安全边界

授权树只是配置 UI。最终安全仍由：

- 前端路由 `meta.permission`
- 前端按钮 `v-permission`
- 后端接口 `@RequirePermission`
- 数据权限 `DataScopeService`

共同兜底。

### 3.5 权限编码保持稳定

权限编码进入角色配置和操作日志后不应随意改名。

新增编码必须满足：

```text
模块:资源:动作
```

例如：

- `market:history-order:view`
- `market:quote-process:export`
- `engineer:pricing:complete-order`

### 3.6 不可逆发布能力不得回补重置权限

议价提单已经收口为不可逆发布流程：

- `order_delivery_ticket` 是不可逆发布记录，也是 APS 同步工艺快照的单一来源。
- QPO 内部工艺表展示/导出结果从 `order_delivery_ticket` 动态生成；`order_process_sheet` 已通过 V36 回填后删除。
- 分批提单通过累计提单数量和剩余可提数量控制。
- 订单最终状态仍使用 `已生成提单`，零件最终状态使用 `已提单`。
- `market:release:reset` 已废弃，授权树不得展示，也不得通过默认角色或 fallback catalog 重新赋权。

因此，议价提单模块下只能出现 `market:release:create` 这类正向生成权限；已生成提单行和已生成工艺表行只读展示，不再建模删除或重置按钮权限。

## 4. 当前差距

### 4.1 前端授权 UI 是扁平列表

文件：

- `quote-frontend/src/components/SystemRoleManage.vue`

现状：

- `permissions` 是后端返回的权限数组。
- `permissionCodes` 是角色已选权限编码数组。
- UI 使用 `el-checkbox-group` 平铺展示。

问题：

- 没有模块层级。
- 没有批量勾选/取消模块。
- 无法展示“查看权限 / 操作权限 / 模块级基础能力”的关系。

### 4.2 数据库字段有树能力，但未真正使用

文件：

- `quote-system/src/main/resources/db/migration/V25__enterprise_permission_system.sql`
- `quote-system/src/main/java/com/machining/quote/service/PermissionService.java`

现状：

- `system_permission.parent_id` 已存在。
- 当前初始化多数权限 `parent_id = 0`。
- 按钮权限没有挂到对应菜单权限下面。

结论：

> 数据库已经具备建树字段，但权限目录还没有被规范成树。

### 4.3 可点击左侧入口没有完全一一建模

当前明显问题：

| 左侧入口 | 当前权限 | 问题 |
| --- | --- | --- |
| 订单管理 | `market:order:view` | 正常 |
| 历史订单 | 暂共用 `market:order:view` | 不能单独授权，必须拆出 `market:history-order:view` |
| 角色管理 | `system:role:view` | 迁移后应确保 route_path 为 `/roles` |
| 报价模板 | `market:template:view` | 已独立权限，正常 |

企业级目标：

> 每个左侧可点击入口都应当拥有一个明确的 `MENU` 权限点；隐藏子页面可以作为模块内子权限。

## 5. 推荐设计

### 5.1 权限树结构

后端仍以 `system_permission` 为唯一权限源。

建议把权限分为三层：

```text
UI 分组节点，前端合成，不保存权限编码
  MENU 模块节点，来自 system_permission.permission_type = MENU
    BUTTON/API/隐藏 MENU 子权限，来自 system_permission.parent_id
```

示例：

```json
{
  "groupKey": "market",
  "groupName": "市场",
  "children": [
    {
      "permissionCode": "market:quote-process:view",
      "permissionName": "报价处理",
      "permissionType": "MENU",
      "routePath": "/quote-process",
      "children": [
        {
          "permissionCode": "market:quote-process:update-lead-time",
          "permissionName": "维护报价交期",
          "permissionType": "BUTTON"
        },
        {
          "permissionCode": "market:quote-process:export",
          "permissionName": "导出报价单",
          "permissionType": "BUTTON"
        }
      ]
    }
  ]
}
```

### 5.2 分组规则

前端授权树分组可以按权限编码前缀和路由归属生成。

| 分组 | 匹配规则 | 展示顺序 |
| --- | --- | --- |
| 市场 | `market:*` 且不是订单管理专属 | 100 |
| 订单 | `market:order:*`、`market:history-order:*` | 200 |
| 工程 | `engineer:*` | 300 |
| 系统 | `system:*` | 800 |
| 隐藏兼容权限 | 旧 `common:*` | 不展示 |

说明：

- `market:order:*` 从业务上属于市场域，但左侧已经单独放在“订单”分组，授权树也应保持一致。
- 旧 `common:*` 不再作为管理员可授权能力展示；选择客户、选择订单、文件预览、任务查看等基础动作必须拆成模块级权限编码。

### 5.3 历史订单建模

建议新增独立权限：

| 权限编码 | 类型 | 名称 | 路由 | 默认授权 |
| --- | --- | --- | --- | --- |
| `market:history-order:view` | `MENU` | 历史订单 | `/history-orders` | 拥有 `market:order:view` 的默认角色同步拥有 |

调整：

- `quote-frontend/src/router/index.js`：`/history-orders` 改为 `market:history-order:view`。
- `quote-frontend/src/App.vue`：历史订单菜单改为 `market:history-order:view`。
- 后端默认角色权限增加 `market:history-order:view`。
- 操作日志、数据权限仍沿用订单数据范围。

这样历史订单就不再依赖“同权限伴随菜单”的前端兼容逻辑。

完全根治要求历史订单必须使用独立 `market:history-order:view`。不再保留“历史订单与订单管理长期共用同一 `MENU` 权限”的方案。

### 5.4 逐件核价建模

`/pricing` 不在左侧直接显示，但它是零件核价流程的重要子页面。

建议在授权树中展示为“零件核价”模块下的子权限：

```text
零件核价
  查看零件核价
  保存全局设定
  查看逐件核价
  保存单件核价
  一键刷新核价
  完成整单报价
```

保存规则：

- 勾选逐件核价相关权限时，自动包含 `engineer:setup:view`。
- 进入 `/pricing` 仍校验 `engineer:pricing:view`。
- 左侧仍只显示“零件核价”，不新增“逐件核价”菜单。

### 5.5 操作按钮权限建模

按钮权限必须挂到对应模块。

| 模块 | 子权限 |
| --- | --- |
| 新单导入 | `market:rfq:import`、`market:rfq:upload-drawing` |
| 订单管理 | `market:order:supplement-drawing`、`market:order:delete` |
| 报价处理 | `market:quote-process:update-lead-time`、`market:quote-process:save-quote`、`market:quote-process:export` |
| 议价提单 | `market:release:create` |
| 报价模板 | `market:template:upload` |
| 零件核价 | `engineer:setup:save-config`、`engineer:pricing:*` |
| 材料工艺 | `engineer:dict:material-manage`、`engineer:dict:process-manage`、`engineer:dict:fee-manage` |
| 用户权限 | `system:user:create/update/disable/reset-password/delete` |
| 角色管理 | `system:role:create/update/delete/assign-permission/assign-data-scope` |
| 操作日志 | `system:audit:export`、`system:audit:retention` |

说明：`market:release:reset` 已废弃，不属于议价提单模块子权限。新增或重构议价提单页面时，只能围绕“查看 / 生成 / 模块级基础能力”维护权限。

### 5.6 公共能力完全模块化

本阶段采用完全根治方案：公共能力不再独立授权，必须拆到实际业务模块。

原因：

- 管理员授权时会按业务职责理解权限，而不是按技术复用理解权限。
- “没有市场模块权限，却有市场选择客户/订单能力”不符合治理直觉。
- 通用接口虽然技术上可复用，但权限治理必须按业务使用场景归属。
- 旧 `common:*` 如果继续暴露给角色，会绕开模块边界，长期会变成灰色权限。

推荐规则：

```text
技术复用可以保留在 service 层
授权编码必须归属业务模块
授权树不得展示可分配的 common:* 权限
旧 common:* 只能作为迁移期隐藏兼容权限
```

例如：

```text
市场
  新单导入
    选择客户
    上传图纸
  报价处理
    选择客户
    选择订单
    查看异步任务
    导出报价单
  议价提单
    选择客户
    选择订单
    查看异步任务

工程
  零件核价
    选择客户
    选择订单
    预览图纸
```

推荐新增模块级权限：

| 模块 | 权限编码 | 名称 |
| --- | --- | --- |
| 新单导入 | `market:rfq:customer-select` | 新单导入选择客户 |
| 新单导入 | `market:rfq:file-preview` | 新单导入预览文件 |
| 报价处理 | `market:quote-process:customer-select` | 报价处理选择客户 |
| 报价处理 | `market:quote-process:order-select` | 报价处理选择订单 |
| 报价处理 | `market:quote-process:task-view` | 报价处理查看异步任务 |
| 议价提单 | `market:release:customer-select` | 议价提单选择客户 |
| 议价提单 | `market:release:order-select` | 议价提单选择订单 |
| 议价提单 | `market:release:task-view` | 议价提单查看异步任务 |
| 订单管理 | `market:order:customer-select` | 订单管理选择客户 |
| 订单管理 | `market:order:file-preview` | 订单管理预览文件 |
| 历史订单 | `market:history-order:customer-select` | 历史订单选择客户 |
| 历史订单 | `market:history-order:file-preview` | 历史订单预览文件 |
| 零件核价 | `engineer:setup:customer-select` | 零件核价选择客户 |
| 零件核价 | `engineer:setup:order-select` | 零件核价选择订单 |
| 零件核价 | `engineer:setup:file-preview` | 零件核价预览图纸 |
| 逐件核价 | `engineer:pricing:task-view` | 逐件核价查看异步任务 |

旧权限处理：

| 旧权限 | 处理方式 |
| --- | --- |
| `common:customer:select` | 已通过 V38 退役删除，改用各模块 `*:customer-select` |
| `common:order:select` | 已通过 V38 退役删除，改用各模块 `*:order-select` |
| `common:file:preview` | 标记为隐藏兼容，不在授权树展示，不允许新增角色主动选择 |
| `common:task:view` | 标记为隐藏兼容，不在授权树展示，不允许新增角色主动选择 |

接口治理：

- 前端页面调用模块级 API，例如 `/api/market/quote-process/order-options`、`/api/engineer/setup/order-options`。
- 模块级 API 可以复用同一个后端查询 service，但 Controller 必须挂模块级权限。
- 订单选择和客户选择不再保留旧公共 API；后端接口必须直接使用模块级 `@RequirePermission(...)`。
- 文件预览和任务查看如仍有兼容入口，应保持隐藏且不可分配，并逐步迁移到模块级权限。

保存规则：

- 勾选模块时，只自动勾选该模块需要的模块级基础权限。
- 取消模块时，只取消该模块下的模块级基础权限，不影响其他模块。
- 保存请求中如果出现可分配范围外的 `common:*`，后端要拒绝或过滤，并记录 WARN 文件日志。
- 超级管理员可以拥有旧兼容权限，但授权 UI 不展示这些旧权限。

## 6. 后端改造方案

### 6.1 新增 Flyway 迁移

建议新增：

```text
quote-system/src/main/resources/db/migration/V31__permission_module_tree.sql
```

职责：

1. 补齐可点击菜单权限。
2. 设置按钮权限的 `parent_id`。
3. 修正 `system:role:view` 等菜单的 `route_path` 和 `visible`。
4. 初始化 `market:history-order:view`。
5. 初始化选择客户、选择订单、文件预览、任务查看等模块级基础权限。
6. 将旧 `common:*` 标记为隐藏兼容权限，不允许在角色授权树中主动分配。
7. 保持已有角色兼容授权。

关键迁移逻辑：

```sql
ALTER TABLE system_permission
ADD COLUMN IF NOT EXISTS assignable BOOLEAN DEFAULT TRUE;
```

```sql
INSERT INTO system_permission (
  parent_id, permission_type, permission_code, permission_name,
  route_path, component_key, icon, sort_order, visible, enabled, assignable
)
VALUES
  (0, 'MENU', 'market:history-order:view', '历史订单',
   '/history-orders', 'HistoryOrderManage', 'Files', 125, TRUE, TRUE, TRUE)
ON CONFLICT (permission_code) DO UPDATE
SET permission_name = EXCLUDED.permission_name,
    route_path = EXCLUDED.route_path,
    component_key = EXCLUDED.component_key,
    icon = EXCLUDED.icon,
    sort_order = EXCLUDED.sort_order,
    visible = TRUE,
    enabled = TRUE,
    updated_at = CURRENT_TIMESTAMP;
```

模块级基础权限示例：

```sql
INSERT INTO system_permission (
  parent_id, permission_type, permission_code, permission_name,
  route_path, component_key, icon, sort_order, visible, enabled, assignable
)
SELECT p.id, 'API', 'market:quote-process:order-select', '报价处理选择订单',
       NULL, NULL, NULL, 133, FALSE, TRUE, TRUE
FROM system_permission p
WHERE p.permission_code = 'market:quote-process:view'
ON CONFLICT (permission_code) DO UPDATE
SET parent_id = EXCLUDED.parent_id,
    permission_name = EXCLUDED.permission_name,
    permission_type = EXCLUDED.permission_type,
    sort_order = EXCLUDED.sort_order,
    visible = FALSE,
    enabled = TRUE,
    assignable = TRUE,
    updated_at = CURRENT_TIMESTAMP;
```

旧公共权限收口示例：

```sql
DELETE FROM system_role_permission
WHERE permission_id IN (
  SELECT id
  FROM system_permission
  WHERE permission_code IN ('common:customer:select', 'common:order:select')
);

DELETE FROM system_permission
WHERE permission_code IN ('common:customer:select', 'common:order:select');

UPDATE system_permission
SET visible = FALSE,
    assignable = FALSE,
    updated_at = CURRENT_TIMESTAMP
WHERE permission_code IN (
  'common:file:preview',
  'common:task:view'
);
```

按钮挂载示例：

```sql
UPDATE system_permission child
SET parent_id = parent.id,
    updated_at = CURRENT_TIMESTAMP
FROM system_permission parent
WHERE parent.permission_code = 'market:quote-process:view'
  AND child.permission_code IN (
    'market:quote-process:update-lead-time',
    'market:quote-process:export'
  );
```

默认角色兼容示例：

```sql
INSERT INTO system_role_permission (role_id, permission_id)
SELECT r.id, p.id
FROM system_role r
JOIN system_permission p ON p.permission_code = 'market:history-order:view'
WHERE r.role_code IN ('SUPER_ADMIN', 'MARKET_USER', 'MARKET_MANAGER', 'READONLY')
ON CONFLICT (role_id, permission_id) DO NOTHING;
```

当前接口：

```text
GET /api/system/permissions/tree
```

返回结构：

```json
[
  {
    "key": "market",
    "label": "市场",
    "type": "GROUP",
    "sortOrder": 100,

      {
        "key": "market:quote-process:view",
```

- 树接口只返回 `assignable = TRUE` 的权限。
- 旧 `common:*` 不返回给授权树，避免管理员误分配。

### 6.4 保存授权时做权限规范化

文件：

- `quote-system/src/main/java/com/machining/quote/service/SystemRoleService.java`

当前：

```java
List<String> nextCodes = normalizeCodes(req.getPermissionCodes());
```

目标：

```java
List<String> nextCodes = permissionTreeService.normalizeAssignableCodes(req.getPermissionCodes());
```

规范化规则：

1. 移除空编码、重复编码、group key。
2. 校验权限编码存在且启用。
3. 子权限选中时自动补齐最近的 `MENU` 祖先。
4. 拒绝或过滤 `assignable = FALSE` 的旧 `common:*` 权限，并写入 WARN 文件日志。
5. 不允许普通角色保存 `super_admin` 专属保留权限，除非当前操作者是超级管理员。
6. 审计日志记录 before/after，并增加：
   - 新增权限数量
   - 移除权限数量
   - 变更模块数量

## 8. 数据权限与授权树关系

功能权限和数据权限仍分开管理。

角色授权树解决：

```text
能不能看这个模块？
能不能点这个按钮？
能不能调用这个接口？
```

数据范围抽屉解决：

```text
同一个模块里能看哪些订单？
能看哪些客户？
能看哪些操作日志？
```

不要把数据权限放进权限树，否则管理员会混淆：

- 功能权限是“能做什么”。
- 数据权限是“能看到谁的数据”。

详情页中文化字段：

| 字段 | 中文 |
| --- | --- |

6. 左侧菜单元数据使用同一权限编码。
7. 按钮使用 `v-permission`。
8. 后端接口加 `@RequirePermission`。
9. 权限清单文档补充。
10. 前后端测试补充。

禁止：

- 页面只在前端本地写菜单，不进入后端权限目录。
- 多个左侧独立入口长期共用一个 `MENU` 权限。
- 在角色授权树中暴露 `common:*` 权限。
- 复用选择弹窗、文件预览、任务查看时写死 `common:*` 权限。
- 只隐藏按钮但后端接口不加权限注解。
- 直接按角色名写业务判断。

## 14. 推荐下一步

建议下一步从阶段 8.1 开始：

> 先补授权树测试护栏，再做后端权限目录树化与公共权限退役。

原因：

- 当前权限体系已经进入核心安全模块，不能先改 UI 再补规则。
- 历史订单问题说明“菜单入口和权限目录不一致”会产生真实回归。
- 先用测试固定“每个左侧入口必须有 MENU 权限”，后续改动才不会漂移。
