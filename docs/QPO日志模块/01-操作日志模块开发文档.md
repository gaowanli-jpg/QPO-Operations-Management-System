# QPO 操作日志模块开发文档

> 适用范围：QPO/ERP 系统。当前阶段只面向 `quote-backend` 与 `quote-frontend`，不涉及 APS。

## 1. 背景与目标

QPO 已经有基础审计日志能力：后端存在 `audit_log` 表、`AuditLog` 实体、`AuditLogMapper` 和 `AuditService.record(...)` 写入服务。当前问题是这些日志只能在数据库或归档文件中查看，系统内没有面向管理员的日志查询页面，也缺少企业排查常用字段，例如 IP、User-Agent、请求路径、执行结果和失败原因。

本次新增“操作日志”模块，目标是把现有审计能力产品化：

- 在左侧菜单 **系统** 下新增 **操作日志**。
- 仅 `ADMIN` 可见、可访问。
- 支持管理员查询、筛选、分页查看关键操作记录。
- 支持查看单条日志详情，包括操作前后 JSON 数据。
- 在不破坏已有日志数据的前提下，逐步补齐企业级审计字段和关键动作覆盖。
- 操作日志保留、归档和清理由系统页面统一配置。

## 2. 当前现状

### 2.1 已有数据表

已有 Flyway 迁移中创建了 `audit_log`：

```sql
CREATE TABLE IF NOT EXISTS audit_log (
    id SERIAL PRIMARY KEY,
    username VARCHAR(80),
    role VARCHAR(30),
    action VARCHAR(100) NOT NULL,
    target_type VARCHAR(80),
    target_id VARCHAR(120),
    before_data TEXT,
    after_data TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_audit_log_created_at ON audit_log(created_at);
CREATE INDEX IF NOT EXISTS idx_audit_log_action ON audit_log(action);
CREATE INDEX IF NOT EXISTS idx_audit_log_target ON audit_log(target_type, target_id);
```

对应文件：

- `quote-backend/src/main/resources/db/migration/V2__auth_audit_and_hardening.sql`
- `quote-backend/src/main/java/com/machining/quote/entity/AuditLog.java`
- `quote-backend/src/main/java/com/machining/quote/mapper/AuditLogMapper.java`
- `quote-backend/src/main/java/com/machining/quote/service/AuditService.java`

### 2.2 已有写入点

当前已经写入日志的动作包括：

| 模块 | 已记录动作 |
| --- | --- |
| 字典 | 材料、工艺、加价费用、非工时费用的新增、编辑、删除 |
| 用户 | 新增用户、编辑用户、修改密码、删除用户 |
| 工程 | 保存逐件核价、刷新报价、完成工程报价、应用历史报价、保存工程配置 |
| 市场 | 客户交期批量调整、客户交期单项设置、客户交期单项更新 |
| 内部交期 | 内部目标交期批量调整、单项设置、单项更新 |
| 交付 | 生成提单 |
| 订单 | 补传图纸、询价订单状态治理；彻底删除订单仅为旧兼容接口 |

### 2.3 保留与归档策略

操作日志保留策略由系统页面配置，替代单纯依赖运维脚本的方式：

- 管理员在 **系统 > 操作日志 > 日志保留策略** 中配置是否开启自动清理。
- 默认不开启自动清理，默认保留天数为 180 天。
- 开启后，后端定时检查配置时间；到期日志会先按配置导出 CSV，再从在线库删除。
- 归档文件默认写入 `ERP_BACKUP_DIR/audit-logs/<yyyyMMdd>/audit_log_before_<timestamp>.csv`。
- 系统页面保留策略是操作日志到期清理的唯一维护入口，避免多套清理链路重复执行。

## 3. 目标用户与权限

### 3.1 目标用户

操作日志模块面向系统管理员，用于：

- 查询谁在什么时候做了什么操作。
- 追踪高风险动作，例如删除订单、删除字典、重置密码。
- 排查报价、交期、提单、工艺表数据被修改的来源。
- 配合备份、归档、上线验收进行审计。

### 3.2 权限规则

- 左侧菜单入口只在 `canSee(['ADMIN'])` 时显示。
- 路由 `meta.roles` 只允许 `ADMIN`。
- 后端接口使用 `@RequireRole({"ADMIN"})`。
- 操作日志不提供单条前端删除、编辑能力；到期清理只能通过管理员配置的保留策略统一执行。
- `ADMIN` 默认仍保留系统内其它角色的通行能力，不额外修改现有权限模型。

### 5.4 详情抽屉

点击“查看详情”打开右侧抽屉，展示：

- 基本信息：ID、时间、操作人、角色、模块、动作、结果。
- 请求信息：IP、User-Agent、请求方法、请求路径、Request ID。
- 对象信息：目标类型、目标 ID。
- 摘要：message、errorMessage。
- 操作前数据：格式化 JSON。
- 操作后数据：格式化 JSON。

前端规则：

- JSON 可折行展示。
- 文本过长使用固定高度滚动容器。
- 空值展示 `-`。
- 敏感字段显示 `[已脱敏]`。

## 7. 数据库扩展设计

### 7.1 新增字段

新增迁移建议命名：

```text
quote-backend/src/main/resources/db/migration/V23__audit_log_enrichment.sql
```

建议 SQL：

```sql
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS module VARCHAR(60);
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS result VARCHAR(30) DEFAULT 'SUCCESS';
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS message VARCHAR(500);
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS ip_address VARCHAR(80);
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS user_agent TEXT;
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS request_method VARCHAR(20);
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS request_path VARCHAR(300);
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS request_id VARCHAR(80);
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS error_message TEXT;

CREATE INDEX IF NOT EXISTS idx_audit_log_module ON audit_log(module);
CREATE INDEX IF NOT EXISTS idx_audit_log_result ON audit_log(result);
CREATE INDEX IF NOT EXISTS idx_audit_log_username ON audit_log(username);
CREATE INDEX IF NOT EXISTS idx_audit_log_request_id ON audit_log(request_id);
```

### 7.2 历史数据兼容

旧数据没有 `module/result/message` 时：

- `result` 默认按 `SUCCESS` 展示。
- `module` 由 `action` 前缀推断：
  - `DICT_` -> `DICT`
  - `USER_` -> `SYSTEM`
  - `ORDER_` -> `ORDER`
  - `DELIVERY_` / `PROCESS_SHEET_` -> `DELIVERY`
  - `QUOTE_` -> `MARKET`
  - `INTERNAL_TARGET_` -> `MARKET`
  - `ITEM_` / `REPEAT_` -> `ENGINEER`
- `message` 由 action、targetType、targetId 拼接兜底。

## 11. 敏感信息与脱敏规则

### 11.1 永不记录

以下内容不得写入 `audit_log`：

- 原始密码。
- 密码哈希。
- JWT token。
- Authorization header。
- `X-Auth-Token`。
- 上传文件二进制内容。

### 11.2 脱敏字段

`AuditService` 在写入 JSON 前应递归处理以下 key：

```text
password
newPassword
oldPassword
confirmPassword
passwordHash
token
authorization
xAuthToken
templateFile
file
files
drawings
```

脱敏值统一写：

```text
[已脱敏]
```

### 11.3 登录失败日志

登录失败只记录：

- username。
- IP。
- User-Agent。
- 失败原因分类：用户名密码错误、账号禁用、账号锁定、参数缺失。

不得记录密码。

## 12. 阶段化实施计划

### 阶段 1：查询现有审计日志

目标：不改现有写入逻辑，先让管理员能在页面看到已有 `audit_log`。

后端：

- 新增 `AuditLogController`。
- 新增 `AuditLogQueryService`。
- 新增 `AuditLogDTO` 和 `AuditLogQueryReq`。
- 提供分页查询、详情查询、筛选项接口。
- 仅使用现有字段，不新增数据库字段。

前端：

- 新增 `auditApi.js`。
- 新增 `AuditLogManage.vue`。
- `App.vue` 系统菜单下新增“操作日志”。
- `router/index.js` 新增 `/audit-logs` 懒加载路由，权限 `ADMIN`。

验收：

- 管理员可以进入系统 > 操作日志。
- 非管理员不可见菜单，直接访问会被路由权限拦截。
- 默认展示最近 7 天日志。
- 可以按操作人、动作、对象类型、对象 ID、关键词查询。
- 可以打开详情抽屉查看 before/after 原始 JSON。

### 阶段 2：企业级字段扩展

目标：让日志具备更好的排查能力。

后端：

- 新增 Flyway 迁移扩展字段。
- 扩展 `AuditLog` 实体。
- 新增 `RequestTraceFilter`，写入 requestId、IP、User-Agent、method、path。
- 扩展 `AuditService.record(...)`，支持 module、result、message、errorMessage。
- 保留旧签名，旧调用继续可用。

验收：

- 新日志包含 module、result、message、IP、User-Agent、path。
- 旧日志仍能正常查询和展示。
- 前端筛选模块、结果状态可用。

### 阶段 3：补齐关键动作覆盖

目标：把企业审计最关心的动作纳入日志。

后端补充记录：

- 登录成功：`AUTH_LOGIN_SUCCESS`。
- 登录失败：`AUTH_LOGIN_FAILED`。
- 账号锁定：`AUTH_ACCOUNT_LOCKED`。
- 登出：`AUTH_LOGOUT`。
- 报价模板上传：`QUOTE_TEMPLATE_UPLOAD`。
- RFQ 导入：`RFQ_IMPORT`。
- 报价单导出任务提交：`QUOTE_EXPORT_TASK_SUBMIT`。
- 一键刷新核价任务提交：`QUOTE_REFRESH_TASK_SUBMIT`。

验收：

- 登录成功/失败均可在操作日志中查到。
- 上传报价模板后可查到文件名和更新时间摘要。
- 导入 RFQ 后可查到客户名、订单号、导入数量摘要。
- 导出任务和刷新任务提交后可查到任务 ID。

### 阶段 4：详情可读化与导出

目标：让业务管理员不用直接读原始 JSON。

前端：

- JSON 格式化展示。
- before/after 分区展示。
- 常见字段中文化，例如 partNo -> 图号、qty -> 数量。
- 长文本区域支持复制。
- 新增导出 CSV。

后端：

- 提供 `/api/admin/audit-logs/export`。
- 限制最大导出行数。
- CSV 使用 UTF-8 BOM，方便 Excel 打开。

验收：

- 详情页 JSON 缩进可读。
- 空值和异常 JSON 不导致页面报错。
- 导出文件能用 Excel 打开，中文不乱码。

### 阶段 5：日志保留策略与自动归档清理

目标：让管理员不依赖脚本，也能在系统内配置日志保留周期，并由后端自动归档和清理到期日志。

后端：

- 新增 `audit_log_retention_config` 单行配置表，保存开关、保留天数、是否清理前归档、执行时间和最近一次执行结果。
- 新增 `AuditLogRetentionService`，负责读取配置、保存配置、手动执行清理、定时检查是否到点执行。
- 新增 `/api/admin/audit-logs/retention` 查询和保存接口。
- 新增 `/api/admin/audit-logs/retention/run` 手动执行一次清理接口。
- 清理前导出 CSV 时继续使用 UTF-8 BOM，方便 Excel 打开。
- 每次保存策略、执行清理或清理失败，都写入操作日志：
  - `AUDIT_RETENTION_CONFIG_UPDATE`
  - `AUDIT_LOG_CLEANUP_RUN`
  - `AUDIT_LOG_CLEANUP_FAILED`

前端：

- 操作日志页右上角新增 **日志保留策略**。
- 设置抽屉中可配置：
  - 自动清理开关。
  - 保留天数。
  - 清理前是否归档 CSV。
  - 每日执行时间。
  - 最近一次执行状态、清理数量、说明和归档文件路径。
- 支持管理员手动点击 **立即执行一次**。

验收：

- 默认策略为关闭自动清理、保留 180 天、清理前归档、每日 02:00 执行。
- 管理员可以在页面保存保留策略，保存动作能在操作日志中查到。
- 开启后，到期日志会按配置导出 CSV，再从在线查询中消失。
- 关闭后，定时任务不会自动删除日志。
- 手动执行清理时能返回本次清理数量、执行状态和归档文件路径。
- 归档 CSV 字段与页面查询字段一致，且中文不乱码。

## 15. 推荐执行顺序

推荐先做阶段 1 和阶段 2：

1. 阶段 1 能最快让已有 `audit_log` 可见，验证产品形态。
2. 阶段 2 补齐企业级字段，避免后续新增动作继续写入信息不足的日志。

阶段 3 到阶段 5 再按优先级推进：

1. 先补登录成功/失败、账号锁定、报价模板上传。
2. 再补 RFQ 导入、导出任务、刷新任务。
3. 最后做 CSV 导出、系统内保留策略、自动归档清理和运维文档闭环。

## 16. 风险与注意事项

- 不要把所有请求都自动记录为审计日志，否则数据量会膨胀，也会淹没关键操作。
- 只记录关键写操作、安全动作、系统配置动作、导出任务和高风险删除动作。
- `before_data` 和 `after_data` 可能较大，表格只展示摘要，详情抽屉按需查看。
- 登录失败日志要谨慎处理，避免用户名枚举风险，前端不展示过细错误给普通用户。
- 如果后续引入专门日志平台，`audit_log` 仍保留为业务审计，不替代容器运行日志。
