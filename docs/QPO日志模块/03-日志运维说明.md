# QPO 日志运维说明

## 1. 日志类型与入口

QPO 当前保留三类日志，各自职责不同：

| 日志类型 | 查看方式 | 主要用途 |
| --- | --- | --- |
| 操作日志 | 系统页面：系统 > 操作日志 | 查询谁在什么时候做了什么业务动作 |
| 后端运行日志 | 容器内 `/data/backups/logs/backend/` | 排查 Java 后端接口、任务、异常和 requestId |
| Postgres 慢 SQL / 锁等待日志 | `docker logs quote-postgres` | 排查数据库慢查询、锁等待、死锁相关问题 |

操作日志用于业务审计，后端运行日志和数据库日志用于运维排查；不要把所有运行日志写入 `audit_log`。

## 2. 操作日志

系统管理员在页面查看：

```text
系统 > 操作日志
```

适合查询：

- 登录成功、登录失败、账号锁定、登出。
- 用户、字典、报价模板、RFQ 导入、报价处理、提单等关键业务动作。
- 日志保留策略修改、手动归档清理等系统动作。

字典维护审计口径：

- 材料、工艺、普通百分比费用、组装件百分比费用类、非工时费用工艺的新增/编辑/删除写入操作日志；普通查询不写操作日志，也不增加业务 INFO。
- 组装件百分比费用类动作编码为 `DICT_ASSEMBLY_MARKUP_FEE_CREATE`、`DICT_ASSEMBLY_MARKUP_FEE_UPDATE`、`DICT_ASSEMBLY_MARKUP_FEE_DELETE`，`targetType` 为 `dict_assembly_markup_fee`。
- 排查时可在 **系统 > 操作日志** 按模块 `DICT`、上述动作编码、操作人或 requestId 查询。

个人入口审计口径：

- `USER_PROFILE_UPDATE`：当前登录用户通过右上角个人入口更新自己的手机号、邮箱。
- 该动作归入 `SYSTEM` 模块，`targetType` 为 `system_user`，`before/after` 只记录 `phone`、`email` 摘要。
- 个人入口不能修改部门、岗位、角色、权限、数据范围或启用状态；这些管理员治理动作仍分别通过用户管理、组织档案、角色管理记录。
- 排查时可按动作 `USER_PROFILE_UPDATE`、操作人或 requestId 查询；严禁在操作日志或文件日志中记录密码、token、Authorization header、Cookie。

提单相关审计口径：

- `order_delivery_ticket` 是不可逆发布记录，也是 MES/WMS 对接需求池和工艺快照来源。
- `order_process_sheet` 已通过 `V36__decommission_order_process_sheet.sql` 在回填快照后删除；新提单的 QPO 工艺表展示/导出从 `order_delivery_ticket` 动态生成。
- 分批提单通过累计提单数量和剩余可提数量控制；操作日志应记录本次生成数量和剩余摘要。
- 多订单议价提单仍是前端按订单分组调用现有生成接口：批量候选零件分页、订单选择、跨订单导入匹配不新增操作日志；实际生成时继续写入 `DELIVERY_TICKET_GENERATE`，并按订单分别产生审计记录。
- 议价提单生成前的单行版本修改写入 `RELEASE_ITEM_VERSION_UPDATE`，摘要只记录 `rfqId`、`rfqNo`、`itemId`、`partNo`、`beforeVersion`、`afterVersion`。
- 议价提单导入替换图纸写入 `RELEASE_DRAWING_REPLACE`，摘要只记录 `rfqIds`、上传数量、匹配数量、替换数量、未匹配数量和跳过数量；不得记录 PDF 内容、文件字节、完整请求体、Authorization header、token 或 Cookie。
- 提单表据导出写入操作日志，动作编码为 `DELIVERY_TICKET_EXPORT`、`DELIVERY_PROCESS_SHEET_EXPORT`，`targetType` 为 `order_rfq`，摘要只记录 `rfqId`、`rfqNo`、`status`、`exportType` 和 `rowCount`。
- 提单表据页面打开、客户/订单选择、摘要和分页查询不新增操作日志；只有导出动作写入上述业务审计记录。
- 订单最终状态仍使用 `已生成提单`，零件最终状态使用 `已提单`。
- `market:release:reset` 已废弃；操作日志中旧删除/重置动作仅作为历史查询，不再新增。

MES 物料号同步审计口径：

- MES 物料号同步是已提零件模块下的受控写操作，权限点为 `market:delivered-item:mes-sync`。
- 操作日志动作：`DELIVERY_MES_MATERIAL_SYNC_SUBMIT`、`DELIVERY_MES_MATERIAL_SYNC_SUCCESS`、`DELIVERY_MES_MATERIAL_SYNC_FAILED`。
- 该动作归入 `DELIVERY` 模块，`targetType` 为 `order_delivery_ticket`，`targetId` 为提单行 ID。
- 操作日志摘要应包含 `ticketId`、`taskId`、`rfqId`、`partNo`、`version`、`internalProjectNo`，成功时可记录 `materialNo`，不得记录 MES token、Authorization header、图纸文件内容或完整请求体。
- 排查时先在 **已提零件** 页面或 **系统 > 操作日志** 拿到 `taskId` / `requestId`，再到后端文件日志按 `MES material sync`、`System task failed`、`taskId` 或 `requestId` 关联查询。

WMS 锁库分配审计口径：

- WMS 锁库分配是已提零件模块下的受控写操作，权限点为 `market:delivered-item:wms-allocate`。
- 操作日志动作：`DELIVERY_WMS_ALLOCATION_SUBMIT`、`DELIVERY_WMS_ALLOCATION_SUCCESS`、`DELIVERY_WMS_ALLOCATION_FAILED`。
- 该动作归入 `DELIVERY` 模块，`targetType` 为 `order_delivery_ticket`，`targetId` 为提单行 ID；拆分结果写入 `order_delivery_ticket_allocation`。
- 操作日志摘要应包含 `ticketId`、`taskId`、`rfqId`、`materialNo`、`demandQty`，成功时记录 `allocationCount`、`inStockQty`、`inProductionQty`、`productionRequiredQty`，不得记录 WMS token、Authorization header 或完整请求/响应 JSON。
- 排查时先在 **已提零件** 页面或 **系统 > 操作日志** 拿到 `ticketId`、`taskId`、`requestId`，再按 `WMS allocation`、`taskType=WMS_ALLOCATION`、`ticketId`、`taskId`、`requestId` 关联文件日志和错误堆栈。

订单状态管理审计口径：

- 订单管理新增 `废弃` 状态，用于停止订单继续流转但保留全部业务内容。
- 状态管理只改订单和非提单零件状态，不清空核价、报价交期、图纸、材料、工艺、提单快照等业务字段。
- `部分已提单` / `已生成提单` 不允许废弃或回退；只要订单存在 `order_delivery_ticket` 提单行，即使订单状态异常也必须拒绝状态动作。
- 操作日志动作：`ORDER_STATUS_ROLLBACK_QUOTED`、`ORDER_STATUS_ROLLBACK_PRICED`、`ORDER_DISCARD`、`ORDER_RESTORE`。
- 排查时可在 **系统 > 操作日志** 按模块 `ORDER`、动作编码、操作人、对象 ID 或 requestId 查询；详情里的 before/after 展示状态变化、更新零件数和提单行数量摘要。

组织档案审计口径：

- 组织档案用于维护用户的部门、岗位身份字典；这些动作在 **系统 > 操作日志** 中归入系统治理类事件。
- 部门动作：`SYSTEM_DEPT_CREATE`、`SYSTEM_DEPT_UPDATE`、`SYSTEM_DEPT_ENABLE`、`SYSTEM_DEPT_DISABLE`、`SYSTEM_DEPT_DELETE`。
- 岗位动作：`SYSTEM_POST_CREATE`、`SYSTEM_POST_UPDATE`、`SYSTEM_POST_ENABLE`、`SYSTEM_POST_DISABLE`、`SYSTEM_POST_DELETE`。
- 用户组织属性变更：`SYSTEM_USER_ORG_UPDATE`，用于追踪用户部门、岗位、真实姓名、手机号、邮箱等组织身份资料调整。
- 排查时可按模块 `SYSTEM`、动作编码、操作人或 requestId 筛选；部门和岗位是身份属性，不作为订单数据范围。

客户资料审计口径：

- 客户资料维护是系统主数据治理动作；新增、编辑、删除写入操作日志，普通分页查询和客户选择不写操作日志。
- 操作日志动作：`CUSTOMER_MASTER_CREATE`、`CUSTOMER_MASTER_UPDATE`、`CUSTOMER_MASTER_DELETE`。
- 该动作归入 `SYSTEM` 模块，`targetType` 为 `customer_master`，`before/after` 只记录 `customerId`、`customerCode`、`customerShortName`、`customerName` 等摘要字段。
- 排查时可在 **系统 > 操作日志** 按模块 `SYSTEM`、上述动作编码、操作人或 requestId 查询；后端文件日志只记录 `Customer master created/updated/deleted` 级别摘要，不记录完整请求体或敏感上下文。

客户资料阶段 5 收口：

- 新增、编辑、删除写入操作日志，动作编码为 `CUSTOMER_MASTER_CREATE`、`CUSTOMER_MASTER_UPDATE`、`CUSTOMER_MASTER_DELETE`。
- 普通分页查询、客户选项查询、客户选择弹窗不写操作日志、不新增业务 INFO。
- 后端文件日志只记录写操作摘要：`Customer master created customerId={} customerCode={}`、`Customer master updated customerId={} customerCode={}`、`Customer master deleted customerId={} customerCode={}`。
- 不记录完整请求体或敏感上下文，也不记录 token、Authorization header、Cookie。

系统对接配置审计口径：

- 系统对接配置属于系统治理动作，页面入口为 **系统 > 系统配置 > 系统对接**，权限点为 `system:config:integration:update`、`system:config:integration:test`、`system:config:integration:activate`。
- 操作日志动作：`SYSTEM_INTEGRATION_CONFIG_CREATE`、`SYSTEM_INTEGRATION_CONFIG_UPDATE`、`SYSTEM_INTEGRATION_CONFIG_TEST`、`SYSTEM_INTEGRATION_CONFIG_TEST_FAILED`、`SYSTEM_INTEGRATION_CONFIG_ACTIVATE`、`SYSTEM_INTEGRATION_CONFIG_DISABLE`。
- 该动作归入 `SYSTEM` 模块，`targetType` 为 `system_external_integration_config`，`targetId` 为配置 ID；摘要只记录 `systemCode`、`configId`、`active/enabled`、host/path、timeout、测试状态和脱敏失败摘要。
- MES/WMS/U9 业务调用优先使用页面激活的 DB 配置；没有 active DB 配置时才回退到 `erp.env` 中的 `ERP_MES_*`、`ERP_WMS_*`、`ERP_U9_*`。排查“配置未生效”时先看激活记录，再看 fallback 环境变量注入。
- 后端文件日志只记录 `Integration config created/updated/tested/activated/disabled` 级别摘要，不记录 token、clientSecret、Authorization header、完整请求体或完整响应体。
- 数据中心当前仅做前端预留展示，不写操作日志、不落库、不产生后端运行日志。

保留策略在页面中配置。当前策略设计为：

- 默认关闭自动清理。
- 默认在线保留 180 天。
- 开启自动清理后，到期日志先按配置归档 CSV，再从在线库删除。
- 归档文件默认在容器内 `/data/backups/audit-logs/<yyyyMMdd>/`。

## 3. 后端运行日志

后端文件日志位于 backend 容器内：

```text
/data/backups/logs/backend/
```

常用命令：

```powershell
docker exec quote-backend sh -lc "ls -lh /data/backups/logs/backend"
docker exec quote-backend sh -lc "tail -n 200 /data/backups/logs/backend/qpo-backend.log"
docker exec quote-backend sh -lc "tail -n 200 /data/backups/logs/backend/qpo-error.log"
```

文件说明：

| 文件 | 内容 |
| --- | --- |
| `qpo-backend.log` | INFO/WARN/ERROR 级别后端运行日志 |
| `qpo-error.log` | ERROR 级别错误日志和异常堆栈 |
| `archive/*.gz` | 按日期和大小滚动后的历史日志 |

日志格式包含 `requestId`，例如：

```text
2026-07-17 20:11:54.085 INFO [http-nio-8080-exec-2] [requestId=stage-6-1-check] ...
```

如果页面操作日志中有 requestId，可以用它反查后端文件日志：

```powershell
docker exec quote-backend sh -lc "grep -R 'requestId值' /data/backups/logs/backend"
```

如果先在 `qpo-error.log` 中发现 requestId，也可以复制该值到 **系统 > 操作日志** 的 `Request ID` 筛选框，反查对应业务审计记录。

## 4. Docker 容器日志

容器控制台日志仍然可用：

```powershell
docker logs quote-backend
docker logs quote-postgres
docker logs quote-frontend
```

查看最近日志：

```powershell
docker logs --tail 200 quote-backend
docker logs --tail 200 quote-postgres
```

实时跟随：

```powershell
docker logs -f quote-backend
docker logs -f quote-postgres
```

Docker `json-file` 日志轮转由 `erp.env` 控制：

```env
LOG_MAX_SIZE=20m
LOG_MAX_FILE=5
```

总保留空间约为：

```text
LOG_MAX_SIZE * LOG_MAX_FILE
```

## 5. Postgres 慢 SQL 与锁等待日志

Postgres 日志输出到 Docker 容器日志，通过以下命令查看：

```powershell
docker logs quote-postgres
```

筛选慢 SQL：

```powershell
docker logs quote-postgres 2>&1 | Select-String "duration:"
```

筛选锁等待：

```powershell
docker logs quote-postgres 2>&1 | Select-String "lock"
```

当前 Compose 配置只打开轻量排查项：

- `log_min_duration_statement=${POSTGRES_LOG_MIN_DURATION_STATEMENT_MS:-500}`：记录超过阈值的 SQL。
- `log_statement=none`：不记录每条 SQL，避免日志爆炸。
- `log_lock_waits=on`：记录锁等待。
- `deadlock_timeout=${POSTGRES_DEADLOCK_TIMEOUT:-1s}`：锁等待超过阈值后记录。
- `log_timezone=Asia/Shanghai`：数据库日志使用北京时间。

本地 `erp.env` 建议值：

```env
POSTGRES_LOG_MIN_DURATION_STATEMENT_MS=500
POSTGRES_DEADLOCK_TIMEOUT=1s
```

如果慢 SQL 日志过多，可以把阈值调高：

```env
POSTGRES_LOG_MIN_DURATION_STATEMENT_MS=1000
```

## 6. 常用验收命令

重建 Postgres 和 backend：

```powershell
docker compose --env-file erp.env up -d --build postgres backend
```

确认 Postgres 正常启动：

```powershell
docker logs --tail 80 quote-postgres
```

人工触发慢 SQL：

```powershell
docker exec quote-postgres psql -U postgres -d postgres -c "SELECT pg_sleep(0.7);"
```

确认出现 `duration:`：

```powershell
docker logs quote-postgres 2>&1 | Select-String "duration:"
```

确认未打开全量 SQL：

```powershell
docker exec quote-postgres psql -U postgres -d postgres -c "SHOW log_statement;"
```

预期结果：

```text
none
```

## 7. 保留策略汇总

| 日志类型 | 保留策略 |
| --- | --- |
| Docker json-file | `LOG_MAX_SIZE * LOG_MAX_FILE` |
| 后端文件日志 | `LOG_FILE_MAX_HISTORY`，默认 30 天 |
| 操作日志 | 系统页面保留策略配置，默认 180 天在线保留 |
| Postgres 慢 SQL / 锁等待日志 | 跟随 `quote-postgres` Docker json-file 轮转 |

## 8. 注意事项

- 不要打开 `log_statement=all`，否则会记录大量 SQL，并可能泄露业务数据。
- 不要把 JWT、Authorization header、密码、上传文件内容写入任何日志。
- 后端运行日志与操作日志可以通过 requestId 关联，但职责保持分离。
- 当前日志文件存放在 Docker named volume 中，不改成 Windows 可见目录挂载。
## 9. 主流程文件日志事件命名

主流程文件日志统一采用“英文事件名 + key=value”的稳定格式，便于 `grep` 和跨日志关联。新增业务日志时优先沿用下列命名风格：

| 场景 | 事件名前缀示例 | 关键字段 |
| --- | --- | --- |
| RFQ 导入 | `RFQ import started/completed/failed` | `rfqId`、`rfqNo`、`itemCount`、`durationMs` |
| 核价与刷新 | `Item quote saved`、`Order quote refresh completed` | `rfqId`、`itemId`、`partNo`、`skippedCount` |
| 生成核价单 | `Pricing sheet export started/completed/rejected/failed` | `rfqId`、`status`、`itemCount`、`durationMs` |
| 后台任务 | `System task submitted/started/completed/failed` | `taskId`、`taskType`、`durationMs`、`filePath` |
| MES物料号同步 | `MES material sync submitted/started/completed/rejected/failed` | `ticketId`、`taskId`、`rfqId`、`partNo`、`materialNo`、`durationMs` |
| WMS锁库分配 | `WMS allocation submitted/started/completed/rejected/failed` | `ticketId`、`taskId`、`rfqId`、`materialNo`、`demandQty`、`allocationCount`、`durationMs` |
| 报价保存 | `Quote sheet save started/completed/rejected/failed` | `rfqId`、`fromStatus`、`toStatus`、`itemCount`、`durationMs` |
| 提单与交期 | `Delivery ticket generation started/completed/failed`、`Quote lead time set` | `rfqId`、`selectedItemCount`、`ticketCount`、`dynamicProcessSheetCount`、`remainingItemCount`、`toOrderStatus` |
| 提单表据导出 | `Delivery document export started/completed/rejected/failed` | `rfqId`、`exportType`、`rowCount`、`durationMs` |
| 系统治理 | `System governance action completed`、`Department created/updated/deleted` | `action`、`deptId`、`deptCode`、`deptName` |
| 系统治理 | `Post created/updated/deleted`、`User organization updated` | `postId`、`postCode`、`targetUserId`、`deptId`、`postId` |
| 用户自助资料 | `User profile updated/rejected` | `userId`、`systemUserId`、`reason`、`durationMs` |
| 日志清理 | `Audit log cleanup started/completed/failed` | `manual`、`retentionDays`、`deletedCount`、`archiveFile` |

MES/WMS 外部系统任务必须保留完整文件日志事件名，便于运维直接复制 grep：

| 任务 | 文件日志事件名 | Level |
| --- | --- | --- |
| MES物料号同步 | `MES material sync submitted` | INFO |
| MES物料号同步 | `MES material sync started` | INFO |
| MES物料号同步 | `MES material sync completed` | INFO |
| MES物料号同步 | `MES material sync rejected` | WARN |
| MES物料号同步 | `MES material sync failed` | ERROR |
| WMS锁库分配 | `WMS allocation submitted` | INFO |
| WMS锁库分配 | `WMS allocation started` | INFO |
| WMS锁库分配 | `WMS allocation completed` | INFO |
| WMS锁库分配 | `WMS allocation rejected` | WARN |
| WMS锁库分配 | `WMS allocation failed` | ERROR |

新增日志时注意：

- 正常列表查询、字典查询、健康检查不加业务 INFO。
- 批量循环内不打 INFO，只在流程结束打汇总。
- 业务可恢复问题用 WARN，例如缺图、跳过无效文件、模板校验失败。
- 未预期失败用 ERROR，并把异常对象作为最后一个参数传给 logger。
- 严禁记录密码、JWT、Authorization header、Cookie、上传文件内容和完整 Excel/JSON 明细。

## 10. 常用 grep 示例

按 RFQ 导入排查：

```powershell
docker exec quote-backend sh -lc "grep -R 'RFQ import' /data/backups/logs/backend"
docker exec quote-backend sh -lc "grep -R 'rfqId=123' /data/backups/logs/backend"
```

按后台任务排查：

```powershell
docker exec quote-backend sh -lc "grep -R 'taskId=45' /data/backups/logs/backend"
docker exec quote-backend sh -lc "grep -R 'System task failed' /data/backups/logs/backend/qpo-error.log"
```

按 MES 物料号同步排查：

```powershell
docker exec quote-backend sh -lc "grep -R 'MES material sync' /data/backups/logs/backend"
docker exec quote-backend sh -lc "grep -R 'taskId=45' /data/backups/logs/backend"
docker exec quote-backend sh -lc "grep -R 'taskType=MES_MATERIAL_SYNC' /data/backups/logs/backend"
docker exec quote-backend sh -lc "grep -R 'requestId=页面上的requestId' /data/backups/logs/backend"
docker exec quote-backend sh -lc "grep -R 'MES material sync failed' /data/backups/logs/backend/qpo-error.log"
```

业务审计记录在 **系统 > 操作日志** 中按动作 `DELIVERY_MES_MATERIAL_SYNC_SUBMIT`、`DELIVERY_MES_MATERIAL_SYNC_SUCCESS`、`DELIVERY_MES_MATERIAL_SYNC_FAILED` 查询。页面提示的 taskId 可直接查任务生命周期；操作日志详情中的 requestId 可反查提交接口；失败堆栈进入 `qpo-error.log`，必须包含 `taskId`。

按 WMS 锁库分配排查：

## 11. 销售订单 U9 同步审计口径

- 旧 Excel 直连 U9 导入兼容动作保留为 `SALES_ORDER_IMPORT_U9`，模块为 `MARKET`，`targetType` 为 `sales_order_import_batch`。
- 阶段 5 历史直连 U9 过渡口径只同步 U9，不创建 QPO 订单、不进入议价提单，摘要保留 `batchNo`、`successOrderCount`、`failedOrderCount`，不记录完整 Excel 内容、U9 token、clientsecret 或完整 U9 请求体。
- 阶段 7 独立销售订单 U9 同步动作编码为 `SALES_ORDER_U9_SYNC`，模块为 `MARKET`，`targetType` 为 `sales_order_header`。
- 阶段 7 同步摘要只记录 `totalOrderCount`、`successOrderCount`、`failedOrderCount`、`salesOrderNoSample`、`u9OrderCodeSample`、`durationMs` 等排查字段。
- 不记录完整 Excel 内容、U9 token、clientsecret、完整 U9 请求体、完整 U9 响应大对象、Authorization header 或 Cookie。
- 独立销售订单同步从 `sales_order_header` / `sales_order_item` / `order_delivery_ticket` 组装请求，缺少提单物料号时返回明确失败摘要，不影响已生成 QPO 提单记录。
- 运维排查时先在 **系统 > 操作日志** 按 `SALES_ORDER_U9_SYNC`、销售订单号或 requestId 查询，再到后端文件日志按 `Sales order U9 sync` 和 `orderCount` / `durationMs` 关联。

## 12. requestId + taskId + audit_log 关联排查方法

推荐从用户现象出发按以下顺序排查：

1. 在 **系统 > 操作日志** 按操作人、模块、动作或 `Request ID` 找到业务动作。
2. 复制操作日志中的 requestId，到后端文件日志里查同一次请求的主流程事件。
3. 如果该动作提交了后台任务，先在操作日志详情或业务页面拿到 taskId，再查 `System task submitted/started/completed/failed`。
4. 如果是 MES/WMS 任务，同时记录 `ticketId`：用 `ticketId` 定位同一条已提零件，用 `taskId` 定位本次异步任务，用 `requestId` 定位触发任务的页面请求。
5. 如果 `qpo-error.log` 里先出现异常，复制其中的 requestId 反查操作日志；如果异常里有 taskId，再继续查任务生命周期。
6. 如果日志显示数据库耗时或锁等待，再去 `docker logs quote-postgres` 查 `duration:` 或 `lock`。

常见组合：

```text
操作日志 audit_log.request_id
  -> qpo-backend.log requestId=...
  -> qpo-backend.log taskId=...
  -> qpo-backend.log ticketId=...
  -> qpo-error.log taskId=... / requestId=...
  -> docker logs quote-postgres duration: / lock
```

## 13. 销售订单 QPO 导入审计口径

- 销售订单导入独立主表写入操作日志，动作编码为 `SALES_ORDER_IMPORT_QPO`，模块为 `MARKET`，`targetType` 为 `sales_order_import_batch`。
- 操作日志摘要只记录 `batchNo`、`sourceFileName`、`customerCode`、`customerName`、`documentTypeCode`、`totalOrderCount`、`successOrderCount`、`failedOrderCount`、`salesOrderNos`、`matchedItemCount`、`unmatchedItemCount`、`durationMs` 等排查字段。
- 不记录完整 Excel 内容、完整行明细、图纸文件内容、token、Authorization header、Cookie 或完整请求体。
- 第一阶段销售订单导入只落地独立主表骨架并隔离旧 RFQ 写入方向；实际独立表写入接入后也不调用 U9，后续 U9 同步排查仍按 `SALES_ORDER_IMPORT_U9` 和 U9 文件日志口径处理。
- 文件日志事件名使用 `Sales order QPO import started/parsed/enriched/completed/rejected/failed`，只记录批次级摘要，保持低噪声。
