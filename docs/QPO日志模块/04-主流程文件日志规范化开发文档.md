# QPO 6.4 主流程文件日志规范化开发文档

## 1. 背景

QPO 已经完成三类日志基础能力：

- **操作日志 / 审计日志**：记录“谁在什么时候做了什么业务动作”，通过系统页面查看。
- **后端文件日志**：记录 Java 后端运行过程、请求链路、异常堆栈，写入 `/data/backups/logs/backend/`。
- **Postgres 慢 SQL / 锁等待日志**：通过 `docker logs quote-postgres` 查看数据库运行问题。

当前 6.1 到 6.3 已经把文件日志和慢 SQL 日志基础设施搭好，但主流程文件日志仍不够规范：

- `RequestTraceFilter` 已能记录每个 HTTP 请求和 `requestId`。
- `GlobalExceptionHandler` 已能记录未预期异常。
- `audit_log` 已覆盖大量业务审计动作。
- 但业务主流程中正式 `Logger` 使用较少，部分关键流程仍使用 `System.out.println(...)`。
- 异步任务、导入、核价、导出、日志归档等流程缺少统一的开始、成功、失败摘要日志。

因此阶段 6.4 的目标不是“到处加日志”，而是**在关键业务边界补足少量、高价值、可关联、可排查的文件日志**。

## 2. 目标

### 2.1 本阶段目标

- 建立 QPO 后端统一文件日志标准。
- 替换主流程中的 `System.out.println(...)`。
- 给所有核心模块补齐关键节点运行日志。
- 保持日志量可控，不在循环、明细、单元格、每条 SQL、每个零件上无脑打 INFO。
- 让 `qpo-backend.log` 能回答：
  - 某个 RFQ 导入是否开始、导入了多少零件、缺图多少、耗时多少。
  - 某个核价/刷新/导出任务是否开始、结束、失败。
  - 某个后台任务失败原因是什么，taskId 是多少。
  - 某个 requestId 在后端经历了哪些关键业务节点。
- 让 `qpo-error.log` 能回答：
  - 哪个主流程失败。
  - 失败对象 ID 是什么。
  - 异常堆栈是什么。
  - 是否能通过 requestId 反查操作日志。

### 2.2 不做范围

- 不新增前端日志上报。
- 不接入 ELK、Loki、Sentry、Prometheus、Grafana。
- 不把所有运行日志写入 `audit_log`。
- 不把所有查询接口都加业务 INFO 日志。
- 不记录完整请求体、完整 Excel 内容、完整 JSON、上传文件二进制内容。
- 不记录明文密码、JWT、Authorization header、Cookie、敏感数据库连接信息。
- 不开启数据库全量 SQL 日志。

## 3. 日志职责边界

| 类型 | 位置 | 解决的问题 | 不解决的问题 |
| --- | --- | --- | --- |
| 操作日志 | `audit_log` / 系统页面 | 谁做了什么业务动作 | Java 堆栈、接口耗时、线程异常 |
| 后端运行日志 | `/data/backups/logs/backend/qpo-backend.log` | 系统运行主流程、请求链路、业务摘要 | 长期业务审计查询 |
| 后端错误日志 | `/data/backups/logs/backend/qpo-error.log` | ERROR 级别异常堆栈 | 正常业务流水 |
| Postgres 慢 SQL | `docker logs quote-postgres` | 慢 SQL、锁等待、死锁 | Java 业务上下文 |

原则：

- 用户可见、需要审计追责的动作写 `audit_log`。
- 系统运行过程、排错定位、失败堆栈写文件日志。
- 同一动作可以同时有操作日志和文件日志，但内容不同：
  - 操作日志记录业务主体、动作、前后数据摘要。
  - 文件日志记录开始/结束/耗时/异常/技术上下文。

## 4. 总体日志标准

### 4.1 Logger 使用标准

每个需要业务运行日志的类统一使用 SLF4J：

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

private static final Logger log = LoggerFactory.getLogger(CurrentClass.class);
```

禁止在正式主流程中继续使用：

```java
System.out.println(...);
e.printStackTrace();
```

### 4.2 日志级别标准

| Level | 使用场景 | 示例 |
| --- | --- | --- |
| `INFO` | 主流程开始、成功、提交后台任务、导入/导出/核价完成摘要 | `RFQ import completed rfqId=174 itemCount=30 matchedDrawingCount=28 durationMs=1200` |
| `WARN` | 可恢复异常、业务不完整但流程可继续、模板校验失败、缺图、跳过无效文件 | `RFQ import completed with missing drawings rfqId=174 missingDrawingCount=2` |
| `ERROR` | 未预期异常、后台任务失败、文件写入失败、导出失败、数据库异常 | `System task failed taskId=15 taskType=EXPORT_QUOTE` |
| `DEBUG` | 默认不启用，仅用于局部开发排查 | 单元格解析细节、单个零件计算明细 |

不建议：

- 不要把正常查询接口全部打 INFO。
- 不要在每个循环项中打 INFO。
- 不要把业务校验失败都打 ERROR；用户可修正的输入错误通常是 WARN 或只由全局异常处理。

### 4.3 日志消息格式标准

采用“英文事件名 + key=value”的稳定格式，方便 grep：

```text
RFQ import started customerName={} rfqNo={} drawingFileCount={}
RFQ import completed rfqId={} rfqNo={} itemCount={} matchedDrawingCount={} missingDrawingCount={} unmatchedDrawingCount={} durationMs={}
System task failed taskId={} taskType={} durationMs={}
```

规则：

- 事件名稳定，不随文案变化。
- 关键字段使用 `key=value`。
- ID 字段优先：`rfqId`、`itemId`、`taskId`、`userId`、`templateFileName`。
- 数量字段用 `Count` 结尾。
- 耗时字段统一 `durationMs`。
- 不在日志 message 中拼接大对象；需要异常时使用 logger 的异常参数。

### 4.4 必带字段建议

| 场景 | 建议字段 |
| --- | --- |
| HTTP 请求 | `requestId`、method、path、status、durationMs，由 `RequestTraceFilter` 统一记录 |
| RFQ / 订单流程 | `rfqId`、`rfqNo`、`customerName`、`status` |
| 零件流程 | `rfqId`、`itemId`、`partNo`，批量场景只记录数量 |
| 分批提单 | `rfqId`、`selectedItemCount`、`ticketCount`、`processSheetCount`、`remainingItemCount`、`toOrderStatus` |
| 后台任务 | `taskId`、`taskType`、`status`、`durationMs` |
| 文件流程 | `fileName`、`fileSize`、`targetPath` 或 `outputFile` |
| 导入解析 | `itemCount`、`matchedDrawingCount`、`missingDrawingCount`、`unmatchedDrawingCount` |
| 导出 | `exportType`、`outputFile`、`durationMs` |

### 4.5 敏感信息禁止清单

任何日志都不得记录：

- 明文密码。
- JWT / token。
- Authorization header。
- Cookie。
- 数据库密码。
- 上传文件内容。
- 完整 Excel 行数据。
- 完整报价单 JSON / 大型 before-after JSON。
- 客户图纸文件二进制内容。

允许记录：

- 文件名。
- 文件大小。
- RFQ ID。
- 订单号。
- 客户名称。
- 数量统计。
- 状态。
- 业务错误摘要。

### 4.6 性能与日志量标准

- 每个主流程最多记录：
  - 1 条 started。
  - 1 条 completed。
  - 0 到少量 WARN 摘要。
  - 失败时 1 条 ERROR。
- 批量循环内不打 INFO。
- 大量明细需要排查时使用 DEBUG，默认生产不打开。
- 不做字符串大拼接；使用参数化日志：

```java
log.info("RFQ import completed rfqId={} itemCount={}", rfqId, itemCount);
```

不要写：

```java
log.info("RFQ import completed rfqId=" + rfqId + " itemCount=" + itemCount);
```

## 5. 当前问题清单

### 5.1 需要替换的非标准日志

当前存在 `System.out.println(...)` 的主要位置：

- `quote-system/src/main/java/com/machining/quote/controller/MarketController.java`
  - RFQ 导入开始。
  - Excel 解析完成。
  - 图纸识别。
  - 主单生成。
  - 零件图纸绑定。
  - 导入结束。
- `quote-system/src/main/java/com/machining/quote/service/EngineerService.java`
  - 工序字典未找到。
  - 工序单价匹配。
  - 零件核价完成。
  - 组合件核价完成。

处理方式：

- 将主流程级别输出改为 `log.info / log.warn / log.error`。
- 单个零件或单道工序的高频明细改为 `log.debug`，默认不开启。
- 缺图、工序未找到等可恢复问题用 `log.warn`。

## 6. 模块覆盖矩阵

### 6.1 认证模块

涉及文件：

- `quote-system/src/main/java/com/machining/quote/service/AuthService.java`
- `quote-system/src/main/java/com/machining/quote/controller/AuthController.java`

现状：

- 操作日志已覆盖登录成功、失败、账号锁定、登出。
- 文件日志没有专门记录认证主流程。

建议：

- 登录成功：`INFO`，记录 `username`、`userId`、`role`。
- 登录失败：`WARN`，记录 `username`、失败原因枚举，不记录密码。
- 账号锁定：`WARN`，记录 `username`、`failedLoginAttempts`、`lockedUntil`。
- 登出：一般不需要文件 INFO；操作日志足够。如需排查 token 解析问题，可在异常处 WARN。

示例：

```java
log.info("Auth login succeeded username={} userId={} role={}", user.getUsername(), user.getId(), user.getRole());
log.warn("Auth login failed username={} reason={}", safeUsername, "bad_credentials");
log.warn("Auth account locked username={} failedLoginAttempts={} lockedUntil={}", user.getUsername(), user.getFailedLoginAttempts(), user.getLockedUntil());
```

涉及文件：

- `quote-system/src/main/java/com/machining/quote/service/UserAdminService.java`

现状：

- 操作日志已覆盖用户新增、编辑、改密、删除。

建议：

- 文件日志只记录失败和高风险动作摘要。
- 创建、删除用户可打 `INFO`，但不记录密码。
- 普通列表查询不打业务日志。

示例：

### 6.4 市场新单导入模块

涉及文件：

- `quote-system/src/main/java/com/machining/quote/controller/MarketController.java`
- `quote-system/src/main/java/com/machining/quote/service/RfqNumberService.java`
- `quote-system/src/main/java/com/machining/quote/service/OrderFilePathService.java`

现状：

- `RFQ_IMPORT` 操作日志已记录。
- `MarketController` 中存在多处 `System.out.println(...)`。

建议：

- 将 RFQ 导入作为重点主流程补齐文件日志。
- 开始导入时打 INFO。
- Excel 解析完成打 INFO。
- 图纸匹配完成打 INFO 或 WARN。
- 导入成功打 INFO。
- 导入失败打 ERROR 并带异常堆栈。
- 单个文件绑定、单个零件缺图不打 INFO；缺图用汇总 WARN。

必备字段：

- `customerName`
- `rfqNo`
- `rfqId`
- `excelFileName`
- `drawingFileCount`
- `itemCount`
- `matchedDrawingCount`
- `missingDrawingCount`
- `unmatchedDrawingCount`
- `durationMs`

示例：

```java
long startedAt = System.currentTimeMillis();
log.info("RFQ import started customerName={} rfqNo={} excelFileName={} drawingFileCount={}",
        customerName, autoRfqNo, excelFile.getOriginalFilename(), drawings == null ? 0 : drawings.size());

log.info("RFQ import parsed excel rfqNo={} itemCount={}", autoRfqNo, excelDataList.size());

if (drawingReport.getMissingItemCount() > 0 || drawingReport.getUnmatchedDrawingCount() > 0) {
    log.warn("RFQ import completed with drawing warnings rfqId={} rfqNo={} missingDrawingCount={} unmatchedDrawingCount={}",
            generatedRfqId, autoRfqNo, drawingReport.getMissingItemCount(), drawingReport.getUnmatchedDrawingCount());
}

log.info("RFQ import completed rfqId={} rfqNo={} customerName={} itemCount={} matchedDrawingCount={} durationMs={}",
        generatedRfqId, autoRfqNo, customerName, excelDataList.size(), drawingReport.getMatchedItemCount(),
        System.currentTimeMillis() - startedAt);
```

### 6.8 议价提单 / 内部目标交期模块

涉及文件：

- `quote-system/src/main/java/com/machining/quote/service/InternalTargetLeadTimeService.java`
- `quote-system/src/main/java/com/machining/quote/service/DeliveryService.java`
- `quote-system/src/main/java/com/machining/quote/controller/InternalTargetLeadTimeController.java`
- `quote-system/src/main/java/com/machining/quote/controller/MarketController.java`

现状：

- 操作日志覆盖内部目标交期调整和提单生成。
- 提单行、工艺表行删除以及订单重置提单/工艺能力已经废弃；历史审计动作只用于旧数据追溯。
- `order_delivery_ticket` 是不可逆发布记录，也是 APS 同步工艺快照的单一来源。
- `order_process_sheet` 是 QPO 内部工艺表展示/导出结果，不作为 APS 同步主来源。

建议：

- 内部目标交期批量调整打 INFO 摘要。
- 生成提单开始/结束打 INFO，包含 `rfqId`、选择零件数、生成提单行数、工艺表行数、剩余未提完零件数和订单目标状态。
- 提单数量超过剩余可提数量、订单状态不允许提单、零件无剩余数量等用户可修正问题打 WARN。
- 提单行 / 工艺表行不提供删除入口；不再新增删除或重置类文件日志事件。
- 对每个零件生成明细不打 INFO。
- 分批提单状态回算只记录汇总：部分提单后零件仍为 `已报价`，全部提完后零件为 `已提单`，订单最终状态仍为 `已生成提单`。

示例：

```java
log.info("Delivery ticket generation started rfqId={} selectedItemCount={}", req.getRfqId(), req.getItemIds().size());
log.info("Delivery ticket generation completed rfqId={} ticketCount={} processSheetCount={} remainingItemCount={} toOrderStatus={} durationMs={}",
        rfqId, ticketCount, processSheetCount, remainingItemCount, toOrderStatus, durationMs);
log.warn("Delivery ticket generation rejected rfqId={} itemId={} requestedQty={} remainingQty={} reason={}",
        rfqId, itemId, requestedQty, remainingQty, "exceeds_remaining_qty");
```

### 6.10 导出与后台任务模块

涉及文件：

- `quote-system/src/main/java/com/machining/quote/service/SystemTaskService.java`
- `quote-system/src/main/java/com/machining/quote/service/ExcelExportService.java`
- `quote-system/src/main/java/com/machining/quote/service/QuoteTemplateExportService.java`
- `quote-system/src/main/java/com/machining/quote/controller/SystemTaskController.java`

现状：

- 任务提交有操作日志。
- 任务状态会写数据库。
- 文件日志缺少 task lifecycle。

建议：

- 创建任务打 INFO：`taskId`、`taskType`、`rfqId`、`exportType`。
- 任务开始打 INFO。
- 任务成功打 INFO：`taskId`、`outputFile`、`durationMs`。
- 任务失败打 ERROR：带异常堆栈。
- 下载任务文件可不打 INFO，失败由异常处理。

示例：

```java
log.info("System task submitted taskId={} taskType={} request={}", task.getId(), task.getTaskType(), safeSummary(request));
log.info("System task started taskId={} taskType={}", taskId, task.getTaskType());
log.info("System task completed taskId={} taskType={} durationMs={} filePath={}", taskId, taskType, durationMs, filePath);
log.error("System task failed taskId={} taskType={} durationMs={}", taskId, taskType, durationMs, error);
```

注意：

- 异步任务不一定天然继承 HTTP request MDC。若要通过 requestId 串联任务，需要在提交任务时捕获 `RequestTraceContext.get()` 或 requestId，并写入任务 requestJson 或任务日志上下文。
- 第一版可以先记录 taskId，再通过操作日志中的 taskId 和 requestId 关联。

### 6.11 操作日志与归档模块

涉及文件：

- `quote-system/src/main/java/com/machining/quote/service/AuditLogRetentionService.java`
- `quote-system/src/main/java/com/machining/quote/service/AuditLogQueryService.java`
- `quote-system/src/main/java/com/machining/quote/controller/AuditLogController.java`

现状：

- 操作日志保留策略操作会写 `audit_log`。
- 自动清理/归档没有充分文件运行日志。

建议：

- 手动/自动清理开始打 INFO。
- 未启用或未到执行时间不打 INFO，避免每分钟刷屏。
- 清理成功打 INFO。
- 无到期日志可不打或 DEBUG。
- 归档文件写入失败打 ERROR。
- 清理失败打 ERROR。

示例：

```java
log.info("Audit log cleanup started manual={} retentionDays={} archiveBeforeCleanup={}", manual, config.getRetentionDays(), config.getArchiveBeforeCleanup());
log.info("Audit log cleanup completed manual={} deletedCount={} archiveFile={} durationMs={}", manual, deletedCount, archiveFile, durationMs);
log.error("Audit log cleanup failed manual={} retentionDays={}", manual, config.getRetentionDays(), e);
```

log.warn("Upload file access rejected path={} reason={}", requestPath, "outside_upload_root");

### 6.13 APS 数据源接口模块

- `quote-system/src/main/java/com/machining/quote/controller/ApsSourceController.java`
- `quote-system/src/main/java/com/machining/quote/service/ApsSourceService.java`

建议：

- 普通 APS 查询不打业务 INFO。
- 大批量同步或被 APS 拉取交付项时，如果后续排查需要，可打 DEBUG。

- `quote-system/src/main/java/com/machining/quote/controller/HealthController.java`

### 6.15 支撑服务与启动初始化模块

涉及文件：

- `quote-system/src/main/java/com/machining/quote/service/AuditService.java`
- `quote-system/src/main/java/com/machining/quote/service/JwtService.java`
- `quote-system/src/main/java/com/machining/quote/service/LeadTimeService.java`
- `quote-system/src/main/java/com/machining/quote/service/RfqNumberService.java`
- `quote-system/src/main/java/com/machining/quote/service/OrderFilePathService.java`
- `quote-system/src/main/java/com/machining/quote/service/StorageInitializer.java`

定位：

- 这些类不是独立业务页面模块，但会支撑多个主流程。
- 默认不额外打大量 INFO，避免辅助方法被频繁调用时刷屏。
- 只在“跨模块排查有价值”的边界记录 WARN / ERROR / 少量 INFO。

建议：

- `AuditService`：操作日志写入失败必须 `ERROR`，但不要把完整 before/after JSON 写入文件日志；文件日志只记录 action、module、objectType、objectId、requestId 摘要。
- `JwtService`：token 解析失败可以 `WARN`，但严禁输出 token 原文、Authorization header 或 Cookie。
- `LeadTimeService`：日期解析失败如果是用户导入数据问题，用 `WARN` 摘要记录原始单元格展示值和行号；不要逐行 INFO。
- `RfqNumberService`：RFQ 编号生成异常打 `ERROR`；正常生成编号不需要单独 INFO，由 RFQ 导入主流程日志覆盖。
- `OrderFilePathService`：目录创建失败、路径越界、文件移动失败打 `ERROR` 或 `WARN`；正常路径拼接不打日志。
- `StorageInitializer`：应用启动时目录创建成功可以打一条 INFO 摘要；目录创建失败必须 `ERROR` 并带异常堆栈。

示例：

```java
log.error("Audit log record failed action={} module={} objectType={} objectId={}",
        action, module, objectType, objectId, e);
log.warn("JWT parse failed reason={}", "expired_or_invalid");
log.warn("Lead time parse failed rowIndex={} rawValue={}", rowIndex, rawValue);
log.info("Storage directories initialized uploadRoot={} backupRoot={}", uploadRoot, backupRoot);
```
