# QPO 6.4 主流程文件日志规范化开发文档

## 1. 背景

QPO 已经完成三类日志基础能力：

- **操作日志 / 审计日志**：记录“谁在什么时候做了什么业务动作”，通过系统页面查看。
- **后端文件日志**：记录 Java 后端运行过程、请求链路、异常堆栈，写入 `/data/backups/logs/backend/`。
- **Postgres 慢 SQL / 锁等待日志**：通过 `docker logs quote-postgres` 查看数据库运行问题。

当前 6.1 到 6.3 已经把文件日志和慢 SQL 日志基础设施搭好，但主流程文件日志仍不够规范：

- `RequestTraceFilter` 已能记录每个 HTTP 请求和 `requestId`。
- `GlobalExceptionHandler` 已能记录未预期异常。
- `audit_log` 已覆盖大量业务审计动作。
- 但业务主流程中正式 `Logger` 使用较少，部分关键流程仍使用 `System.out.println(...)`。
- 异步任务、导入、核价、导出、日志归档等流程缺少统一的开始、成功、失败摘要日志。

因此阶段 6.4 的目标不是“到处加日志”，而是**在关键业务边界补足少量、高价值、可关联、可排查的文件日志**。

## 2. 目标

### 2.1 本阶段目标

- 建立 QPO 后端统一文件日志标准。
- 替换主流程中的 `System.out.println(...)`。
- 给所有核心模块补齐关键节点运行日志。
- 保持日志量可控，不在循环、明细、单元格、每条 SQL、每个零件上无脑打 INFO。
- 让 `qpo-backend.log` 能回答：
  - 某个 RFQ 导入是否开始、导入了多少零件、缺图多少、耗时多少。
  - 某个核价/刷新/导出任务是否开始、结束、失败。
  - 某个后台任务失败原因是什么，taskId 是多少。
  - 某个 requestId 在后端经历了哪些关键业务节点。
- 让 `qpo-error.log` 能回答：
  - 哪个主流程失败。
  - 失败对象 ID 是什么。
  - 异常堆栈是什么。
  - 是否能通过 requestId 反查操作日志。

### 2.2 不做范围

- 不新增前端日志上报。
- 不接入 ELK、Loki、Sentry、Prometheus、Grafana。
- 不把所有运行日志写入 `audit_log`。
- 不把所有查询接口都加业务 INFO 日志。
- 不记录完整请求体、完整 Excel 内容、完整 JSON、上传文件二进制内容。
- 不记录明文密码、JWT、Authorization header、Cookie、敏感数据库连接信息。
- 不开启数据库全量 SQL 日志。

## 3. 日志职责边界

| 类型 | 位置 | 解决的问题 | 不解决的问题 |
| --- | --- | --- | --- |
| 操作日志 | `audit_log` / 系统页面 | 谁做了什么业务动作 | Java 堆栈、接口耗时、线程异常 |
| 后端运行日志 | `/data/backups/logs/backend/qpo-backend.log` | 系统运行主流程、请求链路、业务摘要 | 长期业务审计查询 |
| 后端错误日志 | `/data/backups/logs/backend/qpo-error.log` | ERROR 级别异常堆栈 | 正常业务流水 |
| Postgres 慢 SQL | `docker logs quote-postgres` | 慢 SQL、锁等待、死锁 | Java 业务上下文 |

原则：

- 用户可见、需要审计追责的动作写 `audit_log`。
- 系统运行过程、排错定位、失败堆栈写文件日志。
- 同一动作可以同时有操作日志和文件日志，但内容不同：
  - 操作日志记录业务主体、动作、前后数据摘要。
  - 文件日志记录开始/结束/耗时/异常/技术上下文。

## 4. 总体日志标准

### 4.1 Logger 使用标准

每个需要业务运行日志的类统一使用 SLF4J：

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

private static final Logger log = LoggerFactory.getLogger(CurrentClass.class);
```

禁止在正式主流程中继续使用：

```java
System.out.println(...);
e.printStackTrace();
```

### 4.2 日志级别标准

| Level | 使用场景 | 示例 |
| --- | --- | --- |
| `INFO` | 主流程开始、成功、提交后台任务、导入/导出/核价完成摘要 | `RFQ import completed rfqId=174 itemCount=30 matchedDrawingCount=28 durationMs=1200` |
| `WARN` | 可恢复异常、业务不完整但流程可继续、模板校验失败、缺图、跳过无效文件 | `RFQ import completed with missing drawings rfqId=174 missingDrawingCount=2` |
| `ERROR` | 未预期异常、后台任务失败、文件写入失败、导出失败、数据库异常 | `System task failed taskId=15 taskType=EXPORT_QUOTE` |
| `DEBUG` | 默认不启用，仅用于局部开发排查 | 单元格解析细节、单个零件计算明细 |

不建议：

- 不要把正常查询接口全部打 INFO。
- 不要在每个循环项中打 INFO。
- 不要把业务校验失败都打 ERROR；用户可修正的输入错误通常是 WARN 或只由全局异常处理。

### 4.3 日志消息格式标准

采用“英文事件名 + key=value”的稳定格式，方便 grep：

```text
RFQ import started customerName={} rfqNo={} drawingFileCount={}
RFQ import completed rfqId={} rfqNo={} itemCount={} matchedDrawingCount={} missingDrawingCount={} unmatchedDrawingCount={} durationMs={}
System task failed taskId={} taskType={} durationMs={}
```

规则：

- 事件名稳定，不随文案变化。
- 关键字段使用 `key=value`。
- ID 字段优先：`rfqId`、`itemId`、`taskId`、`userId`、`templateFileName`。
- 数量字段用 `Count` 结尾。
- 耗时字段统一 `durationMs`。
- 不在日志 message 中拼接大对象；需要异常时使用 logger 的异常参数。

### 4.4 必带字段建议

| 场景 | 建议字段 |
| --- | --- |
| HTTP 请求 | `requestId`、method、path、status、durationMs，由 `RequestTraceFilter` 统一记录 |
| RFQ / 订单流程 | `rfqId`、`rfqNo`、`customerName`、`status` |
| 零件流程 | `rfqId`、`itemId`、`partNo`，批量场景只记录数量 |
| 分批提单 | `rfqId`、`selectedItemCount`、`ticketCount`、`dynamicProcessSheetCount`、`remainingItemCount`、`toOrderStatus` |
| 后台任务 | `taskId`、`taskType`、`status`、`durationMs` |
| 文件流程 | `fileName`、`fileSize`、`targetPath` 或 `outputFile` |
| 导入解析 | `itemCount`、`matchedDrawingCount`、`missingDrawingCount`、`unmatchedDrawingCount` |
| 导出 | `exportType`、`outputFile`、`durationMs` |

### 4.5 敏感信息禁止清单

任何日志都不得记录：

- 明文密码。
- JWT / token。
- Authorization header。
- Cookie。
- 数据库密码。
- 上传文件内容。
- 完整 Excel 行数据。
- 完整报价单 JSON / 大型 before-after JSON。
- 客户图纸文件二进制内容。

允许记录：

- 文件名。
- 文件大小。
- RFQ ID。
- 订单号。
- 客户名称。
- 数量统计。
- 状态。
- 业务错误摘要。

### 4.6 性能与日志量标准

- 每个主流程最多记录：
  - 1 条 started。
  - 1 条 completed。
  - 0 到少量 WARN 摘要。
  - 失败时 1 条 ERROR。
- 批量循环内不打 INFO。
- 大量明细需要排查时使用 DEBUG，默认生产不打开。
- 不做字符串大拼接；使用参数化日志：

```java
log.info("RFQ import completed rfqId={} itemCount={}", rfqId, itemCount);
```

不要写：

```java
log.info("RFQ import completed rfqId=" + rfqId + " itemCount=" + itemCount);
```

## 6. 模块覆盖矩阵

### 6.1 认证模块

涉及文件：

- `quote-backend/src/main/java/com/machining/quote/service/AuthService.java`
- `quote-backend/src/main/java/com/machining/quote/controller/AuthController.java`

现状：

- 操作日志已覆盖登录成功、失败、账号锁定、登出。
- 文件日志没有专门记录认证主流程。

建议：

- 登录成功：`INFO`，记录 `username`、`userId`、`role`。
- 登录失败：`WARN`，记录 `username`、失败原因枚举，不记录密码。
- 账号锁定：`WARN`，记录 `username`、`failedLoginAttempts`、`lockedUntil`。
- 登出：一般不需要文件 INFO；操作日志足够。如需排查 token 解析问题，可在异常处 WARN。

示例：

```java
log.info("Auth login succeeded username={} userId={} role={}", user.getUsername(), user.getId(), user.getRole());
log.warn("Auth login failed username={} reason={}", safeUsername, "bad_credentials");
log.warn("Auth account locked username={} failedLoginAttempts={} lockedUntil={}", user.getUsername(), user.getFailedLoginAttempts(), user.getLockedUntil());
```

### 6.2 用户与权限管理模块

涉及文件：

- `quote-backend/src/main/java/com/machining/quote/service/UserAdminService.java`
- `quote-backend/src/main/java/com/machining/quote/controller/AdminController.java`

现状：

- 操作日志已覆盖用户新增、编辑、改密、删除。

建议：

- 文件日志只记录失败和高风险动作摘要。
- 创建、删除用户可打 `INFO`，但不记录密码。
- 普通列表查询不打业务日志。

示例：

```java
log.info("User admin action completed action={} targetUserId={} targetUsername={}", "USER_CREATE", user.getId(), user.getUsername());
log.warn("User admin action rejected action={} reason={}", "USER_DELETE", "cannot_delete_self");
```

### 6.2.1 系统治理与组织档案模块

涉及文件：

- `quote-backend/src/main/java/com/machining/quote/service/SystemDeptService.java`
- `quote-backend/src/main/java/com/machining/quote/service/SystemPostService.java`
- `quote-backend/src/main/java/com/machining/quote/service/UserAdminService.java`

现状：

- 操作日志覆盖部门新增、修改、启停、删除，岗位新增、修改、启停、删除，以及用户组织属性变更。
- 部门和岗位是用户身份属性，不作为订单数据范围。

建议：

- 系统治理类写操作可以记录一条稳定 INFO 摘要，统一使用 `System governance action completed` 作为通用事件前缀。
- 部门新增、修改、删除使用 `Department created/updated/deleted`，记录 `deptId`、`deptCode`、`deptName`、`parentId`，不记录无关用户明细。
- 岗位新增、修改、删除使用 `Post created/updated/deleted`，记录 `postId`、`postCode`、`postName`。
- 用户组织资料调整使用 `User organization updated`，记录 `targetUserId`、`deptId`、`postId` 和操作动作摘要，不记录密码、token 或完整 before/after JSON。
- 删除部门时存在子部门或用户、删除岗位时存在用户、用户绑定不存在或禁用的部门/岗位时使用 WARN。
- 普通部门树、岗位列表、部门/岗位选项查询不打业务 INFO，避免后台管理页面刷新造成日志噪声。
- 未预期异常由全局异常处理进入 ERROR，并携带 requestId。

示例：

```java
log.info("System governance action completed action={} objectType={} objectId={}", action, objectType, objectId);
log.info("Department created/updated/deleted action={} deptId={} deptCode={} deptName={}", action, deptId, deptCode, deptName);
log.info("Post created/updated/deleted action={} postId={} postCode={} postName={}", action, postId, postCode, postName);
log.info("User organization updated targetUserId={} deptId={} postId={}", targetUserId, deptId, postId);
log.warn("System governance action rejected action={} reason={}", action, reason);
```

### 6.2.1.1 系统配置出站 / 入站接口

涉及文件：

- `quote-backend/src/main/java/com/machining/quote/service/SystemIntegrationConfigManageService.java`
- `quote-backend/src/main/java/com/machining/quote/service/SystemInboundCallbackConfigService.java`

建议：

- 出站接口配置记录 `Integration config created/updated/tested/activated/disabled`，字段包含 `systemCode`、`configId`、host、path、timeout、testStatus，不记录 token、clientSecret、Authorization header、完整请求体或完整响应体。
- 数据中心连接配置记录 `Data center config created/updated/token test completed/token test failed/activated/disabled`，字段包含 `configId`、baseUrl/tokenUrl host、clientId、timeout、testStatus 和脱敏失败摘要，不记录 `client_secret`、access token、Authorization header、完整 token 响应或完整请求体。
- 数据中心功能接口配置记录 `Data center endpoint updated/test completed/test failed`，字段包含 `endpointCode`、`targetSystemCode`、host、path、timeout、testStatus 和脱敏摘要；统一 client 调用只记录 `endpointCode`、`targetSystemCode`、host、path、HTTP status 或网络错误摘要，不记录 access token、Authorization header、完整业务请求体或完整业务响应体。
- 数据中心统一对接阶段 8 收口要求：统一 client 调用只记录 `endpointCode`、`targetSystemCode`、host、path、HTTP status 或网络错误摘要；不得记录 `client_secret`、access token、QPO 入站 token、Authorization header、完整 token 响应、完整业务请求体或完整业务响应体。
- 入站接口配置记录 `Inbound callback config updated`、`Inbound callback token rotated`、`Inbound callback config validated`，字段包含 `callbackCode`、`configId`、`enabled`、`tokenEnabled`、`tokenConfigured`、`configSource`、`callbackPath`、`validateStatus`。
- 生成或轮换 MES 回调 token 时，明文只返回前端一次；文件日志不得记录真实 token、token hash、Authorization header、完整 MES 回调 JSON 或完整请求体。
- 关闭 token 校验时可以记录 `MES material callback token verification disabled` WARN 风险提示，只包含 `callbackCode` 和配置来源。

### 6.2.2 用户自助资料模块

涉及文件：

- `quote-backend/src/main/java/com/machining/quote/service/UserAdminService.java`
- `quote-backend/src/main/java/com/machining/quote/controller/AuthController.java`

现状：

- 操作日志覆盖当前登录用户通过个人入口更新本人手机号、邮箱，动作编码为 `USER_PROFILE_UPDATE`。
- 个人入口不新增可分配权限点，不允许用户自助修改部门、岗位、角色、权限、数据范围、启用状态或强制改密状态。

建议：

- 成功更新联系方式记录一条低噪声 INFO 摘要，事件名使用 `User profile updated`，字段包含 `userId`、`systemUserId` 和 `durationMs`。
- 输入校验失败、强制改密期间拒绝、历史账号无法映射等可恢复拒绝使用 WARN，事件名使用 `User profile update rejected`，字段包含 `userId` 和安全的 `reason`。
- 未预期异常由全局异常处理或业务边界记录 ERROR，并带 requestId；不得把完整手机号、邮箱 before/after 写入文件日志。
- 操作日志可以记录 `{ phone, email }` 的 before/after 摘要；文件日志只保留 ID、结果和拒绝原因，严禁记录密码、token、Authorization header、Cookie。
- 普通 `GET /api/auth/me` 查询不额外打业务 INFO，避免每次刷新页面产生噪声。

示例：

```java
log.info("User profile updated userId={} systemUserId={} durationMs={}", userId, systemUserId, durationMs);
log.warn("User profile update rejected userId={} reason={}", userId, reason);
```

### 6.4 市场新单导入模块

涉及文件：

- `quote-backend/src/main/java/com/machining/quote/controller/MarketController.java`
- `quote-backend/src/main/java/com/machining/quote/service/RfqNumberService.java`
- `quote-backend/src/main/java/com/machining/quote/service/OrderFilePathService.java`

现状：

- `RFQ_IMPORT` 操作日志已记录。
- `MarketController` 中存在多处 `System.out.println(...)`。

建议：

- 将 RFQ 导入作为重点主流程补齐文件日志。
- 开始导入时打 INFO。
- Excel 解析完成打 INFO。
- 图纸匹配完成打 INFO 或 WARN。
- 导入成功打 INFO。
- 导入失败打 ERROR 并带异常堆栈。
- 单个文件绑定、单个零件缺图不打 INFO；缺图用汇总 WARN。

必备字段：

- `customerName`
- `rfqNo`
- `rfqId`
- `excelFileName`
- `drawingFileCount`
- `itemCount`
- `matchedDrawingCount`
- `missingDrawingCount`
- `unmatchedDrawingCount`
- `durationMs`

示例：

```java
long startedAt = System.currentTimeMillis();
log.info("RFQ import started customerName={} rfqNo={} excelFileName={} drawingFileCount={}",
        customerName, autoRfqNo, excelFile.getOriginalFilename(), drawings == null ? 0 : drawings.size());

log.info("RFQ import parsed excel rfqNo={} itemCount={}", autoRfqNo, excelDataList.size());

if (drawingReport.getMissingItemCount() > 0 || drawingReport.getUnmatchedDrawingCount() > 0) {
    log.warn("RFQ import completed with drawing warnings rfqId={} rfqNo={} missingDrawingCount={} unmatchedDrawingCount={}",
            generatedRfqId, autoRfqNo, drawingReport.getMissingItemCount(), drawingReport.getUnmatchedDrawingCount());
}

log.info("RFQ import completed rfqId={} rfqNo={} customerName={} itemCount={} matchedDrawingCount={} durationMs={}",
        generatedRfqId, autoRfqNo, customerName, excelDataList.size(), drawingReport.getMatchedItemCount(),
        System.currentTimeMillis() - startedAt);
```

### 6.5 询价订单模块

涉及文件：

- `quote-backend/src/main/java/com/machining/quote/service/OrderManagementService.java`
- `quote-backend/src/main/java/com/machining/quote/controller/OrderManagementController.java`

现状：

- 补传图纸、询价订单状态治理已有操作日志；彻底删除订单仅为旧兼容接口日志，新页面不触发。
- 询价订单状态管理已有操作日志和少量文件日志。
- 文件运行日志需要明确事件名和低噪声边界。

建议：

- 询价订单列表、客户列表、详情查询不打业务 INFO。
- 提单/工艺回退能力已废弃，不再新增重置类业务日志。
- 补传图纸开始/结束打 INFO，部分未匹配打 WARN。
- 旧兼容彻底删除接口如被调用仍按开始/结束打 INFO，删除文件失败打 ERROR；销售订单页面和询价订单新治理页面不再调用。

- `JwtService`：token 解析失败可以 `WARN`，但严禁输出 token 原文、Authorization header 或 Cookie。
- `LeadTimeService`：日期解析失败如果是用户导入数据问题，用 `WARN` 摘要记录原始单元格展示值和行号；不要逐行 INFO。
- `RfqNumberService`：RFQ 编号生成异常打 `ERROR`；正常生成编号不需要单独 INFO，由 RFQ 导入主流程日志覆盖。
- `OrderFilePathService`：目录创建失败、路径越界、文件移动失败打 `ERROR` 或 `WARN`；正常路径拼接不打日志。
- `StorageInitializer`：应用启动时目录创建成功可以打一条 INFO 摘要；目录创建失败必须 `ERROR` 并带异常堆栈。

示例：

```java
log.error("Audit log record failed action={} module={} objectType={} objectId={}",
        action, module, objectType, objectId, e);
log.warn("JWT parse failed reason={}", "expired_or_invalid");
log.warn("Lead time parse failed rowIndex={} rawValue={}", rowIndex, rawValue);
log.info("Storage directories initialized uploadRoot={} backupRoot={}", uploadRoot, backupRoot);
```

完成阶段 6.4 后，QPO 日志体系应达到以下状态：

- 管理员想看业务动作：进入系统页面的操作日志。
- 开发/运维想排查接口和异常：看 `qpo-backend.log` / `qpo-error.log`。
- 开发/运维想排查数据库慢：看 `docker logs quote-postgres`。
- 页面有 requestId：可以反查后端文件日志。
- 后台任务有 taskId：可以反查任务生命周期和失败堆栈。
- 日志量保持可控，不因零件明细、字典查询、健康检查造成刷屏。

### 9.2 销售订单 QPO 导入

销售订单导入独立主表属于市场新单导入下的主流程写操作。该阶段不调用 U9，不创建 `order_rfq` 或 `item_quote_version`，而是写入 `sales_order_header` / `sales_order_item` 并记录批次级摘要。

```text
Sales order QPO import started batchNo={} customerCode={} sourceFileName={}
Sales order QPO import parsed batchNo={} orderCount={} lineCount={}
Sales order QPO import enriched batchNo={} matchedItemCount={} unmatchedItemCount={}
Sales order QPO import completed batchNo={} successOrderCount={} failedOrderCount={} durationMs={}
Sales order QPO import rejected batchNo={} reason={}
Sales order QPO import failed batchNo={} durationMs={}
```

- 不记录完整 Excel 内容、完整行明细、图纸文件内容、token、Authorization header、Cookie 或完整请求体。
- 可恢复的模板校验、历史快照未匹配等问题使用 WARN；数据库写入失败等未预期问题使用 ERROR，并把异常对象作为 logger 最后一个参数。
- 普通客户列表、模板下载和页面查询不新增业务 INFO。

### 9.3 销售订单管理

销售订单管理模块承载销售订单废弃、恢复和整单图纸补传。该模块只写 `sales_order_header` / `sales_order_item`，不写 `order_rfq` 或 `item_quote_version`。

```text
Sales order status change started action={} salesOrderId={}
Sales order status change completed action={} salesOrderId={} salesOrderNo={} fromStatus={} toStatus={} updatedItemCount={} ticketCount={} durationMs={}
Sales order status change rejected action={} salesOrderId={} fromStatus={} ticketCount={} reason={}
Sales order drawing supplement completed salesOrderId={} uploadCount={} boundCount={} alreadyBoundCount={} unmatchedCount={} skippedCount={}
```

- `SALES_ORDER_DISCARD` / `SALES_ORDER_RESTORE` 写操作日志，`targetType = sales_order_header`。
- `SALES_ORDER_DRAWING_SUPPLEMENT` 写操作日志，`targetType = sales_order_header`，`targetId = salesOrderId`。
- 状态动作只记录安全摘要，不记录完整请求体；图纸补传不记录文件内容。
- 销售订单列表、详情、零件分页、提单行分页和工艺表分页不新增业务 INFO。
