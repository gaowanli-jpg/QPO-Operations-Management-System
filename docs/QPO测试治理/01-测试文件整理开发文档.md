# QPO 测试文件整理开发文档

## 1. 背景

当前 QPO 测试文件已经能覆盖大量业务边界，但测试资产随着阶段式开发快速增长，出现了以下问题：

- 后端测试文件数量较多：约 `214` 个 Java 测试文件，约 `42,175` 行。
- 前端测试文件数量较多：约 `107` 个 JS 测试文件，约 `8,128` 行。
- 后端约 `134` 个测试文件包含 `Stage` 命名，前端约 `54` 个测试文件包含 `Stage/stage` 命名。
- 部分测试文件按开发阶段命名，而不是按长期业务职责命名，例如 `SalesOrderQpoImportStage3Test`、`PermissionSystemStage5Test`。
- 一些小型源码扫描测试分散在多个文件里，查找成本高。
- 一些大型集成测试文件过大，例如 `CoreWorkflowIntegrationTests`、`SalesOrderQpoImportStage3Test`，定位失败点不够直观。

这些测试仍然有价值，不能简单删除。整理目标是把“阶段开发测试”转化为长期可维护的“业务回归测试资产”。

## 2. 开发目标

1. 建立统一测试分层和命名规则。
2. 分批整理 `Stage` 命名测试文件，降低长期维护成本。
3. 合并低价值分散小文件，拆分超大测试文件。
4. 保留现有业务覆盖，不降低回归保护能力。
5. 支持快速本地验证、模块验证和发版前全量验证三种使用场景。
6. 避免与其他功能开发混杂提交，每批测试整理独立提交。

## 3. 非目标

- 不在本次整理中删除有效业务断言。
- 不因为减少文件数量而合并所有测试。
- 不一次性大规模移动全部测试目录。
- 不修改生产业务逻辑。
- 不清理 QPO 兼容标识，例如 `erp.env`、`ERP_*`、`erp_*`、`ErpUser` 等。
- 不处理 APS 历史兼容逻辑，除非用户单独确认。

## 4. 整理原则

### 4.1 先分类，再合并

测试文件多不是唯一问题。真正需要解决的是：测试职责不清、命名不稳定、执行范围不明确。

整理顺序：

1. 标注测试类型。
2. 重命名阶段式文件。
3. 合并很薄的源码/文档扫描测试。
4. 拆分超大集成测试。
5. 最后再考虑目录迁移。

### 4.2 测试覆盖不能下降

每次整理必须满足：

- 原测试语义仍存在。
- 关键断言没有被弱化。
- 删除测试前必须确认该断言已有等价覆盖。
- 每批整理后运行对应模块测试。

### 4.3 保留必要的 Characterization 测试

当前项目有不少读取源码/文档的测试。这类测试不是传统单元测试，但在 QPO 当前阶段有价值：

- 防止旧接口被误加回来。
- 防止权限点误复用。
- 防止文档口径和代码口径再次分叉。

这类测试应明确标记为 `Characterization`，不应混在业务行为测试里。

## 5. 目标测试分层

### 5.1 后端测试分类

| 类型 | 建议后缀 | 说明 | 是否依赖 Spring | 是否依赖数据库 |
|---|---|---|---|---|
| Unit | `*Test` | 纯 Java 服务、工具、计算、校验逻辑 | 否 | 否 |
| Service | `*ServiceTest` | 使用 mock 验证服务行为 | 否/少量 | 否 |
| Controller | `*ControllerTest` | 控制器权限、参数、响应结构 | 可选 | 否 |
| Integration | `*IntegrationTest` | SpringBootTest、真实 mapper、事务链路 | 是 | 是 |
| Migration | `*MigrationTest` | Flyway、数据库结构、基线压缩 | 可选 | 是 |
| Contract | `*ContractTest` | MES/WMS/U9 请求响应契约 | 否/可选 | 否 |
| Characterization | `*CharacterizationTest` | 源码/文档/权限口径防回退扫描 | 否 | 否 |

### 5.2 前端测试分类

| 类型 | 建议后缀 | 说明 |
|---|---|---|
| Component | `*.component.test.js` | 组件结构、状态、交互 |
| Service | `*.service.test.js` | API 封装、参数构造 |
| Workflow | `*.workflow.test.js` | 页面级流程、跨组件行为 |
| Characterization | `*.characterization.test.js` | 源码扫描、防回退断言 |
| Contract | `*.contract.test.js` | 前后端字段契约、导入描述一致性 |

## 6. 命名规范

### 6.1 后端命名

推荐格式：

```text
{Module}{Capability}{Type}Test.java
```

示例：

| 旧命名 | 建议命名 |
|---|---|
| `SalesOrderQpoImportStage3Test` | `SalesOrderQpoImportWorkflowTest` |
| `SalesOrderQpoImportStage2DefaultsTest` | `SalesOrderQpoImportDefaultsTest` |
| `SalesOrderU9SyncStage7Test` | `SalesOrderU9SyncWorkflowTest` |
| `PermissionSystemStage5Test` | `PermissionControllerGuardCharacterizationTest` |
| `MaterialMasterStage7SnapshotTest` | `MaterialMasterSnapshotCharacterizationTest` |

### 6.2 前端命名

推荐格式：

```text
{module}.{type}.test.js
```

示例：

| 旧命名 | 建议命名 |
|---|---|
| `salesOrderImportPanel.test.js` | `sales-order-import.workflow.test.js` |
| `salesOrderU9SyncModule.test.js` | `sales-order-u9-sync.workflow.test.js` |
| `permissionStage4.test.js` | `permission.characterization.test.js` |
| `releaseItemDataReplacementStage6.test.js` | `release-item-data-replacement.workflow.test.js` |

## 7. 建议目录结构

### 7.1 第一阶段：不移动 package，仅重命名

为了降低风险，第一阶段保留现有目录：

```text
quote-backend/src/test/java/com/machining/quote/
quote-frontend/src/
```

只做：

- 文件重命名。
- 类名同步。
- 测试方法重命名。
- 小文件合并。
- 超大文件拆分。

### 7.2 第二阶段：可选目录分层

后续稳定后，可考虑迁移为：

```text
quote-backend/src/test/java/com/machining/quote/
  unit/
  service/
  integration/
  migration/
  contract/
  characterization/

quote-frontend/src/tests/
  component/
  service/
  workflow/
  contract/
  characterization/
```

第二阶段需要同步 Maven/Jest/Vitest 配置，成本较高，不建议作为第一批动作。

## 8. 执行策略

### 8.1 第一批：销售订单相关测试整理

优先整理最近刚维护过、业务边界清晰的销售订单测试。

建议范围：

- 销售订单导入。
- 销售订单自动补全。
- 销售订单自动提单。
- 销售订单 U9 同步。
- 销售订单管理清理测试。

建议操作：

1. 将 `SalesOrderQpoImportStage*` 重命名为稳定业务名。
2. 将源码扫描类测试集中到 `SalesOrderImportCharacterizationTest`。
3. 将真实流程测试保留为 `SalesOrderQpoImportWorkflowTest` 或拆成多个 workflow 文件。
4. 将 U9 同步测试按契约、服务流程、页面入口分开。
5. 每次只移动/重命名一组，提交一组。

验收命令示例：

```powershell
cd quote-backend
.\mvnw.cmd "-Dtest=SalesOrder*Test" test

cd ..\quote-frontend
npm test -- salesOrder
```

### 8.2 第二批：权限与日志 Characterization 测试整理

建议范围：

- `PermissionSystemStage*Test`
- `PermissionModuleTreeTest`
- `AuditActionCoverageTests`
- `LoggingConventionTest`

建议操作：

1. 将权限源码扫描测试集中为 `PermissionCatalogCharacterizationTest`。
2. 将控制器注解扫描集中为 `PermissionControllerGuardCharacterizationTest`。
3. 将日志动作覆盖集中为 `AuditActionCatalogCharacterizationTest`。
4. 保留纯服务行为测试，例如 `AuditServiceTests`，不与扫描测试混合。

### 8.3 第三批：MES/WMS/U9 外部契约测试整理

建议范围：

- MES material / process master data。
- MES production dispatch。
- WMS reservation / allocation。
- U9 customer / sales order sync。

建议操作：

1. 将 payload 格式测试归为 `*ContractTest`。
2. 将客户端错误处理归为 `*ClientTest`。
3. 将数据库迁移归为 `*MigrationTest`。
4. 将端到端链路归为 `*IntegrationTest`。

### 8.4 第四批：超大测试拆分

优先拆分：

- `CoreWorkflowIntegrationTests`
- `SalesOrderQpoImportStage3Test`
- `LargeOrderItemPagingTest`
- `MesMaterialSyncTest`
- `LockedItemMesProductionDispatchTest`

拆分规则：

- 一个文件只覆盖一个业务入口或一个事务链路。
- 超过 500 行时优先拆分。
- fixture/helper 只在确实重复时抽取。
- 不为了抽象而抽象，避免测试 helper 过度封装。

## 9. JUnit Tag 建议

后续可以逐步增加：

```java
@Tag("unit")
@Tag("integration")
@Tag("migration")
@Tag("contract")
@Tag("characterization")
```

建议执行口径：

```powershell
# 日常快速回归
.\mvnw.cmd "-Dgroups=unit,contract,characterization" test

# 数据库相关回归
.\mvnw.cmd "-Dgroups=integration,migration" test

# 发版前
.\mvnw.cmd test
```

如果当前 Maven 配置暂不支持 group/tag 过滤，则先只完成标注和文档，后续单独做 Maven 配置调整。

## 10. 前端测试整理建议

当前前端测试很多是源码字符串断言。建议保留，但命名上区分：

- 页面交互：`*.workflow.test.js`
- 组件结构：`*.component.test.js`
- API 封装：`*.service.test.js`
- 防回退扫描：`*.characterization.test.js`
- 前后端契约：`*.contract.test.js`

第一阶段不建议大规模移动到 `src/tests`，避免影响现有测试脚本。先重命名、合并小文件即可。

## 11. 提交要求

每批整理单独提交，提交粒度建议：

1. `test: 整理销售订单导入测试命名`
2. `test: 合并销售订单导入防回退测试`
3. `test: 整理销售订单U9同步测试`
4. `test: 整理权限防回退测试`
5. `test: 拆分核心流程集成测试`

每个提交必须满足：

- `git diff --check` 通过。
- 对应模块测试通过。
- 未混入生产业务逻辑变更。
- 未混入其他会话正在开发的文件。

## 12. 验收标准

第一轮测试治理完成后，应达到：

- 主要 `Stage` 文件减少或更名为稳定业务命名。
- 销售订单相关测试能按文件名看出职责。
- 权限/日志源码扫描类测试集中到 Characterization 文件。
- 超大文件拆分出至少一个更小的业务场景文件。
- 文档记录后续新增测试应遵守的命名和分层规则。
- 全量或目标测试通过。

## 13. 风险与防护

| 风险 | 防护 |
|---|---|
| 重命名后 Maven/Jest 找不到测试 | 每次只重命名一组并立即运行目标测试 |
| 合并测试时遗漏断言 | 先复制断言再删除旧文件，使用 `rg` 复查关键字符串 |
| 大文件拆分引入 fixture 差异 | 保留原 fixture，先搬运测试方法，再做小幅去重 |
| 数据库集成测试受本地环境影响 | 明确使用 `erp.env` 映射 `DB_URL/DB_USERNAME/DB_PASSWORD` |
| 源码扫描测试误伤历史文档 | 只扫描 `src/main`、`src/test` 或明确列出的当前文档，不扫废弃历史方案全文 |
