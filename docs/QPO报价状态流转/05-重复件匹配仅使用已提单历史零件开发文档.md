# QPO 重复件匹配图号版本识别与已核价快照复用开发文档

> 2026-08-07 价格字段收口：历史候选的完整核价结果以 `tax_included_unit_price`、`material_data`、`process_route` 为准，金额字段使用 `tax_included_total_price`；`final_*` 不属于现行字段。

> 2026-08-09 材料主数据阶段 10 收口：重复件匹配复用的工程材料身份统一为 `材料编码 + 材料名称 + 材料类型 + 材质分类 + 材料形态`。自动复用按材料编码识别真实材料，材料类型来自 `dict_material_type`，材质分类保存钢铁、铝、塑料等分类，材料形态保存板材、棒材、管材；不得再把旧 `dict_material.material_type` 当作业务材料类型。

> 2026-08-07 物料号确认收口：RFQ 重复件核价会复用历史材料参数、工艺身份和工时，并按当前核价规则重新计算报价结果；同时在来源满足 `material_no` 非空且 `material_no_status = 已确认` 时复制完整物料号确认元组。目标物料号为空时写入，目标同值时幂等补齐元数据，目标异值时拒绝覆盖但继续处理其他可复用核价数据；来源未确认不阻断核价快照复用，也就是不阻断材料和工艺参数复用。普通件、组合件父件和子件均遵循同一规则。

> 2026-08-08 两级工艺主数据阶段 15 收口：重复件复用复制历史路线中的 `processDetailId` 和 `unitWorkHours`，并按当前有效小时价格重新计算工艺金额。当前具体工艺或大类缺失、停用时不按名称模糊替代，改为跳过并提示人工处理；复用成功后的新路线必须包含 `processCode / categoryName / detailName`。

> 2026-08-18 历史口径：历史零件只要 `item_quote_version.repeat_match_eligible = TRUE`，就视为已经提单过并可进入候选。提单生成时同步置位该字段；`V14` 会一次性回填既有 `已提单` 或已有提单行的历史零件。

> 2026-08-31 现行口径：重复识别只看 `图号 part_no + 版本 version`；可自动复用再看 `图号 + 版本 + 已核价及之后状态 + 有价格 + 有材料快照 + 有工艺快照`。运行时不再用 `repeat_match_eligible` 决定可复用资格；RFQ 逐件核价和销售订单导入自动补生产快照共用这套可复用来源，命中多条时取最新合格零件。

## 1. 背景

早期重复件复用入口在 `EngineerService.findRepeatSources()` 中，历史候选链路为：

```text
当前订单零件
  -> 按 customer_name 查历史 order_rfq
  -> 查历史订单下 order_delivery_ticket
  -> 用提单行 part_no + version 命中候选
  -> 回 item_quote_version 读取核价结果
```

这个链路偏保守，后续曾收口到 `repeat_match_eligible` 主表标记；现行口径进一步放宽为“已核价即可沉淀经验”，但仍区分重复识别和可自动复用：

- QPO 内部已经确认 **图号 + 版本** 是零件身份主键语义，不同客户之间不会重复。
- 客户字段不适合作为重复件匹配前置条件，且客户筛选不能帮助图号版本命中。
- 已核价后的零件已经具备可复用核价经验，不需要等到提单后才能成为候选。
- 真正需要复用的材料、工艺、价格、组合件父子关系，事实来源仍是 `item_quote_version` 和 `item_assembly_relation`。
- `order_delivery_ticket` 是不可逆发布记录和 MES/WMS 需求池；运行时不再用提单表判定重复件可复用资格。

因此重复件匹配应改为直接从零件主表查找：

```text
当前订单零件 part_no + version
  -> item_quote_version 中识别同图号版本历史零件
  -> 可自动复用时，筛选已核价及之后状态且价格 / 材料快照 / 工艺快照完整的历史零件
  -> 复用核价输入 / 工艺 / 材料，并按当前规则重新计算
  -> 组合件再按 item_assembly_relation 重建当前订单父子关系
```

## 2. 核心结论

1. 重复识别和可自动复用都以 `item_quote_version` 为事实来源。
2. 重复识别键只使用 `part_no + version`，不再按 `customer_name`、客户订单号、项目号或物料号限制。
3. 可自动复用候选必须是已核价及之后状态：`已核价 / 已报价 / 部分已提单 / 已生成提单 / 已提单`。
4. 可自动复用候选必须有完整核价结果：`tax_included_unit_price`、`material_data`、`process_route` 均不可为空，且材料 / 工艺快照不能是空 JSON。
5. `repeat_match_eligible` 保留为历史字段和历史迁移产物，不再作为运行时可复用资格条件。
6. 多条历史候选命中同一个 `part_no + version` 时，使用满足可自动复用条件的最新历史零件，按 `item_quote_version.id DESC`。
7. 普通件复用材料、工艺、费用、重量、价格等核价结果。
8. 组合件复用仍读取历史父件的 `item_assembly_relation`，并按当前订单子件 `part_no + version` 重建当前关系。
9. 组合件历史子件在当前订单不存在时，父件保持 `未核价`，不写错误关系，不额外弹窗或行内提示。
10. 全局设定页和逐件核价页都复用同一后端候选口径；全局设定页只做预览和推荐，不执行自动套用。
11. 大数据量下候选查询必须使用 **部分索引 + `VALUES` + `JOIN LATERAL` + 分批查询**；不使用 MyBatis-Plus `QueryWrapper` 大量 `OR` 条件拼接。

## 3. 非目标

- 不修改订单状态流转。
- 不修改零件状态定义；`未核价`、历史待核价状态、无图和废弃零件不能自动复用。
- 不把 MES 物料号作为自动复用门槛；来源未确认物料号时仍可复用核价快照，只是不复制物料号。
- 不把组合件父子关系冗余写入 `item_quote_version`。
- 不从 `order_delivery_ticket` 复制核价快照作为重复件复用来源。
- 不新增前端缺子件提示。
- 不改变重复件自动复用的触发位置，仍由逐件核价页首次完整加载后触发。

## 4. 目标行为

### 4.1 匹配规则

候选查询规则：

```sql
WITH current_keys(part_no, version) AS (
    VALUES
      (:partNo1, :version1),
      (:partNo2, :version2)
      -- 当前订单去重后的有效图号版本集合
)
SELECT h.*
FROM current_keys k
JOIN LATERAL (
    SELECT *
    FROM item_quote_version h
    WHERE h.part_no = k.part_no
      AND h.version = k.version
      AND h.rfq_id <> :currentRfqId
      AND h.status IN ('已核价', '已报价', '部分已提单', '已生成提单', '已提单')
      AND h.tax_included_unit_price IS NOT NULL
      AND h.material_data IS NOT NULL
      AND h.material_data <> '{}'::jsonb
      AND h.process_route IS NOT NULL
      AND h.process_route <> '[]'::jsonb
    ORDER BY h.id DESC
    LIMIT 1
) h ON true;
```

候选入选规则：

- 当前零件 `part_no` 或 `version` 为空时，不参与重复件匹配。
- 当前订单零件先按 `part_no + version` 去重，避免重复 key 放大 SQL 参数。
- 历史零件 `rfq_id` 等于当前订单时，不参与匹配。
- 历史零件不是已核价及之后状态时，不参与自动复用。
- 历史零件缺少完整核价结果或材料 / 工艺快照为空时，不参与自动复用。
- 同一 `part_no + version` 多条历史命中时，由 `JOIN LATERAL ... ORDER BY id DESC LIMIT 1` 在数据库侧只取最新合格来源。
- 当前订单唯一图号版本数量较大时，按固定批次拆分查询，建议每批 300～500 个 key，避免 SQL 参数过长。

### 4.2 大数据量查询策略

后期历史核价零件会持续增长，重复件匹配不能依赖“先查一批历史订单再回表过滤”的链路，也不能把当前订单所有 `part_no + version` 拼成很长的 `OR` 查询。推荐固定为以下策略：

1. Java 侧从当前订单零件提取有效 `part_no + version`，先去空、去重。
2. Java 侧按固定批次拆分 key，默认 `REPEAT_SOURCE_KEY_BATCH_SIZE = 500`，如单个订单零件极多可下调到 300。
3. Mapper 层使用专用 SQL，把当前批次 key 组装成 `WITH current_keys(part_no, version) AS (VALUES ...)`。
4. SQL 层用 `JOIN LATERAL` 对每个 key 命中 `item_quote_version` 中最新一条可复用历史零件。
5. 数据库通过 `idx_item_quote_version_repeat_priced_snapshot_key` 覆盖已具备自动复用资格的历史零件；运行时不再查 `order_delivery_ticket`。
6. 命中历史零件后，按历史 `rfq_id` 批量回查来源订单，避免逐条 `selectById`。
7. 返回给业务层时仍按 `part_no + version` 做防御性去重，防止异常数据或 SQL 变更造成重复来源。

禁止做法：

- 禁止从 `order_delivery_ticket` 复制核价快照，禁止在服务层或重复件候选 SQL 中逐行扫描提单候选；自动复用资格只读取 `item_quote_version` 的状态、价格和快照完整性。
- 禁止用 `customer_name` 缩小候选范围。
- 禁止用 `QueryWrapper` 拼大量 `or().eq("part_no", ...).eq("version", ...)`。
- 禁止一次性把几千个 key 塞进单条 SQL。

### 4.3 普通件复用

普通件历史候选命中后，继续沿用现有复用内容：

- `material_name`
- `surface_treatment`
- `material_data`
- `process_route`
- `part_net_weight`
- `base_cost`
- `tax_included_unit_price`
- `tax_included_total_price`
- `status = 已核价`
- 已确认的物料号确认元组：`material_no`、`material_no_status`、`material_no_source`、`material_no_source_ticket_id`、`material_no_synced_at`、`material_no_message`

自动复用只代表工程核价结果被带入，不会自动完成整单核价，也不会把订单或零件直接写为 `已报价`。

物料号确认元组是可选增强信息，不作为重复件候选条件。来源未确认不阻断核价快照复用，也就是不阻断材料和工艺参数复用；目标已有不同物料号时只跳过物料号元组，不能覆盖目标值，也不能回退材料、工艺输入数据复用和当前价格重算。

### 4.4 组合件复用

组合件历史父件命中后：

1. 判断历史父件 `quote_mode = ASSEMBLY`。
2. 读取历史父件 `item_assembly_relation`。
3. 逐个读取历史子件。
4. 用历史子件的 `part_no + version` 到当前订单中查找当前子件。
5. 当前子件存在时，递归复用子件核价结果。
6. 当前子件全部可用且有价格后，按当前子件 ID 重建当前父件的 `item_assembly_relation`。
7. 当前订单缺少任一历史子件时，跳过父件：
   - 不写 `quote_mode`
   - 不写 `assembly_fee`
   - 不写 `tax_included_unit_price`
   - 不写 `item_assembly_relation`
   - 父件保持 `未核价`

## 5. 数据库与索引

当前重复件可自动复用候选会高频按 `part_no + version` 查询已核价及之后状态、且完整核价快照的历史零件。后期历史零件会非常多，因此不建议使用普通全量联合索引；运行时通过 **PostgreSQL 部分索引** 命中主表：

```sql
CREATE INDEX IF NOT EXISTS idx_item_quote_version_repeat_priced_snapshot_key
    ON item_quote_version(part_no, version, id DESC)
    WHERE status IN ('已核价', '已报价', '部分已提单', '已生成提单', '已提单')
      AND tax_included_unit_price IS NOT NULL
      AND material_data IS NOT NULL
      AND material_data <> '{}'::jsonb
      AND process_route IS NOT NULL
      AND process_route <> '[]'::jsonb;
```

说明：

- `part_no + version` 是业务匹配主键语义，放在索引前缀便于精确命中。
- 部分索引只包含已核价及之后状态且核价结果完整的历史零件，索引体积明显小于全表索引。
- `repeat_match_eligible` 保留为历史字段，不再参与运行时可自动复用资格判定。
- `id DESC` 用于每个图号版本快速取最新历史零件。
- 对于 `JOIN LATERAL` 的每个当前 key，数据库可以用该部分索引做小范围命中并 `LIMIT 1`。
- 不新增客户索引，因为重复件匹配不再使用客户作为条件。
- 不新增重复件专用提单索引；运行时重复件候选不再依赖提单表。

不推荐方案：

```sql
CREATE INDEX idx_item_quote_version_part_version_status_id
    ON item_quote_version(part_no, version, status, id DESC);
```

该普通联合索引会覆盖所有状态和不完整核价记录；历史零件量很大时，索引更大、缓存命中更差，不如部分索引贴合重复件复用场景。

迁移文件建议：

```text
quote-backend/src/main/resources/db/migration/V28__repeat_match_priced_snapshot_index.sql
```

实际版本号按项目当前最大 Flyway 版本顺延。

## 6. 后端修改设计

### 6.1 `EngineerService.findRepeatSources()`

目标：

- 删除按 `customer_name` 查询历史 `order_rfq` 的前置逻辑。
- 删除通过 `order_delivery_ticket` 构造候选图号版本集合的逻辑。
- 直接基于当前订单零件的 `part_no + version` 查询 `item_quote_version`。
- 可自动复用查询限制为已核价及之后状态，且价格 / 材料快照 / 工艺快照完整，不再运行时读取提单表。
- 保留 `RepeatSource(order, item)` 结构，用历史 `rfq_id` 回查 `order_rfq` 只用于展示来源 RFQ 信息。

建议伪代码：

```java
private Map<String, RepeatSource> findRepeatSources(OrderRfq order, List<ItemQuoteVersion> currentItems) {
    Map<String, ItemQuoteVersion> currentItemByKey = buildCurrentItemByKey(currentItems);
    if (currentItemByKey.isEmpty()) {
        return Map.of();
    }

    List<PartVersionKey> keys = currentItemByKey.values().stream()
            .map(item -> new PartVersionKey(item.getPartNo(), item.getVersion()))
            .distinct()
            .toList();

    List<ItemQuoteVersion> historicalItems = new ArrayList<>();
    for (List<PartVersionKey> batch : partition(keys, 500)) {
        historicalItems.addAll(itemMapper.selectLatestReleasedRepeatSources(order.getId(), batch));
    }
    // SQL 已保证每个 key 返回最新一条，Java 侧仍按 itemKey 做防御性去重
}
```

实现要求：

- 不建议用 `QueryWrapper` 拼大量 `or().eq("part_no"...).eq("version"... )`，订单零件多时 SQL 冗长且优化器压力大。
- 建议新增 Mapper XML 或 `@SelectProvider` 专用 SQL，使用 `VALUES` 构造当前订单 key 集合。
- SQL 使用 `JOIN LATERAL`，每个 key 在部分索引上取最新一条，避免全表排序。
- Java 侧负责把当前订单 key 去重并分批，默认批次建议 500，可通过常量控制。
- 如果某批 key 为空，直接跳过，不访问数据库。
- `RepeatSource(order, item)` 结构可以保留，但来源订单应按命中的历史 `rfq_id` 批量回查，避免每个历史零件逐条 `selectById`。

建议 Mapper 接口：

```java
List<ItemQuoteVersion> selectLatestReleasedRepeatSources(
        @Param("currentRfqId") Long currentRfqId,
        @Param("keys") List<PartVersionKey> keys);
```

建议新增轻量 key 类型：

```java
public record PartVersionKey(String partNo, String version) {
}
```

如果项目继续保持无 XML Mapper 的风格，优先新增 `RepeatQuoteSourceSqlProvider` 给 `ItemQuoteVersionMapper` 使用；Provider 只负责生成 `VALUES + JOIN LATERAL` SQL，不承载业务判断。

### 6.2 可复用判断

新增或调整判断方法：

```java
private boolean hasReusableQuote(ItemQuoteVersion item) {
    return item != null
            && AUTO_REUSABLE_REPEAT_STATUSES.contains(trimmedStatus(item.getStatus()))
            && item.getTaxIncludedUnitPrice() != null
            && !normalizeMap(item.getMaterialData()).isEmpty()
            && !normalizeProcessRoute(item.getProcessRoute()).isEmpty();
}
```

`applyRepeatQuoteRecursive()` 入口也应使用该判断，避免递归子件绕过可自动复用门槛。

### 6.3 日志和返回

- `analyzeRepeatOrder()` 的 `repeatItems` 仍返回来源订单、来源零件、历史单价和工艺路线。
- `applyRepeatQuotes()` 的 `skippedItems` 可继续返回未找到原因，建议文案调整为：

```text
未找到可自动复用的历史重复件
```

- 不把 `skippedItems` 展示到前端缺子件提示。

## 7. 前端修改设计

### 7.1 `GlobalSetup.vue`

全局设定页仍只做前 10 个零件预览和默认配置推荐。

需要同步文案：

```text
已根据图号和版本识别历史重复件；可自动复用的历史核价会推荐默认材料与工艺路线，可继续手动调整后覆盖到本单其他零件。
```

不得再出现：

```text
同客户已提单历史重复件
```

### 7.2 `ItemPricing.vue`

- 首次加载完整订单后调用 `applyRepeatQuotes(rfqId)`。
- 有 `engineer:pricing:save-item` 权限才自动调用。
- 自动复用成功后刷新完整核价数据。
- 不读取 `skippedItems` 展示缺子件原因。
