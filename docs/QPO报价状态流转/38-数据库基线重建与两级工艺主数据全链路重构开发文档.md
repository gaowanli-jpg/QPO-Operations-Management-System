## 1. 文档目的

本次改造解决两个已经叠加到一起的问题：

1. 当前数据库迁移文件已经累积到 `V90`，后续继续叠加会让新环境初始化、测试维护和问题排查越来越重。
2. 当前工艺字典 `dict_process` 是单层工艺表，且保留了 8 档数量价格字段；后续 QPO 要与 MES 前后贯通，工艺需要具备稳定工艺编码、大类名称、具体工艺名称和统一小时价格，不能再只靠 `processName` 和数量分级价格识别。

用户已确认当前业务数据库可以清空重建，不需要兼容历史业务数据。因此本次不再按“保留旧库平滑迁移”的小步方案处理，而是趁清库窗口完成一次数据库基线整理和工艺全链路重构。

完成后目标链路为：

```text
工艺大类主数据
    -> 具体工艺主数据
    -> 全局核价模板
    -> 零件核价工艺路线
    -> RFQ / 销售订单 / 提单 / WMS / 待产 / 锁库 工艺快照
    -> MES 生产下发结构化工艺路线
```

## 2. 当前实现和问题

### 2.1 当前工艺主数据

当前后端存在实体：

```text
quote-backend/src/main/java/com/machining/quote/entity/DictProcess.java
```

当前数据库表：

```text
dict_process
```

主要字段包括：

| 字段 | 当前语义 | 问题 |
| --- | --- | --- |
| `process_name` | 工艺名称 | 既是用户展示名，又被当作业务身份，不能承载 MES 工艺编码。 |
| `calc_type` | 计算类型，当前主要为 `工时` | 本次工艺只保留工时小时价格；非工时费用应继续走费用字典。 |
| `sort_no` | 排序 | 可以保留排序语义，但需要拆到大类和具体工艺各自排序。 |
| `price_1_5` 到 `price_3000_plus` | 按数量档位价格 | 当前实际数据各档价格一致，后续不再分级定价。 |

当前核价逻辑在 `EngineerService` 中按 `processName` 查 `dict_process`，再按数量选择档位价格。当前页面和全局模板也主要通过 `processName`、`sourceType`、`optionKey` 等字段识别工艺。

### 2.2 当前工艺路线快照

当前工艺路线在多张主表或快照表中以 JSON 形式保存，常见字段为：

```json
{
  "sortNo": 10,
  "processName": "CNC1",
  "calcType": "工时",
  "inputVal": 2.5,
  "unitRate": 80,
  "lineCost": 200
}
```

涉及位置包括但不限于：

| 数据位置 | 字段 | 说明 |
| --- | --- | --- |
| `item_quote_version` | `process_route` | RFQ 零件核价结果。 |
| `sales_order_item` | `process_route` | 销售订单补全或派生时的生产快照。 |
| `order_delivery_ticket` | `process_route` | 提单时固化的不可变工艺事实。 |
| `order_delivery_ticket_allocation` | `process_route` | WMS 拆分后锁库 / 待产行继承的工艺快照。 |
| 前端全局模板 | `processRoute` | 工程部全局工艺模板。 |
| MES 生产下发 DTO | `processRoute` | 当前仍是 `Object`，缺少结构化契约。 |

这些快照当前只保存 `processName`，没有稳定 `processCode`，也没有区分“大类工艺”和“具体工艺”。后续对 MES 传递时，无法稳定表达“工艺编码 + 具体工艺名称 + 大类名称”。

### 2.3 当前数据库迁移问题

当前 Flyway 文件已经包含 `V1` 到 `V90`。运行时使用 Flyway，`schema.sql` 不是生产初始化来源，但部分测试仍检查 `schema.sql`。继续长期维护两套 schema 来源会增加误差。

本次允许清库重建，因此最终应把迁移整理为新的干净基线：

```text
quote-backend/src/main/resources/db/migration/V1__qpo_baseline_schema.sql
quote-backend/src/main/resources/db/migration/V2__qpo_baseline_seed_data.sql
```

后续新变更从 `V3` 开始继续追加。

## 3. 范围与不变项

### 3.1 本次范围

- 重建 QPO 数据库基线，移除现有 `V1` 到 `V90` 的长期迁移链。
- 删除运行时依赖的 `schema.sql`，测试改为基于 Flyway 新基线验证。
- 将 `dict_process` 改造为两级工艺主数据：`dict_process_category` 和 `dict_process_detail`。
- 将工艺定价从 8 档数量价格改为大类统一小时价格。
- 零件核价、全局模板、重复件核价、销售订单异常治理、RFQ 派生销售订单、提单、WMS、待产、锁库、导出和 MES 生产下发全链路改用新工艺快照契约。
- 工艺相关页面保留“材料工艺”模块入口和既有权限 code，不新增左侧模块。
- 为未来 MES 同步工艺大类预留字段，但本阶段不开发真实 MES 工艺同步接口。

### 3.2 不在本阶段处理

- 不重构材料表和 BOM 结构；材料主数据后续单独立项。
- 不接入 MES 工艺大类同步定时任务或外部接口。
- 不把非工时费用伪装成 MES 工艺；表面处理、组装费、百分比费用等继续按现有费用口径处理。
- 不保留旧业务数据迁移兼容；数据库清空后重新导入测试数据。
- 不新增 `common:*` 权限。
- 不修改 QPO 与 APS 的边界；APS 相关代码只作为历史兼容读取，不作为新设计目标。

## 4. 核心业务规则

1. 工艺大类由系统本地维护，未来可由 MES 同步；现阶段先通过 QPO 页面手工创建。
2. 工艺大类字段包括：工艺编码、工艺名称、小时价格、备注、来源类型、MES 外部 ID、启用状态、排序。
3. 具体工艺由工程部人员基于一个工艺大类自由创建。
4. 具体工艺只维护：具体工艺名称、具体备注、启用状态、排序；不重复保存大类编码、大类名称或小时价格。
5. 一个工艺大类可以有多个具体工艺；同一大类下具体工艺名称不可重复。
6. 工艺大类的 `process_code` 全局唯一，用于后续对接 MES 和其他外部系统。
7. 具体工艺的内部稳定身份是 `processDetailId`。
8. 对外业务身份是 `processCode + detailName`，展示时同时显示 `categoryName`。
9. 工艺小时价格只来自大类，具体工艺不维护单独价格。
10. 工艺大类价格变更后，只影响未来选择、核价刷新和重新核价，不自动改写已经提单、已经锁库或已经下发的历史快照。
11. 已保存的核价工艺路线必须固化当时的 `processCode`、`detailName`、`categoryName`、`hourlyRate`、`unitWorkHours` 和 `lineCost`。
12. 后端保存核价时必须以 `processDetailId` 重新查库获取大类编码、名称和小时价格，不能信任前端传入价格或名称。
13. 禁用工艺不允许新选择；历史快照可继续展示，但重新保存或刷新时必须提示失效并阻断，不能按名称静默映射到其他工艺。
14. 重复件核价复用时，可以复用历史工艺身份和工时，但按当前大类小时价格重新计算工艺费用，保持现有“刷新时使用当前字典价格”的业务口径。
15. 销售订单异常治理、RFQ 派生销售订单、提单、WMS、待产、锁库等快照复制不重新计价，只复制源快照事实。

## 5. 目标数据模型

### 5.1 工艺大类表

新增表：

```sql
CREATE TABLE dict_process_category (
    id BIGSERIAL PRIMARY KEY,
    process_code VARCHAR(64) NOT NULL,
    category_name VARCHAR(120) NOT NULL,
    hourly_rate NUMERIC(18, 4) NOT NULL,
    remarks VARCHAR(500),
    source_type VARCHAR(30) NOT NULL DEFAULT 'LOCAL',
    mes_external_id VARCHAR(120),
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    sort_no INTEGER NOT NULL DEFAULT 0,
    mes_synced_at TIMESTAMP,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uk_dict_process_category_code UNIQUE (process_code),
    CONSTRAINT chk_dict_process_category_rate CHECK (hourly_rate >= 0),
    CONSTRAINT chk_dict_process_category_source CHECK (source_type IN ('LOCAL', 'MES'))
);
```

索引：

```sql
CREATE INDEX idx_dict_process_category_enabled_sort
    ON dict_process_category(enabled, sort_no, id);

CREATE INDEX idx_dict_process_category_name
    ON dict_process_category(category_name, id);

CREATE INDEX idx_dict_process_category_mes_external
    ON dict_process_category(mes_external_id)
    WHERE mes_external_id IS NOT NULL;
```

字段规则：

| 字段 | 规则 |
| --- | --- |
| `process_code` | 必填，全局唯一，建议使用大写英文、数字、下划线或短横线，例如 `PACKAGING`。 |
| `category_name` | 必填，例如 `包装`。 |
| `hourly_rate` | 必填，非负，单位为 CNY / 小时。 |
| `remarks` | 可空，记录大类说明。 |
| `source_type` | 当前手工维护写 `LOCAL`；未来 MES 同步写 `MES`。 |
| `mes_external_id` | 预留 MES 主键或编码。 |
| `enabled` | 启停生命周期，不做普通硬删除。 |

### 5.2 具体工艺表

新增表：

```sql
CREATE TABLE dict_process_detail (
    id BIGSERIAL PRIMARY KEY,
    category_id BIGINT NOT NULL REFERENCES dict_process_category(id),
    detail_name VARCHAR(120) NOT NULL,
    detail_remarks VARCHAR(500),
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    sort_no INTEGER NOT NULL DEFAULT 0,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uk_dict_process_detail_category_name UNIQUE (category_id, detail_name)
);
```

索引：

```sql
CREATE INDEX idx_dict_process_detail_category_enabled_sort
    ON dict_process_detail(category_id, enabled, sort_no, id);

CREATE INDEX idx_dict_process_detail_name
    ON dict_process_detail(detail_name, id);
```

字段规则：

| 字段 | 规则 |
| --- | --- |
| `category_id` | 指向大类，具体工艺不复制大类编码、名称和价格。 |
| `detail_name` | 必填，同一大类下唯一，例如 `精细包装`。 |
| `detail_remarks` | 可空，例如 `包装选择精细包装`。 |
| `enabled` | 禁用后不能被新核价选择，但历史快照仍可展示。 |

## 6. 标准工艺路线快照契约

### 6.1 JSON 字段

所有实际业务快照中的工艺路线统一为数组，单行结构如下：

```json
{
  "routeType": "PROCESS",
  "processCategoryId": 1,
  "processDetailId": 10,
  "processCode": "PACKAGING",
  "categoryName": "包装",
  "detailName": "精细包装",
  "hourlyRate": 10,
  "unitWorkHours": 2.5,
  "lineCost": 25,
  "sortNo": 10,
  "categoryRemarks": "包装类工艺",
  "detailRemarks": "包装选择精细包装"
}
```

字段说明：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `routeType` | 是 | 固定为 `PROCESS`，避免和费用项混淆。 |
| `processCategoryId` | 是 | 保存当时选择的大类 ID，便于内部追溯。 |
| `processDetailId` | 是 | 保存当时选择的具体工艺 ID，是后端重新取价的主键。 |
| `processCode` | 是 | 保存当时大类编码，用于后续外部系统传输。 |
| `categoryName` | 是 | 保存当时大类名称，用于展示和外部传输快照。 |
| `detailName` | 是 | 保存具体工艺名称。 |
| `hourlyRate` | 是 | 保存当时参与计算的大类小时价格。 |
| `unitWorkHours` | 是 | 用户输入的工时。 |
| `lineCost` | 是 | `unitWorkHours * hourlyRate`。 |
| `sortNo` | 是 | 工艺顺序。 |
| `categoryRemarks` | 否 | 快照备注。 |
| `detailRemarks` | 否 | 快照备注。 |

### 6.2 旧字段兼容读取

本次允许清库，不需要保留旧业务数据迁移。但开发期间为避免页面读取旧草稿或测试 fixture 直接崩溃，格式化展示工具可以兼容以下旧字段读取：

```text
processName -> detailName
inputVal    -> unitWorkHours
unitRate    -> hourlyRate
calcType    -> routeType 推断
```

兼容读取只用于开发过渡和测试 fixture，不作为新数据保存格式。最终源码测试必须禁止新保存逻辑继续输出 `processName`、`inputVal`、`unitRate` 作为主字段。

### 6.3 非工时费用分离

以下内容不能写成 `routeType = PROCESS`：

| 业务项 | 现行承载 | 本次规则 |
| --- | --- | --- |
| 表面处理费 | 费用 / 生产快照字段 | 继续按现有费用或快照口径保存，不进入工艺大类。 |
| 组装件百分比费用 | `dict_assembly_markup_fee` 等费用字典 | 继续由费用字典维护。 |
| 非工时费用项 | `dict_extra_fee_item` / feeData | 继续作为费用项，不传成 MES 工艺。 |
| 组合件组装费快照 | 现有组合件核价快照 | 可以保留为费用项或合计项，不与工艺路线混用。 |

## 7. 定价规则

### 7.1 新公式

工艺费用统一为：

```text
lineCost = unitWorkHours * dict_process_category.hourly_rate
```

零件最终含税 / 未税价格、材料成本、费用项、重量和利润等其他核价公式不在本阶段重新设计。数量仍用于零件总金额计算，但不再用于选择工艺小时价格档位。

### 7.2 后端取价边界

保存核价时，前端只能提交：

```json
{
  "processDetailId": 10,
  "unitWorkHours": 2.5,
  "sortNo": 10
}
```

后端必须：

1. 按 `processDetailId` 查询 `dict_process_detail`。
2. Join `dict_process_category`。
3. 校验大类和具体工艺均启用。
4. 使用当前 `hourly_rate` 计算 `lineCost`。
5. 写入完整工艺路线快照。

前端传入的 `processCode`、`categoryName`、`detailName`、`hourlyRate`、`lineCost` 只能作为展示辅助，后端保存时必须丢弃并重新计算。

### 7.3 大类价格变更影响

| 场景 | 是否使用新价格 | 说明 |
| --- | --- | --- |
| 新增零件核价 | 是 | 按当前大类小时价格计算。 |
| 编辑未完成核价并保存 | 是 | 重新保存时按当前小时价格计算。 |
| 一键刷新核价 | 是 | 保持现有刷新语义，按当前字典价格重算。 |
| 重复件核价复用 | 是 | 复用工艺身份和工时，但按当前大类小时价格重算。 |
| 已报价 RFQ 历史快照展示 | 否 | 展示当时保存的 `hourlyRate` 和 `lineCost`。 |
| 已生成提单 | 否 | `order_delivery_ticket.process_route` 不自动改写。 |
| WMS / 待产 / 锁库 | 否 | 继承提单快照，不重新计价。 |
| MES 生产下发 | 否 | 发送提单 / allocation 快照，不按当前字典重算。 |

### 11.1 开发过程策略

| --- | --- |

## 19. 回滚方案

本次属于清库重建和破坏性基线调整，不提供应用层字段回滚脚本。若阶段开发中发现问题，按以下方式处理：

1. 未执行最终压缩前，回退当前代码分支或临时迁移。
2. 执行最终清库前，保留 PostgreSQL 备份。
3. 清库后发现严重问题时，停止后端，恢复清库前备份，并切回旧版本代码。
4. 不通过新增“反向迁移”恢复旧 `dict_process` 和分级价格模型。

## 20. 交付结果

完成后，QPO 工艺链路统一为：

```text
工艺大类：processCode + categoryName + hourlyRate
具体工艺：processDetailId + detailName
核价路线：processCode + categoryName + detailName + hourlyRate + unitWorkHours + lineCost
外部传输：processCode + categoryName + detailName + unitWorkHours
```

数据库也统一为新基线启动，不再背负 90 个历史迁移和旧 `schema.sql` 双源。这样后续接 MES 工艺同步、重构材料表和扩展 BOM 时，工艺身份、价格来源和外部传输字段都已经干净稳定。
