# 图纸按图号版本精确绑定入口开发文档

最后更新：2026-08-03

## 1. 背景

QPO 当前所有图纸导入、补传、替换入口都以 PDF 文件名解析出的“图号”作为绑定依据。这个规则对早期使用足够简单，但在实际业务中会出现同一图号存在多个版本的情况，只按图号匹配会比较宽松，容易把某个版本的图纸绑定到同图号的其它版本零件上。

本阶段目标是在每一个现有“按图号绑定图纸”的入口右侧，并列新增一个“按图号+版本绑定”的入口。新入口只改变上传文件到零件之间的匹配条件：从“图号命中”收紧为“图号 + 版本同时命中”。一旦命中，后续保存图纸、写入 `drawing_url` / `has_drawing`、结果展示、日志审计、跳过规则、覆盖规则等全部沿用原入口逻辑，不改变任何下游业务流程。

## 2. 一句话规则

原入口继续按 `图号` 匹配；新入口按 `图号_版本` 匹配。匹配命中后，仍然执行原来的图纸绑定逻辑，只是目标零件由更严格的“图号+版本”规则找到。

## 3. 文件命名规则

### 3.1 原入口保持不变

原“按图号绑定”入口继续支持：

```text
图号.pdf
图号 空格说明.pdf
图号-说明.pdf
```

示例：

```text
L20100000733.pdf
L20100000733 定位块.pdf
L20100000733-定位块.pdf
```

### 3.2 新入口新增规则

新“按图号+版本绑定”入口支持：

```text
图号_版本.pdf
图号_版本 空格说明.pdf
图号_版本-说明.pdf
```

示例：

```text
L20100000733_A.pdf
L20100000733_A 定位块.pdf
L20100000733_A-定位块.pdf
```

说明：

- 使用 `_` 作为图号和版本的分隔符。
- 不使用 `/`，因为 Windows 文件名不允许 `/` 作为普通字符。
- 文件扩展名仍只接受 `.pdf`，大小写按现有逻辑处理。
- 描述部分仅用于人工识别，不参与匹配。

## 4. 适用入口

本阶段覆盖项目内所有支持上传图纸并绑定零件的入口。

| 场景 | 现有入口 | 新增入口 | 命中后行为 |
|---|---|---|---|
| 新单导入：询价单导入关联图纸 | 按图号绑定 | 按图号+版本绑定 | 保存图纸，写 `item_quote_version.drawing_url` |
| 新单导入：销售订单导入关联图纸 | 按图号绑定 | 按图号+版本绑定 | 保存图纸，写 `sales_order_item.drawing_url`，同步 `has_drawing=true` |
| 询价订单详情：补传图纸 | 按图号补传 | 按图号+版本补传 | 只补缺图零件，已有图纸跳过 |
| 销售订单详情：补传图纸 | 按图号补传 | 按图号+版本补传 | 只补缺图零件，已有图纸跳过，同步 `has_drawing=true` |
| 议价提单：导入替换图纸 | 按图号替换 | 按图号+版本替换 | 按选中订单范围替换可变更零件图纸，支持 RFQ / 销售订单 / 混合来源 |

## 5. 明确不改变的内容

- 不改变图纸保存目录和对象存储逻辑。
- 不新增图纸版本表。
- 不改变图纸预览、导出、MES / WMS / U9 下游读取图纸地址的逻辑。
- 不改变订单、零件、提单状态流转。
- 不改变补传入口“已有图纸跳过”的业务规则。
- 不改变议价提单“导入替换图纸”的覆盖规则。
- 不改变新单导入时 Excel 行解析和零件创建逻辑。
- 不新增权限点；新入口沿用对应原入口的权限。
- 不把版本写入额外字段；版本只用于本次上传时定位目标零件。

## 6. 前端设计

### 6.1 UI 总体规则

每个图纸上传区域展示两个并列入口：

```text
[ 按图号绑定图纸 ]    [ 按图号+版本绑定图纸 ]
```

每个入口内部的选择按钮改成上下排列：

```text
选择多个 PDF
选择文件夹
```

视觉要求：

- 两个入口左右并列，宽度一致。
- 小屏时可自然换行或上下堆叠，不能压缩到文字溢出。
- 旧入口说明保持“图号.pdf / 图号 空格说明.pdf / 图号-说明.pdf”。
- 新入口说明展示“图号_版本.pdf / 图号_版本 空格说明.pdf / 图号_版本-说明.pdf”。
- 两个入口使用同一权限控制、同一禁用状态、同一 pending 规则。
- 选择多个 PDF 和选择文件夹按钮在每个入口内上下排列，不再左右并列。

## 7. 后端设计

### 7.1 FormData 字段约定

所有现有接口路径保持不变，只新增一个可选文件字段：

| 字段 | 含义 | 匹配方式 |
|---|---|---|
| `drawings` | 原入口上传的图纸 | 按图号匹配 |
| `versionDrawings` | 新入口上传的图纸 | 按图号 + 版本匹配 |

接口包括：

```text
POST /api/market/import-rfq
POST /api/market/sales-orders/import-qpo
POST /api/order-management/orders/{rfqId}/supplement-drawings
POST /api/market/sales-order-management/orders/{salesOrderId}/supplement-drawings
POST /api/market/release/drawings/replace
```

Controller 改造原则：

- 在上述接口中新增：

```java
@RequestParam(value = "versionDrawings", required = false) List<MultipartFile> versionDrawings
```

- 原 `drawings` 参数保留，兼容旧前端和旧使用习惯。
- 如果两个字段都为空，沿用原来的“请上传图纸”提示。

### 7.2 解析工具

目标文件：

```text
quote-backend/src/main/java/com/machining/quote/util/DrawingPartNoResolver.java
```

在现有 `extractPartNo(...)` 基础上新增“图号+版本”解析能力。

建议新增 record：

```java
public record DrawingIdentity(String partNo, String version) {
}
```

建议新增方法：

```java
public static DrawingIdentity extractPartNoVersion(
        String filename,
        Collection<DrawingIdentity> knownIdentities)
```

匹配规则：

1. 清理路径，只取文件名。
2. 去掉 `.pdf` 后缀。
3. 归一化为大写并 trim。
4. 对已知零件身份集合按 `partNo` 长度倒序、`version` 长度倒序遍历。
5. 目标前缀为：

```text
normalizePartNo(partNo) + "_" + normalizeVersion(version)
```

6. 文件名 base 满足以下任一条件则命中：
   - 完全等于目标前缀。
   - 以目标前缀开头，且后续第一个字符不是英文字母或数字。

这样可支持：

```text
P-100_A.pdf
P-100_A 定位块.pdf
P-100_A-定位块.pdf
```

并避免 `P-100_A1.pdf` 被误识别成 `P-100_A`。

版本归一化：

```java
public static String normalizeVersion(String version) {
    return version == null ? "" : version.trim().toUpperCase();
}
```

当解析失败时返回空身份或 `null`，由调用方进入未匹配结果。

### 7.3 匹配优先级

同一次提交同时包含 `versionDrawings` 和 `drawings` 时：

1. 先处理 `versionDrawings`，按图号+版本精确匹配。
2. 再处理 `drawings`，按原图号规则匹配。
3. 如果同一个目标零件已经被本次 `versionDrawings` 命中并处理，`drawings` 不再覆盖该目标。

原因：

- 新入口是更严格的匹配。
- 用户同时上传两类文件时，应优先保留精确匹配结果。
- 对单独使用旧入口的用户没有任何影响。

## 8. 各后端链路改造

### 8.1 RFQ 新单导入

目标文件：

```text
quote-backend/src/main/java/com/machining/quote/controller/MarketController.java
```

当前 RFQ 导入在 Controller 内完成图纸文件解析、保存和 Excel 行绑定。本阶段保持该结构，只新增 `versionDrawings`。

改造要点：

- Excel 行读取完成后，构建已知身份：

```java
partNo + version
```

- `versionDrawings` 使用 `extractPartNoVersion(...)` 得到精确图纸映射：

```text
Map<partNo||version, DrawingFileInfo>
```

- `drawings` 保持当前 `Map<partNo, DrawingFileInfo>`。
- 绑定每一行时：
  1. 先用 `partNo||version` 查精确图纸。
  2. 找不到再用 `partNo` 查旧图纸。
  3. 找到后仍按现有逻辑写入 `drawing_url`。

结果结构保持现有 `drawingReport`，可补充字段：

| 字段 | 说明 |
|---|---|
| `versionUploadedDrawingCount` | 新入口上传 PDF 数 |
| `versionMatchedDrawingCount` | 新入口命中的图纸数 |

不要求前端必须展示这两个字段；主要用于日志和测试。

### 8.2 销售订单新单导入

目标文件：

```text
quote-backend/src/main/java/com/machining/quote/service/SalesOrderQpoImportService.java
```

当前 `prepareDrawingBindings(...)` 负责图纸保存和 `drawingByPartNo` 映射。本阶段建议将其扩展为同时返回：

```java
Map<String, DrawingFileInfo> drawingByPartNo
Map<String, DrawingFileInfo> drawingByPartNoVersion
```

其中 `partNoVersion` key 使用：

```java
normalizePartNo(partNo) + "||" + normalizeVersion(version)
```

销售订单行绑定时：

1. 先查 `drawingByPartNoVersion`。
2. 再查 `drawingByPartNo`。
3. 命中后继续写 `sales_order_item.drawing_url`，同步 `has_drawing=true`。

其它报告字段、缺图列表、未匹配图纸逻辑沿用现有结构。

### 8.3 询价订单详情补传

目标文件：

```text
quote-backend/src/main/java/com/machining/quote/service/OrderManagementService.java
```

当前 `supplementDrawings(rfqId, drawings)` 按图号构建：

```java
Map<String, List<ItemQuoteVersion>> itemMap
```

本阶段扩展为：

```java
Map<String, List<ItemQuoteVersion>> itemMapByPartNo
Map<String, List<ItemQuoteVersion>> itemMapByPartNoVersion
```

处理规则：

- `versionDrawings` 只在 `itemMapByPartNoVersion` 中查找。
- `drawings` 仍只在 `itemMapByPartNo` 中查找。
- 命中后沿用现有补图逻辑：
  - 已有图纸跳过。
  - 缺图零件保存文件并写 `drawing_url`。
  - 返回 `boundItems` / `alreadyBoundItems` / `unmatchedDrawings` / `skippedFiles`。

### 8.4 销售订单详情补传

目标文件：

```text
quote-backend/src/main/java/com/machining/quote/service/SalesOrderManageService.java
```

改造方式与询价订单详情补传一致，只是目标实体为 `SalesOrderItem`：

- `versionDrawings` 按 `partNo||version` 查找。
- `drawings` 按 `partNo` 查找。
- 命中后沿用现有逻辑：
  - 已有 `drawing_url` 的销售订单零件跳过。
  - 缺图零件写 `drawing_url`。
  - 同步 `has_drawing=true`。

### 8.5 议价提单导入替换图纸

目标文件：

```text
quote-backend/src/main/java/com/machining/quote/service/InternalTargetLeadTimeService.java
```

当前替换逻辑已经支持 RFQ / 销售订单 / 混合来源，并按图号构建目标：

```java
Map<String, List<ReleaseDrawingTarget>> targetsByPartNo
```

本阶段新增：

```java
Map<String, List<ReleaseDrawingTarget>> targetsByPartNoVersion
```

处理规则：

- `versionDrawings` 按 `partNo||version` 精确查目标。
- `drawings` 按现有图号规则查目标。
- 命中后仍调用现有保存和替换逻辑：
  - RFQ：写 `item_quote_version.drawing_url`。
  - 销售订单：写 `sales_order_item.drawing_url`，同步 `has_drawing=true`。
  - 可变更判断、跳过逻辑、结果结构保持不变。
- 不依赖当前勾选零件，仍按当前选中订单范围全量匹配。

## 9. 日志、审计与权限

### 9.1 权限

不新增权限点，新入口沿用原入口权限：

| 场景 | 权限 |
|---|---|
| RFQ 导入图纸 | `market:rfq:upload-drawing` |
| 询价订单补传图纸 | `market:order:supplement-drawing` |
| 销售订单补传图纸 | `market:sales-order:supplement-drawing` |
| 议价提单替换图纸 | `market:release:create` |

### 9.2 操作日志

沿用现有操作日志事件，不新增事件类型。建议在摘要中补充计数：

```json
{
  "drawingMatchModes": {
    "partNo": 5,
    "partNoVersion": 3
  }
}
```

日志要求：

- 不记录文件内容。
- 不记录完整 multipart 请求体。
- 文件名可继续按现有摘要展示。
- 记录数量、命中数量、未匹配数量、跳过数量即可。

### 9.3 文件日志

沿用现有文件日志风格：

- 成功：记录订单 / 来源范围、上传数、命中数、绑定或替换数。
- 警告：记录未匹配数、跳过数。
- 失败：记录业务对象 id、上传数量、异常栈。

## 13. 风险与约束

- 图号本身可能包含 `_`，所以不能简单按第一个 `_` 切分，必须结合已知零件身份集合做最长前缀匹配。
- 版本本身可能包含 `-`，所以不能简单按第一个 `-` 切分版本，必须按已知 `partNo + "_" + version` 前缀匹配。
- 同一次上传同时使用两个入口时，精确匹配结果应优先，避免旧图号宽松匹配覆盖新图号+版本匹配。
- 前端两个入口的文件列表必须分开管理，避免用户误删或误提交。
- 后端必须兼容旧前端只传 `drawings` 的请求。
