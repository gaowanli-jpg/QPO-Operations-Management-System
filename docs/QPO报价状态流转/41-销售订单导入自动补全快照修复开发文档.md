# 41-销售订单导入自动补全快照修复开发文档

最后更新：2026-08-10

## 1. 背景与结论

本次问题来自销售订单直接导入链路：导入销售订单后，系统日志显示按 `图号 + 版本` 命中历史已提单 RFQ 零件，并自动生成销售订单来源提单行，但 `sales_order_item` 和 `order_delivery_ticket` 中的生产快照 JSON 仍为空，导致已提零件、工艺表、WMS/待产/锁库后续链路无法看到完整材料与工艺快照。

排查样例：销售订单 `sourceOrderId=56` 导入后，日志显示 `matched=10 / unmatched=0`、`ticketCount=10`，但 `processRouteCount=0`；数据库中 10 行 `sales_order_item.match_status = 已匹配`，并写入 `matched_rfq_id / matched_item_id`，同时生成 10 行 `order_delivery_ticket`。实际缺口是 `sales_order_item.material_data = {}`、`process_route = []`、`fee_data = []`，对应 ticket 也继承为空快照。

根因不是“没有匹配到历史件”，而是“匹配成功后未按空快照语义补全”：

- `sales_order_item.material_data / process_route / fee_data` 数据库默认值分别是 `{}` / `[]` / `[]`，导入后重新查询出来不是 `null`。
- `SalesOrderAutoSnapshotCompletionService.applyProductionSnapshot(...)` 只用 `== null` 判断是否补快照，导致 `{}` / `[]` 被当成已有真实快照，跳过历史快照复制。
- `DeliveryService.insertSalesOrderTicket(...)` 从 `sales_order_item` 生成 ticket；上游销售订单行为空快照时，ticket 也只会得到空快照。
- `ProcessRouteSnapshotService` 只完整支持 `String`、`Collection`、`Map`，未统一处理 `JsonNode` 等 JSON 对象形态，后续 JSONB 处理或测试夹具变化时仍可能复制成空数组。

本修复统一口径：销售订单直接导入命中历史已提单零件后，所有可补的生产快照字段在目标为空、空字符串、空 JSON、或导入默认占位值时都要补齐；销售订单自身事实字段不被历史 RFQ 覆盖；补齐后的销售订单行必须作为自动提单来源写入 `order_delivery_ticket`，并继续传递到 WMS、待产、锁库和工艺表。

## 2. 历史文档基线

### 2.1 重复件来源

`05-重复件匹配仅使用已提单历史零件开发文档.md` 和 `15-销售匹配模块开发文档.md` 确认：

- 匹配键只使用 `part_no + version`，不按客户过滤。
- 来源只查 `item_quote_version.status = 已提单`，或已经存在对应 `order_delivery_ticket.rfq_id + item_id` 提单行的历史零件。
- 同一 `part_no + version` 多条历史候选时取最新 `item_quote_version.id`。
- 历史候选应具备完整核价结果，至少包含 `tax_included_unit_price`、`material_data`、`process_route`。
- `order_delivery_ticket` 是不可逆发布记录和 MES/WMS 需求池，只用于判断历史零件是否曾生成提单，不作为生产快照来源。

### 2.2 销售订单补全职责

`15-销售匹配模块开发文档.md` 和 `33-销售订单导入即提单与异常治理重构开发文档.md` 确认：

- 新销售订单导入事务内自动执行历史快照补全，异常治理只作为历史订单或异常排查兜底入口。
- 补全只写 `sales_order_item`，不写 `order_rfq`，不新增 `item_quote_version`。
- 可补字段是生产快照字段：工程材料身份、材料形态、毛重/净重、核价模式、组合件类型、组装费、基础成本、`material_data`、`process_route`、`fee_data`、组合件关系、匹配追溯字段。
- 保护字段是销售订单事实：数量、交期、客户订单字段、`description`、`material_name`、`surface_treatment`、图纸、销售价格、`material_no` 等，不由历史 RFQ 覆盖。
- 自动提单允许销售价格为空；价格为空只阻断 U9 预览/同步，不阻断导入和进入已提零件。

### 2.3 订单默认信息与 Excel 描述

`35-销售订单导入订单级默认信息与零件级覆盖开发文档.md` 与当前前端描述保持一致：

- 必填表头：`图号`、`订单数量`、`版本`。
- 可选表头：`序号`、`下单日期`、`客户订单号`、`客户项目号`、`客户下单抬头`、`订单类型`、`内部项目号`、`客户交期`、`内部交期(给生产的交期)`、`描述`、`材料`、`表面处理`、`VAT单价-含税`、`未税单价(CNY)`、`（未税）金额`、`备注`。
- 订单级字段以下方“订单默认信息”为准；Excel 行内同名字段只作为零件级覆盖值，行内为空时继承订单默认信息。
- 日期支持 `2026-03-08`、`2026-3-8`、`2026.03.08`、`2026.3.8`、`2026/3/8`、`2026年3月8日` 和 Excel 日期序列号，例如 `46089`。
- 订单数量必须为正整数；`（未税）金额` 为空且未税单价存在时按未税单价乘以订单数量计算。

### 2.4 物料号与价格边界

`36-重复匹配复用MES已确认物料号并收窄已提零件MES去重开发文档.md` 确认：

- 历史来源只有同时满足 `material_no` 非空且 `material_no_status = 已确认` 时，才允许前置复制物料号确认元组。
- 来源未确认物料号不能阻断材料、工艺、费用、重量和组合件快照复用。
- 销售订单 U9 同步继续使用 `sales_order_item.material_no` 和 `sales_order_item.tax_included_unit_price`；未确认物料号或含税单价为空只阻断 U9，不回滚已提零件。

价格字段当前存在历史文档口径差异：RFQ 重复件文档强调普通重复件复用价格结果；销售订单异常治理文档明确保护销售订单价格，不从历史 RFQ 覆盖。为避免自动把历史报价误当销售订单商业价格，本修复默认不改变销售订单价格保护规则。若后续产品确认“销售订单价格为空时允许历史 RFQ 价格兜底”，应作为单独子任务同步修改 `15 / 33 / 34 / 37` 号文档、U9 提示和价格来源审计。

## 3. 当前代码偏差

### 3.1 空 JSON 被当作已有快照

相关文件：

- `quote-backend/src/main/resources/db/migration/V1__qpo_baseline_schema.sql`
- `quote-backend/src/main/java/com/machining/quote/service/SalesOrderQpoImportService.java`
- `quote-backend/src/main/java/com/machining/quote/service/SalesOrderAutoSnapshotCompletionService.java`

`sales_order_item` 表定义中：

```sql
material_data jsonb DEFAULT '{}'::jsonb,
process_route jsonb DEFAULT '[]'::jsonb,
fee_data jsonb DEFAULT '[]'::jsonb,
```

导入服务插入销售订单行时没有主动设置这三个字段。随后自动补全服务重新查询 `sales_order_item`，得到 `{}` / `[]` / `[]`，而 `applyProductionSnapshot(...)` 只判断 `item.getMaterialData() == null`、`item.getProcessRoute() == null`、`item.getFeeData() == null`。因此导入默认空 JSON 会阻止历史快照补齐。

### 3.2 工艺路线复制工具不够通用

相关文件：

- `quote-backend/src/main/java/com/machining/quote/service/ProcessRouteSnapshotService.java`

`copySnapshot(...)` 当前只稳定支持：

- JSON 字符串。
- `Collection<?>`。
- `Map<?, ?>`。

但 JSONB 字段经 MyBatis / Jackson / 测试夹具处理后可能出现 `JsonNode` 或其他 JSON 兼容对象。当前 `normalizeMap(...)` 遇到非 `Map` 对象会返回空 Map，导致路线被复制为空数组。即便主故障来自数据库默认空 JSON，本工具仍需要统一升级，防止后续同类快照丢失。

### 3.3 预览与应用的“可补字段”判断不一致

相关文件：

- `quote-backend/src/main/java/com/machining/quote/service/SalesOrderAutoSnapshotCompletionService.java`

`changedFields(...)` 中的 `materialSnapshotAvailable / processSnapshotAvailable / feeSnapshotAvailable` 同样只按 `current == null && source != null` 判断。导入自动补全会误以为 `{}` / `[]` 不是可补快照，不能暴露真实缺口。

### 3.4 自动提单只继承销售订单行现状

相关文件：

- `quote-backend/src/main/java/com/machining/quote/service/DeliveryService.java`

`insertSalesOrderTicket(...)` 当前设置：

```java
ticket.setProcessRoute(processRouteSnapshotService.copySnapshot(item.getProcessRoute()));
ticket.setMaterialData(item.getMaterialData());
ticket.setMaterialGrossWeight(item.getMaterialGrossWeight());
ticket.setPartNetWeight(item.getPartNetWeight());
```

因此若上一步补全失败，ticket 不会兜底回查历史 RFQ。这个方向本身正确：ticket 应从销售订单行复制最终快照，避免提单时再做不同口径的重复匹配。但前提是自动提单前必须确保销售订单行补全完成，并且 ticket 写入时对 JSON 做深拷贝，避免共享引用或对象形态转换导致空快照。

## 4. 修复目标口径

### 4.1 “可补”的统一定义

目标字段满足以下任一条件时视为缺失，可以从历史来源补齐：

- Java 值为 `null`。
- 字符串为空或全空白。
- JSON 字符串为空、`{}`、`[]`。
- `Map` 为空。
- `Collection` 为空。
- `JsonNode` 为 missing/null/empty object/empty array。
- 导入默认占位值：`quote_mode = NORMAL` 且来源为 `ASSEMBLY`，同时目标没有真实组合件快照或组合件关系。

来源字段满足以下条件才允许复制：

- 标量字段非空。
- JSON 快照不是空对象或空数组。
- 工艺路线至少包含一条有效工艺/费用行。
- 组合件关系必须能按当前销售订单 `part_no + version` 找到全部子件，才写入 `sales_order_item_assembly_relation`。

### 4.2 销售订单行补全字段矩阵

| `fee_data` | 历史费用 JSON | 目标缺失且来源非空 JSON | 必须深拷贝。 |
| `matched_rfq_id` | 历史 RFQ ID | 每次命中更新 | 追溯字段。 |
| `matched_item_id` | 历史 `item_quote_version.id` | 每次命中更新 | 追溯字段。 |
| `match_status` / `match_message` | 匹配结果 | 每次更新 | 不能因物料号未确认而失败。 |
| `assembly_relation_status` | 组合件关系重建结果 | 每次更新 | 关系完整才写关系表。 |

### 4.3 继续保护的字段

以下字段不由历史 RFQ 自动覆盖；如果销售订单行自身有值，自动提单应按现有字段映射带入 ticket 或 U9 链路：

- `qty`、`released_qty`、`remaining_qty`。
- `sales_order_date`、`customer_delivery_date`、`internal_delivery_date`。
- `customer_order_no`、`customer_project_no`、`customer_order_title`、`order_type`、`internal_project_no`。
- `description`、`material_name`、`surface_treatment`、`drawing_url`、`has_drawing`、`remark`。
- `tax_included_unit_price`、`tax_included_total_price`、`untaxed_unit_price`、`untaxed_total_price`。
- `material_no` 及确认元组，除非历史来源满足“已确认物料号”规则。

说明：`order_delivery_ticket` 当前没有价格字段。价格是否进入已提零件展示应通过页面/DTO 关联 `sales_order_item` 或单独设计 ticket 价格快照字段，不应在本修复中隐式改表。

### 4.4 物料号规则

保持现有 `ConfirmedMaterialNoReuseService` 规则：

- 来源 `material_no` 为空：不复制。
- 来源 `material_no_status != 已确认`：不复制。
- 目标为空且来源已确认：复制完整确认元组。
- 目标同值：幂等补齐元数据。
- 目标异值：拒绝覆盖，只记录物料号冲突，不阻断其他生产快照补全。

- 价格为空不阻断导入和自动提单；U9 预览继续阻断。

**新增测试：**

- 导入 Excel 只含必填列也能成功，空白价格不会导致服务器 500。
- `（未税）金额` 为空且 `未税单价(CNY)` 存在时，保存为 `未税单价 * 订单数量`。
- `VAT单价-含税` 存在时，`tax_included_total_price = VAT单价-含税 * 订单数量`。
- 日期字段三处都支持文案列出的格式。
- 命中历史已提单零件后，销售订单行和 ticket 都有非空生产快照。

## 7. 验收标准

### 7.1 功能验收

- 销售订单直接导入后，命中历史已提单零件的行不再停留在 `{}` / `[]` 空快照。
