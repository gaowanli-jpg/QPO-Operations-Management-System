# 销售订单直提流程方案讨论文档

最后更新：2026-07-30

## 1. 文档定位

本文档用于记录“销售订单直提”需求的当前理解、代码核查结论、推荐方向和后续待确认信息。

这不是最终开发文档，也不拆实施阶段。后续市场、工程、历史数据、Excel 模板、权限和日志口径继续补充后，再基于本文档整理正式开发文档。

后续维护约定：

- 每次围绕销售订单直提、U9 销售订单接口、销售订单导入模板、历史匹配规则或提单流程边界继续讨论后，都先回看本文档。
- 对话结束前，把新增理解、结论、待确认问题或已确认决策补回本文档。
- 本文档保留讨论痕迹和阶段性判断；正式实施前再沉淀为开发文档和阶段计划。

## 2. 需求背景

当前 QPO 主流程是：

1. 市场新单导入 RFQ 和零件。
2. 工程进行零件核价、维护材料和工艺。
3. 工程完成整单报价，订单进入 `已核价`。
4. 市场在报价处理模块保存报价单，订单进入 `已报价`。
5. 市场在议价提单模块选择已报价零件，生成正式提单和工艺表。

市场部提出的新场景是：部分老客户不走询价和报价流程，客户直接下单，业务本质更接近“销售订单”或“老产品复购”。这类订单不需要重新核价、重新写工艺、重新生成报价单，而是基于系统内已有资料直接进入提单。

初步命名：`销售订单`。

目标理解：

- 市场导入一种新的订单类型或新导入入口。
- 导入后订单和零件应直接处于可提单状态。
- 市场可在现有议价提单界面选择该订单并生成正式提单。
- 后续提单表据、已提零件、锁库零件、MES/WMS 等下游仍沿用现有提单结果。

### 2.1 最新补充：QPO 作为统一生产入口并同步 U9

进一步讨论后，销售订单直提不是单纯“在 QPO 里导入一个已报价订单”。它更接近一个统一业务入口：

1. 市场原来在 U9 财务 / ERP 系统里录入销售订单。
2. 生产相关流程在 QPO 里单独走提单、工艺表、已提零件、锁库等链路。
3. 新需求希望市场只在 QPO 录入一次销售订单数据。
4. QPO 一边向 U9 发送销售订单，生成或同步 U9 销售订单；另一边在 QPO 内部生成可进入议价提单的订单和零件。
5. 这样同一入口同时服务财务销售订单和生产提单流程。

系统定位理解：

- QPO 的本质仍是服务生产管理，越往后走，材料、工艺、图纸、交期、提单和锁库比价格更关键。
- QPO 仍承担部分价格相关功能，例如零件核价和报价单生成，但销售订单直提场景下，价格主要是为了满足销售订单和提单准入，不应把 QPO 改造成完整财务系统。
- U9 是正式财务 / ERP 销售订单系统，销售订单对账、财务口径和 U9 需要的销售字段以后要以 U9 接口文档为准。
- QPO 需要判断：U9 销售订单接口需要哪些输入，现有销售订单导入模板能不能同时满足 U9 和 QPO 的提单准入要求。

### 2.2 最新补充：U9 同步配置入口

2026-07-24 核对部署配置时发现：后端 `application.yaml` 已经从 `ERP_U9_*` 环境变量读取 U9 连接参数，但根目录 `erp.env` 和 `docker-compose.yml` backend 环境变量注入没有同步暴露这些配置项。

结论和处理方向：

- U9 销售订单同步需要在本地 `erp.env` 配置 `ERP_U9_BASE_URL`、`ERP_U9_USER_CODE`、`ERP_U9_ENT_CODE`、`ERP_U9_ORG_CODE`、`ERP_U9_CLIENT_ID`、`ERP_U9_CLIENT_SECRET`、`ERP_U9_CONNECT_TIMEOUT_MS`、`ERP_U9_READ_TIMEOUT_MS`。
- `erp.env.example` 只保留空占位和默认超时，不写真实密钥。
- `docker-compose.yml` 必须把同名变量注入 backend 容器，否则容器运行时仍然读不到 U9 配置。
- 这次补的是第一阶段“销售订单导入并同步 U9”的部署配置入口，不改变“当前阶段不创建 QPO 订单、不进入议价提单”的边界。

### 2.3 最新补充：导入模板下载

2026-07-24 确认新单导入中心需要在 `询价单` 和 `销售订单` 两个入口都提供 Excel 模板下载。模板由后端生成，第一张表直接放可导入表头，第二张表放字段说明，用颜色区分必填和选填字段。销售订单模板字段继续以 `SalesOrderExcelParser` 当前解析口径为准；模板下载权限沿用销售订单导入权限 `market:rfq:import-sales-order`。

### 2.4 最新补充：U9 实际录单由页面头字段和 Excel 明细组成

2026-07-30 补充：市场部人员当前在 U9 创建销售订单时，不是只上传一张 Excel 明细表。实际操作还会在 U9 页面输入或选择：

1. 单据类型。
2. 单号。
3. 客户。
4. 销售订单明细 Excel。

随后 U9 基于“页面头字段 + Excel 明细表”完成销售订单创建。

这个补充解释了为什么 U9 管理者提供给市场的销售订单模板，和 QPO 当前阶段实现的接口型模板不完全一致：

- U9 业务模板里没有强制出现 `客户编码`、`单据类型编码` 等字段，是因为这些信息在 U9 页面上由用户单独填写或选择，而不是在 Excel 每一行重复填写。
- QPO 当前阶段的销售订单模板，是为了直接构造 `SO_Create` 接口 DTO，所以把 `OrderBy`、`DocumentType`、`ItemCode` 等接口必填字段放进了 Excel。
- 如果 QPO 后续要贴合市场现有 U9 操作习惯，销售订单导入页面也应拆成“订单头输入区 + Excel 明细上传区”。
- 页面头输入区建议承载：客户、单据类型、单号 / 客户订单号等订单头字段。
- Excel 明细区建议兼容 U9 管理者模板字段：下单日期、客户订单号、客户项目号、客户下单抬头、订单类型、料号、内部项目号、客户交期、内部交期、图号、订单数量、已出数量、未出数量、描述、材料、表面处理、版本、含税 / 未税单价、金额、实际出货日期、备注。
- 后续正式设计应把页面输入字段优先映射到 U9 订单头，例如 `DocumentType`、`DocNo`、`OrderBy`；Excel 明细优先映射到销售订单行、计划行和 QPO 零件 / 提单快照。

待确认问题：

1. U9 页面“单号”是否对应接口 `DocNo`，QPO 是否应该传入；如果不传，是否由 U9 自动生成。
2. U9 页面客户选择背后给接口的是否就是 `OrderBy` 客户编码，QPO 是否已有客户名称与 U9 客户编码映射。
3. U9 页面单据类型显示值（例如“样品订单”）到接口 `DocumentType` 编码的映射来源。
4. U9 管理者模板中的 `料号` 是否就是接口 `ItemCode`；样例为空时，U9 是否通过图号、客户料号或其他主数据自动匹配料号。
5. QPO 页面里的“客户订单号”和 U9 页面“单号”是否是同一个业务概念，还是分别对应客户 PO 号和 U9 销售订单号。

### 2.5 最新补充：U9 同步应等待 QPO 零件取得物料号

2026-07-30 进一步确认：销售订单最终目标不是只把 Excel 发给 U9，也不是只在 QPO 中生成可提单订单，而是同一批销售订单数据要同时满足：

1. 能进入 QPO 现有主流程，形成订单、零件、提单、提单表据、已提零件和后续 MES/WMS 生产链路。
2. 能按 U9 `SO_Create` 要求创建正式销售订单。

关键变化是：U9 销售订单行需要物料号，而 QPO 当前物料号来源是 MES。现有 MES 物料号同步写回位置是 `order_delivery_ticket.material_no`，也就是提单行，而不是 `item_quote_version` 零件行。

因此后续销售订单直提的推荐同步时点需要调整为：

- 先在 QPO 创建销售订单型 `order_rfq` 和 `item_quote_version`，并按历史 `图号 + 版本` 补齐报价、工艺、材料、图纸、重量等可提单快照。
- 销售订单进入议价提单，生成 `order_delivery_ticket`。
- 对提单行触发或自动触发 MES 物料号获取，写回 `order_delivery_ticket.material_no`。
- 待需要同步 U9 的销售订单行都有物料号后，再组装 U9 `SO_Create` 请求并发送 U9。

这意味着阶段一“导入 Excel 后立即直接同步 U9”的实现，只适合 U9 明细 Excel 已经提供可用 `U9料号 / ItemCode` 的临时场景；如果最终以“QPO 先拿 MES 物料号”为准，则 U9 同步应成为提单 / MES 物料号之后的动作，而不是最初导入动作。

已确认编码口径：

- U9 `DocumentType` 单据类型编码固定使用 `SO01`。
- U9 `OrderBy` 客户编码来自现有客户资料，需要在 QPO 页面支持选择和输入。
- QPO 当前没有独立客户主数据表；现有“选择客户”主要从 `order_rfq.customer_name` 历史订单中 `DISTINCT` 去重，并受数据权限过滤。
- 后续建议先把客户资料能力扩充为独立客户主数据，不宜继续只依赖 `order_rfq.customer_name` 字符串。第一步客户主数据只维护客户编码、客户简称、客户名称；U9 单据类型和其他销售默认值后续在销售订单页面或单独字典中处理。

### 2.6 最新补充：先做客户主数据，再做销售订单单据类型输入

2026-07-30 进一步确认分步方案：

第一步先把整个 QPO 系统的客户能力升级为可维护客户主数据模块。新增独立客户表，字段暂定只保留三个核心字段：

1. 客户编码。
2. 客户简称。
3. 客户名称。

设计理解：

- 这三个字段都代表同一个客户，只是不同表达方式。
- 现有所有“选择客户”的地方，后续都应逐步改为以客户主数据表为来源，而不是从历史 `order_rfq.customer_name` 去重。
- 客户选择弹窗应支持按客户编码、客户简称、客户名称任一字段筛选。
- 用户选择任一客户后，前端和后端都能拿到同一条客户记录的三个字段，避免只保存一个字符串后丢失 U9 客户编码。
- 为兼容现有订单、权限和筛选逻辑，正式开发时需要设计历史 `customer_name` 数据如何映射到新客户主数据，以及新订单到底保存客户编码、客户简称、客户名称中的哪几个快照字段。

第二步再处理销售订单页面的单据类型编码：

- 销售订单页面支持手动输入单据类型编码。
- 同时支持从可维护选项中选择单据类型编码。
- 当前业务默认值为 `SO01`。
- 单据类型编码不需要混进 Excel 每一行，优先作为销售订单页面头字段进入 U9 `DocumentType`。

对应第一步开发文档：

- `docs/QPO报价状态流转/12-客户主数据模块开发文档.md`

### 2.7 阶段 5 更新：客户主数据已落地

2026-07-30 客户主数据阶段 1 到阶段 5 已完成收口。客户主数据模块已经落地，成为全系统客户选择的数据来源。

已落地边界：

- 客户主数据维护三字段：`customerCode`、`customerShortName`、`customerName`。
- `customerCode` 可作为后续 U9 `OrderBy` 来源。
- `customerName` 仍作为 QPO 订单筛选和数据权限兼容快照。
- 现有客户选择弹窗按客户编码、客户简称、客户名称筛选，选择后旧页面继续用 `customerName` 过滤订单和列表。
- 销售订单单据类型编码暂不进客户主数据，后续页面默认 `SO01`，并支持页面输入或选择。
- 本阶段仍不让销售订单进入议价提单；销售订单进入 QPO 提单生产链路继续作为第二步单独讨论。

### 2.8 最新补充：销售订单入口先进入 QPO 主流程，U9 同步后置

2026-07-30 进一步确认第二步方向：销售订单页面不应继续只做“导入并同步 U9”。原因是最终 U9 销售订单需要物料号，而 QPO 当前物料号是在提单后通过 MES 写回提单行，因此页面初始导入阶段无法稳定完成真实 U9 同步。

推荐把销售订单页改为“销售订单导入并创建 QPO 订单”：

- 页面头部选择客户，客户来自客户主数据；后续 U9 `OrderBy` 使用 `customerCode`，QPO 主流程继续保存 `customerName` 兼容现有筛选和数据权限。
- 页面头部输入 / 选择单据类型编码，默认 `SO01`；单据类型编码不再强制放入 Excel 每行。
- Excel 只承载销售订单明细和 QPO 建单所需行信息，例如客户订单号、客户项目号、内部项目号、图号、版本、数量、交期、描述、材料、表面处理、单价等。
- 导入成功后，系统分配新的 QPO `rfqNo`，创建 `order_rfq` 和 `item_quote_version`，订单来源标识为销售订单。
- 成功匹配并补齐历史报价、工艺、材料、图纸、重量等可提单快照的订单和零件进入 `已报价` 状态，并可在议价提单按现有规则选择。
- 不能只改状态；如果零件没有 `finalUnitPrice`、工艺材料快照或其他提单必要数据，应返回导入失败 / 待处理明细，不能强行置为 `已报价`。
- U9 同步改为后置动作：销售订单提单后获取 MES 物料号，再按客户编码、单据类型编码、提单行物料号和销售订单明细组装 U9 `SO_Create`。

按钮命名建议从 `导入并同步 U9` 调整为 `导入销售订单` 或 `创建销售订单`；U9 同步状态后续应作为提单 / 已提零件之后的独立同步能力展示，避免用户误以为初始导入已经完成 U9 生单。

### 2.9 最新补充：采用市场实际销售订单模板作为第一阶段导入模板

2026-07-30 查看市场提供的 `销售订单模版.xlsx` 后确认，销售订单导入第一阶段应改为按市场实际使用表导入，不再沿用当前 QPO 为 U9 `SO_Create` 临时设计的接口型模板。

市场实际模板表头为：

| 字段 | 第一阶段建议归属 |
| --- | --- |
| 序号 | 仅导入展示 / 错误定位，不入主表 |
| 下单日期 | 订单头或销售订单导入批次字段，当前 `order_rfq` 无对应字段 |
| 客户订单号 | 销售订单头 / 行快照字段，当前只在提单表 `order_delivery_ticket` 有字段，零件主表无字段 |
| 客户项目号 | 销售订单头 / 行快照字段，当前只在提单表 `order_delivery_ticket` 有字段，零件主表无字段 |
| 客户下单抬头 | 销售订单头字段，当前 `order_rfq` 无对应字段 |
| 订单类型 | 可映射 `order_rfq.order_type` / `item_quote_version.order_type` |
| 料号 | U9 / MES 料号候选字段，当前零件主表无字段；提单行有 `material_no` |
| 内部项目号 | 销售订单头 / 行快照字段，当前只在提单表 `order_delivery_ticket` 有字段，零件主表无字段 |
| 客户交期 | 可映射零件 `lead_time` 或新增客户交期字段 |
| 内部交期（给生产的交期） | 可映射零件 `internal_target_lead_time` |
| 图号 | 映射 `item_quote_version.part_no` |
| 订单数量 | 映射 `item_quote_version.qty` |
| 已出数量 | 当前订单 / 零件主表无字段，建议新增销售订单行快照字段 |
| 未出数量 | 当前订单 / 零件主表无字段；可由订单数量 - 已出数量计算，也建议保存导入快照 |
| 描述 | 映射 `item_quote_version.description` |
| 材料 | 映射 `item_quote_version.material_name`；历史匹配成功时可补 `engineering_material_name` / `material_data` |
| 表面处理 | 映射 `item_quote_version.surface_treatment` |
| 版本 | 映射 `item_quote_version.version` |
| VAT单价-含税 | 当前零件主表无字段，建议新增 `tax_included_unit_price`，并同步现有 `final_unit_price` 兼容字段 |
| 未税单价(CNY) | 当前零件主表无字段，建议新增 `untaxed_unit_price` |
| （未税）金额 | 当前零件主表无字段，建议新增 `untaxed_total_price`；含税总价用 `tax_included_total_price` 保存，可按含税单价 × 订单数量计算 |
| 实际出货日期 | 当前订单 / 零件主表无字段，建议作为销售订单行快照字段 |
| 备注 | 映射 `item_quote_version.remark` |

结论：

- 这张表已经包含含税单价、未税单价和未税金额，本质上可以作为“已报价零件”的价格来源；QPO 主表应补齐未税单价、未税总价、含税单价、含税总价四个字段。
- 第一阶段目标应是把销售订单接入 QPO 现有主流程：选择客户和单据类型编码后导入 Excel，生成新的 QPO `rfqNo`、`order_rfq` 和 `item_quote_version`。
- 导入成功的订单和零件可以进入 `已报价`，前提是至少写入含税单价 / 含税总价，并同步 `finalUnitPrice` 和 `finalTotalPrice` 兼容现有提单准入；历史重复件匹配只作为增强，用来补充工艺、材料结构、重量、图纸、组合件等生产快照。
- 如果历史匹配不上，不应阻断第一阶段建单；但这些零件后续提单 / 工艺表可能缺工艺和图纸，需要在导入结果中提示“价格已导入，生产快照未匹配”。
- 2026-07-30 继续确认：第一阶段优先补齐 `order_rfq` 和 `item_quote_version` 主表字段，而不是只放在独立侧表。原因是客户订单号、客户项目号、内部项目号、订单类型、价格、交期等字段后续会在议价提单页面作为默认值展示并允许修改，最终写入提单表。导入批次 / 明细表继续用于审计和结果追踪，不作为主流程唯一数据来源。

## 3. 当前代码核查结论

### 3.1 不能只改订单和零件状态

代码核查后结论明确：销售订单导入后，不能只是把订单状态和零件状态改成 `已报价`。

原因是议价提单当前有多层校验：

1. **订单状态门槛**
   - `QuoteStatusWorkflow.canGenerateDeliveryTicket(status)` 只允许 `已报价` 和 `部分已提单` 生成提单。
   - `已生成提单` 只允许进入查看，不允许继续生成。
   - `已核价` 会被提示先去报价处理模块保存报价单。

2. **零件可选门槛**
   - 候选零件行要求 `finalUnitPrice != null`。
   - 剩余可提数量必须大于 0。
   - 零件不能是已提单或历史已提单状态。
   - 前端 `canSelectItem()` 会看后端返回的 `canSelect`，后端也会再次校验。

3. **生成提单硬校验**
   - `DeliveryService.generateTickets()` 会再次检查订单状态。
   - 每个被提单零件必须有 `finalUnitPrice`。
   - 提单数量不能超过询价数量和剩余可提数量。

因此，如果只把状态改成 `已报价`，但零件没有 `finalUnitPrice`：

- 议价提单列表可能展示该订单。
- 零件会显示未报价或不可选。
- 即使绕过前端，后端生成提单也会失败。

### 3.2 提单和工艺表依赖零件快照

生成提单时，`order_delivery_ticket` 会从 `item_quote_version` 快照这些字段：

- 图号、版本、物料描述、数量。
- 材料名称、工程材料、表面处理。
- 交期、内部目标交期、开工日期、安排类型。
- 材料数据、工艺路线、毛重、净重。
- 普通件 / 组合件类型。

动态工艺表也是从提单行中的 `processRoute` 等字段生成。

所以销售订单如果希望提单表和工艺表完整，导入时不只需要单价，还应该尽量补齐历史材料、工艺、重量、组合件属性等核价快照。

## 4. 推荐方向

### 4.1 推荐方案：按历史已报价 / 已提单零件带出销售订单资料

推荐把销售订单理解为“基于历史成熟零件资料的直接销售”。

导入销售订单时：

1. 市场上传销售订单 Excel 和必要图纸。
2. 系统按 `图号 + 版本` 匹配历史已报价、部分已提单或已生成提单订单中的零件。
3. 匹配成功后，从历史零件复制关键快照到新销售订单零件：
   - `finalUnitPrice`
   - `finalTotalPrice`
   - `baseCost`
   - `materialData`
   - `processRoute`
   - `feeData`
   - `engineeringMaterialName`
   - `materialGrossWeight`
   - `partNetWeight`
   - `quoteMode`
   - `assemblyFee`
   - 其他提单和工艺表需要的字段
4. 新订单状态直接设为 `已报价`。
5. 成功匹配并补齐资料的零件状态设为 `已报价`。
6. 未匹配或资料不完整的零件不能直接提单，应进入异常结果或待处理区。

推荐原因：

- 最符合“老客户、老产品、直接下单”的业务语义。
- 不需要工程重复核价。
- 不需要市场重复走报价保存。
- 能保证议价提单、提单表据、工艺表、已提零件、锁库零件下游数据完整。
- 对现有状态流转侵入最小，本质是新增一种导入来源，导入后落到现有 `已报价 -> 提单` 流程。

### 4.2 次选方案：销售订单 Excel 自带销售单价

销售订单 Excel 直接提供销售单价，系统导入后写入：

- `finalUnitPrice`
- `finalTotalPrice = finalUnitPrice * qty`
- 状态置为 `已报价`

这种方案能解决提单生成的最低门槛，但仍有风险：

- 工艺表可能缺工艺路线。
- 材料、重量、组合件属性可能不完整。
- 后续 MES/WMS 或工艺表导出可能出现空字段。

如果采用此方案，也建议同时按 `图号 + 版本` 尝试匹配历史资料；Excel 单价只作为价格来源，历史零件作为工艺和材料来源。

### 4.3 不建议方案：只改状态

不建议导入后只写：

- 订单 `status = 已报价`
- 零件 `status = 已报价`

原因：

- 没有 `finalUnitPrice` 时无法提单。
- 没有 `processRoute` 时工艺表不完整。
- 没有材料和重量时提单表据、锁库或后续外部系统可能缺信息。
- 会把“可提单状态”和“资料完整状态”混在一起，后续排查困难。

## 5. 销售订单导入后的建议数据状态

### 5.1 订单状态

匹配成功且至少存在一个可提零件时：

- `order_rfq.status = 已报价`
- 可继续走议价提单生成正式提单。

如果整单没有任何零件匹配成功，建议不要创建为 `已报价`，而是：

- 导入失败并返回未匹配明细；或
- 创建为单独待处理状态。

是否需要新增“销售订单待确认”这类状态，暂不确定，后续讨论。

### 5.2 零件状态

匹配成功且资料完整：

- `item_quote_version.status = 已报价`
- `finalUnitPrice` 必须非空。
- `finalTotalPrice` 建议同步写入。
- `processRoute`、`materialData`、`quoteMode` 等尽量从历史零件复制。

匹配失败或缺关键资料：

- 不建议强行置为 `已报价`。
- 应在导入结果中明确展示原因，例如：
  - 未找到历史图号版本。
  - 找到历史零件但无最终单价。
  - 找到历史零件但无工艺路线。
  - 多个历史版本候选无法确定。

## 6. 可能的页面和入口形态

后续可讨论三种入口：

1. **新单导入页面新增“销售订单导入”模式**
   - 优点：复用客户选择、Excel 上传、图纸上传。
   - 缺点：新单导入页面语义会变复杂。

2. **新增独立模块“销售订单导入”**
   - 优点：业务边界清晰，权限和日志独立。

3. **订单管理里新增销售订单导入按钮**
   - 优点：入口靠近订单管理。
   - 缺点：导入流程较重，放在订单管理可能不够清晰。

当前倾向：如果销售订单后续规则复杂，建议独立模块或新单导入中的独立模式，不建议只在订单管理里塞一个按钮。

## 9. 与现有模块的关系

### 9.1 与报价处理

销售订单目标是跳过报价处理，不要求进入报价处理保存报价单。

但系统上仍必须满足“已报价”的数据条件：

- 订单状态是 `已报价`。
- 零件有最终单价。
- 交期和提单所需字段可用。

### 9.2 与议价提单

销售订单导入成功后，应能像普通 `已报价` 订单一样：

- 在议价提单订单选择中出现。
- 候选零件可分页展示。
- 支持导入表格选定。
- 支持多订单一起提单。
- 生成正式提单时按现有逻辑分组调用。

不建议为销售订单单独复制一套提单页面。

### 9.3 与提单表据

销售订单生成提单后：

- 提单行进入提单表据模块。
- 工艺表行仍从提单快照动态展示和导出。
- 不需要新增单独销售订单表据模块。

### 9.4 与历史订单 / 已提零件 / 锁库零件

销售订单生成提单后，下游应与普通订单一致：

- 历史订单可查看。
- 已提零件可进入需求池。
- 锁库零件可走 WMS 分配。
- MES 获取物料号和 WMS 锁库仍以 `order_delivery_ticket` 为需求来源。

### 9.5 与 U9 财务 / ERP 销售订单

U9 是销售订单的财务和 ERP 承载系统。QPO 销售订单直提流程需要与 U9 建立明确边界：

- QPO 负责市场统一录入、历史资料匹配、生产资料快照、提单和后续 MES/WMS 生产链路。
- U9 负责正式销售订单生成、财务销售口径、客户订单财务数据和后续 U9 内部流程。
- QPO 导入销售订单时，应尽量一次性采集 U9 销售订单接口和 QPO 提单所需字段。
- 如果字段只对 U9 有意义，应作为销售订单头 / 行的同步字段保存或透传，不应该影响 QPO 的提单工艺逻辑。
- 如果字段只对 QPO 生产有意义，例如图纸、工艺、材料、重量、内部目标交期，应进入 QPO 订单和零件快照，不一定发送给 U9，除非 U9 接口要求。
- 如果 U9 接口要求价格字段，QPO 必须明确价格来源：历史报价快照、销售订单 Excel 输入，或后续人工维护。
- QPO 不能因为 U9 同步成功就默认零件可提单；仍必须满足 QPO 内部 `finalUnitPrice`、剩余数量、工艺材料快照等准入条件。
- QPO 也不能因为 QPO 提单资料完整就默认 U9 可同步；仍必须满足 U9 接口必填字段和编码规则。

后续收到 U9 销售订单接口文档后，需要重点判断：

1. U9 销售订单头需要哪些字段。
2. U9 销售订单行需要哪些字段。
3. U9 是否要求物料编码，还是可以用图号 / 客户料号。
4. U9 是否要求客户编码、币种、税率、销售组织、部门、业务员、仓库等基础资料编码。
5. U9 是否要求单价、金额、税额、交期、收货地址等销售字段。
6. U9 接口返回什么单号、状态和错误信息，QPO 是否需要保存。
7. QPO 导入成功但 U9 同步失败时，订单应该如何处理。
8. U9 同步成功但 QPO 历史匹配失败时，是否允许销售订单存在但不能提单。

### 9.6 U9 `SO_Create` 接口初步整理

本次查看的 U9 页面为 `U9C OPENAPI / SO / SO_Create`。该页面是 Knife4j/Vue 动态文档，普通网页抓取只返回 JavaScript 外壳；本次通过浏览器渲染页面，并解析页面加载的 `U9COPENAPI.json` 得到接口结构。

接口基本信息：

- 接口名称：`SO_Create`
- 接口说明：创建 SO / 创建销售订单。
- 请求方法：`POST`
- 接口地址：`/webapi/SO/Create`
- 请求数据类型：`application/json`
- 请求体：销售订单 DTO 数组，即支持批量创建。
- 请求头：`token` 必填。
- 通用调用前置：先通过 U9 授权接口获取 token，业务接口调用时把 token 放在 Headers 中。

通用 U9 WebAPI 调用口径：

- U9 通用业务接口路径形态为 `U9访问地址/webapi/Controller/Method`。
- 获取 token 的接口示例为 `/u9c/webapi/OAuth2/AuthLogin`，需要 `userCode`、`entcode`、`orgcode`、`clientid`、`clientsecret`。
- `entcode`、`orgcode`、`userCode` 是关键上下文字段，需要 U9 实施顾问确认真实编码。
- `ResCode = 0` 只代表接口调用成功，不等于每一条业务数据创建成功。
- 批量传入时，各行或各单据成功失败互不影响；逐条结果在 `Data` 中返回，成功看 `m_isSucess` / `IsSucess`，失败原因看 `m_errorMsg` / `ErrorMsg`。
- `OtherID` 只是批量生单标识，通用说明里写明标准产品暂时不会把它记录到 U9 后台，所以 QPO 不能依赖 `OtherID` 作为 U9 持久追踪字段。

销售订单头主要字段：

- `ID`：ID，可空，有默认值。
- `OtherID`：第三方传入 ID，可用于本次批量请求结果对应。
- `DocNo`：单据编码，可空。
- `BusinessDate`：单据日期，可空。
- `OrderBy`：客户编码，OpenAPI required，文档描述不可为空。
- `Seller`：业务员编码，可空。
- `SaleDepartment`：部门编码，可空。
- `DocumentType`：单据类型编码，OpenAPI required，文档描述不可为空。
- `TC`：交易币编码，可空。
- `AC`：核币编码，可空。
- `ShipToSite`：收货位置编码，可空。
- `BillToSite`：立账位置编码，可空。
- `PayerCustomer`：付款客户编码，可空。
- `PayerToSite`：付款位置编码，可空。
- `BargainMode`：成交方式，可空；文档说明无默认值时传 `-1`。
- `ShippingPort` / `AimPort`：装运港 / 目的港，可空。
- `IsRollBack`：回滚。
- `AutoCreateSOM`：自动创建变更单。
- `AutoApproveSOM`：自动审核变更单。
- `DescFlexField`：扩展字段，含 `PrivateDescSeg1-30` 和 `PubDescSeg1-50`。
- `SOLineDTOList`：销售订单行，文档描述不可为空。
- `IsPriceIncludeTax`：是否价格含税。
- `Memo` / `MemoFor`：备注和备注用途。
- `ContextDTO`：上下文，可含企业编码、组织编码、用户编码等。
- `IsPeriodBeginSO`：是否期初订单。
- `ConfirmTermCode`：立账条件。
- `IsFillDoc`：是否补单。
- `TradePath`：贸易路径编码。

销售订单行主要字段：

- `ID` / `DocLineNo`：行 ID / 行号。
- `CustomerItemNo`：客户料号，文档描述不可为空。
- `CustomerItemName`：客户品名，文档描述不可为空。
- `ItemCode`：U9 料号，OpenAPI required，文档描述不可为空。
- `ItemVersion`：料品版本。
- `PriceList`：价表编码。
- `FreeType`：免费品类型，OpenAPI required；无默认值传 `-1`，赠品传 `0`，备损品传 `1`。
- `FreeReason`：免费品原因；无默认值传 `-1`。
- `Grade`：等级，默认 `-1`；传等级时计划行需要同步传值。
- `Project` / `Task`：项目编码 / 任务编码。
- `Manufacturer`：厂牌编码。
- `OrderByQtyTU`：销售数量。
- `OrderByQtyPU`：计价数量。
- `TU` / `PU`：销售单位编码 / 计价单位编码。
- `TBUToPBURate`：销售-计价换算率。
- `OrderPriceTC`：定价。
- `FinallyPriceTC`：最终价。
- `DiscountTC`：折扣额。
- `NetMoneyTC`：未税金额。
- `TaxMoneyTC`：税额。
- `TotalMoneyTC`：价税合计。
- `TaxSchedule`：税组合编码。
- `PriceSource`：价格来源，`0` 取价表，`1` 手工定价，`2` 部件，`3` 来源单据。
- `ShipTogetherFlag`：成套收发货标志，OpenAPI required；无默认值传 `-1`，成套传 `0`。
- `SOShiplineDTOList`：销售订单计划行，文档描述不可为空。
- `ShipToSite`：收货位置编码。
- `RecTermCode`：收款条件。
- `SupplyOrg`：供应组织编码。
- `SrcDocType` / `SrcDocNo` / `SrcDocLineNo` / `SrcDocSubLineNo` / `SrcDocLineID`：来源单据信息；当前描述支持手工创建、报价单、销售合同、预测订单。

销售订单计划行主要字段：

- `ID` / `DocSubLineNo`：计划行 ID / 行号。
- `ItemCode`：料号，文档描述不可为空。
- `RequireDate`：交期。
- `DeliveryDate`：承诺日期。
- `PlanDate`：计划出货日。
- `AffirmShipDate`：客户确认出货日。
- `ShipPlanQtyTU`：计划出货量（销售单位）。
- `ShipPlanQtyPU`：计划出货量（计价单位）。
- `TU` / `PU`：销售单位编码 / 计价单位编码。
- `TUBaseToPUBaseRate`：销售-计价换算率。
- `SupplySource` / `DemandTransformType` / `SupplyOrg` / `PlanOrg`：供应和计划相关编码。
- `Wh`：存储地点编码。
- `ShipToSite`：收货位置编码。
- `ShipMode`：出货方式，`1` 配送，`2` 自提。
- `Memo`：备注。

响应结构：

- `ResCode`：错误编码，`0` 标识接口调用成功。
- `Success`：接口成功标识。
- `ResMsg`：错误信息。
- `Data`：逐条业务结果数组。
- `Data[].m_isSucess`：该条业务数据是否成功。
- `Data[].m_otherID`：回传第三方标识。
- `Data[].m_iD`：U9 业务 ID。
- `Data[].m_code`：U9 业务编码，预计可作为 U9 销售订单号候选字段，需实测确认。
- `Data[].m_errorMsg`：该条失败原因。
- `Data[].m_datas`：附加数据。
- `Exception`：异常信息。

对 QPO 销售订单直提的影响：

- QPO 销售订单导入模板不能只考虑 QPO 提单字段，还要能得到 U9 需要的客户编码、单据类型、U9 料号、单位、数量、价格、计划行、税组合、币种等销售字段。
- 当前 QPO 的图号 / 版本不能直接等同于 U9 `ItemCode`，除非客户确认 U9 料号编码就是图号或存在稳定映射；否则需要新增“图号版本 -> U9 料号 / 版本 / 单位 / 税组合”等映射来源。
- `CustomerItemNo` 和 `CustomerItemName` 虽未在 OpenAPI required 中，但文档描述为不可为空，建议导入模板或映射结果中补齐。
- `SOShiplineDTOList` 文档描述不可为空，且计划行中也需要 `ItemCode`；因此 QPO 至少应按每个销售订单行生成一条计划行，数量与交期默认跟订单行一致。
- 如果 QPO 采用历史快照补齐工艺材料，也仍需要额外解决 U9 主数据编码问题，例如客户编码、业务员编码、部门编码、销售单位、计价单位、税组合、币种、收货位置等。
- `PriceSource = 1` 手工定价看起来适合 QPO 按历史报价或 Excel 单价向 U9 传价，但还需要 U9 实测确认是否只传 `OrderPriceTC` / `FinallyPriceTC` 即可，还是必须同步金额、税额、价税合计。
- U9 支持批量创建但逐条返回成功失败，所以 QPO 不能只看 HTTP 200 或 `ResCode = 0`；必须解析 `Data` 明细，按单据或按行记录同步结果。
- QPO 建议保存 U9 返回的 `m_iD`、`m_code`、`m_errorMsg` 和同步状态，便于市场查看、重试和运维排查。
- `OtherID` 可以传 QPO 的临时批次号、RFQ 号或内部请求行标识来对应返回结果，但不能作为 U9 后台持久字段依赖。

本次接口查看后的初步判断：

- 可以实现 QPO 统一入口同步 U9 销售订单，但前提不是“直接把现有 QPO 导入表发给 U9”，而是需要在 QPO 新增一层销售订单同步 DTO / 映射层。
- QPO 现有订单和零件导入字段可以覆盖一部分生产提单需要，但明显不足以覆盖 U9 销售订单创建所需主数据编码。
- 后续需要 U9 实施顾问或市场确认：客户编码、单据类型、业务员、部门、币种、单位、税组合、收货位置、U9 料号等字段从哪里来，是 Excel 输入、QPO 字典维护、客户默认配置，还是通过 U9 查询接口反查。
- 推荐把 U9 同步设计成独立状态：`未同步 / 同步成功 / 同步失败 / 待重试`，不要让 U9 同步成功直接代表 QPO 可提单，也不要让 QPO 可提单直接代表 U9 已成功。

## 11. 初步推荐的最终形态

当前推荐采用以下方向继续细化：

1. 销售订单作为一种新的订单导入流程，不改变议价提单主流程。
2. QPO 作为市场统一入口，一次导入后同时服务 U9 销售订单同步和 QPO 提单生产链路。
3. 导入时按 `图号 + 版本` 匹配历史已报价 / 已提单零件。
4. 匹配成功后复制历史核价快照，使新零件直接满足议价提单可选条件。
5. 导入成功的订单和零件进入 `已报价`，但前提是同时满足 QPO 提单准入数据要求。
6. 未匹配或资料不完整的零件明确返回导入报告，不强行置为可提单。
7. U9 同步字段、销售单号回写、失败重试和事务边界等待 U9 接口文档确认。
8. 提单生成、提单表据、已提零件、锁库零件沿用现有逻辑。
9. 权限、日志、数据权限按 QPO 主流程标准同步设计，避免只做前端入口。
10. U9 `SO_Create` 需要独立 DTO / 映射层；不能把 QPO 图号、版本、客户名直接当成 U9 料号、料品版本、客户编码使用，除非后续确认编码体系一致。

这条路线的核心原则是：

> 销售订单不是绕过系统校验，而是在导入时把“报价已完成所需的数据快照”补齐，然后复用现有已报价到提单的稳定流程。

补充原则：

> QPO 不替代 U9 的财务销售订单职责，而是成为市场录入和生产流转的统一入口；U9 需要的销售字段和 QPO 需要的生产字段要在导入阶段被明确区分、校验和同步。

## 12. 2026-07-24 最新阶段拆分决策

本次进一步确认：销售订单直提不一次性做完，先分两步走。

### 12.1 第一步：销售订单导入并同步 U9

第一步只做“在 QPO 里导入销售订单并直接传给 U9”的能力。

已确认口径：

- 入口放在市场 `新单导入` 页面下面。
- 子入口名称叫 `销售订单`。
- 用户上传销售订单 Excel。
- QPO 解析 Excel，构造 U9 `SO_Create` 请求。
- QPO 调用 U9 `POST /webapi/SO/Create` 创建销售订单。
- QPO 保存导入批次、U9 返回的 `m_iD`、`m_code`、`m_errorMsg` 和同步状态。
- 第一阶段不创建 QPO `order_rfq`。
- 第一阶段不创建 QPO `item_quote_version`。
- 第一阶段不把订单置为 `已报价`。
- 第一阶段不进入 `议价提单`。
- 第一阶段不复制历史工艺、材料、图纸和核价快照。

对应开发文档：

- `docs/QPO报价状态流转/11-销售订单导入与U9同步开发文档.md`

### 12.2 第二步：销售订单进入 QPO 提单生产链路

第二步后续再讨论：

- U9 同步成功后是否立即创建 QPO 内部订单。
- 如何按 `图号 + 版本` 匹配历史已报价 / 已提单零件。
- 如何复制历史单价、材料、工艺、重量、组合件等快照。
- 如何让销售订单进入 `已报价 -> 议价提单` 主流程。
- U9 同步状态和 QPO 提单状态如何并行展示。

当前推荐先让 U9 同步入口稳定，再开展第二步，避免 U9 主数据映射问题和 QPO 提单准入问题混在一个阶段里。

### 12.3 阶段 5 收口结论

阶段 1 到阶段 5 只完成销售订单导入并同步 U9，作为 QPO 市场 `新单导入` 页下的销售订单子入口。

已收口边界：

- 不创建 QPO `order_rfq`。
- 不创建 QPO `item_quote_version`。
- 不把订单或零件置为 `已报价`。
- 不进入 `议价提单`。
- 不复制历史工艺、材料、图纸、重量或核价快照。
- 权限使用 `market:rfq:import-sales-order`，不新增左侧模块。
- 操作日志使用 `SALES_ORDER_IMPORT_U9`，文件日志只记录批次摘要，不记录 token、密钥、完整 Excel 内容或完整 U9 请求体。

第二步再讨论销售订单进入 QPO 提单生产链路，包括历史快照匹配、可提单准入、QPO 内部订单生成、U9 同步状态和提单状态并行展示。

### 12.4 新阶段：销售订单先进入 QPO 主流程

根据市场后续补充，销售订单流程调整为“两步走”：第一步先按市场实际销售订单模板导入 QPO，创建 `order_rfq` 和 `item_quote_version`，订单和零件进入 `已报价` 状态，可被 `议价提单` 选中；第一步不调用 U9。第二步等提单后取得 MES 物料号，再设计 U9 销售订单同步。

本阶段价格追溯字段统一为 `untaxed_unit_price`、`untaxed_total_price`、`tax_included_unit_price`、`tax_included_total_price`；原 `final_unit_price` / `final_total_price` 继续作为现有页面、报价单导出和提单准入使用的含税兼容价。

销售订单导入进入 QPO 主流程的审计动作使用 `SALES_ORDER_IMPORT_QPO`，权限仍沿用 `market:rfq:import-sales-order`，不新增左侧模块，不复用 RFQ 普通导入权限。

### 12.5 最新决策：销售订单改为独立主表

2026-07-30 进一步复盘后，确认 12.4 的“创建 `order_rfq` 和 `item_quote_version`”方向不再继续实施。原因是销售订单和 RFQ 订单混入同一订单主表、零件主表后，会影响重复订单匹配、订单管理、零件核价历史、RFQ 数据权限解释和后续维护。

最新方向：

- 原 RFQ / 报价 / 议价提单主流程保持不动。
- 销售订单新增独立订单主表 `sales_order_header`。
- 销售订单零件新增独立明细表 `sales_order_item`，字段完整承载市场销售订单模板、价格、交期、图纸、材料工艺快照和 `material_no`。
- 销售订单导入不再创建 `order_rfq`。
- 销售订单导入不再创建 `item_quote_version`。
- 销售订单需要进入议价提单时，通过 `sourceType = RFQ / SALES_ORDER` 的来源适配层统一提供候选订单、候选零件和生成提单能力。
- 旧 `13-销售订单导入进入QPO主流程开发文档.md` 作为历史方案保留，但不再作为实施依据。
- 新实施依据为 `docs/QPO报价状态流转/14-销售订单独立主表开发文档.md`。

保留前期成果：

- 客户主数据继续复用，`customer_code` 后续仍可作为 U9 `OrderBy` 来源。
- 销售订单模板下载、权限 `market:rfq:import-sales-order`、U9 配置和低噪声日志规范继续保留。
- 已经加到 RFQ 主表上的销售订单字段如果已随迁移执行，后续代码停止写入和读取，稳定后再评估是否做数据库治理清理。
