# 销售变更通知模块

> 当前实现基线：V64。销售变更用于把已形成的 MES 生产工单或提库存工单的零件变化通知给下游；通知只传递信息，不直接修改下游工单。

## 1. 范围与业务规则

纳入通知池的事件：

- 已下发 MES 生产工单的销售订单零件发生非价格字段修改。
- 已下发提库存工单的销售订单零件发生非价格字段修改。
- 已下发的零件执行关联废弃或关联恢复。
- 订单级关联废弃、恢复按零件行逐条生成通知，并沿用订单级输入理由。

不进入通知池：

- 已提零件与获取物料号流程。
- 尚未形成生产工单或提库存工单的 Allocation。
- 只有 WMS 库存锁定，没有后续生产或提库存工单的 Allocation。
- 仅修改未税单价、含税单价、价格金额或其他名称包含 `price` 的字段。
- 保存时字段值没有实际变化。
- 新建订单、追加新零件、预览操作。

修改通知只记录非价格变化。废弃、恢复通知各自独立保留，不与修改通知合并。废弃和恢复理由必填，去除首尾空格后长度为 1 至 500；修改通知理由为空。

## 2. 下游工单判定与定位

每个销售订单零件可以对应多个 Allocation 和多个下游工单；每个“零件 + 下游工单”目标各生成一条通知。

| 下游类型 | 目标来源 | 活跃判定 |
| --- | --- | --- |
| `PRODUCTION` | `PRODUCTION_REQUIRED` Allocation 的 `mesProductionExternalId`（MES 响应 `items[].id`）；批次号来自 MES 生产批次行及批次表 | MES 成功、提交中、处理中、结果未知、收到响应待应用或本地应用失败，或者已经有外部工单号 |
| `STOCK_PICKING` | `IN_STOCK_LOCK` / `IN_PRODUCTION_LOCK` Allocation 的 `stockPickingExternalId`（MES 响应 `items[].id`）与 `stockPickingBizId` | 提库存工单已成功、提交中、处理中、结果未知或本地应用失败，或者已经有外部工单号 |

工单定位优先级：

1. `targetExternalId`：生产工单使用 MES 返回的工单 `id`，提库存工单使用 MES 返回的任务 `id`；QPO 两个 `*_external_id` 字段只保存该 `id`，不使用 `planNo` 或 `productOrder`。
2. 外部工单号尚未回写时，使用 `sourceBizId + salesOrderNo + saleOrderItemNo` 回溯原始下发批次和行。
3. `saleOrderItemNo` 是 `sales_order_item.line_no`，不是数据库主键。
4. `allocationId` 仅供 QPO 内部追踪；`bizId` 仅代表一次批量通知请求。
5. QPO 无法取得外部工单号时，内部 `targetKey` 使用 `ALLOCATION:{allocationId}`，此值不作为 MES 内部工单主键。

明确失败且没有外部工单号的 Allocation 不生成通知。收到销售变更后，MES 以 `targetExternalId` 或回溯组合定位原工单；不得按物料号、图号或数组位置匹配。

## 3. 通知生成入口

通知在销售订单零件写入事务中生成，事务失败时通知也回滚。所有入口复用目标解析和通知快照逻辑：

- 销售订单详情的零件批量保存。
- 销售订单详情的整单字段替换确认。
- U9 页面零件保存。
- U9 页面表格替换确认。
- 订单头字段传播后，只有实际被改动的既有零件行生成通知。
- 零件级和订单级关联废弃、关联恢复。

表格预览不产生通知。单独价格修改不会生成通知；混合价格和普通字段修改时，只记录普通字段。数量变更先完成现有 Allocation 数量兼容同步，再生成通知。关联废弃、恢复在清理或恢复 Allocation 状态前批量解析目标，以免丢失原工单定位信息。

修改通知按“销售订单零件 + 下游类型 + targetKey”合并未发送的 `PENDING` 项：快照更新为最新零件数据，`changedFields` 合并此前字段与本次字段，`noticeId` 保持不变。进入 `SENDING`、`SENT`、`FAILED` 或 `RESULT_UNKNOWN` 后不再合并；后续修改生成新通知。数据库部分唯一索引保证同一零件和目标最多有一条待发送修改通知，业务保存入口锁定订单/零件行来串行化同一零件的并发修改。

关联废弃和恢复按事件独立生成。失败或结果未知通知重试使用原 `noticeId` 和原快照，保证下游幂等。

## 4. 通知快照与隐私边界

通知快照包括销售订单号、销售订单行号、Allocation 追踪号、下游类型和工单定位字段、变更类型、变更字段、理由，以及变更发生时的零件业务数据。零件快照可包含图号、版本、物料号、数量、项目号、交期、材料、工艺、描述、备注、制造加工类型及备用字段。

不写入通知快照或审计日志：价格、图纸 URL、Token、Authorization、Cookie、认证凭据、完整外部请求或完整外部响应。历史通知快照不随销售订单后续编辑而改变。

## 5. 数据库结构

V64 新建：

- `sales_order_change_notice`：通知快照、目标工单、发送状态、尝试次数、自动模式批次、操作人和时间。
- `sales_order_change_dispatch_setting`：固定单例 `id = 1`，保存发送模式、自动批次编号和自动模式生效时间，默认 `MANUAL`。

V64 删除已退役的本地销售变更主表和明细表；V55/V56 的 `sales_order_linked_change_notice` 关联废弃/恢复通知历史快照继续保留。

通知状态为 `PENDING`、`SENDING`、`SENT`、`FAILED`、`RESULT_UNKNOWN`。V65 在通知行增加软隐藏状态、隐藏理由和最近恢复信息；隐藏不改变通知状态、业务数据或下游工单。`notice_id` 有唯一索引；待发送 `MODIFY` 按零件和目标建立部分唯一索引；状态时间、订单零件目标和事件键有查询索引。

Flyway 迁移只追加，不修改历史迁移。历史旧表数据按本次确认要求删除，不转换为新通知；新通知只反映 V64 生效后的新业务事件。

## 6. 数据中心与 MES 接口

QPO 通过数据中心调用 MES，不直连 MES：

```text
endpointCode: MES_SALES_ORDER_CHANGE_NOTICE
method: POST
path: /api/v1/mes/openapi/sales-order/change-notice
```

请求结构：

```json
{
  "bizId": "QPO-SOC-20261019-000001",
  "items": [{
    "noticeId": "QPO-SOCN-01J...",
    "changeType": "MODIFY",
    "targetType": "PRODUCTION",
    "targetExternalId": "1001",
    "sourceBizId": "QPO-PROD-20261019-000001",
    "salesOrderNo": "SO-001",
    "saleOrderItemNo": "1",
    "allocationId": 1001,
    "changedFields": ["qty", "internalDeliveryDate"],
    "reason": null,
    "item": {
      "partNo": "P-001",
      "version": "A",
      "materialNo": "MAT-001",
      "qty": 10,
      "internalProjectNo": "IP-001",
      "customerOrderNo": "CO-001",
      "customerProjectNo": "CP-001",
      "materialName": "钢板",
      "processRoute": [],
      "remark": "备注"
    }
  }]
}
```

MES 按 `noticeId` 幂等去重，且逐条回传原始 `noticeId`：

```json
{
  "code": "0",
  "msg": "success",
  "data": {
    "bizId": "QPO-SOC-20261019-000001",
    "items": [{
      "noticeId": "QPO-SOCN-01J...",
      "status": "ACCEPTED",
      "targetExternalId": "1001",
      "message": "accepted"
    }]
  }
}
```

每次批次可生成新的 `bizId`；网络重试时 `noticeId` 与快照不变。明确拒绝写为 `FAILED`；超时或网络结果不确定、响应无法解析、回执缺失/重复/不匹配时写为 `RESULT_UNKNOWN`。QPO 不按数组顺序推测回执对应行。

## 7. 手动与自动发送

- 默认 `MANUAL`。手动模式允许批量认领 `PENDING`、`FAILED` 和 `RESULT_UNKNOWN` 通知。
- `AUTO` 模式自动认领当前 `auto_dispatch_epoch` 的新 `PENDING` 通知；调度任务每 5 秒批量认领，单批最多 100 条，再交给现有异步任务池。
- 从手动切到自动时递增 `auto_dispatch_epoch`。切换前的积压不会自动发送；旧待发送记录在切换后再次发生修改时，快照和自动批次更新为当前批次，因此该新变化可自动发送。
- 自动模式允许人工发送早于当前自动批次的积压 `PENDING`，也允许重试 `FAILED` 和 `RESULT_UNKNOWN`；当前自动批次的 `PENDING` 由调度器处理，避免操作员与自动任务重复认领。
- 从自动切回手动后，新通知的自动批次设为 0，等待人工发送。
- 数据库行锁、`FOR UPDATE SKIP LOCKED` 和状态条件更新防止同一通知被多个任务认领。

批量发送以异步 `SystemTask` 执行，不在销售订单保存事务中等待数据中心或 MES。任务提交失败将已认领记录恢复为 `FAILED`；调用超时按数据中心返回的失败确定性更新状态。

## 8. API 与权限

基础路径：`/api/change/sales-order-changes`

| API | 用途 | 权限 |
| --- | --- | --- |
| `GET /` | 分页和筛选通知池 | `change:sales-change:view` |
| `GET /{noticeId}` | 通知详情和历史快照 | `change:sales-change:view` |
| `GET /customers` | 客户筛选选项 | `change:sales-change:customer-select` |
| `POST /batch-send` | 批量异步发送或重试 | `change:sales-change:send` |
| `POST /batch-hide` | 批量隐藏可见的待发送、失败或结果未知通知；理由必填 | `change:sales-change:hide` |
| `POST /batch-restore` | 批量恢复已隐藏通知；恢复理由可选 | `change:sales-change:restore` |
| `GET /settings` | 读取发送模式 | `change:sales-change:view` |
| `PUT /settings/mode` | 切换手动/自动 | `change:sales-change:mode-update` |

查看与客户选择权限授予 `SUPER_ADMIN`、`MARKET_USER`、`MARKET_MANAGER`、`READONLY`；发送与模式修改授予前三种角色。后端 `@RequirePermission` 是最终校验。通知列表、详情及认领查询均应用销售订单数据范围；无范围时不返回数据。

前端路由 `/sales-changes`，菜单“变更 > 销售变更”。通知池有“有效通知”“已隐藏”“已发送”三个视图，支持客户、销售订单号、行号、变更类型、下游类型、状态和时间筛选，支持分页、批量选择、发送模式切换和快照详情。有效视图允许批量发送或带必填理由隐藏；隐藏视图允许批量恢复；已发送视图只读。隐藏通知不能被手动或自动认领。恢复只重新显示通知，自动模式下不会自动发送恢复的积压；操作员可手动发送。新修改合并到隐藏的待发送 `MODIFY` 通知时保留 `noticeId` 和隐藏理由、刷新快照并自动重新显示，再按当前自动批次规则处理。

## 10. 回归验收

- 非价格修改能按已形成的生产和提库存工单目标生成通知；一个零件有两类目标时生成两条。
- 未形成工单、仅有 WMS 库存结果、明确失败且无外部工单号时不生成通知。
- 保存、整单替换、U9 保存、U9 替换、订单默认传播和订单/零件关联废弃恢复均接入；预览和新建不生成通知。
- 未发送修改可合并，快照取最新数据且字段集合累积；发送后或失败/未知后再修改会生成新通知。
- 价格单独修改不生成通知；价格与其他字段混合修改时只保留非价格字段。
- 自动切换前积压不会自动发送，但可由操作员手动发送；切换后新修改进入当前批次并自动发送；自动模式下当前批次的待发送项不可手动抢占，失败和结果未知项可手动重试。
- MES 回执按 `noticeId` 匹配；缺失、重复或多余回执进入 `RESULT_UNKNOWN`；重试复用原 `noticeId` 和快照。
- 权限、数据范围、操作审计、异步任务状态与前端菜单/路由一致。
- `V1`、`V2` 及其他历史迁移不修改；`git diff --check`、后端测试、前端测试和构建通过。
