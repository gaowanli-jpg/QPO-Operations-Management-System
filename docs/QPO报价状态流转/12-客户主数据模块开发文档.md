# QPO 客户主数据模块开发文档

最后更新：2026-07-30

## 1. 背景

当前 QPO 的“选择客户”不是来自独立客户主数据表，而是从历史订单表 `order_rfq.customer_name` 做 `DISTINCT` 去重后得到。这个方式能支撑早期询价、核价、报价和提单流程，但已经不能满足销售订单直提与 U9 同步的后续要求。

本次确认的第一步目标是：先把整个系统的客户能力升级为一个可维护的客户主数据模块。客户表只维护三个业务字段：

1. 客户编码。
2. 客户简称。
3. 客户名称。

这三个字段代表同一个客户的不同表达。后续现有客户选择能力都应以该客户主数据为来源；用户可以按任一字段筛选并选择客户，选中后系统能拿到同一客户的三个字段。

## 2. 目标

- 新增客户主数据表，作为 QPO 全系统客户选择的数据源。
- 新增客户资料维护页面，支持新增、编辑、删除未引用客户。
- 改造现有客户选择弹窗，展示客户编码、客户简称、客户名称三列。
- 支持按客户编码、客户简称、客户名称筛选客户。
- 保留现有各模块客户选择权限边界，不新增可分配 `common:*` 权限。
- 保持现有订单、提单、核价、报价、数据权限流程不回退。

## 3. 非目标

- 本阶段不实现销售订单直提。
- 本阶段不调整 U9 销售订单同步时点。
- 本阶段不维护单据类型编码；单据类型编码在销售订单页面后续支持输入和选择，默认 `SO01`。
- 本阶段不引入币种、税组合、收货位置、业务员、部门等 U9 默认字段。
- 本阶段不把现有订单数据范围从 `customer_name` 切换为客户编码。
- 本阶段不批量改写历史 `order_rfq.customer_name`。

## 4. 当前代码核查

### 4.1 客户来源

当前客户选择来源主要是：

- `OrderManagementService.listCustomers()` 查询 `order_rfq.customer_name` 去重。
- 市场、报价处理、议价提单、零件核价、订单管理、历史订单、提单表据等模块通过各自的客户选择接口复用该结果。
- `CustomerPickerDialog.vue` 当前接收字符串数组，并在前端按客户名称 / 代码做本地过滤。

### 4.2 数据权限

当前数据权限中的指定客户仍按客户名称匹配：

- `system_role_data_scope_customer.customer_name`
- `order_rfq.customer_name`
- `DataScopeService` 根据 `customer_name` 拼接数据范围条件。

本阶段为了降低风险，数据权限仍保存和匹配客户名称；客户主数据模块只是成为可维护客户来源。

## 5. 总体方案

推荐方案：新增客户主数据表，并把客户选择弹窗升级为“客户主数据选择器”。

### 5.1 模块位置

新增左侧入口：

- 分组：`系统`
- 菜单：`客户资料`
- 路由：`/customers`
- 组件：`CustomerManage.vue`

原因：

- 客户主数据影响市场、工程、订单、提单、销售订单和数据权限，不属于单一市场页面。
- 超级管理员需要治理该数据。
- 市场主管需要维护客户资料，可以通过权限单独授权。

### 5.2 表字段

业务字段只保留三个：

| 字段 | 建议数据库列 | 说明 |
| --- | --- | --- |
| 客户编码 | `customer_code` | 后续映射 U9 `OrderBy`。 |
| 客户简称 | `customer_short_name` | 业务常用简称。 |
| 客户名称 | `customer_name` | 当前 QPO 订单和数据权限仍使用的客户名称。 |

技术字段建议保留：

- `id`
- `created_at`
- `updated_at`

说明：用户可维护和业务理解的字段只有三个；`id` 和时间戳用于数据库主键、审计、排序和前端行操作。

### 5.3 唯一性

建议三个业务字段都要求非空并唯一：

- `customer_code` 唯一。
- `customer_short_name` 唯一。
- `customer_name` 唯一。

如果后续发现客户简称可能重复，再单独调整简称唯一性。本阶段先按“任一表达都能唯一选中一个客户”的规则实现。

### 5.4 历史数据初始化

迁移脚本从历史订单中初始化客户主数据：

```sql
SELECT DISTINCT TRIM(customer_name)
FROM order_rfq
WHERE customer_name IS NOT NULL AND TRIM(customer_name) <> '';
```

初始化规则：

- 对每个历史客户名生成一条 `customer_master` 记录。
- 初始 `customer_code`、`customer_short_name`、`customer_name` 可先同值，保证现有选择客户列表不突然变空。
- 后续由管理员或市场主管在客户资料页逐步修正客户编码和客户简称。
- 初始化不改写历史订单，不级联更新提单、已提零件或锁库零件快照。

## 6. 权限设计

### 6.1 新增权限

| 授权能力 | 权限编码 | 类型 | 推荐默认角色 | 说明 |
| --- | --- | --- | --- | --- |
| 客户资料 | `system:customer:view` | `MENU` | `SUPER_ADMIN`, `MARKET_MANAGER` | 控制左侧客户资料入口和列表查询。 |
| 新增客户 | `system:customer:create` | `BUTTON` | `SUPER_ADMIN`, `MARKET_MANAGER` | 新增客户主数据。 |
| 编辑客户 | `system:customer:update` | `BUTTON` | `SUPER_ADMIN`, `MARKET_MANAGER` | 修改客户编码、简称、名称。 |
| 删除客户 | `system:customer:delete` | `BUTTON` | `SUPER_ADMIN`, `MARKET_MANAGER` | 仅允许删除未被订单或数据权限引用的客户。 |

### 6.2 现有选择客户权限

不新增 `common:customer:select`。

现有模块级客户选择权限继续保留，例如：

- `market:rfq:customer-select`
- `market:quote-process:customer-select`
- `market:release:customer-select`
- `market:delivery-document:customer-select`
- `market:order:customer-select`
- `market:history-order:customer-select`
- `market:delivered-item:customer-select`
- `market:locked-item:customer-select`
- `engineer:setup:customer-select`

这些接口的后端权限不变，只把数据源从 `order_rfq.customer_name` 切换到客户主数据表。

## 7. 日志设计

客户主数据维护是关键基础数据写操作，需要写操作日志和低噪声文件日志。

### 7.1 操作日志动作

| 动作编码 | 中文动作 | 模块 | targetType |
| --- | --- | --- | --- |
| `CUSTOMER_MASTER_CREATE` | 新增客户资料 | `SYSTEM` | `customer_master` |
| `CUSTOMER_MASTER_UPDATE` | 更新客户资料 | `SYSTEM` | `customer_master` |
| `CUSTOMER_MASTER_DELETE` | 删除客户资料 | `SYSTEM` | `customer_master` |

记录摘要：

- `customerId`
- `customerCode`
- `customerShortName`
- `customerName`
- 编辑前后只记录三个业务字段。

不记录内容：

- 不记录完整请求头。
- 不记录 token、Authorization header、Cookie。
- 不为普通客户列表查询写操作日志。

### 7.2 文件日志

建议 INFO 级别只记录写操作摘要：

- `Customer master created customerId={} customerCode={}`
- `Customer master updated customerId={} customerCode={}`
- `Customer master deleted customerId={} customerCode={}`

列表、搜索、选择客户属于高频读取，不新增业务 INFO。

## 8. 后端设计

### 8.1 数据库迁移

新增迁移：

- `V61__customer_master.sql`

内容：

- 新建 `customer_master`。
- 建唯一索引。
- 从历史 `order_rfq.customer_name` 初始化客户资料。
- 新增权限点并授权默认角色。

建议表结构：

```sql
CREATE TABLE IF NOT EXISTS customer_master (
    id BIGSERIAL PRIMARY KEY,
    customer_code VARCHAR(200) NOT NULL,
    customer_short_name VARCHAR(200) NOT NULL,
    customer_name VARCHAR(200) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### 8.2 后端类

新增：

- `CustomerMaster.java`
- `CustomerMasterMapper.java`
- `CustomerMasterController.java`
- `CustomerMasterService.java`
- `CustomerMasterReq.java`
- `CustomerMasterDTO.java`
- `CustomerOptionDTO.java`

### 8.3 管理接口

路径前缀：`/api/system/customers`

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/api/system/customers` | `system:customer:view` | 分页查询客户资料。 |
| `POST` | `/api/system/customers` | `system:customer:create` | 新增客户。 |
| `PUT` | `/api/system/customers/{id}` | `system:customer:update` | 编辑客户。 |
| `DELETE` | `/api/system/customers/{id}` | `system:customer:delete` | 删除未引用客户。 |

查询参数：

- `keyword`
- `field`：`all` / `code` / `shortName` / `name`
- `page`
- `pageSize`

### 8.4 选择接口

现有各模块客户选择接口不改权限，但返回结构建议升级为客户对象：

```json
{
  "id": 1,
  "customerCode": "C0001",
  "customerShortName": "GSQ",
  "customerName": "某某科技有限公司"
}
```

兼容策略：

- 后端统一通过 `CustomerMasterService.listOptions(field, keyword)` 获取客户选项。
- 前端 `CustomerPickerDialog` 支持对象结构。
- 旧页面选择后默认继续使用 `customerName` 作为查询和保存字段。
- 新销售订单页面后续可直接使用 `customerCode` 作为 U9 `OrderBy`。

### 8.5 删除校验

删除客户前必须检查：

- `order_rfq.customer_name = customer_master.customer_name`
- `system_role_data_scope_customer.customer_name = customer_master.customer_name`
- 其他使用客户名称快照的表，如提单、已提零件、锁库零件只作为历史快照，不建议作为删除硬拦截的第一优先级。

建议第一版只允许删除完全未被订单和数据权限引用的客户；被引用客户需要通过编辑修正，不允许物理删除。

## 10. 数据兼容

### 10.1 历史订单

历史订单仍保留 `order_rfq.customer_name` 快照。

新增客户主数据后：

- 历史订单不被迁移修改。
- 历史客户名会初始化为客户主数据。
- 用户后续编辑客户主数据，不自动改写历史订单客户名。

### 10.2 数据权限

本阶段数据权限继续按客户名称匹配。

角色管理中的“指定客户”选项应来自客户主数据表，但保存到 `system_role_data_scope_customer.customer_name` 时仍保存 `customerName`。

后续如果要升级为客户编码数据权限，应另开阶段设计，避免影响当前权限安全边界。

### 10.3 销售订单衔接

本阶段完成后，销售订单页面可以在下一步复用客户选择器：

- 页面展示客户编码、客户简称、客户名称。
- 选择客户后取 `customerCode` 作为 U9 `OrderBy`。
- 取 `customerName` 作为 QPO 订单客户快照。
- 单据类型编码独立输入或选择，默认 `SO01`。

## 13. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 历史订单只有 `customer_name`，没有客户编码 | 迁移时先以历史客户名初始化三字段同值，再由业务人员维护真实客户编码。 |
| 客户名称修改影响数据权限理解 | 本阶段不级联修改历史订单；数据权限仍按订单客户名称快照匹配。 |
| 各模块客户选择接口很多 | 保留模块级权限和接口路径，只替换底层数据源和返回结构。 |
| 前端旧调用方期望字符串 | 统一改造 `CustomerPickerDialog` 和调用方，旧页面显式取 `customerName`。 |
| 销售订单需要客户编码 | 本阶段提供客户编码字段，下一步销售订单页面直接复用。 |

## 14. 完成标准

- 客户资料成为全系统客户选择来源。
- 客户资料页面具备独立权限和操作日志。
- 所有现有客户选择页面仍能正常工作。
- 数据权限不泄露、不扩大范围。
- 不新增可分配 `common:*` 权限。
- 文档、测试和构建全部通过。
