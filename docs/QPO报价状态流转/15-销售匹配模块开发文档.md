# QPO 销售匹配 / 异常治理模块开发文档

最后更新：2026-08-06

> 2026-08-07 价格字段收口：异常治理预览和历史候选只使用 `tax_included_unit_price`、`tax_included_total_price` 等正式价格字段；`final_*` 不再作为当前字段。普通列表、详情和预览是只读操作，不写操作日志。

> 阶段 7 最新口径：页面显示名称已改为 **异常治理**，路由 `/sales-match` 和权限 code 继续保留 `market:sales-match:*`。新销售订单导入事务已经自动执行补全并自动提单，异常治理不作为新销售订单日常流程入口，只用于排查历史销售订单或导入自动补全异常。

## 1. 背景与结论

`14-销售订单独立主表开发文档.md` 已确认销售订单使用独立主表 `sales_order_header` 和独立零件表 `sales_order_item`，不再写入 RFQ 主表 `order_rfq`，也不再新增 `item_quote_version` 零件记录。

销售订单导入后仍需要尽量复用历史已提单零件的生产快照，例如真实材料、材料形态、工艺、重量和组合件信息。这个动作本质不是“创建 RFQ”或“进入 RFQ 核价流程”，而是对销售订单零件的一次空缺生产信息补全。当前主链路已经在导入事务内自动完成该补全；本模块保留为异常治理兜底入口，用于历史订单、补全失败或运维排查。

```text
市场
  新单导入
  异常治理
  报价处理
  议价提单
```

核心结论：

1. 当前模块显示名称为 **异常治理**，历史文档和代码中的“销售匹配”均指同一路由 `/sales-match`。
2. 左侧边栏放在 **新单导入** 和 **报价处理** 之间。
3. 异常治理只能选择销售订单，即数据来源只能是 `sales_order_header` / `sales_order_item`。
4. 匹配来源复用现有重复件查询口径：按 `part_no + version` 查历史 `item_quote_version.status = 已提单` 且核价快照完整的最新零件。
5. 匹配结果只补全 `sales_order_item` 的生产快照字段，不写 `order_rfq`，不新增 `item_quote_version`。
6. 销售订单零件不会进入 RFQ 重复件匹配候选池，避免 RFQ 主链路和销售订单主链路在议价提单前互相污染。
7. 匹配动作要有预览、补全结果、审计能力；补全采用固定后端规则，不提供字段覆盖选择。
8. `sales_order_item.material_name` 明确定义为销售订单导入材料，销售匹配永不写入；`engineering_material_name / material_data.name` 明确定义为真实材料 / 核价材料。
9. 销售订单模板已有或为空的 `surface_treatment` 和 `drawing_url` 都不由销售匹配写入；描述 `description` 也不由历史 RFQ 描述覆盖。
10. 销售订单组合件父子关系必须使用销售订单自己的 `sales_order_item_assembly_relation` 表保存；`sales_order_item.assembly_relation_status` 只负责展示是否已指定父子关系。

## 2. 目标

- 市场人员可在左侧进入 **异常治理** 模块。
- 页面只允许选择销售订单，不展示 RFQ 订单选择入口。
- 异常治理沿用订单级工作台，操作路径为 `选择销售订单 -> 整单预览 -> 补全异常快照`。
- 共享订单选择弹窗按 `选择客户 -> 选择状态 -> 选择销售订单` 展示，且只允许选择 `已报价` 销售订单。
- 用户选中单张销售订单后自动加载整单预览，不再维护页面内销售订单列表或零件分页列表。
- 预览结果显示当前销售订单零件、历史来源 RFQ / 零件、可补空缺生产快照字段和保护字段。
- 用户触发补全后，后端按固定规则把空缺生产快照补全到 `sales_order_item`；补全执行只传销售订单 ID，不传零件选择范围。
- 补全后更新销售订单头表的 `matched_item_count`、`unmatched_item_count`、`warning_message` 等摘要。
- 匹配失败的零件不阻断流程，保留 `match_status = 未匹配` 和清晰 `match_message`。
- 销售订单图纸完全由导入绑定或补传图纸维护；销售匹配不补历史图纸，也不覆盖当前图纸。

## 3. 非目标

- 不把销售订单包装成 RFQ。
- 不把销售订单写入 `order_rfq`。
- 不把销售订单零件写入 `item_quote_version`。
- 不把销售订单零件作为 RFQ 重复件匹配来源。
- 不在本模块做 U9 同步、MES 获取物料号或 WMS 锁库。
- 不在本模块生成议价提单；销售订单提单由导入事务自动生成，RFQ 仍走 `议价提单` 模块。
- 不修改 RFQ 导入、零件核价、报价处理的既有匹配流程。
- 不提供字段级逐项选择、零件级选择或覆盖选项；销售匹配固定按订单级补空缺生产快照执行。

## 4. 业务流程

### 4.1 页面流程

```text
进入异常治理
  -> 点击“选择销售订单”
  -> 选择客户
  -> 选择状态（仅已报价）
  -> 选择一张销售订单
  -> 页面自动执行整单预览
  -> 后端按 sales_order_item.part_no + version 查历史已提单零件
  -> 页面展示匹配成功、未匹配、跳过、可补空缺快照和保护字段说明
  -> 点击“补全生产快照”
  -> 后端只补 sales_order_item 空缺生产快照字段
  -> 页面刷新匹配状态和订单摘要
```

### 4.2 状态口径

销售订单头表和行表继续使用独立状态，不复用 RFQ 状态机。

| 场景 | 处理口径 |
| --- | --- |
| `已报价` 销售订单 | 可被共享订单选择器选中，用于历史订单或异常订单整单预览和补全异常快照；新导入销售订单正常会自动提单后离开该状态。 |
| `部分已提单` 销售订单 | 不进入销售匹配可选订单列表，后端预览和补全接口也拒绝，避免补全动作影响已进入提单链路的订单解释。 |
| `已生成提单` 销售订单 | 不进入销售匹配可选订单列表，后端预览和补全接口也拒绝。 |
| `已废弃` 销售订单 | 不进入可选订单列表。 |
| 销售订单图纸 | 由导入绑定或补传图纸维护；销售匹配不补写历史 `drawing_url`，也不覆盖当前 `drawing_url`。 |
| 未匹配零件 | 保留导入数据，`match_status = 未匹配`，不阻断导入自动提单；如确需处理，可通过异常治理追溯。 |

### 4.3 导入链路调整

销售订单导入现在负责写入 `sales_order_header`、`sales_order_item`、销售订单图纸绑定、自动历史快照补全和自动提单。导入事务已经自动执行补全；异常治理只保留手工兜底能力：

- 导入成功后自动调用内部补全入口，写入 `matchedItemCount / unmatchedItemCount / warningMessage`。
- 导入结果展示销售订单号、客户订单号、零件数、图纸绑定结果、已补全 / 未补全数量、自动提单行和缺价格数量。
- 导入自动补全失败或历史订单需要治理时，才由 **异常治理** 页面显式触发预览和补全。
- 权限 code 继续保留 `market:sales-match:*`；导入自动补全由 `market:rfq:import-sales-order` 覆盖，不额外要求 `market:sales-match:apply`。

## 5. 匹配规则

### 5.1 历史来源

历史候选只来自 RFQ 零件主表：

```text
item_quote_version
```

候选必须同时满足：

- `part_no` 等于销售订单零件 `part_no`。
- `version` 等于销售订单零件 `version`。
- `status = 已提单`。
- `tax_included_unit_price IS NOT NULL`。
- `material_data IS NOT NULL`。
- `process_route IS NOT NULL`。
- 同一 `part_no + version` 多条候选时，取 `id DESC` 最新一条。

该口径与 `05-重复件匹配仅使用已提单历史零件开发文档.md` 保持一致。销售匹配模块只是消费这个历史查询口径，不改变 RFQ 重复件复用规则。

### 5.2 可补全字段与保护策略

销售匹配是“补全空缺信息”动作，不是“历史覆盖当前销售订单”。因此字段分为三类：

1. **销售订单导入事实字段**：销售订单模板、图纸绑定、补传图纸或后续 MES/U9 维护的事实字段，销售匹配永不写入。
2. **生产快照字段**：销售订单模板通常不提供，可由历史快照补齐；如果已经补过，不重复覆盖。
3. **追溯字段**：记录历史来源和匹配结果，可随本次匹配更新。

写回 `sales_order_item` 的字段和默认策略如下：

| 字段 | 含义 |
| --- | --- |
| `material_name` | 导入材料。来自销售订单模板 `材料`，销售匹配永不写入，即使为空也不补历史 RFQ 导入材料。 |
| `description` | 零件描述 / 材料描述。销售订单模板表头为 `描述`，语义对应 RFQ 导入模板 `物料描述`，销售匹配永不写入。 |
| `surface_treatment` | 表面处理。来自销售订单模板 `表面处理`，销售匹配永不写入，即使为空也不补历史 RFQ 表面处理。 |
| `drawing_url` / `has_drawing` | 销售订单图纸。由导入绑定或补传图纸维护，销售匹配永不写入。 |
| `engineering_material_name` | 真实材料 / 核价材料名称快照。属于生产快照字段，空缺时可补全，取值优先历史 `engineering_material_name`，其次历史 `material_data.name`。 |
| `material_shape` | 材料形态。属于生产快照字段，空缺时可补全，取值优先历史 `material_shape`，其次历史 `material_data.shape`。 |
| `material_gross_weight` | 材料毛重。属于生产快照字段，可补全。 |
| `part_net_weight` | 零件净重。属于生产快照字段，可补全。 |
| `quote_mode` | 普通件 / 组合件核价模式，值如 `NORMAL`、`ASSEMBLY`。 |
| `item_type` | 页面展示用零件类型，例如普通件、组合件。 |
| `assembly_fee` | 组合件组装费。 |
| `base_cost` | 历史基础成本快照。 |
| `material_data` | 材料核价 JSON 快照。 |
| `process_route` | 工艺路线 JSON 快照。 |
| `fee_data` | 费用结构 JSON 快照。 |
| `matched_rfq_id` | 历史来源 RFQ ID，仅用于追溯。 |
| `matched_item_id` | 历史来源 `item_quote_version.id`，仅用于追溯。 |
| `match_status` | 历史快照匹配状态：`已匹配`、`未匹配`、`跳过`。组合件父子关系是否指定不混入该状态。 |
| `match_message` | 面向页面和审计的匹配说明。 |

销售匹配不提供任何字段覆盖选项。即使旧请求传入 `overwriteTemplateMaterial` 或 `overwriteExistingProductionSnapshot`，后端也必须按“只补空缺信息”执行，不接受覆盖指令。

### 5.3 不允许覆盖字段

以下字段属于销售订单自身事实，销售匹配不得覆盖：

| 字段 | 保护原因 |
| --- | --- |
| `qty` | 销售订单数量来自客户订单。 |
| `released_qty` / `remaining_qty` | 提单数量状态来自议价提单生成。 |
| `shipped_qty` / `unshipped_qty` | 销售出货快照来自销售订单模板或后续回写。 |
| `tax_included_unit_price` / `untaxed_unit_price` | 销售价格来自销售订单。 |
| `tax_included_total_price` / `untaxed_total_price` | 销售金额来自销售订单。 |
| `tax_included_unit_price` / `tax_included_total_price` | 销售订单提单展示价格，不从历史 RFQ 覆盖。 |
| `customer_order_no` / `customer_project_no` | 客户侧订单信息。 |
| `internal_project_no` | 内部项目号。 |
| `description` | 销售订单模板 `描述`，语义对应 RFQ 导入模板 `物料描述`。 |
| `sales_material_no` | 销售订单模板中的料号。 |
| `material_no` | MES / U9 确认物料号，不能用历史 RFQ 候选覆盖。 |
| `customer_delivery_date` / `internal_delivery_date` | 销售订单交期。 |
| `status` | 销售订单零件生命周期状态。 |
| `drawing_url` / `has_drawing` | 销售订单图纸由导入绑定或补传图纸维护。 |
| `material_name` / `surface_treatment` | 销售订单模板事实，空值也不由销售匹配补历史 RFQ 导入字段。 |

### 5.4 组合件补全口径

现有 RFQ 组合件父子关系保存在 `item_assembly_relation`，该表的 `parent_item_id` / `child_item_id` 指向 `item_quote_version.id`，只能服务 RFQ 零件。销售订单零件使用 `sales_order_item.id`，不能复用 RFQ 的组合件关系表。

组合件补全分为三层：

1. **组合件基础字段**：写在 `sales_order_item` 上，用于识别该零件是组合件及其核价快照。
2. **组合件关系状态**：写在 `sales_order_item` 上，用于告诉页面当前组合件是否已经指定父子关系。
3. **组合件父子明细**：写在销售订单专用 `sales_order_item_assembly_relation` 表，用于保存父件、子件、每套用量和排序。

组合件基础字段包括：

- `quote_mode`
- `item_type`
- `assembly_fee`
- `material_data`
- `process_route`
- `fee_data`
- `base_cost`

销售订单零件主表新增字段：

| 字段 | 建议类型 | 说明 |
| --- | --- | --- |
| `assembly_relation_status` | `VARCHAR(30)` | 组合件关系状态。普通件为 `不适用`；组合件未建立关系为 `未指定父子关系`；后续如实际建立关系，可为 `已指定父子关系`。 |

| 场景 | `assembly_relation_status` |
| --- | --- |
| 普通件或历史来源不是组合件 | `不适用` |
| 历史来源是组合件，但无法完整建立父子关系 | `未指定父子关系` |
| 历史来源是组合件，且已写入 `sales_order_item_assembly_relation` | `已指定父子关系` |

销售订单组合件父子结构新增独立表：

```text
sales_order_item_assembly_relation
```

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键。 |
| `sales_order_id` | 销售订单 ID。 |
| `parent_item_id` | 销售订单父件 `sales_order_item.id`。 |
| `child_item_id` | 销售订单子件 `sales_order_item.id`。 |
| `qty_per_parent` | 每套用量，来自历史 `item_assembly_relation.child_qty_per_parent`。 |
| `sort_no` | 排序，来自历史组合件关系。 |
| `source_parent_item_id` | 历史来源父件 `item_quote_version.id`。 |
| `source_child_item_id` | 历史来源子件 `item_quote_version.id`。 |
| `created_at` / `updated_at` | 审计时间。 |

匹配写入规则：

1. 历史来源父件 `quote_mode = ASSEMBLY` 时，先补全组合件基础字段。
2. 第一版不因为子件找不到而把父件标记为 `部分补全`；历史生产快照命中则 `match_status = 已匹配`。
3. 读取历史父件的 `item_assembly_relation`，再用历史子件的 `part_no + version` 到同一张销售订单内查找当前 `sales_order_item` 子件。
4. 历史关系中的所有子件都能在当前销售订单内找到时，先删除当前父件已有 `sales_order_item_assembly_relation`，再重建完整关系，并将父件 `assembly_relation_status` 更新为 `已指定父子关系`。
5. 任一历史子件在当前销售订单内找不到时，不写不完整关系，不记录缺失子件清单，只将父件 `assembly_relation_status` 更新为 `未指定父子关系`。
6. `sales_order_item_assembly_relation` 只能引用 `sales_order_item.id`，不得写 RFQ `item_assembly_relation`，也不得把销售订单子件写回 `item_quote_version`。

## 6. 后端设计

### 6.1 新增控制器

建议新增：

```text
quote-backend/src/main/java/com/machining/quote/controller/SalesOrderMatchController.java
```

基础路径：

```text
/api/market/sales-match
```

接口建议：

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/customers` | `market:sales-match:customer-select` | 销售匹配客户筛选，遵守数据权限。 |
| `GET` | `/orders` | `market:sales-match:order-select` | 共享订单选择弹窗分页查询可匹配销售订单，默认只返回 `已报价` 的 `sales_order_header`。 |

| `GET` | `/orders/{salesOrderId}/items` | `market:sales-match:view` | 兼容或内部查询接口；订单级工作台不再把它作为页面内零件分页主入口。 |

| `POST` | `/apply` | `market:sales-match:apply` | 兼容旧 payload 补全接口；仍需校验销售订单为 `已报价`，不能绕过订单级边界。 |
| `GET` | `/items/{itemId}/source` | `market:sales-match:view` | 查看单个零件的历史来源摘要。 |

订单级工作台不再要求前端构造零件选择范围；`SalesOrderMatchApplyReq` 中的旧字段仅用于兼容旧接口，后端必须重新按订单状态和数据权限校验。

`changedFields` 只返回摘要，不返回完整 `material_data`、`process_route`、`fee_data` 大对象，避免前端和日志承载过重。查看详情时可单独查单行来源摘要。

### 6.3 服务层设计

建议新增或重命名现有服务：

```text
SalesOrderMatchService
```

职责：

- 从 `sales_order_header` / `sales_order_item` 读取销售订单和零件。
- 校验数据权限。
- 提取有效 `part_no + version` key。
- 复用 `ItemQuoteVersionMapper.selectLatestReleasedRepeatSources(...)` 查询历史已提单来源。
- `preview(...)` 只返回匹配结果和差异摘要，不更新数据库。
- `apply(...)` 在事务中更新 `sales_order_item` 的安全生产快照字段。
- `apply(...)` 在组合件子件完整匹配时写入 `sales_order_item_assembly_relation`，并将父件 `assembly_relation_status` 置为 `已指定父子关系`。
- `apply(...)` 在组合件子件无法完整匹配时不写不完整关系，并将父件 `assembly_relation_status` 置为 `未指定父子关系`。
- 汇总更新 `sales_order_header.matched_item_count`、`unmatched_item_count`、`warning_message`。
- 写入操作日志和低噪声文件日志。

现有 `SalesOrderRepeatEnrichmentService` 可作为内部实现继续保留，但建议收口为：

```text
SalesOrderMatchService
  -> SalesOrderReleasedSnapshotMatcher
  -> SalesOrderProductionSnapshotApplier
```

这样页面预览和补全执行可以共享同一套匹配逻辑，不会出现“预览命中但应用结果不一致”。

### 6.4 写入保护

`apply(...)` 必须满足：

- 锁定待更新的 `sales_order_item` 行，避免并发补全覆盖。
- 拒绝更新 `status = 已生成提单` 或 `remaining_qty = 0` 的已完成零件，除非后续业务明确批准。
- 不覆盖销售订单价格、数量、交期、客户字段、`description` 和 `material_no`。
- 不写入 `material_name`、`surface_treatment`、`drawing_url`、`has_drawing`，空值也不补历史 RFQ 导入字段。
- 已有生产快照字段不重复覆盖；后端不接受任何覆盖指令。
- 组合件关系只写 `sales_order_item_assembly_relation`；不得写 RFQ `item_assembly_relation`。
- 对没有历史来源的行写入 `match_status = 未匹配` 和明确 `match_message`。
- 对跳过的行写入 `match_status = 跳过` 或保持原状态，并在返回结果里说明原因。

## 9. 数据权限

销售匹配属于市场模块，但必须遵守客户数据范围。

数据过滤口径：

- `ALL`：可查看全部销售订单。
- `CUSTOMER`：只能查看角色绑定客户名称范围内的销售订单。
- `SELF`：只能查看当前用户创建或归属的销售订单。
- `NONE`：返回空列表，不泄露订单存在性。

实现要求：

- 销售订单列表从 `sales_order_header` 过滤。
- 销售订单零件从已授权的 `sales_order_header` 关联读取。
- `preview` 和 `apply` 不能只校验前端传入 ID；后端必须重新校验每个 `sales_order_id` / `sales_order_item_id` 的数据权限。
- 数据权限失败时返回 403 或空结果，不能返回其他客户订单的图号、版本或历史来源。

- [ ] 销售匹配拥有独立 `MENU` 权限 `market:sales-match:view`。
- [ ] 销售匹配已收口为订单级工作台。
- [ ] 页面只能选择销售订单，不能选择 RFQ。
- [ ] 只允许选择 `已报价` 销售订单。
- [ ] 操作路径为 `选择销售订单 -> 整单预览 -> 补全生产快照`。
- [ ] 不再提供页面内销售订单列表、零件分页列表或零件级勾选。
- [ ] 预览匹配不落库。
- [ ] 补全执行只传销售订单 ID，不传零件选择范围。
- [ ] 补全只写 `sales_order_item` 空缺生产快照字段和匹配追溯字段。
- [ ] 补全字段均为生产快照字段。
- [ ] 销售订单数量、价格、交期、客户字段、`description` 和 `material_no` 不被覆盖。
- [ ] 销售订单 `material_name`、`surface_treatment`、`drawing_url` 不由销售匹配写入。
- [ ] 未匹配零件仍保留在销售订单中并显示清晰原因。
- [ ] 操作日志记录 `SALES_ORDER_MATCH_APPLY`。
- [ ] 文件日志不记录完整 JSON 快照、token、密钥或完整请求体。
- [ ] 销售匹配不新增 `order_rfq`。
- [ ] 销售匹配不新增 `item_quote_version`。
- [ ] RFQ 重复件匹配结果不包含销售订单零件。
- [ ] 议价提单前 RFQ 主链路和销售订单主链路保持独立。
- [ ] 后端测试通过。
- [ ] 前端测试通过。
- [ ] 前端构建通过。
