# 关联变更下游影响通知闭环开发文档

## 1. 背景

销售订单零件支持“关联废弃”，可以从销售订单零件级或销售订单整单级联动处理下游零件。当前关联废弃负责更新 QPO 内各业务表的废弃状态：

- 销售订单零件更新关联废弃状态，并继续影响 U9 同步 / 销售变更可见性；
- 仍在已提零件工作池中的记录执行关联废弃；
- 仍在待产零件工作池中的记录执行关联废弃；
- 仍在锁库零件工作池中的记录执行关联废弃；
- 已完成外部动作的记录不再回滚，也不阻断本次关联废弃。

但下游动作完成后，记录会从对应模块的默认工作池中隐藏。业务员在销售订单上执行关联废弃时，无法只通过当前页面判断该零件此前是否已经发生过 WMS 锁库、MES 生产下发或锁库库存工单动作，也无法确认自己是否已经人工通知相关下游人员。

本需求新增“关联变更”模块，形成从关联废弃到人工通知的闭环追踪能力。

## 2. 目标

在“变更”分组下新增“关联变更”页面，作为零件级工作池，记录每次销售订单零件关联废弃产生的下游影响事实，并支持业务员查询和标记人工通知状态。

每条关联变更记录至少需要回答：

1. 哪个客户、哪个销售订单、哪个销售订单零件被关联废弃；
2. 该零件在关联废弃前是否提交过 WMS 锁库；
3. 该零件在关联废弃前是否下发过 MES 生产；
4. 该零件在关联废弃前是否在锁库零件流程中提交过库存工单；
5. 业务员是否已经人工通知下游，谁处理的、什么时候处理的。

## 3. 业务口径

### 3.1 记录产生时机

以下两类操作均需要为销售订单下的每一个零件生成一条关联变更记录：

- 销售订单零件行点击“关联废弃”；
- 销售订单详情点击订单级“关联废弃”。

订单级关联废弃必须按订单内零件逐行生成记录，不能只生成一条订单汇总记录，否则无法在零件级别确认下游影响。

记录生成应与关联废弃操作处于同一后端事务中。只要关联废弃事务回滚，关联变更记录也必须回滚；只要关联废弃提交成功，即使三个下游动作均未发生，也必须保留记录。

### 3.2 关联恢复的处理

关联恢复不删除、不覆盖历史关联变更记录。历史记录仍保留原来的：

- 关联废弃时间、操作人和原因；
- WMS、MES 生产、库存工单的历史影响快照；
- 人工通知状态、处理人、处理时间和处理备注。

如果同一个销售订单零件后续再次执行关联废弃，应新增一轮关联变更记录，不能复用上一轮记录。每轮关联废弃都是独立事件，便于审计和追溯。

关联恢复只执行现有的业务恢复逻辑，不将“已处理”自动改回“未处理”，也不对已经成功完成的 WMS、MES 或库存工单动作做回滚。

### 3.3 “已处理”的含义

“已处理”只表示业务员已经人工通知了受影响的下游系统或相关人员，不表示：

- WMS 数据已经回滚；
- MES 生产任务已经取消；
- 库存工单已经取消；
- 销售订单或下游零件恢复；
- 系统已经自动通知外部系统。

点击“已处理”时记录当前操作人和处理时间。处理备注建议支持填写，用于记录通知对象、通知方式或外部处理单号，但不能要求录入外部系统的完整请求、响应、token 或密钥。

第一版建议提供“重新标记未处理”或管理员纠正能力，避免误点击后无法修正。该动作只修改人工通知状态，不修改下游事实快照。

### 3.4 下游三类动作的实际系统映射

用户业务描述中的“已提零件、待产零件、锁库零件三步”需要按当前系统真实架构落地。根据现行“待产零件与锁库零件模块解耦”设计，三个状态列定义如下：

| 关联变更列 | 实际业务动作 | 事实来源 | 成功状态 |
| --- | --- | --- | --- |
| WMS 锁库 | 已提零件提交 WMS 锁库 / 库存分配 | `order_delivery_ticket.wms_allocate_status` | `SUCCESS` |
| MES 生产 | 待产零件下发 MES 生产 | `order_delivery_ticket_allocation.allocation_type = 'PRODUCTION_REQUIRED'` 与 `mes_production_status` | `SUCCESS` |
| 库存工单 | 锁库零件提交库存工单 | `allocation_type IN ('IN_STOCK_LOCK', 'IN_PRODUCTION_LOCK')` 与 `stock_picking_status` | `SUCCESS` |

当前锁库零件模块不再承担 MES 生产下发，MES 生产由待产零件模块负责；锁库零件对应的第三列是库存工单提交状态。页面展示时可以使用业务名称“锁库库存工单”或“库存工单”，避免继续显示会误导用户的“锁库下发 MES”。如果后续业务确认第三列确实要追踪其他动作，应单独补充状态来源和验收口径，不能仅修改列名。

### 3.5 状态不是简单布尔值

每一类下游动作需要区分“是否发生过提交”和“当前结果”，不能只保存一个成功布尔值。建议统一展示以下状态：

- 未发生：没有对应下游记录，或从未提交；
- 处理中：已提交，当前仍在处理；
- 成功：下游返回成功；
- 失败：下游返回失败，可根据现有业务状态重试；
- 结果待确认：已发起但等待回调或结果确认；
- 未知：历史数据不足以判定，不能误显示为未发生。

“是否进行过动作”由是否存在提交记录、请求编号或已写入处理状态判定；“成功 / 失败 / 处理中”由关联废弃时读取的现有状态字段判定。

## 4. 数据模型设计

### 4.1 新增表

建议新增表：`sales_order_linked_change_notice`。

该表是关联废弃事件的历史快照表，不依赖当前三个模块是否还能查询到下游行。不要只通过页面查询时临时关联现有表，否则成功下发后从默认工作池隐藏的记录会丢失。

### 4.2 字段建议

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 主键 |
| `sales_order_id` | `BIGINT` | 销售订单 ID |
| `sales_order_item_id` | `BIGINT` | 销售订单零件行 ID |
| `sales_order_no` | `VARCHAR(100)` | 销售订单号快照 |
| `line_no` | `INTEGER` | 销售订单行号快照 |
| `customer_id` | `BIGINT` | 客户 ID 快照或可追溯 ID |
| `customer_code` | `VARCHAR(100)` | 客户编码快照 |
| `customer_name` | `VARCHAR(255)` | 客户名称快照 |
| `part_no` | `VARCHAR(255)` | 图号快照 |
| `version` | `VARCHAR(100)` | 版本快照 |
| `description` | `VARCHAR(500)` | 物料描述快照 |
| `material_name` | `VARCHAR(500)` | 材料名称快照 |
| `trigger_scope` | `VARCHAR(30)` | `ITEM` 零件级 / `ORDER` 订单级 |
| `linked_discard_event_key` | `VARCHAR(100)` | 本轮关联废弃事件标识 |
| `linked_discarded_at` | `TIMESTAMP` | 关联废弃时间 |
| `linked_discarded_by` | `BIGINT` | 关联废弃操作人 |
| `linked_discard_reason` | `VARCHAR(500)` | 关联废弃原因 |
| `wms_submitted` | `BOOLEAN` | 是否发生过 WMS 锁库动作 |
| `wms_status` | `VARCHAR(50)` | WMS 锁库状态快照 |
| `wms_request_id` | `VARCHAR(255)` | WMS 请求或任务编号快照，可为空 |
| `wms_action_at` | `TIMESTAMP` | WMS 动作时间 |
| `mes_production_submitted` | `BOOLEAN` | 是否发生过 MES 生产下发 |
| `mes_production_status` | `VARCHAR(50)` | MES 生产状态快照 |
| `mes_production_request_id` | `VARCHAR(255)` | MES 生产请求编号快照，可为空 |
| `mes_production_action_at` | `TIMESTAMP` | MES 生产动作时间 |
| `stock_picking_submitted` | `BOOLEAN` | 是否发生过库存工单动作 |
| `stock_picking_status` | `VARCHAR(50)` | 库存工单状态快照 |
| `stock_picking_biz_id` | `VARCHAR(255)` | 库存工单业务编号快照，可为空 |
| `stock_picking_action_at` | `TIMESTAMP` | 库存工单动作时间 |
| `downstream_impact_count` | `INTEGER` | 三类动作中发生过动作的数量 |
| `handling_status` | `VARCHAR(30)` | `UNHANDLED` / `HANDLED` |
| `handled_at` | `TIMESTAMP` | 人工处理时间 |
| `handled_by` | `BIGINT` | 人工处理人 |
| `handle_remark` | `VARCHAR(500)` | 人工通知备注 |
| `created_at` | `TIMESTAMP` | 创建时间 |
| `updated_at` | `TIMESTAMP` | 更新时间 |

字段命名可以根据项目现有实体规范调整，但必须保留“动作是否发生”和“动作结果”两个维度。不能只保存 `wms_success`、`mes_success`、`stock_success` 三个字段，因为失败、处理中和结果待确认同样需要让业务员看到。

### 4.3 事件幂等

每次关联废弃需要生成一个事件 key。建议格式包含销售订单 ID、关联废弃操作时间或 UUID，不直接使用零件 ID 作为唯一键。

约束建议：

- `linked_discard_event_key + sales_order_item_id` 唯一；
- 零件级关联废弃创建一条记录；
- 订单级关联废弃为每个订单零件使用同一个事件 key 创建多条记录；
- 同一事务重试不能重复插入；
- 关联恢复不删除通知表记录；
- 再次关联废弃生成新的事件 key 和新记录。

## 5. 关联废弃时的快照采集

### 5.1 采集范围

在现有 `SalesOrderLinkedDiscardService` 的零件级和订单级关联废弃事务中，完成下游关系加载并确定本次处理对象后，构造通知快照。快照需要覆盖：

- 销售订单和零件基本信息；
- 本次操作来源是零件级还是订单级；
- 下游已提单记录的 WMS 状态；
- `PRODUCTION_REQUIRED` 分配记录的 MES 生产状态；
- `IN_STOCK_LOCK`、`IN_PRODUCTION_LOCK` 分配记录的库存工单状态；
- 请求编号、业务编号、动作时间等现有字段；
- 本次关联废弃跳过的已完成记录。

### 5.2 “已发生”的判定

建议使用以下规则：

1. WMS：存在对应销售订单零件的已提单记录，且 `wms_allocate_status` 曾进入 `PROCESSING`、`SUCCESS`、`FAILED`、`RESULT_UNKNOWN` 或其他已提交状态时，`wms_submitted = true`。只有明确没有提交记录且状态为空 / `PENDING` 才判定为未发生。
2. MES：存在 `allocation_type = 'PRODUCTION_REQUIRED'` 的分配记录，且 `mes_production_request_id`、外部任务号或状态表明已经提交时，`mes_production_submitted = true`。
3. 库存工单：存在锁库类型分配记录，且 `stock_picking_biz_id`、外部单号或 `stock_picking_status` 表明已经提交时，`stock_picking_submitted = true`。

如果历史字段不足以判断是否已经提交，状态应保存为 `UNKNOWN`，页面显示“未知”，并进入人工核查范围，不能默认显示“未发生”。

### 5.3 与现有关联废弃动作的关系

现有关联废弃逻辑仍然负责：

- 销售订单零件 U9 / 销售变更排除状态；
- 仍在工作池中的 `order_delivery_ticket` 废弃；
- 仍在工作池中的 `order_delivery_ticket_allocation` 废弃；
- 已完成下游动作的记录跳过废弃并保留原事实。

通知快照是旁路的历史记录，不替换现有废弃字段，也不新增一个字段来代表零件废弃。销售订单零件、已提零件、待产零件和锁库零件原有的废弃字段继续作为业务状态来源。

## 6. 后端接口设计

建议新增后端模块，接口路径统一为 `/api/change/linked-changes`。

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/api/change/linked-changes` | `change:linked-change:view` | 分页查询关联变更 |
| `GET` | `/api/change/linked-changes/customers` | `change:linked-change:customer-select` | 查询可选客户 |
| `GET` | `/api/change/linked-changes/{id}` | `change:linked-change:view` | 查看单条完整快照 |
| `POST` | `/api/change/linked-changes/{id}/handle` | `change:linked-change:handle` | 标记已处理 |
| `POST` | `/api/change/linked-changes/{id}/reopen` | `change:linked-change:handle` | 恢复为未处理，建议保留 |

### 6.1 查询参数

列表接口支持：

- 客户；
- 销售订单号；
- 图号；
- 版本；
- 触发范围：零件级 / 订单级；
- 人工处理状态：未处理 / 已处理；
- WMS 影响状态；
- MES 生产影响状态；
- 库存工单影响状态；
- 关联废弃时间范围；
- 关键词；
- 页码和每页数量。

默认查询条件建议为：`handlingStatus=UNHANDLED` 且至少一个下游动作已发生。页面必须提供查看全部记录的入口，避免没有下游影响的记录被误认为不存在。

列表返回至少包含：

- 记录 ID；
- 客户名称；
- 销售订单号；
- 行号；
- 图号；
- 版本；
- 触发来源；
- 关联废弃时间和操作人；
- WMS、MES 生产、库存工单三列状态；
- 人工处理状态、处理人、处理时间；
- 详情和处理按钮状态。

详情接口返回订单、零件和三类下游快照的完整信息，但仍只返回当前用户数据权限范围内的数据。

### 6.2 标记已处理

请求体建议：

```json
{
  "remark": "已电话通知客户项目负责人和生产计划员"
}
```

后端保存前需要：

- 校验记录存在且当前用户具备销售订单数据权限；
- 使用行锁或条件更新保证重复点击幂等；
- 只更新 `handling_status`、`handled_at`、`handled_by`、`handle_remark`；
- 不修改销售订单、已提零件、待产零件、锁库零件及任何外部同步状态；
- 返回最新处理人和处理时间。

## 7. 权限和数据范围

新增权限，不复用销售订单变更保存权限：

| 能力 | 权限编码 | 类型 | 建议角色 |
| --- | --- | --- | --- |
| 关联变更 | `change:linked-change:view` | `MENU` | `SUPER_ADMIN`、`MARKET_USER`、`MARKET_MANAGER`、`READONLY` |
| 选择客户 | `change:linked-change:customer-select` | `API` | 与查看权限一致 |
| 标记关联变更已处理 | `change:linked-change:handle` | `BUTTON` | `SUPER_ADMIN`、`MARKET_USER`、`MARKET_MANAGER` |

实现时需要同步更新：

- 后端 `PermissionService` fallback catalog；
- Flyway 新迁移中的权限和默认角色授权；
- 前端路由 `meta.permission`；
- “变更”菜单及菜单描述；
- 权限文档和角色映射文档。

列表、详情、客户选择和处理接口都必须在后端执行销售订单数据范围校验。没有客户或订单数据范围时返回空列表，不得通过关联变更快照泄露其他客户的订单信息。

## 8. 前端设计

新增 `LinkedChangeManage.vue`，位于“变更”分组，并放在“销售变更”之前。建议路由：`/linked-changes`。

页面采用与已提零件相近的密集工作台布局：

- 顶部筛选区：客户、销售订单号、图号、版本、处理状态、三类影响状态、时间范围；
- 默认加载“未处理且有下游影响”的记录；
- 分页表格，不在前端一次性加载所有历史记录；
- 三个固定状态列：WMS 锁库、MES 生产、锁库库存工单；
- “未处理”显示主操作按钮“标记已处理”；
- “已处理”显示处理人和时间，并提供查看备注 / 重新标记未处理能力；
- 详情抽屉展示关联废弃原因、销售订单零件快照、各下游请求编号和状态历史；
- 对已完成动作显示明确的“已完成，不可由 QPO 回滚”提示。

页面不提供：

- WMS、MES、库存工单的取消或重试按钮；
- 销售订单普通废弃 / 关联废弃 / 关联恢复按钮；
- 修改销售订单或下游零件业务字段；
- 外部系统完整响应、token、密钥或完整请求体展示。

## 9. 日志设计

### 9.1 不记日志的操作

关联变更列表查询、详情查询和筛选是高频读取，不写操作日志，也不新增高频 INFO 文件日志。

### 9.2 需要记操作日志的操作

建议新增：

- `LINKED_CHANGE_NOTICE_HANDLE`：标记人工通知已处理；
- `LINKED_CHANGE_NOTICE_REOPEN`：恢复为未处理。

日志归入 `CHANGE` 模块，`targetType=sales_order_linked_change_notice`，`targetId` 为通知记录 ID。摘要只记录：

- 通知记录 ID；
- 销售订单号、行号、图号、版本；
- 三类影响的状态摘要；
- 处理前后状态；
- 处理人和备注长度 / 摘要。

不记录完整零件快照、完整外部响应、Excel、Authorization、Cookie、token、密钥或外部系统密码。关联废弃本身继续记录现有 `SALES_ORDER_ITEM_LINKED_DISCARD` 和 `SALES_ORDER_LINKED_DISCARD`，通知快照创建不额外产生一条重复高频日志。

## 10. 性能和并发设计

### 10.1 关联废弃性能

订单级关联废弃已经按订单批量加载零件、提单和分配关系。本需求必须复用批量关系结果，不允许在订单内每个零件上重复查询三次下游表，避免 N+1 查询。

建议流程：

1. 锁定销售订单和销售订单零件；
2. 按订单 ID、销售订单零件 ID 集合一次加载相关提单；
3. 按提单 ID / 来源订单和零件集合一次加载相关分配；
4. 内存中按 `sourceItemId`、`ticketId` 和 `allocationType` 分组；
5. 为每个销售订单零件生成快照对象；
6. 批量插入通知记录；
7. 执行现有关联废弃批量更新；
8. 同一事务提交。

如果当前代码为了执行废弃操作已经锁定了实体，应直接从这些已锁定实体采集状态，不再重复读取数据库。

### 10.2 索引建议

新增迁移中为以下组合建立索引：

- `(sales_order_id, linked_discarded_at DESC, id DESC)`；
- `(sales_order_item_id, linked_discard_event_key)`；
- `(customer_id, handling_status, linked_discarded_at DESC)`；
- `(handling_status, downstream_impact_count, linked_discarded_at DESC)`；
- `(sales_order_no, part_no, version)`，如数据库规模和查询计划需要；
- `linked_discard_event_key` 唯一索引，配合零件 ID 保证幂等。

查询必须后端分页，禁止一次性查询全部历史快照后在前端分页。默认查询应优先使用处理状态、影响数量和时间索引。

### 10.3 并发处理

- 同一销售订单的关联废弃仍由现有销售订单锁控制；
- 通知快照插入使用唯一约束兜底幂等；
- 标记已处理使用条件更新或行锁，重复点击只能产生一次有效状态变更；
- 列表查询不锁业务表；
- 详情读取不阻塞关联废弃事务。

## 11. 数据迁移策略

新增未使用的 Flyway 版本，例如 `V55__sales_order_linked_change_notice.sql`，实际版本号以仓库当前最大迁移号为准。

迁移内容包括：

- 创建 `sales_order_linked_change_notice`；
- 创建必要索引和唯一约束；
- 插入关联变更菜单、客户选择 API、人工处理按钮权限；
- 为默认角色授权；
- 不修改已经执行过的 `V1`、`V2` 或历史迁移；
- 不对历史已发生的关联废弃强行补造通知记录，除非另有明确回填脚本和事实来源。

历史数据无法完整判断三类下游动作时，不应批量猜测为“未发生”。如果确实要回填，应将状态设为 `UNKNOWN` 并在回填说明中记录数据来源。

## 14. 验收标准

1. 零件级和订单级关联废弃均能产生零件级关联变更记录。
2. 记录不依赖当前已提、待产、锁库页面是否仍展示该零件。
3. WMS 锁库、MES 生产、库存工单三个历史动作状态可分别查看，且不把“获取 MES 物料号”误计为 MES 生产。
4. 已完成下游动作的零件仍会进入关联变更，未发生任何下游动作的零件也会保留记录。
5. 关联恢复不删除历史，不回滚外部动作；再次关联废弃能生成新的事件记录。
6. 业务员可以标记人工通知已处理，系统记录处理人和处理时间，重复点击不会产生重复处理记录。
7. 列表默认突出未处理且有下游影响的记录，同时支持查询全部记录。
8. 查询和处理遵守销售订单数据权限，后端权限是最终安全边界。
9. 不改变现有销售订单零件、已提零件、待产零件和锁库零件的废弃字段语义。
10. 订单级批量处理不产生按零件重复查询下游表的 N+1 性能问题。

## 15. 当前口径结论

当前系统第三类动作确定为“锁库零件提交库存工单”，页面列名采用“锁库库存工单”；它不表示锁库零件再次下发 MES。MES 生产列只读取 `PRODUCTION_REQUIRED` 分配记录的生产状态，获取 MES 物料号不计入生产动作。
