# 议价提单导入替换图纸支持 RFQ / 销售订单混合来源开发文档

最后更新：2026-08-03

## 1. 背景

QPO 议价提单模块已经从单一 RFQ 来源演进为混合来源：

- RFQ / 询价订单来源使用 `order_rfq` / `item_quote_version`。
- 销售订单来源使用 `sales_order_header` / `sales_order_item`。
- 议价提单候选零件、提单生成、提单表据、已提零件、锁库零件等下游能力通过 `source_type` 区分来源。

当前候选零件列表和生成提单链路已经支持 RFQ 与销售订单混合来源，但“导入替换图纸”仍停留在 RFQ-only 实现：

- 前端提交时虽然携带了 `sources`，但仍用 `selectedRfqIds` 做上传前校验。
- 后端接口 `/api/market/release/drawings/replace` 只接收 `rfqIds`。
- 服务层只查询 `item_quote_version`，只替换 RFQ 零件的 `drawing_url`。
- 纯销售订单来源时，用户无法通过议价提单入口按图号替换销售订单零件图纸。

本阶段目标是补齐该缺口：议价提单“导入替换图纸”应按当前选中的订单来源范围执行，支持 RFQ 与销售订单两类来源，并且替换范围与当前零件表格勾选状态解耦。

## 2. 核心产品规则

### 2.1 一句话规则

用户在议价提单页面选中订单后，上传 PDF 图纸；系统按 PDF 文件名解析图号，并与选中订单范围内的全部零件匹配，只要图号命中且零件允许变更，就替换该零件图纸。

### 2.2 必须明确的行为

- 替换范围是“当前选中的订单”，不是“当前勾选的零件”。
- 用户不需要为了替换图纸去勾选零件。
- 当前分页、当前筛选、当前表格可见行不限制替换范围。
- 是否替换由上传的 PDF 图号决定：
  - 上传了命中图号的 PDF，则命中的可变更零件替换图纸。
  - 没有上传对应图号 PDF 的零件保持原图纸不变。
- 同一个图号在选中订单范围内命中多条零件时，所有可变更命中零件都替换。
- RFQ 已提单、无剩余数量的零件仍允许替换图纸；只跳过无权限、非 PDF、未匹配或来源本身不可维护的行。
- 本功能是“替换图纸”，不是“补传缺图”：
  - 已有图纸的可变更零件允许被新上传图纸覆盖。
  - 已有图纸但不可变更的零件跳过。

### 2.3 “不可变更零件”定义

本文中的“不可变更零件”是指从提单前资料维护角度不允许继续改源零件图纸的零件，不是指“已有图纸”或“当前未勾选”。

属于不可变更的典型情况：

- 零件已全部提单、剩余可提数量为 0 时，仍可按图号或图号+版本替换 RFQ 零件主表图纸；历史 ticket 图纸快照不回写。
- 零件状态已进入已提单、已生成提单、已完成、废弃等终态或不可维护状态。
- 来源订单状态或零件状态不允许继续进行提单前资料维护。
- 数据权限校验不允许当前用户操作该来源订单。

不属于不可变更的情况：

- 零件已经有旧图纸，但仍处于可维护状态；本功能允许用新上传图纸覆盖旧图纸。
- 零件没有在表格中被勾选；图纸替换不依赖勾选状态。
- 零件在当前分页不可见；图纸替换按选中订单范围全量匹配。

## 3. 范围

### 3.1 本阶段包含

- 前端议价提单“导入替换图纸”入口支持纯销售订单、纯 RFQ、RFQ + 销售订单混合选择。
- 前端上传前校验从 `selectedRfqIds` 改为 `selectedOrderSources`。
- 前端继续支持多 PDF、文件夹上传、拖拽上传和跳过非 PDF 展示。
- 后端替换接口接收 `sources`，并以 `sources` 为主参数。
- 后端保留 `rfqIds` 兼容旧调用。
- 后端按来源分别查询 RFQ 零件和销售订单零件。
- 后端按统一图号规则匹配并替换：
  - RFQ 来源：更新 `item_quote_version.drawing_url`。
  - 销售订单来源：更新 `sales_order_item.drawing_url`，同步 `has_drawing = true`。
- 替换结果返回来源字段，便于前端展示和审计追踪。
- 操作日志、文件日志、权限文档同步更新。
- 更新前后端测试，覆盖混合来源和不勾选零件也能替换。

### 3.2 本阶段不包含

- 不迁移历史图纸文件。
- 不改变询价订单详情“补传图纸”逻辑。
- 不改变销售订单详情“补传图纸”逻辑。
- 不改变新单导入时的图纸绑定逻辑。
- 不改变生成提单时的零件勾选规则。
- 不新增新的图纸版本管理表。
- 不按版本号匹配图纸；本阶段仍只按图号匹配。
- 不新增可分配 `common:*` 权限。

## 4. 当前实现缺口

| 位置 | 当前状态 | 问题 |
|---|---|---|
| `MarketRelease.vue` | 候选列表支持 `sourceType` / `sourceOrderId` | “导入替换图纸”提交前仍要求 `selectedRfqIds.length > 0` |
| `MarketRelease.vue` | 提交 `FormData` 时包含 `sources` 和 `rfqIds` | 后端当前只消费 `rfqIds` |
| `MarketController.replaceReleaseDrawings` | `@RequestParam("rfqIds") String rfqIdsJson` | 不支持销售订单来源 |
| `InternalTargetLeadTimeService.replaceReleaseDrawings` | 入参为 `List<Integer> rfqIds` | 服务模型 RFQ-only |
| `replaceReleaseDrawings` 服务逻辑 | 查询 `item_quote_version` | 不查询 `sales_order_item` |
| `replaceReleaseDrawings` 更新逻辑 | `item.setDrawingUrl(fileUrl)` | 不更新 `sales_order_item.drawing_url` / `has_drawing` |
| 审计摘要 | 记录 `rfqIds` / `rfqNos` | 无法表达混合来源 |

## 5. 目标交互

### 5.1 用户流程

1. 用户进入“议价提单”页面。
2. 用户通过订单选择器选择一个或多个订单：
   - 可以全是 RFQ。
   - 可以全是销售订单。
   - 可以是 RFQ 和销售订单混合。
3. 页面加载选中订单范围内的候选零件。
4. 用户点击“导入替换图纸”。
5. 用户上传多个 PDF 或选择图纸文件夹。
6. 系统按 PDF 文件名解析图号。
7. 系统把解析出的图号与选中订单范围内的全部零件匹配。
8. 命中且可变更的零件替换图纸。
9. 不可变更零件、未匹配图纸、非 PDF 文件进入结果提示。
10. 页面刷新候选零件列表，图纸状态立即更新。

### 5.2 文案调整

- 上传前未选择订单：
  - 原文案：`请先选择询价单。`
  - 新文案：`请先选择订单。`
- 上传前未选择 PDF：
  - 保持：`请先选择需要替换的 PDF 图纸。`
- 弹窗说明建议：
  - `系统会在当前选中的订单范围内按图号匹配全部零件，命中后替换图纸；无需勾选零件。`

## 6. 后端设计

### 6.1 接口

沿用现有接口路径，避免前端和权限大范围迁移：

```text
POST /api/market/release/drawings/replace
Permission: market:release:create
Content-Type: multipart/form-data
```

表单字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `sources` | JSON array | 新调用必填 | 选中的订单来源列表 |
| `rfqIds` | JSON array | 兼容字段 | 旧调用兼容；当 `sources` 为空时转换为 RFQ 来源 |
| `drawings` | files | 是 | 多个 PDF 图纸 |

`sources` 示例：

```json
[
  { "sourceType": "RFQ", "sourceOrderId": 101 },
  { "sourceType": "SALES_ORDER", "sourceOrderId": 2001 }
]
```

### 6.2 Controller 改造

目标文件：

```text
quote-backend/src/main/java/com/machining/quote/controller/MarketController.java
```

改造点：

- `replaceReleaseDrawings` 新增可选参数 `sources`。
- 使用已有 `parseReleaseSources(sourcesJson, rfqIdsJson)` 解析来源。
- 当 `sources` 为空但 `rfqIds` 非空时，保持旧 RFQ 调用兼容。
- 当解析后来源为空时，返回明确错误。

目标签名：

```java
@PostMapping(value = "/release/drawings/replace", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
@RequirePermission("market:release:create")
public Map<String, Object> replaceReleaseDrawings(
        @RequestParam(value = "sources", required = false) String sourcesJson,
        @RequestParam(value = "rfqIds", required = false) String rfqIdsJson,
        @RequestParam(value = "drawings", required = false) List<MultipartFile> drawings) {
    return internalTargetLeadTimeService.replaceReleaseDrawings(
            parseReleaseSources(sourcesJson, rfqIdsJson),
            drawings
    );
}
```

### 6.3 Service 改造

目标文件：

```text
quote-backend/src/main/java/com/machining/quote/service/InternalTargetLeadTimeService.java
```

新增主方法：

```java
@Transactional
public Map<String, Object> replaceReleaseDrawings(
        List<ReleaseOrderSource> sources,
        List<MultipartFile> drawings)
```

保留兼容重载：

```java
@Transactional
public Map<String, Object> replaceReleaseDrawings(
        List<Integer> rfqIds,
        List<MultipartFile> drawings) {
    List<ReleaseOrderSource> sources = rfqIds == null ? List.of() : rfqIds.stream()
            .map(id -> ReleaseOrderSource.rfq(Long.valueOf(id)))
            .toList();
    return replaceReleaseDrawings(sources, drawings);
}
```

如 `ReleaseOrderSource.rfq(...)` 当前不存在，则新增静态工厂方法，与已有 `salesOrder(...)` 保持一致。

### 6.4 数据读取

按来源分组：

- RFQ 来源：
  - 使用 `requireOrdersForUpdate(rfqIds)` 加锁并校验数据权限。
  - 查询 `item_quote_version`。
  - 查询相关 `order_delivery_ticket`，用于判断是否可变更。
- 销售订单来源：
  - 使用 `accessibleSalesOrderMap(...)` 或新增 `requireSalesOrdersForUpdate(...)` 校验数据权限。
  - 建议新增 `requireSalesOrdersForUpdate(Set<Long> salesOrderIds)`，对 `sales_order_header` 加锁。
  - 查询 `sales_order_item`。
  - 以 `released_qty`、`remaining_qty`、订单/零件状态判断是否可变更。

### 6.5 统一匹配模型

为避免 RFQ 与销售订单两套循环重复，建议在 `InternalTargetLeadTimeService` 内部新增私有轻量模型：

```java
private record ReleaseDrawingTarget(
        String sourceType,
        Long sourceOrderId,
        Long sourceItemId,
        String sourceOrderNo,
        String customerName,
        String partNo,
        String version,
        String currentDrawingUrl,
        boolean mutable,
        String blockedReason,
        Object rawItem
) {
}
```

构建目标集合：

- RFQ `ItemQuoteVersion` 映射为 `ReleaseDrawingTarget`。
- 销售订单 `SalesOrderItem` 映射为 `ReleaseDrawingTarget`。
- `sourceType` 固定为 `RFQ` 或 `SALES_ORDER`。
- `sourceItemId` 对应 `item_quote_version.id` 或 `sales_order_item.id`。

按归一化图号建立索引：

```java
Map<String, List<ReleaseDrawingTarget>> targetsByPartNo = new LinkedHashMap<>();
```

归一化规则：

- 继续使用 `DrawingPartNoResolver.normalizePartNo(...)` 或当前项目等价方法。
- 文件名解析继续使用 `DrawingPartNoResolver.extractPartNo(cleanFileName, targetsByPartNo.keySet())`。

### 6.6 替换逻辑

伪代码：

```text
for each uploaded drawing:
  clean filename
  if not PDF:
    skippedFiles += file result
    continue

  partNo = DrawingPartNoResolver.extractPartNo(filename, targetsByPartNo.keys)
  matchedTargets = targetsByPartNo[partNo]
  if empty:
    unmatchedDrawings += file result
    continue

  for each target in matchedTargets:
    matchedCount++
    if !target.mutable:
      skippedItems += item result with blockedReason
      continue

    save file for target source order
    if target.sourceType == RFQ:
      update item_quote_version.drawing_url
    if target.sourceType == SALES_ORDER:
      update sales_order_item.drawing_url
      update sales_order_item.has_drawing = true
    replacedItems += item result
```

保存文件建议：

- RFQ 来源继续使用 `BusinessFileService.saveDrawing(order, drawing, "RELEASE_DRAWING_REPLACE", String.valueOf(order.getId()))`。
- 销售订单来源使用 `BusinessFileService.saveSalesOrderImportDrawing(...)` 或新增更准确的包装方法：
  - `saveSalesOrderReleaseDrawing(SalesOrderHeader order, MultipartFile drawing, String bizType, String bizId)`
  - 如果不新增方法，也可以复用现有销售订单图纸保存方法，但 `bizType` 必须传 `RELEASE_DRAWING_REPLACE`。
- 同一个上传文件如果命中同一个来源订单下多个零件，应保存一次并复用 URL。
- 同一个上传文件命中不同来源订单，按来源订单分别保存，便于文件目录和业务归属清晰。

### 6.7 可变更规则

“可变更”只用于判断是否允许替换源零件图纸。它不等同于“是否已经绑定图纸”，也不等同于“是否被用户勾选”。已有图纸但仍可维护的零件应允许覆盖；未勾选但图号命中的可维护零件也应允许替换。

RFQ 来源沿用现有规则：

- RFQ 已完全提单不跳过。
- RFQ 已提单、已生成提单状态不跳过；废弃、已完成等非议价提单可维护来源仍跳过。
- RFQ 剩余数量为 0 不跳过。
- 具体原因复用 `releaseMutationBlockedReason(...)`。

销售订单来源建议规则：

- `remaining_qty <= 0` 且 `released_qty >= qty`：RFQ 来源仍允许替换图纸。
- 销售订单或非 RFQ 来源状态为已完成、废弃等不可维护状态：跳过。
- 仍有剩余数量且未处于不可维护状态：允许替换。

如项目已有销售订单提单可变更判断工具，应复用现有规则，避免 RFQ 与销售订单判断口径分裂。

## 8. 权限设计

沿用议价提单现有权限：

```text
market:release:create
```

原因：

- 当前“导入替换图纸”是提单前资料维护动作。
- 现有按钮已经归属 `market:release:create`。
- 本阶段不拆分 `replace-drawings` 独立权限，避免权限目录和角色迁移扩大范围。

后端仍必须保留 `@RequirePermission("market:release:create")`，前端权限指令只作为体验隐藏，不作为安全边界。

## 9. 数据权限

必须分别校验：

- RFQ 来源订单数据权限。
- 销售订单来源订单数据权限。

要求：

- 当前用户无权限访问的来源不能参与替换。
- 如果请求来源全部无权限，返回空结果或权限错误，不能泄露订单和零件数据。
- 审计日志只记录用户实际可操作来源。

2. 纯销售订单来源：
   - 请求 `sources=[{sourceType:"SALES_ORDER",sourceOrderId:2001}]`。
   - 上传 `P-200.pdf`。
   - 断言命中的 `sales_order_item.drawing_url` 被替换。
   - 断言 `sales_order_item.has_drawing = true`。
3. 混合来源：
   - 同时选择 RFQ 和销售订单。
   - 上传同一图号 PDF。
   - 断言两个来源下命中的可变更零件都被替换。
   - 这是本阶段核心验收测试：准备一个 RFQ 零件和一个销售订单零件，二者使用相同图号 `P-MIX-001`；请求 `sources=[{sourceType:"RFQ",sourceOrderId:101},{sourceType:"SALES_ORDER",sourceOrderId:2001}]`，上传 `P-MIX-001.pdf`，断言 `item_quote_version.drawing_url` 与 `sales_order_item.drawing_url` 均被替换，且销售订单零件 `has_drawing = true`。
4. 不依赖零件选择：
   - 请求体不包含任何 selected item IDs。
   - 断言仍按订单范围替换。
5. 不可变更跳过：
   - 已提单或剩余数量为 0 的 RFQ / 销售订单零件不替换。
   - 断言进入 `skippedItems`。
6. 未匹配图纸：
   - 上传 `NO-MATCH.pdf`。
   - 断言进入 `unmatchedDrawings`。
7. 非 PDF：
   - 上传 `readme.txt`。
   - 断言进入 `skippedFiles`。
8. 兼容旧调用：
   - 仅传 `rfqIds` 不传 `sources`。
   - 断言 RFQ 替换仍可用。
9. 审计日志：
   - 断言记录 `sources`、`rfqIds`、`salesOrderIds`。
   - 断言日志摘要不包含文件内容或密钥类敏感字段。

## 11. 验收标准

- 议价提单页面只选择 RFQ 订单时，上传命中图号 PDF 能替换 RFQ 零件图纸。
- 议价提单页面只选择销售订单时，上传命中图号 PDF 能替换销售订单零件图纸。
- 核心验收：议价提单页面同时选择 RFQ 和销售订单时，上传同一个图号 PDF；该图号同时命中 RFQ 零件和销售订单零件时，两类来源下的可变更零件都被替换，RFQ 写入 `item_quote_version.drawing_url`，销售订单写入 `sales_order_item.drawing_url` 并同步 `has_drawing=true`。
- 用户不勾选任何零件，只要已选择订单并上传命中图纸，也能替换。
- 当前分页不可见的命中零件也能替换。
- 已有图纸的可变更零件被覆盖为新图纸。
- RFQ 已提单零件允许覆盖主表图纸；真正不可变更零件不覆盖，并出现在跳过结果中。
- 未命中订单范围内任何图号的 PDF 出现在未匹配结果中。
- 非 PDF 文件出现在跳过结果中。
- 操作日志记录混合来源摘要，不记录文件内容或敏感信息。
- 前端定向测试、后端定向测试、前端 build 通过。
