# 材料规格级价格与核价选择重构开发文档

> 编写日期：2026-08-29  
> 适用范围：材料工艺模块材料费用页、核价材料选择弹窗、订单全局默认设定、逐件核价、重复件推荐、MES 材料主数据同步后的本地价格维护。  
> 核心结论：本次可以实现，且建议把“材料价格”从当前单套 `板材/棒材/管材` 改为固定三套规格价格；核价身份从 `材料编码 + 形态` 升级为 `材料编码 + 规格 + 形态`。前端继续做即时预估，最终保存仍以后端数据库最新材料规格价格重新核算。

## 1. 背景

当前 `材料工艺 > 材料费用` 的材料价格模型是：

- 一个材料编码。
- 一个 QPO 维护的具体密度。
- 三个形态单价：`platePrice / barPrice / tubePrice`，对应板材、棒材、管材。

实际业务中，同一个材料会因为用料规格、采购批量或供应规格不同产生规格级价格差异；同时很多材料的板材、棒材、管材价格其实相同。如果继续只维护三种形态价格，会出现两个问题：

- 同材料不同规格无法区分，核价人员只能新建多个材料或临时改价，容易污染材料主数据。
- 板材、棒材、管材价格相同时需要重复维护三次，维护成本高，也容易漏填。

因此本次重构目标是：在材料编码下新增固定三套价格规格，每套规格内维护 `统一价格 + 板材价格 + 棒材价格 + 管材价格`，并让核价时明确选择使用哪一套规格。

## 2. 最终业务口径

### 2.1 材料价格结构

每个材料固定包含三套规格：

| 规格编码 | 展示名 | 含义 |
| --- | --- | --- |
| `SPEC_1` | 规格一 | 第一套规格价格。 |
| `SPEC_2` | 规格二 | 第二套规格价格。 |
| `SPEC_3` | 规格三 | 第三套规格价格。 |

每套规格维护四个价格：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `unifiedPrice` | decimal | 统一价格，作为该规格下板材、棒材、管材的兜底。 |
| `platePrice` | decimal | 板材价格。为空或 0 时使用统一价格。 |
| `barPrice` | decimal | 棒材价格。为空或 0 时使用统一价格。 |
| `tubePrice` | decimal | 管材价格。为空或 0 时使用统一价格。 |

### 2.2 价格取值规则

核价时实际材料单价按 `规格 + 形态` 解析：

```text
板材实际单价 = SPEC_x.platePrice > 0 ? SPEC_x.platePrice : SPEC_x.unifiedPrice
棒材实际单价 = SPEC_x.barPrice   > 0 ? SPEC_x.barPrice   : SPEC_x.unifiedPrice
管材实际单价 = SPEC_x.tubePrice  > 0 ? SPEC_x.tubePrice  : SPEC_x.unifiedPrice
```

关键规则：

- `null`、空字符串、`0` 都视为该形态价格未维护，需要回退统一价格。
- 如果形态价格和统一价格都为空或 0，则视为该规格价格未维护，后端禁止完成普通件核价。
- 不允许负数价格。
- 材料密度规则不变：优先使用 QPO 具体密度，缺失时使用 MES 密度兜底。

### 2.3 核价身份

重构后，普通件核价使用的材料身份为：

```text
材料编码 materialCode + 价格规格 priceSpecCode + 材料形态 shape
```

原因：同一个 `materialCode` 下，`SPEC_1` 与 `SPEC_2` 可能是完全不同采购规格；同一个规格下，板材和棒材也可能因为形态专价不同产生不同材料费。因此重复件推荐、全局默认材料、逐件核价保存都必须带上规格身份。

### 2.4 MES 同步边界

MES 材料同步继续只维护材料基础身份、MES 类型、MES 密度和追踪字段，不覆盖 QPO 规格价格。

新增或重新启用 MES 来源材料时，QPO 自动补齐三条空的规格价格记录；如果 MES 全量同步删除某个 MES 来源材料，其规格价格随材料一并删除。

## 4. 方案选择

### 4.1 方案 A：在 `dict_material` 上平铺 12 个价格字段

新增字段示例：

```text
spec1_unified_price / spec1_plate_price / spec1_bar_price / spec1_tube_price
spec2_unified_price / spec2_plate_price / spec2_bar_price / spec2_tube_price
spec3_unified_price / spec3_plate_price / spec3_bar_price / spec3_tube_price
```

优点：

- 改动文件少。
- 不需要新增 mapper 和子表查询。
- 第一版写起来快。

缺点：

- `dict_material` 字段膨胀明显。
- DTO 和前端表单会出现大量重复字段。
- 后续如果要加规格名称、规格说明、用量区间、启停状态，会继续膨胀。
- 重复逻辑较多，不利于长期维护。

### 4.2 方案 B：新增材料价格规格子表

新增 `dict_material_price_spec`，每个材料固定三行规格价格。

优点：

- 数据模型更贴近业务：材料是主数据，规格价格是材料下的子资源。
- 固定三套规格也能通过 `SPEC_1 / SPEC_2 / SPEC_3` 稳定约束。
- 后续如果要给规格加说明、用量范围或启停，不需要继续加一堆列。
- 前端可以统一按 `priceSpecs[]` 渲染三列和详情弹窗。

缺点：

- 需要新增实体、mapper、批量查询和事务保存。
- 需要确保材料分页查询避免 N+1。

### 4.3 推荐方案

推荐采用 **方案 B：新增材料价格规格子表**。

理由：这次需求已经不只是“多几个价格”，而是新增了一个明确业务维度“规格”。把规格建成子表后，前端表格、详情弹窗、核价快照和重复件匹配都能围绕 `priceSpecCode` 处理，不会把 `dict_material` 变成 12 个价格字段堆叠的宽表。

考虑系统尚未上线，可以不做复杂旧数据兼容；但仍遵守 Flyway 追加迁移规则，不直接修改 `V1__qpo_baseline_schema.sql` 和 `V2__qpo_baseline_seed_data.sql`。

## 5. 数据库设计

### 5.1 新增迁移

新增迁移：

```text
quote-backend/src/main/resources/db/migration/V27__material_price_specs.sql
```

建议 SQL：

```sql
CREATE TABLE IF NOT EXISTS dict_material_price_spec (
    id BIGSERIAL PRIMARY KEY,
    material_id BIGINT NOT NULL,
    spec_code VARCHAR(20) NOT NULL,
    spec_name VARCHAR(40) NOT NULL,
    unified_price NUMERIC(12,2),
    plate_price NUMERIC(12,2),
    bar_price NUMERIC(12,2),
    tube_price NUMERIC(12,2),
    sort_no INTEGER NOT NULL DEFAULT 0,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_material_price_spec_material
        FOREIGN KEY (material_id) REFERENCES dict_material(id) ON DELETE CASCADE,
    CONSTRAINT uk_material_price_spec_material_code UNIQUE (material_id, spec_code),
    CONSTRAINT ck_material_price_spec_code CHECK (spec_code IN ('SPEC_1', 'SPEC_2', 'SPEC_3')),
    CONSTRAINT ck_material_price_spec_unified_non_negative CHECK (unified_price IS NULL OR unified_price >= 0),
    CONSTRAINT ck_material_price_spec_plate_non_negative CHECK (plate_price IS NULL OR plate_price >= 0),
    CONSTRAINT ck_material_price_spec_bar_non_negative CHECK (bar_price IS NULL OR bar_price >= 0),
    CONSTRAINT ck_material_price_spec_tube_non_negative CHECK (tube_price IS NULL OR tube_price >= 0)
);

CREATE INDEX IF NOT EXISTS idx_material_price_spec_material
    ON dict_material_price_spec(material_id, sort_no, id);
```

### 5.2 旧价格字段处理

第一版重构建议把旧字段从运行时代码中彻底移除：

```text
dict_material.plate_price
dict_material.bar_price
dict_material.tube_price
```

迁移策略有两种：

| 策略 | 适用场景 | 说明 |
| --- | --- | --- |
| 保留列但运行时不用 | 风险最低 | `V27` 只新增规格子表，旧列暂时保留，代码不再读写。 |
| 新增子表后删除旧列 | 更彻底 | `V27` 创建子表、可选迁移旧值到 `SPEC_1`，再 `DROP COLUMN IF EXISTS plate_price/bar_price/tube_price`。 |

推荐第一版采用 **新增子表后删除旧列**，原因是用户已确认系统未上线、可以清理旧材料价格；同时可以避免后续代码还误读旧单套价格。

建议迁移内先做一次可选旧值迁移，方便开发库和测试库过渡：

```sql
INSERT INTO dict_material_price_spec(material_id, spec_code, spec_name, unified_price, plate_price, bar_price, tube_price, sort_no)
SELECT id, 'SPEC_1', '规格一',
       COALESCE(NULLIF(plate_price, 0), NULLIF(bar_price, 0), NULLIF(tube_price, 0)),
       plate_price, bar_price, tube_price, 10
FROM dict_material
ON CONFLICT (material_id, spec_code) DO NOTHING;

INSERT INTO dict_material_price_spec(material_id, spec_code, spec_name, sort_no)
SELECT id, 'SPEC_2', '规格二', 20 FROM dict_material
ON CONFLICT (material_id, spec_code) DO NOTHING;

INSERT INTO dict_material_price_spec(material_id, spec_code, spec_name, sort_no)
SELECT id, 'SPEC_3', '规格三', 30 FROM dict_material
ON CONFLICT (material_id, spec_code) DO NOTHING;

ALTER TABLE dict_material
    DROP COLUMN IF EXISTS plate_price,
    DROP COLUMN IF EXISTS bar_price,
    DROP COLUMN IF EXISTS tube_price;
```

如果上线前决定重建干净数据库，也不需要人工维护旧字段兼容；MES 同步后新材料会自动生成三条空规格，业务人员再在 QPO 内维护规格价格。

### 5.3 不新增交易明细规格列

第一版不建议在 `item_quote_version`、`sales_order_item`、`order_delivery_ticket`、`order_delivery_ticket_allocation` 上新增 `material_price_spec_code` 实体列。

原因：

- 这些表当前已经通过 `material_data JSON` 保存核价快照。
- 下游销售订单、提单、WMS、MES、U9 的主身份仍是 `engineeringMaterialCode / materialNo / materialShape`，规格只影响核价材料单价，不改变外部下发合同。
- 重复件推荐当前在 Java 中读取 `materialData`，可以通过 `MaterialDataResolver` 从 JSON 中取规格。

需要保存到快照 JSON 的字段：

```json
{
  "materialCode": "300101017460",
  "materialName": "45#",
  "materialTypeCode": "MATERIAL",
  "materialTypeName": "原材料",
  "materialCategory": "钢铁",
  "shape": "板材",
  "priceSpecCode": "SPEC_1",
  "priceSpecName": "规格一",
  "priceSpec": {
    "specCode": "SPEC_1",
    "specName": "规格一",
    "unifiedPrice": 12.00,
    "platePrice": null,
    "barPrice": 13.00,
    "tubePrice": null
  },
  "unitPrice": 12.00,
  "unitPriceSource": "UNIFIED_PRICE",
  "unitPriceUnit": "元/kg"
}
```

说明：

- `unitPrice` 继续保留，给报价导出、价格摘要和历史快照使用。
- `priceSpec` 是当时选择规格的快照，便于追溯当时为什么得到这个价格。
- 后端保存核价时仍按 `materialCode + priceSpecCode + shape` 重新读数据库价格，重算后再覆盖 `unitPrice / priceSpec / cost`。

### 6.6 改造后端权威计价

修改文件：

```text
quote-backend/src/main/java/com/machining/quote/service/EngineerService.java
```

改造点：

- `calculateMaterialCost(...)` 从 `materialData.priceSpecCode` 读取规格。
- 规格缺失直接拒绝普通件核价，提示 `请重新选择材料规格`。
- `resolveMaterialPrice(material, shape)` 改为 `resolveMaterialPrice(material, priceSpecCode, shape)`。
- 根据 `material_id + spec_code` 读取规格价格。
- 形态价为空或 0 时回退统一价格。
- 形态价和统一价都为空或 0 时拒绝核价，错误信息包含材料编码、材料名称、规格、形态。
- 重算后写回 `materialData.priceSpecCode / priceSpecName / priceSpec / unitPrice / unitPriceSource / cost`。

后端最终计算仍保持：

```text
材料费用 = 毛坯重量 × 当前数据库规格有效单价
基础成本 = 材料费用 + 工艺费用
未税/含税价格 = 基础成本 × 当前百分比费用规则
```

## 7. 前端改造设计

## 11. 数据治理与迁移注意事项

### 11.1 上线前数据处理

系统未正式上线，可以接受旧材料价格数据被清理或迁移到 `SPEC_1`。推荐顺序：

1. 新增 `dict_material_price_spec`。
2. 对已有材料自动补齐三套规格。
3. 如开发库已有旧板棒管价格，可迁移到 `SPEC_1` 方便测试。
4. 删除运行时代码对旧顶层价格字段的依赖。
5. 由业务在材料费用页重新维护真实三套规格价格。

### 11.2 数据检查 SQL

上线前检查每个启用材料是否都有三套规格：

```sql
SELECT m.id, m.material_code, m.material_name, COUNT(s.id) AS spec_count
FROM dict_material m
LEFT JOIN dict_material_price_spec s ON s.material_id = m.id
WHERE m.enabled = TRUE
GROUP BY m.id, m.material_code, m.material_name
HAVING COUNT(s.id) <> 3;
```

检查已核价普通件是否缺少规格身份：

```sql
SELECT id, rfq_id, part_no, version
FROM item_quote_version
WHERE quote_mode = 'NORMAL'
  AND material_data IS NOT NULL
  AND material_data::jsonb ? 'materialCode'
  AND NOT (material_data::jsonb ? 'priceSpecCode');
```

如果正式上线前没有历史业务数据，可以清空并重新核价；如果已有真实业务数据，则这些记录需要人工补齐规格后再启用新逻辑。

## 15. 风险与注意事项

- 这是材料价格模型重构，不建议拆成只改前端展示的小补丁；否则前端能选规格，后端最终核价却无法按规格重算。
- 规格选择必须进入全局模板和逐件核价快照，否则同材料不同规格会被重复件推荐误合并。
- 选择弹窗内未保存草稿如果直接用于核价，会造成前端预估和后端最终保存不一致；第一版建议要求先保存材料规格价格再选择。
- 旧已核价记录如果没有 `priceSpecCode`，第一版不做兜底自动迁移，应提示重新选择规格并重新核价。
- 不要把材料规格价格传给 MES/WMS/U9，它只影响 QPO 内部报价成本，不是外部系统合同字段。
- Flyway 仍按追加迁移处理，不直接修改已存在的基线迁移；如上线前要重建基线，需要单独确认数据库基线重建策略。
