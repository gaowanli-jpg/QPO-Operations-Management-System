# QPO 订单状态管理与废弃恢复开发文档

## 1. 背景

QPO 当前已经完成两条核心状态流：

```text
订单：未核价 -> 已核价 -> 已报价 -> 部分已提单 -> 已生成提单
零件：未核价 -> 已核价 -> 已报价 -> 已提单
```

同时，议价提单已经升级为不可逆发布模型：

- `order_delivery_ticket` 是已提单零件明细表 / 发布记录表。
- `order_delivery_ticket` 是 MES/WMS 需求池与工艺快照事实来源。
- QPO 内部“已生成工艺表行”从 `order_delivery_ticket` 动态生成展示，不再依赖独立 `order_process_sheet`。
- 提单行、工艺表行、订单提单/工艺重置能力已经删除或废弃。

当前缺口是：订单管理模块只能查看和彻底删除订单，缺少企业级的“状态管理”能力。实际业务中，管理员需要处理以下场景：

- 订单已经 `已报价`，但市场发现报价交期或报价确认流程需要重新调整，希望退回 `已核价`。
- 订单已经 `已核价`，但工程认为还需要重新核价，希望退回 `未核价`。
- 订单需要停止继续流转，希望标记为 `废弃`，但不物理删除数据。
- 废弃订单需要恢复处理，希望从 `废弃` 恢复为 `已核价`。

本次开发目标是在订单管理模块内补齐状态管理，而不是新增独立模块。

## 2. 核心结论

1. 状态管理放在 `订单管理` 模块，不新增左侧一级菜单。
2. 订单管理可以检索 6 种订单状态：
   - `未核价`
   - `已核价`
   - `已报价`
   - `部分已提单`
   - `已生成提单`
   - `废弃`
3. `部分已提单` 和 `已生成提单` 不允许废弃，也不允许状态回退。
4. 废弃和恢复是纯状态动作：
   - 不清空核价结果。
   - 不清空报价交期。
   - 不删除图纸。
   - 不删除提单。
   - 不删除动态工艺表展示数据。
   - 不重算价格。
5. 状态动作必须同时更新订单状态和相关零件状态。
6. 每种状态动作必须有独立权限、操作日志、文件日志和测试。
7. 已生成工艺表行继续和议价提单模块一致，从 `order_delivery_ticket` 动态生成展示。

## 3. 非目标

- 不恢复已删除的提单行删除、工艺表行删除、订单重置提单/工艺功能。
- 不新增 `order_process_sheet` 表或兼容写入。
- 不新增旧 APS 同步状态管理。
- 不修改历史兼容接口增量游标。
- 不改变分批提单规则。
- 不清理或重置已有核价、报价、图纸、材料、工艺、交期等业务字段。
- 不把“彻底删除订单”改造成废弃；彻底删除仍是独立高风险能力。
- 不新增可分配 `common:*` 权限。
- 不新增独立“状态管理”左侧菜单。

## 4. 状态定义

### 4.1 订单状态

| 状态 | 含义 | 可进入订单管理列表 | 可执行状态动作 |
| --- | --- | --- | --- |
| `未核价` | RFQ 已导入，工程尚未完成整单核价 | 是 | 可废弃 |
| `已核价` | 工程已完成核价，等待市场保存报价单 | 是 | 可退回未核价、可废弃 |
| `已报价` | 市场已保存报价单，可以进入报价单导出和提单流程 | 是 | 可退回已核价、可废弃 |
| `部分已提单` | 已有部分数量生成不可逆提单 | 是 | 只读，不允许废弃或回退 |
| `已生成提单` | 可提单数量已全部生成不可逆提单 | 是 | 只读，不允许废弃或回退 |
| `废弃` | 订单被业务管理员停止流转，但数据保留 | 是 | 可恢复为已核价 |

### 4.2 零件状态

| 状态 | 含义 | 状态管理写入规则 |
| --- | --- | --- |
| `未核价` | 零件尚未完成核价 | 订单从 `已核价` 退回 `未核价` 时，相关零件同步写入 |
| `已核价` | 零件已完成核价，等待市场保存报价单 | 订单从 `已报价` 退回或从 `废弃` 恢复时，相关零件同步写入 |
| `已报价` | 市场已确认报价单，该零件可进入提单流程 | 本次状态管理不新增写入，仍由保存报价单负责 |
| `已提单` | 零件原始数量已全部生成提单 | 本次状态管理不允许改动 |
| `废弃` | 零件随订单废弃停止流转 | 订单废弃时，相关非提单零件同步写入 |
| `无图` | 特殊展示状态 | 废弃时可随订单写入 `废弃`；恢复时按目标状态写入 `已核价`，但后续保存报价单仍由业务校验兜底 |

说明：

- `废弃` 是订单和零件共用的停止流转状态。
- `部分已提单`、`已生成提单` 是订单状态，不作为新零件状态写入。
- `已提单` 是零件最终状态，不能被状态管理回退。
- 状态管理只改 `status`，不会清除已有字段；如果后续需要“清空核价结果重新开始”，应另立功能和权限。

## 5. 状态动作矩阵

| 动作 | 来源状态 | 目标状态 | 是否允许 | 权限 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 已报价退回已核价 | `已报价` | `已核价` | 允许 | `market:order:rollback-quoted` | 取消市场报价单确认状态，但保留报价交期和报价数据 |
| 已核价退回未核价 | `已核价` | `未核价` | 允许 | `market:order:rollback-priced` | 退回工程核价状态，但保留已录入核价数据作为草稿 |
| 废弃订单 | `未核价` / `已核价` / `已报价` | `废弃` | 允许 | `market:order:discard` | 停止订单继续流转，不物理删除 |
| 废弃订单 | `部分已提单` / `已生成提单` | `废弃` | 禁止 | `market:order:discard` | 已产生不可逆提单，不能废弃 |
| 恢复订单 | `废弃` | `已核价` | 允许 | `market:order:restore` | 人工恢复到市场报价确认前状态 |
| 任意回退 | `部分已提单` / `已生成提单` | 任意前置状态 | 禁止 | 对应权限 | 保护不可逆提单和外部系统需求池稳定性 |

### 5.1 业务后果

`已报价 -> 已核价`：

- 订单不能继续导出报价单。
- 报价处理模块可以重新编辑报价交期。
- 再次点击保存报价单后，订单重新进入 `已报价`。
- 既有报价交期保留为草稿值。

`已核价 -> 未核价`：

- 订单回到工程核价前状态。
- 已有核价数据保留为草稿，方便工程重新调整。
- 如果工程重新完成整单核价，再进入 `已核价`。

`未核价 / 已核价 / 已报价 -> 废弃`：

- 订单不应出现在零件核价、报价处理、议价提单等正常业务候选列表中。
- 订单管理中选择 `废弃` 状态时可以检索。
- 历史查询可以保留展示，但默认不作为可流转订单。

`废弃 -> 已核价`：

- 恢复目标固定为 `已核价`，这是人工管理动作，不按废弃前状态自动恢复。
- 相关零件同步写入 `已核价`。
- 如果零件核价数据或报价交期不完整，后续保存报价单、导出、提单仍由现有业务校验拒绝。

## 6. 数据模型设计

### 6.1 状态常量

扩展现有：

```text
quote-backend/src/main/java/com/machining/quote/domain/QuoteStatusWorkflow.java
```

新增常量：

```java
public static final String DISCARDED = "废弃";
```

建议新增辅助方法：

```java
public static boolean isReleasedOrderStatus(String status) {
    return PARTIALLY_RELEASED.equals(status) || RELEASED.equals(status);
}

public static boolean isDiscardableOrderStatus(String status) {
    return UNPRICED.equals(status) || PRICED.equals(status) || QUOTED.equals(status);
}

public static boolean isStatusManagementVisible(String status) {
    return UNPRICED.equals(status)
            || PRICED.equals(status)
            || QUOTED.equals(status)
            || PARTIALLY_RELEASED.equals(status)
            || RELEASED.equals(status)
            || DISCARDED.equals(status);
}
```

### 6.2 是否新增字段

第一版不建议在 `order_rfq` 新增废弃原因、废弃人、恢复人等字段，原因：

- 这次需求是纯状态管理。
- 现有 `audit_log` 已能记录操作者、时间、before/after、原因摘要、requestId。
- 新增字段会增加迁移和页面维护成本，但不能替代操作日志。

如需填写原因，建议请求体提供可选 `reason`，只写入操作日志和文件日志摘要：

```json
{
  "reason": "客户取消本次询价"
}
```

可选原因规则：

- 前端不强制填写。
- 后端限制最大长度，例如 200 字。
- 文件日志只记录是否有原因和安全摘要，不记录大段文本。

### 6.3 数据完整性守卫

状态动作必须同时检查：

1. `order_rfq.status` 当前状态是否允许动作。
2. `order_delivery_ticket` 是否已经存在提单行。
3. 当前用户是否有订单数据权限。
4. 当前用户是否有对应动作权限。

即使订单状态错误地停留在 `已报价`，只要该订单已经存在提单行，也必须拒绝废弃或回退。

原因：

- 提单行是不可逆发布记录。
- MES/WMS 或历史兼容接口可能已经按 `order_delivery_ticket.id` 读取过数据。
- 不能仅凭订单状态判断是否安全。

## 7. 后端设计

### 7.1 新增服务

建议新增独立服务，避免 `OrderManagementService` 继续膨胀：

```text
quote-backend/src/main/java/com/machining/quote/service/OrderStatusManagementService.java
```

职责：

- 执行订单状态动作。
- 做状态机校验。
- 做提单存在性校验。
- 做数据权限校验。
- 批量同步零件状态。
- 写操作日志和文件日志。

建议方法：

```java
public OrderStatusChangeResult rollbackQuoted(Integer rfqId, OrderStatusChangeReq req);

public OrderStatusChangeResult rollbackPriced(Integer rfqId, OrderStatusChangeReq req);

public OrderStatusChangeResult discard(Integer rfqId, OrderStatusChangeReq req);

public OrderStatusChangeResult restore(Integer rfqId, OrderStatusChangeReq req);
```

### 7.3 Controller 接口

修改：

```text
quote-backend/src/main/java/com/machining/quote/controller/OrderManagementController.java
```

新增接口：

```text
POST /api/order-management/orders/{rfqId}/rollback-quoted
POST /api/order-management/orders/{rfqId}/rollback-priced
POST /api/order-management/orders/{rfqId}/discard
POST /api/order-management/orders/{rfqId}/restore
```

权限：

```java
@RequirePermission("market:order:rollback-quoted")
@RequirePermission("market:order:rollback-priced")
@RequirePermission("market:order:discard")
@RequirePermission("market:order:restore")
```

说明：

- 不使用一个泛用 `change-status` 接口暴露任意目标状态，避免越权或错误状态跳转。
- Controller 可以薄封装，统一调用 `OrderStatusManagementService`。
- 后端仍是最终安全边界，前端隐藏按钮不能替代后端校验。

### 7.4 事务与并发

状态动作必须加事务：

```java
@Transactional
```

建议执行顺序：

1. 锁定订单。
2. 校验当前状态。
3. 校验提单行数量。
4. 校验数据权限。
5. 更新订单状态。
6. 更新相关零件状态。
7. 写操作日志。
8. 返回结果。

如果现有 Mapper 不支持 `FOR UPDATE`，建议新增明确方法：

```java
OrderRfq selectOrderForUpdate(@Param("rfqId") Integer rfqId);
```

并在 XML 或注解 SQL 中使用：

```sql
SELECT * FROM order_rfq WHERE id = #{rfqId} FOR UPDATE
```

这样可以避免管理员状态回退和报价保存、提单生成并发执行导致状态错乱。

### 7.5 状态写入规则

| 动作 | 订单写入 | 零件写入 |
| --- | --- | --- |
| `rollbackQuoted` | `已核价` | 该订单下非 `已提单` 零件写 `已核价` |
| `rollbackPriced` | `未核价` | 该订单下非 `已提单` 零件写 `未核价` |
| `discard` | `废弃` | 该订单下非 `已提单` 零件写 `废弃` |
| `restore` | `已核价` | 该订单下非 `已提单` 零件写 `已核价` |

注意：

- 正常情况下，允许状态管理的订单不应存在 `已提单` 零件。
- 仍建议更新时排除 `已提单`，作为数据异常兜底。
- 如发现目标订单存在提单行，应整体拒绝动作，而不是部分更新。

### 7.6 与订单详情的关系

订单详情保持现状：

- 零件清单来自 `item_quote_version`。
- 已生成提单行来自 `order_delivery_ticket`。
- 已生成工艺表行通过 `DeliveryService.listProcessSheets(rfqId)` 从 `order_delivery_ticket` 动态生成。

本次不改详情结构，只新增状态管理动作和状态筛选。

## 10. 数据权限

状态管理是订单级写操作，必须接入现有数据范围。

要求：

- 订单列表按当前用户数据范围过滤。
- 状态动作执行前再次校验当前用户是否能访问该订单。
- 没有订单数据权限时，列表为空。
- 直接访问无数据权限订单的状态接口，后端返回拒绝。

多角色数据范围仍按现有并集规则执行。

## 11. 操作日志与文件日志

### 11.1 操作日志

新增动作编码：

| 动作编码 | 业务动作 |
| --- | --- |
| `ORDER_STATUS_ROLLBACK_QUOTED` | 已报价退回已核价 |
| `ORDER_STATUS_ROLLBACK_PRICED` | 已核价退回未核价 |
| `ORDER_DISCARD` | 废弃订单 |
| `ORDER_RESTORE` | 恢复废弃订单 |

建议记录：

| 字段 | 内容 |
| --- | --- |
| module | `ORDER_MANAGEMENT` |
| objectType | `order_rfq` |
| objectId | `rfqId` |
| before | `{ status, itemStatusSummary, ticketCount }` |
| after | `{ status, updatedItemCount }` |
| message | `订单状态调整：RFQ xxx，已报价 -> 已核价` |
| result | `SUCCESS` / `FAILED` |

说明：

- `reason` 如有填写，写入操作日志 message 或 after 摘要。
- 不记录完整零件明细。
- 业务拒绝是否写失败操作日志可按现有 `AuditService` 规则统一；未预期异常必须能在文件日志中追踪。

### 11.2 后端文件日志

新增稳定事件：

```text
Order status change started
Order status change completed
Order status change rejected
Order status change failed
```

建议字段：

- `action`
- `rfqId`
- `rfqNo`
- `fromStatus`
- `toStatus`
- `updatedItemCount`
- `ticketCount`
- `durationMs`

日志级别：

| 场景 | Level |
| --- | --- |
| 开始、成功 | INFO |
| 状态不允许、已存在提单、无数据权限等可预期拒绝 | WARN |
| 数据库异常、未预期异常 | ERROR |

示例：

```java
log.info("Order status change completed action={} rfqId={} fromStatus={} toStatus={} updatedItemCount={} durationMs={}",
        action, rfqId, fromStatus, toStatus, updatedItemCount, durationMs);
```

注意：

- ERROR 必须带异常对象。
- 不在每个零件循环里打 INFO。
- 不记录完整 before/after JSON。
- 操作日志和文件日志通过 `requestId` 关联。

## 14. 风险与处理

### 14.1 状态和实际提单明细不一致

风险：订单状态可能由于历史数据或人工操作异常停留在 `已报价`，但实际已经存在提单行。

处理：

- 状态管理不能只看 `order_rfq.status`。
- 必须额外查询 `order_delivery_ticket`。
- 只要存在提单行，废弃和回退全部拒绝。

### 14.2 恢复统一到已核价可能带来数据不完整

风险：如果一个原本 `未核价` 的订单被废弃后恢复为 `已核价`，它可能缺少完整核价数据。

处理：

- 这是人工权限动作，必须由高权限角色执行。
- 后续保存报价单、导出、提单继续依赖现有完整性校验。
- 如果数据不完整，业务接口应给出明确错误，而不是自动补零或清空。

### 14.3 状态回退被误解为清空数据

风险：用户以为退回 `未核价` 会清空已有核价结果。

处理：

- 二次确认文案必须明确“只调整状态，不清空业务数据”。
- 操作日志记录 before/after，方便追溯。
- 后续如需“清空核价结果”另立功能，不混入本次状态管理。

### 14.4 权限配置过宽

风险：普通市场人员误废弃订单或误回退状态。

处理：

- 4 个权限默认只给 `SUPER_ADMIN` 和 `MARKET_MANAGER`。
- 角色管理可按需单独授权。
- 每个动作独立权限，不使用一个大而宽的状态管理权限。

### 14.5 日志噪声

风险：状态动作如果按零件逐条打日志，会造成文件日志刷屏。

处理：

- 文件日志只记录订单级摘要和更新数量。
- 零件明细只在操作日志 before/after 中记录统计，不记录完整列表。
