# 已提零件未完成池与锁库结果池重构开发文档

## 1. 背景

当前 QPO 已经形成 MES/WMS 外部系统处理链路：

- `order_delivery_ticket` 保存提单零件事实记录，也是 MES/WMS 处理的原始需求池。
- 已提零件模块读取 `order_delivery_ticket`，支持获取 MES 物料号、等待 MES 回调、提交 WMS 锁库和失败重试。
- `order_delivery_ticket_allocation` 保存 WMS 成功后的锁库拆分结果。
- 锁库结果池只展示已入库锁定和在产锁定结果；WMS 拆分出的待生产数量进入待产零件模块。

现在业务上希望“已提零件”不再像历史总账一样长期展示所有提单行，而是只展示还没走完整个 MES + WMS 外部系统流程的提单零件。走完整个流程的零件应从已提零件默认列表中消失，并在“锁库零件”模块作为结果展示。

本重构不删除、不搬迁、不复制 `order_delivery_ticket` 主记录。`order_delivery_ticket` 继续作为全量事实表永久保留，页面和接口通过状态过滤形成“未完成池 / 结果池”的模块边界。

## 2. 当前模块现状

### 2.1 已提零件

后端：

- Controller：`OrderDeliveryController`
- 列表接口：`GET /api/order-delivery/tickets`
- 详情接口：`GET /api/order-delivery/tickets/{ticketId}`
- Service：`DeliveredItemService`
- Mapper：`OrderDeliveryTicketMapper.selectDeliveredItems(...)` / `countDeliveredItems(...)`
- 当前默认查询：直接查询 `order_delivery_ticket ticket`，按 `ticket.id DESC` 分页。
- 当前过滤字段：客户、RFQ 号、图号、版本、物料号、内部项目号、客户订单号、客户项目号、MES 状态、WMS 状态、交期范围。
- 当前权限：`market:delivered-item:view`、`market:delivered-item:mes-sync`、`market:delivered-item:wms-allocate`、`market:delivered-item:file-preview`、`market:delivered-item:customer-select`。

前端：

- 页面：`DeliveredItemManage.vue`
- 支持 MES 状态筛选、WMS 状态筛选、单条 / 批量获取物料号、单条 / 批量提交 WMS、查看锁库结果。
- 当前页面会展示完成和未完成的提单行，除非用户手动筛选状态。

### 2.2 锁库零件

后端：

- 列表接口：`GET /api/order-delivery/locked-items`
- 按提单行查结果：`GET /api/order-delivery/tickets/{ticketId}/allocations`
- Service：`LockedItemService`
- Mapper：`OrderDeliveryTicketAllocationMapper.selectLockedItems(...)` / `countLockedItems(...)`
- 当前默认查询：查询 `order_delivery_ticket_allocation alloc`，按 `alloc.id DESC` 分页。
- 当前权限：`market:locked-item:view`、`market:locked-item:customer-select`。

前端：

- 页面：`LockedItemManage.vue`
- 展示 WMS 拆分后的 allocation 明细。

### 2.3 已有性能基础

已有索引包括：

- `idx_order_delivery_ticket_mes_status ON order_delivery_ticket(mes_sync_status, id)`
- `idx_order_delivery_ticket_wms_status ON order_delivery_ticket(wms_allocate_status, id)`
- `idx_order_delivery_ticket_material_no ON order_delivery_ticket(material_no, id)`
- `idx_delivery_allocation_ticket ON order_delivery_ticket_allocation(ticket_id, id)`
- `idx_order_delivery_ticket_part_version ON order_delivery_ticket(part_no, version, id)`
- `idx_order_delivery_ticket_rfq_id_id ON order_delivery_ticket(rfq_id, id)`
- `idx_order_delivery_ticket_source ON order_delivery_ticket(source_type, source_order_id, source_item_id)`

这些索引已经能支撑基础分页、状态过滤和通过 `ticket_id` 查询 allocation。本次需要补一个更适合“未完成池默认列表”的组合 / 部分索引，避免数据量增长后默认页面扫描过多已完成行。

## 3. 目标

### 3.1 业务目标

- 已提零件模块默认只展示还没有完成 MES + WMS 全流程的提单零件。
- 锁库零件模块继续展示 WMS 成功后生成的 allocation 结果。
- 完成流程的提单行不从数据库删除，不移动到新表，不全额复制。
- 通过 `ticketId` 保持提单行、MES 请求、MES 回调、WMS allocation、销售订单物料号回写、操作日志和文件日志的完整溯源。

### 3.2 技术目标

- 后端默认查询加入“未完成流程”过滤。
- 保留后端分页，不允许前端全量拉取再过滤。
- 保持 `order_delivery_ticket` 为事实主表。
- 保持 `order_delivery_ticket_allocation` 为 WMS 结果表。
- 补充索引，确保状态过滤、分页排序和 allocation 存在性判断可被数据库高效执行。
- 不新增用户权限，不新增高频查询日志。

## 4. 非目标

- 不删除 `order_delivery_ticket` 中已完成的提单行。
- 不新增“已完成提单零件主表”。
- 不把 `order_delivery_ticket` 复制到另一个历史表。
- 不改变 MES 获取物料号、MES 回调、同图号版本去重、WMS 锁库分配的写入逻辑。
- 不改变锁库零件 allocation 的业务含义。
- 不在第一阶段新增复杂归档任务、冷热分表或物理归档。

## 5. 核心定义

### 5.1 未完成流程

一条提单零件满足任一条件，即视为“未完成流程”，应出现在已提零件默认列表：

- `material_no` 为空。
- `mes_sync_status` 不是 `SUCCESS`。
- `wms_allocate_status` 不是 `SUCCESS`。
- 没有对应的 `order_delivery_ticket_allocation.ticket_id` 记录。

### 5.2 完成流程

一条提单零件同时满足以下条件，即视为“已完成流程”，默认不再出现在已提零件列表：

```text
material_no 非空
AND mes_sync_status = 'SUCCESS'
AND wms_allocate_status = 'SUCCESS'
AND EXISTS (
  SELECT 1
  FROM order_delivery_ticket_allocation alloc
  WHERE alloc.ticket_id = order_delivery_ticket.id
)
```

完成流程后，该行仍然保留在 `order_delivery_ticket` 中，可通过锁库零件、提单表据、订单详情、日志和内部排查 SQL 反查。

### 5.3 模块边界

```text
order_delivery_ticket
  = 提单零件事实主表 / MES-WMS需求池
  = 不删除、不搬迁、不复制

已提零件模块
  = 默认展示 order_delivery_ticket 中未完成 MES/WMS 全流程的行
  = 用户处理物料号、MES回调、WMS提交、失败重试

order_delivery_ticket_allocation
  = WMS成功后的锁库拆分结果表

锁库零件模块
  = 展示 order_delivery_ticket_allocation 结果
  = 可通过 ticket_id 反查原始提单行
```

## 6. 设计方案

### 6.1 推荐方案

采用“默认过滤 + 索引优化 + 可选查询范围参数”的方式：

- `DeliveredItemService.listTickets(...)` 默认查询 `flowScope = ACTIVE`。
- `ACTIVE` 表示未完成流程。
- `COMPLETED` 表示已完成流程，可作为后端预留，不一定第一版在页面暴露。
- `ALL` 表示全部提单行，可作为后端排查或后续管理员能力预留。
- 前端已提零件页面默认不传 `flowScope`，后端按 `ACTIVE` 处理。
- 锁库零件页面不变，继续查 allocation。

优势：

- 不破坏溯源。
- 不引入双主表。
- 不需要迁移历史数据。
- 改动集中在查询层、少量 UI 文案和索引。
- 性能可通过索引、分页和 `EXISTS` 的 `ticket_id` 索引控制。

### 6.2 不采用的方案

不采用“删除已完成提单行并复制到新表”：

- 会破坏 `ticketId` 溯源链路。
- MES 请求流水、MES 回调、WMS allocation、操作日志、文件日志都会产生跨表追踪复杂度。
- 一条业务事实在两张主表之间迁移，会导致后续查询、审计和重试语义混乱。

不采用“前端拉全量再过滤”：

- 大订单或多年数据会让前端和网络承压。
- 后端分页会失效，用户看到的页码和总数不准确。
- 不符合当前 QPO 大数据分页口径。

## 7. 后端改造

### 7.1 DTO 增加查询范围

修改 `DeliveredItemQueryReq`，新增：

```java
private String flowScope;
```

取值：

| 值 | 含义 | 默认 |
| --- | --- | --- |
| `ACTIVE` | 未完成流程 | 是 |
| `COMPLETED` | 已完成流程 | 否 |
| `ALL` | 全部提单行 | 否 |

兼容规则：

- 空值按 `ACTIVE` 处理。
- 非法值按 `ACTIVE` 处理，或直接抛业务错误；第一版建议按 `ACTIVE` 兜底，避免旧前端或手工调用报错。

### 7.2 DeliveredItemService 查询过滤

在 `DeliveredItemService.buildQuery(...)` 中集中追加流程范围过滤：

伪代码：

```java
private void applyFlowScope(QueryWrapper<DeliveredItemDTO> query, String flowScope) {
    String scope = normalizeFlowScope(flowScope);
    if ("ALL".equals(scope)) {
        return;
    }
    if ("COMPLETED".equals(scope)) {
        query.isNotNull("NULLIF(BTRIM(ticket.material_no), '')");
        query.eq("ticket.mes_sync_status", "SUCCESS");
        query.eq("ticket.wms_allocate_status", "SUCCESS");
        query.exists("""
            SELECT 1
            FROM order_delivery_ticket_allocation alloc_done
            WHERE alloc_done.ticket_id = ticket.id
        """);
        return;
    }
    query.and(active -> active
        .isNull("NULLIF(BTRIM(ticket.material_no), '')")
        .or()
        .ne("COALESCE(ticket.mes_sync_status, 'PENDING')", "SUCCESS")
        .or()
        .ne("COALESCE(ticket.wms_allocate_status, 'PENDING')", "SUCCESS")
        .or()
        .notExists("""
            SELECT 1
            FROM order_delivery_ticket_allocation alloc_done
            WHERE alloc_done.ticket_id = ticket.id
        """)
    );
}
```

实际 MyBatis-Plus 写法要注意：

- `NULLIF(BTRIM(ticket.material_no), '') IS NULL` 这类表达式如果 `QueryWrapper.isNull(...)` 不适配，应使用 `apply(...)`。
- `exists/notExists` 子查询必须固定别名为 `alloc_done`，避免和主 SQL 未来 join 别名冲突。
- 过滤应在 `dataScopeService.applyDeliveryTicketScope(query, "ticket")` 前后均可，但推荐放在业务筛选之后、数据范围之前，便于阅读。

### 7.3 Mapper SQL 保持分页

`OrderDeliveryTicketMapper.selectDeliveredItems(...)` 保持：

```sql
ORDER BY ticket.id DESC
LIMIT #{limit} OFFSET #{offset}
```

不得改成：

- 全量查询后 Java 内存过滤。
- 前端过滤。
- 无分页返回。

`countDeliveredItems(...)` 必须使用同一套 `flowScope` 条件，保证总数和分页一致。

### 7.4 详情接口不默认隐藏

`GET /api/order-delivery/tickets/{ticketId}` 不套默认 `ACTIVE` 过滤。

原因：

- 锁库零件模块需要通过 `ticketId` 反查原始提单行。
- 提单表据、订单详情、日志排查可能需要查看已完成流程的原始提单行。

详情接口继续只校验：

- ticket 存在。
- 当前用户数据权限可访问。

## 8. 数据库与性能设计

### 8.1 新增迁移

新增迁移，例如：

```text
V75__delivered_item_active_pool_indexes.sql
```

如实施时 V75 已被占用，使用实际下一迁移编号。

### 8.2 已有索引复用

继续复用：

```sql
idx_order_delivery_ticket_mes_status
idx_order_delivery_ticket_wms_status
idx_order_delivery_ticket_material_no
idx_delivery_allocation_ticket
```

其中 `idx_delivery_allocation_ticket ON order_delivery_ticket_allocation(ticket_id, id)` 对 `EXISTS / NOT EXISTS` 判断很关键，不能删除。

### 8.3 新增未完成池部分索引

为默认已提零件列表新增部分索引：

```sql
CREATE INDEX IF NOT EXISTS idx_order_delivery_ticket_active_flow_id
ON order_delivery_ticket(id DESC)
WHERE
    NULLIF(BTRIM(material_no), '') IS NULL
    OR COALESCE(mes_sync_status, 'PENDING') <> 'SUCCESS'
    OR COALESCE(wms_allocate_status, 'PENDING') <> 'SUCCESS';
```

说明：

- 这个索引用于快速定位明显未完成的行。
- `id DESC` 匹配默认排序。
- `material_no` 空、MES 未成功、WMS 未成功的行会进入索引。
- “状态都成功但 allocation 缺失”的异常行不在该部分索引中，但 `NOT EXISTS` 会通过 `idx_delivery_allocation_ticket` 判断；这类数据应极少，主要用于兜底和数据一致性保护。

### 8.4 新增完成池组合索引

如果实现 `flowScope=COMPLETED`，建议新增：

```sql
CREATE INDEX IF NOT EXISTS idx_order_delivery_ticket_completed_flow_id
ON order_delivery_ticket(mes_sync_status, wms_allocate_status, id DESC)
WHERE NULLIF(BTRIM(material_no), '') IS NOT NULL;
```

说明：

- 便于后续管理员或排查场景查询已完成提单行。
- 不影响默认页面。

### 8.5 allocation 索引确认

迁移中应确保：

```sql
CREATE INDEX IF NOT EXISTS idx_delivery_allocation_ticket
ON order_delivery_ticket_allocation(ticket_id, id);
```

如果已存在，迁移不会重复创建。

### 8.6 查询性能原则

- 默认列表必须后端分页，`pageSize` 最大仍保持 100。
- 默认排序继续使用 `ticket.id DESC`，不要引入无索引动态排序。
- `LIKE` 字段继续作为用户主动筛选，不作为默认条件。
- 不为了性能搬表；如未来数据量极大，优先用 `EXPLAIN ANALYZE` 评估索引和查询计划，再考虑只读汇总视图或物化视图。
- 不新增高频查询 INFO 文件日志，避免分页刷新刷屏。

## 9. 前端改造

### 9.1 已提零件页面默认未完成池

`DeliveredItemManage.vue`：

- 默认查询不传 `flowScope`，由后端默认 `ACTIVE`。
- 页面标题可继续叫“已提零件”。
- 页面说明或空状态文案调整为：

```text
仅展示尚未完成物料号获取和锁库流程的提单零件。
```

- WMS 成功后刷新列表时，该行从默认列表消失。
- WMS 成功提示调整为：

```text
锁库完成，结果已进入锁库零件模块。
```

### 9.2 是否提供“显示已完成”

第一版建议不暴露“显示已完成”按钮，避免用户继续把已提零件当成历史总账。

后端可以预留 `flowScope=COMPLETED / ALL`，但前端暂不展示入口。后续如管理方确实需要，可增加一个高级筛选：

| 选项 | flowScope | 用途 |
| --- | --- | --- |
| 未完成 | `ACTIVE` | 默认工作台 |
| 已完成 | `COMPLETED` | 排查完成记录 |
| 全部 | `ALL` | 管理员审计 |

若未来前端暴露 `ALL`，建议只给 `MARKET_MANAGER` 或独立管理员能力，避免普通用户把页面当成大数据报表。

### 9.3 锁库零件页面不变

`LockedItemManage.vue` 继续展示 allocation 结果，不需要因为本次重构改变默认查询。

可以在锁库零件详情或操作中继续保留：

- 查看原始提单行。
- 按 `ticketId` 跳转 / 筛选。

## 12. 分阶段实施

### 阶段 1：查询口径和索引骨架

目标：先把后端默认查询边界改成未完成池，并补齐索引。

修改：

- 新增迁移 `V75__delivered_item_active_pool_indexes.sql`，或实际下一编号。
- 新增未完成池部分索引 `idx_order_delivery_ticket_active_flow_id`。
- 新增完成池组合索引 `idx_order_delivery_ticket_completed_flow_id`。
- 确认 / 兜底创建 `idx_delivery_allocation_ticket`。
- `DeliveredItemQueryReq` 新增 `flowScope`。
- `DeliveredItemService` 默认应用 `ACTIVE` 过滤。
- 详情接口不应用默认 `ACTIVE` 过滤。

验收：

- 默认已提零件列表不返回已完成流程行。

## 13. 风险与处理

### 13.1 历史数据中 WMS 成功但无 allocation

风险：

- 如果历史数据存在 `wms_allocate_status=SUCCESS` 但 allocation 缺失，按完成条件它仍会留在已提零件未完成池。

处理：

- 这是合理的，因为流程事实上不完整。
- 可由运维 SQL 排查：

```sql
SELECT ticket.id, ticket.rfq_no, ticket.part_no, ticket.version, ticket.material_no
FROM order_delivery_ticket ticket
WHERE ticket.material_no IS NOT NULL
  AND NULLIF(BTRIM(ticket.material_no), '') IS NOT NULL
  AND ticket.mes_sync_status = 'SUCCESS'
  AND ticket.wms_allocate_status = 'SUCCESS'
  AND NOT EXISTS (
      SELECT 1
      FROM order_delivery_ticket_allocation alloc
      WHERE alloc.ticket_id = ticket.id
  )
ORDER BY ticket.id DESC;
```

### 13.2 默认列表数量变化

风险：

- 用户可能发现已提零件数量明显减少。

处理：

- 页面说明文案明确“仅展示尚未完成物料号获取和锁库流程的提单零件”。
- 锁库零件模块承接完成结果。

### 13.3 查询性能

风险：

- 默认未完成过滤包含 `OR` 和 `NOT EXISTS`，数据量很大时需要关注查询计划。

处理：

- 保持后端分页和 `id DESC`。
- 添加部分索引 `idx_order_delivery_ticket_active_flow_id`。
- 保持 allocation `ticket_id` 索引。
- 不使用前端过滤。
- 不使用无索引动态排序。
- 实施后对大数据环境执行：

```sql
EXPLAIN ANALYZE
SELECT ticket.id
FROM order_delivery_ticket ticket
WHERE (
    NULLIF(BTRIM(ticket.material_no), '') IS NULL
    OR COALESCE(ticket.mes_sync_status, 'PENDING') <> 'SUCCESS'
    OR COALESCE(ticket.wms_allocate_status, 'PENDING') <> 'SUCCESS'
    OR NOT EXISTS (
        SELECT 1
        FROM order_delivery_ticket_allocation alloc_done
        WHERE alloc_done.ticket_id = ticket.id
    )
)
ORDER BY ticket.id DESC
LIMIT 20 OFFSET 0;
```

若真实数据量达到百万级且查询计划仍不理想，再考虑新增轻量派生字段 `external_flow_status`，由 MES/WMS 写入链路维护。但第一版不引入该字段，避免过早增加状态一致性维护成本。

## 14. 完成定义

- 已提零件默认列表只展示未完成 MES/WMS 全流程的提单行。
- 完成 MES + WMS 且有 allocation 的提单行从已提零件默认列表隐藏。
- 锁库零件模块继续展示 WMS allocation 结果。
- 原始 `order_delivery_ticket` 不删除、不搬迁、不复制。
- 详情、锁库结果、日志和销售订单 U9 链路仍能通过 `ticketId` 完整溯源。
- 查询继续后端分页，新增索引支撑默认未完成池过滤。
- 全量后端测试、前端测试和前端 build 通过。

## 15. 关联变更历史快照

销售订单关联废弃时，已提零件工作池中的 WMS 锁库事实需要在废弃事务内快照到 `sales_order_linked_change_notice`。因此，即使提单行已经完成 WMS 动作并从本页面默认未完成池隐藏，关联变更页面仍能显示它是否提交过 WMS、当前结果和请求时间。

该快照是旁路通知记录，不复制、不删除 `order_delivery_ticket`，也不改变本文件定义的未完成池过滤。关联恢复只恢复仍由关联废弃负责的未完成 QPO 行，不回滚已完成 WMS 动作；业务员在关联变更页面通过“未处理 / 已处理”记录人工通知下游的进度。
