# AI 报价模块技术方案文档

日期：2026-08-25
最近更新：2026-08-26
状态：讨论稿
适用系统：QPO 报价系统

本文档记录 AI 自动报价模块的当前技术方案。当前方案不是简单地把“报价”交给大模型，而是在 QPO 现有核价引擎之上，增加“结构化业务属性 + CAD 几何特征驱动的相似件检索 + 可切换 Provider 工艺推荐 + 人工反馈闭环”。技术栈定调为 **Java QPO Core + FastAPI AI Quote Service + OCCT Parser Worker + Qdrant + PostgreSQL + MinIO**。第一阶段不把 OCR 作为前置能力；最终价格仍由系统已有确定性核价逻辑计算。

## 1. 当前阶段结论

1. **相同图号 + 版本仍然优先走历史复用**：系统已有重复报价能力，不需要 AI 重新判断。
2. **新件报价的难点在工艺判断和工时估算**：材料密度、材料单价、费率、工艺小时价都可以由主数据或配置维护。
3. **第一阶段输入可以不依赖 OCR**：物料描述、材料、表面处理、热处理等若已由业务员导入或确认，就应作为权威文字属性。
4. **CAD 图纸应成为新件识别的核心几何输入**：STEP/STP 等三维模型能提供尺寸、体积、面积、孔槽、曲面、复杂度等几何特征，更适合支撑工艺判断。
5. **OCR 后置为 V2 可选补充能力**：用于减少人工录入和校验漏填字段，不作为 V1 主流程依赖，也不作为几何和工时估算的主依据。
6. **RAG + 大模型不是唯一方案**：更稳妥的路线是先做结构化特征、相似件检索、规则推荐，再按条件接入外部 AI 或私有化模型。
7. **AI 只生成工艺草稿，不直接写最终价格**：AI 推荐的工艺路线、工时、非工时费用必须人工确认，再交给现有后端核价引擎重新计算。
8. **AI 报价模块采用双后端架构**：Java 后端保留 QPO 业务闭环、权限、日志、数据落库和最终核价；FastAPI 承接 CAD 解析编排、特征工程、向量检索和 AI 推荐。
9. **向量数据库采用独立 Qdrant**：不使用 `pgvector` 作为第一实现；Qdrant 只作为相似件检索加速器，不作为业务主库。
10. **技术架构必须可切换**：通过 Provider 抽象支持外部 AI、私有化模型、纯规则/相似件三种实现，避免未来被单一模型方案绑定。

## 3. 总体架构

推荐架构：**Java QPO Core + FastAPI AI Quote Service + OCCT Parser Worker + Qdrant 相似件检索 + PostgreSQL 业务事实库 + MinIO 文件对象库**。

```text
逐件核价页面
  -> AI 推荐工艺
    -> QPO Java 后端
       -> 权限校验 / 数据权限校验 / 操作日志
       -> 精确重复件检查
       -> 从 PostgreSQL 加载结构化业务属性、材料、工艺、费率、文件元数据
       -> 生成 AI 推荐任务
       -> 调用 FastAPI AI Quote Service
          -> 从 MinIO 读取 CAD 文件
          -> 调用 OCCT Parser Worker 解析 CAD 几何特征
          -> 生成 CAD 几何特征向量和业务属性向量
          -> 调用 Qdrant 召回历史相似件 ID
          -> Provider 生成工艺草稿
             -> RuleOnlyProvider
             -> ExternalAiProvider
             -> PrivateModelProvider
          -> 返回相似件 ID、相似原因、推荐草稿、置信度、风险提示
       -> Java 回 PostgreSQL 查询完整历史核价数据
       -> Java 后端输出校验和推荐结果落库
  -> 工程人员确认 / 修改
  -> 现有 submit-quote 保存
  -> QPO 现有核价引擎重新计算最终价格
```

### 3.1 系统边界

- AI 推荐接口不直接写 `tax_included_unit_price`、`base_cost` 等最终价格字段。
- 材料价格始终来自材料主数据或公司维护的材料价格配置。
- 工艺小时价始终来自 `dict_process_detail` / `dict_process_category`。
- 费率始终来自当前费用字典。
- 文件原件始终存储在 MinIO，PostgreSQL 保存文件元数据和业务事实。
- Qdrant 只保存向量、检索 ID 和少量过滤 payload，不保存业务主数据。
- FastAPI AI 服务不绕过 Java 写最终报价字段。
- 保存最终报价仍走现有核价保存链路，保证导出、历史快照、权限、日志继续兼容。

### 3.2 为什么不是“纯大模型报价”

纯大模型直接估价有三个问题：

1. **不可控**：模型可能编造工艺、漏工序、给出系统不存在的工艺项。
2. **不可审计**：报价金额很难解释到材料、工艺、费率、工时这些业务字段。
3. **不可稳定复算**：同一个零件在不同时间调用模型可能得到不同价格。

因此推荐让 AI 做“建议工艺路线和工时”，让 QPO 做“确定性计价”。这样既能利用 AI 处理复杂新件，又不破坏报价系统的可控性。

### 3.3 技术栈职责分工

| 组件 | 技术栈 | 职责 | 不负责 |
| --- | --- | --- | --- |
| QPO Java Core | Spring Boot / PostgreSQL / MinIO 客户端 | 用户权限、数据权限、操作日志、RFQ 主流程、报价保存、最终核价计算、业务数据落库 | CAD 几何解析、embedding、向量检索、模型推理 |
| FastAPI AI Quote Service | FastAPI / Python | AI 推荐编排、CAD 解析任务编排、特征工程、embedding 生成、Qdrant 检索、Provider 调用、推荐草稿生成 | 最终报价写入、费率计算、权限最终裁决 |
| OCCT Parser Worker | C++ / OCCT，可由 FastAPI 调用 | STEP/STP/IGES 读取、BRep/TopoDS_Shape 构建、几何属性和拓扑特征提取 | 业务权限、报价计算、AI 推理 |
| Qdrant | 独立向量数据库 | CAD 几何向量、业务属性向量、Top N 相似件召回、payload 过滤 | 业务主数据存储、报价历史权威存储 |
| PostgreSQL | 关系型数据库 | 零件、文件元数据、业务员确认属性、CAD 特征快照、历史核价、AI 推荐记录、反馈记录 | 大文件对象存储、向量主检索 |
| MinIO | 对象存储 | CAD/PDF/图片等图纸原文件存储 | 业务事实存储、向量检索 |

定调：AI 报价模块不是纯 Java，也不是纯 FastAPI。Java 是 QPO 业务主后端，FastAPI 是 AI 能力服务。两者通过明确 API 协作，避免后续 CAD、向量库、模型能力接入时推翻第一阶段架构。

## 4. 输入数据定位

### 4.1 V1 输入原则

第一阶段建议使用两类确定数据作为新件属性：

1. **业务员导入或确认的结构化属性**：用于表达材料、物料描述、表面处理、热处理、精度要求等文字和业务要求。
2. **CAD 解析得到的几何属性**：用于表达尺寸、体积、面积、孔槽、曲面、复杂度等加工难度特征。

这样可以先避开 OCR 的不确定性，把系统做成“确定字段 + 几何特征 + 历史经验”的推荐底座。OCR 后续可以作为减少人工录入和漏填校验的增强能力，不影响 V1 主流程上线。

### 4.2 业务导入属性：V1 权威文字来源

如果业务员已经能在导入或核价前提供以下字段，这些字段就应优先作为系统权威输入：

- 物料描述 / 零件名称。
- 材料牌号、材料形态、材料规格。
- 表面处理，例如阳极氧化、电镀、喷砂、发黑、喷涂。
- 热处理，例如淬火、调质、时效、硬度要求。
- 关键公差等级、精度要求、表面粗糙度等级。
- 去毛刺、倒角、清洗、包装、检验等技术要求。
- 数量、客户、版本、交付或特殊备注。

这些字段比 OCR 更稳定，也更适合作为相似件检索和 Provider 工艺推荐的输入。系统第一阶段应重点保证这些字段可导入、可校验、可补录、可追溯。

### 4.3 三维 CAD：V1 核心几何输入

CAD 文件，尤其是 STEP/STP，适合作为新件工艺推荐的主输入。它能提供稳定的几何特征，用于判断零件复杂度、加工难度和相似件。

建议优先提取：

- 包围盒尺寸：长、宽、高。
- 体积、表面积、表面积/体积比。
- 面数量、边数量、曲面数量、圆柱面数量。
- 孔数量、孔径范围、深孔风险。
- 槽、腔体、薄壁、倒角、台阶、曲面等复杂特征。
- 几何复杂度评分。
- 可加工方向、装夹复杂度的初步判断。

### 4.4 PDF / OCR：V2 可选补充

在物料描述、表面处理、材料等关键文字属性可由业务员导入的前提下，OCR 可以先不做。它的定位应从“主流程输入”调整为“后置增强能力”。

OCR 后续主要解决两类问题：

1. **减少人工录入**：自动识别标题栏、材质、表面处理、热处理、技术要求、公差备注等文字。
2. **校验漏填风险**：例如 OCR 识别到“阳极氧化”，但业务员未填写表面处理，系统提示补充确认。

OCR 能提取的内容主要包括：

- 标题栏：图号、版本、名称、客户、比例、单位。
- 材质：材料牌号、状态、替代材料说明。
- 表面处理：阳极氧化、电镀、喷砂、发黑、喷涂等。
- 热处理：淬火、调质、时效、硬度要求。
- 技术要求：去毛刺、锐边倒钝、清洗、包装、检测要求。
- 公差和备注：一般公差、关键尺寸说明、特殊检验说明。

OCR 不适合直接解决：

- 准确识别三维几何结构。
- 稳定计算体积、面积、孔槽数量。
- 直接判断完整工艺路线。
- 直接估算每道工艺工时。

因此 V1 可以不建设 OCR；V2 再把 OCR 作为“字段预填 + 漏填校验 + 风险提示”接入。

### 4.5 人工确认数据：最终业务权威

以下数据建议仍由人工选择或公司配置维护，AI 只做辅助：

- 材料选型和材料形态。
- 材料价格、密度、损耗规则。
- 工艺大类小时价、具体工艺小时价。
- 费用费率、税率、管理费、利润率等。
- 是否采纳 AI 推荐工艺。

### 4.6 历史核价：经验来源

历史核价是 AI 报价最重要的数据资产。系统应从历史记录中提取：

- 零件图号、版本、名称、客户、行业。
- 材料数据、尺寸、重量。
- 业务导入的物料描述、表面处理、热处理、技术要求等结构化属性。
- CAD 特征快照。
- V2 可选 OCR 文字摘要。
- 最终人工确认的工艺路线。
- 每道工艺工时和非工时费用。
- 最终报价、毛利、报价结果。
- AI 建议与人工修改差异。

## 5. 推荐分层策略

### 5.1 第一层：精确重复件

输入：当前零件 `partNo + version`。

处理：

1. 复用现有重复报价逻辑。
2. 查找可复用历史项：有价格、有材料快照、有工艺路线、允许重复匹配。
3. 命中后直接建议使用历史报价逻辑。
4. 不调用 AI，避免不必要成本和不确定性。

输出：

- `mode = EXACT_REPEAT`
- 历史 RFQ、历史零件 ID、历史工艺路线。
- 建议操作：使用现有重复报价。

### 5.2 第二层：CAD 特征相似件检索

输入：当前零件结构化业务属性、CAD 特征、人工材料选择；如果 V2 启用 OCR，再补充 OCR 摘要。

相似度可由多类特征共同计算：

- 材料类别和材料牌号。
- 包围盒尺寸、体积、表面积、重量。
- 孔、槽、腔体、薄壁、曲面等加工特征。
- 表面处理、热处理、技术要求。
- 零件名称和描述文本。

输出：

- Top N 个相似历史零件。
- 每个案例展示材料、尺寸、CAD 特征、工艺路线、工时、最终价格。
- 相似原因，例如“材料一致、体积接近、孔数量接近、表面处理一致”。

注意：输入件在推荐前没有工艺路线，因此相似件检索不能用“输入件工艺”做匹配条件。历史工艺路线只作为被召回相似件的参考结果，用于帮助业务员判断输入件可能需要哪些工艺和工时。

### 5.3 第三层：Provider 工艺推荐

Provider 根据相似案例、工艺字典、结构化业务属性、CAD 特征生成结构化工艺草稿；OCR 摘要只在 V2 启用后作为可选补充。

输出只允许使用系统已有工艺 ID 和费用项，例如：

```json
{

  "mode": "AI_SUGGESTION",
  "confidence": 0.82,

  "processRoute": [
```

## 6. CAD 特征解析方案

### 6.1 支持优先级

建议按落地难度和业务价值分阶段支持：

1. **STEP / STP**：优先支持，格式通用，适合提取三维几何特征。
2. **IGES / IGS**：第二阶段支持，兼容部分历史 CAD 文件。
3. **DXF / DWG**：适合二维图纸和轮廓信息，但对三维工艺判断帮助有限。
4. **SolidWorks / ProE / UG / CATIA 等原生格式**：可放到后期，通过商业 SDK 或统一转 STEP 处理。

### 6.2 CAD 解析工具选型决策

当前明确选择 **Open Cascade / OCCT** 作为 CAD 几何解析的正式技术路线。

选择原因：

1. OCCT 是面向三维建模、CAD 数据交换和可视化的底层几何内核，适合做长期可控的 CAD 解析能力。
2. OCCT 支持 STEP、IGES、BREP 等中性格式，符合当前优先解析 STEP/STP 的方向。
3. OCCT 能做拓扑遍历、曲面类型识别、圆柱面识别、几何属性计算，后续可以继续扩展孔、槽、薄壁、深腔等加工特征。
4. OCCT 更适合作为正式服务底座，避免先用 FreeCAD 或 pythonocc 做完原型后再重构一遍核心解析逻辑。

官方依据：OCCT 官方介绍将其定位为提供三维曲面和实体建模、CAD 数据交换、可视化能力的软件开发平台；其数据交换模块包含 STEP、IGES、BREP 等相关能力。

其他工具定位调整如下：

| 工具 | 角色定位 | 是否作为主路线 | 说明 |
| --- | --- | --- | --- |
| Open Cascade / OCCT | 正式 CAD 几何解析内核 | 是 | V1/V2 主路线，负责 STEP/STP、IGES、BREP 解析和几何特征提取 |
| pythonocc-core | 原型验证或离线分析辅助 | 否 | 可用于快速实验算法，但不作为正式生产依赖 |
| FreeCAD CLI | 格式转换或人工排障辅助 | 否 | 可用于临时验证文件和转换，不作为核心解析服务 |
| 商业 CAD SDK | 后期原生格式增强 | 否，后期评估 | 仅当必须稳定支持 SolidWorks、UG/NX、Creo、CATIA 原生格式时再评估 |

结论：V1 就按成熟方向建设 `OCCT CAD 解析服务`，不再把 FreeCAD CLI 或 pythonocc-core 作为主方案。

### 6.3 OCCT 解析服务形态

考虑到 QPO 后端是 Java 服务，而 OCCT 是 C++ CAD 内核，CAD 解析能力应放在 FastAPI AI Quote Service 侧编排，并由独立 OCCT Parser Worker 执行。Java 后端不直接依赖 OCCT 编译环境，也不直接执行 CAD 几何解析。

推荐形态：

```text
QPO Java 后端
  -> 创建 CAD 解析 / AI 推荐任务
  -> 调用 FastAPI AI Quote Service
     -> 读取 MinIO CAD 文件或接收临时文件引用
     -> 调用 OCCT Parser Worker
        -> STEP/STP/IGES 文件读取
        -> BRep / TopoDS_Shape 构建
        -> 几何属性计算
        -> 拓扑和曲面特征提取
        -> 返回结构化 JSON
     -> 生成几何特征向量
     -> 写入 / 查询 Qdrant
     -> 返回 CAD 特征、向量索引 ID、相似件 ID
  -> Java 保存 cad_feature_snapshot 和推荐记录
```

这样设计的好处：

- CAD 解析失败不会拖垮 QPO Java 主后端进程。
- FastAPI AI 服务和 OCCT Parser Worker 可以单独扩容。
- OCCT 版本、编译环境、系统依赖可以独立管理。
- 解析服务可以先做同步接口，文件大或耗时长时再升级为异步任务。
- 后续接商业 SDK 或原生 CAD 转换服务时，不影响 QPO 主核价链路。

### 6.5 特征提取阶段

2. **复杂度特征阶段**：孔、槽、圆柱面、曲面、薄壁、深腔、倒角、台阶。
3. **工艺提示阶段**：根据特征提示 CNC、车削、线切割、表面处理、热处理、检验等可能工艺。

## 7. Provider 架构和技术选型

### 7.1 Provider 抽象

Provider 抽象建议放在 FastAPI AI Quote Service 内，Java 后端只通过统一 AI 推荐接口调用 FastAPI，不直接接触外部模型、私有模型或 Qdrant 客户端。

```text
QPO Java 后端
  -> AiQuoteClient
    -> FastAPI AI Quote Service
       -> AiQuoteSuggestionService
          -> AiQuoteSimilarityService
          -> AiQuoteProviderRouter
             -> RuleOnlyProvider
             -> ExternalAiProvider
             -> PrivateModelProvider
          -> AiQuoteValidationService
```

Provider 输入一致，输出也一致。未来切换外部 AI、私有化模型或纯规则实现时，不影响前端、Java 权限日志、PostgreSQL 业务事实和最终核价保存链路。

### 7.2 RuleOnlyProvider

适用场景：初期低成本验证、AI 服务不可用、合规未通过、标准件或相似度很高的零件。

实现方式：

1. 精确重复件优先。
2. 根据结构化业务属性、材料和 CAD 特征召回相似件。
3. 输出相似件工艺路线、工时区间、中位数、参考案例。
4. 不调用大模型，不生成自由工艺名称。

价值：稳定、可解释、容易先落地，也可以作为所有 AI Provider 的降级方案。

### 7.3 ExternalAiProvider

适用场景：允许数据出网，希望快速验证 AI 效果，图纸理解需求较强。

实现方式：

1. 后端先完成相似件召回和敏感信息最小化。
2. 只发送必要的结构化业务属性、CAD 特征摘要、工艺字典、相似案例摘要；V2 启用 OCR 后再附加 OCR 摘要。
3. 外部模型按 JSON Schema 返回工艺草稿。
4. 后端强校验工艺 ID、工时、费用项、置信度和异常范围。
5. 失败或超时时降级到 RuleOnlyProvider。

优点：上线快，多模态和文本理解能力强，适合 POC。

限制：需要合规评估、调用成本、网络稳定性和供应商依赖。

### 7.4 PrivateModelProvider

适用场景：图纸和客户数据敏感，要求内网闭环，长期生产环境希望可控。

实现方式：

1. CAD 解析、embedding、Qdrant 检索和模型推理全部在内网完成；如果启用 OCR，OCR 也在内网完成。
2. 使用 Qdrant 召回历史相似件 ID，再由 Java 回 PostgreSQL 查询完整业务数据。
3. 私有 LLM 按同一 JSON Schema 生成工艺草稿。
4. 后端执行同一套校验、日志和反馈记录。

优点：数据不出内网，长期可控，可逐步结合自有历史样本优化。

限制：初期硬件、模型部署、运维、效果调优成本较高。

### 7.5 技术选型建议

当前最推荐的落地顺序：

1. **先建设 Java + FastAPI 双后端、OCCT CAD 特征解析服务、Qdrant 相似件检索和 RuleOnlyProvider**，快速验证历史数据是否足够支撑推荐。
2. **允许数据出网时接 ExternalAiProvider 做 POC**，验证复杂新件的工艺草稿质量。
3. **数据敏感或长期生产时再建设 PrivateModelProvider**，把同一套接口、校验和反馈迁移到内网模型。
4. **数据积累后再训练专门模型**，例如工艺选择多标签分类模型、工时回归模型。

#### 10.5.1 CAD 几何特征向量生成方式

CAD 几何特征向量不是直接把 CAD 文件整体丢给向量库，而是先由 OCCT 解析出可解释的几何字段，再把这些字段转换成统一尺度的数值数组。

示例原始特征：

- `bbox_length`
- `bbox_width`
- `bbox_height`
- `volume`
- `surface_area`
- `surface_area_to_volume_ratio`
- `face_count`
- `edge_count`
- `curved_face_count`
- `cylindrical_face_count`
- `hole_count`
- `min_hole_diameter`
- `max_hole_diameter`
- `thin_wall_risk`
- `deep_cavity_risk`
- `complexity_score`

生成步骤：

1. **解析原始特征**：OCCT 从 STEP/STP 中提取尺寸、体积、面积、拓扑数量和复杂度特征。
2. **补充派生特征**：生成长宽高比例、面积/体积比、孔密度、曲面占比、复杂度分段等更适合比较的字段。
3. **做单位统一**：统一长度、面积、体积单位，避免 mm、cm、m 混用。
4. **做数值变换**：对体积、面积、面数、边数等跨度很大的字段做 `log1p` 等压缩，避免大零件完全压过其他特征。
5. **做标准化**：基于历史样本均值和标准差，把不同量纲的字段变成可比较尺度。
6. **做权重调整**：按业务经验给关键特征更高权重，例如材料和体积通常比边数更重要。
7. **写入向量索引**：保存向量、特征版本、标准化版本、源 `cad_feature_snapshot_id`。

示例：

```json
{
  "itemId": 12345,
  "cadFeatureSnapshotId": 66,
  "featureSchemaVersion": "cad-geom-v1",
  "scalerVersion": "cad-scaler-2026-08",
  "vector": [0.18, -0.42, 1.31, 0.77, -0.12, 0.64, 0.09, 1.02]
}
```

成熟落地方式建议先采用“可解释特征工程 + 标准化 + 加权近邻检索”。不建议第一阶段直接上三维深度学习、点云模型或 mesh embedding，因为它们需要大量高质量标注样本，解释性和落地成本都不如结构化几何特征方案。

## 11. 输出校验规则

AI 或规则推荐结果进入前端前必须校验：

1. `processDetailId` 必须存在于启用的具体工艺字典。
2. 具体工艺所属大类必须启用。
3. `unitWorkHours` 必须大于 0 且不超过配置上限。
4. 非工时费用项必须存在于启用的 `dict_extra_fee_item`。
5. 非工时金额必须大于等于 0 且不超过配置上限。
6. 工序数量不能超过配置上限。
7. 工序顺序必须合法，不允许重复或空排序。
8. 置信度低于阈值时只能展示，不能一键应用。
9. Provider 返回的金额只作为展示参考，保存时必须由现有核价引擎重算。
10. CAD 解析失败不能阻断人工核价，应降级到手工或 RuleOnly 模式；V2 OCR 失败只影响字段预填和漏填提示。

### 12.2 `engineerApi.js`

建议新增：

- `suggestAiQuote(itemId, payload)`
- `saveAiQuoteFeedback(suggestionId, payload)`
- `extractCadFeature(itemId, payload)`

### 12.3 交互原则

- AI 推荐不应自动关闭核价弹窗。
- AI 推荐失败不能影响用户手工核价。
- 应用 AI 推荐后，用户仍可以手动调整。
- 用户提交核价时仍调用现有 `submitQuote`。
- AI 推荐必须展示参考案例和风险提示，不能只给一个结论。

## 14. 分阶段实施路线

### 阶段 0：数据盘点

目标：确认历史数据能不能支撑推荐。

- 统计历史可复用核价数量。
- 统计 `process_route` 非空数量和质量。
- 统计材料编码完整率。
- 统计工艺路线平均行数、常见工艺组合和工时分布。
- 统计 STEP/STP、IGES、DWG/DXF、原生 CAD、PDF 格式占比。
- 统计业务员可导入字段的完整率，例如物料描述、材料、表面处理、热处理、技术要求。
- 抽样检查历史人工核价是否稳定一致。

阶段产出：历史样本质量报告、图纸格式报告、第一版相似件特征清单。

### 阶段 1：双后端基础和 OCCT CAD 特征解析服务

目标：建立 Java + FastAPI 双后端基础，并基于 Open Cascade / OCCT 建设正式 CAD 解析能力，先让系统能从 STEP/STP 中稳定提取基础几何特征。

- 建立 FastAPI AI Quote Service 基础工程和内部 API。
- Java 后端新增 `AiQuoteServiceClient`，通过内部接口调用 FastAPI。
- 建立独立 `OCCT Parser Worker`。
- Java 后端创建解析任务、校验文件哈希、复用已有快照；FastAPI 调用 OCCT Parser Worker 执行解析。
- 解析服务优先支持 STEP/STP，第二阶段扩展 IGES/IGS。
- 提取尺寸、体积、表面积、面数、边数等基础特征。
- 提取圆柱面、曲面等可支撑后续孔洞和复杂度判断的拓扑特征。
- 保存 `cad_feature_snapshot`。
- 在逐件核价页面展示 CAD 特征摘要。

阶段产出：Java/FastAPI 内部调用链路、OCCT Parser Worker、CAD 特征快照、解析成功率、解析耗时、失败原因分类。

### 阶段 2：结构化业务属性和相似件检索

目标：不依赖 OCR，先用业务员导入的确定字段和 CAD 几何特征建立可解释推荐。

- 明确 V1 必填或建议填写的业务属性字段。
- 建立字段校验和缺失提醒，例如表面处理、热处理、关键精度要求未填写时提示风险。
- 建立历史核价样本视图。
- 建立 Qdrant collection 和索引重建任务。
- FastAPI 生成 CAD 几何向量和业务属性向量，写入 Qdrant。
- 用材料、业务导入属性和 CAD 几何特征做相似件召回。
- 召回后带出历史相似件的工艺路线分布、工时中位数和区间，作为输入件工艺参考。
- 前端支持用户从相似件中套用或调整工艺路线。

阶段产出：V1 可用的相似件推荐底座，也是 AI 失败时的降级方案。

### 阶段 3：RuleOnlyProvider 工艺草稿

目标：在不接大模型的情况下，根据相似件和规则生成工艺草稿。

- 在 FastAPI 中新增 `AiQuoteProvider` 抽象和 `RuleOnlyProvider`。
- 只基于确定字段、CAD 特征和历史相似件输出推荐工艺路线。
- 输出工时区间、中位数、参考案例和置信度。
- 不调用大模型，不依赖 OCR。

阶段产出：低成本可上线版本，工程人员可人工确认或修改后保存。

### 阶段 4：Provider 抽象和外部 AI 验证

目标：验证 AI 对复杂新件工艺草稿的帮助。

- 在 FastAPI 中新增 `ExternalAiProvider`。
- 定义统一 JSON Schema。
- 调用外部 AI 时只发送脱敏业务属性、CAD 特征、工艺字典和相似案例；不把 OCR 作为前置条件。
- FastAPI 做结构化输出校验，Java 后端做最终业务校验和落库。
- 记录 AI 建议和人工修改差异。

阶段产出：AI 推荐采纳率、修改率、失败率、平均耗时、典型错误清单。

### 阶段 5：私有化模型评估

目标：判断是否需要内网模型替代外部 AI。

- 评估图纸和客户数据合规要求。
- 评估本地 embedding、Qdrant 容量、LLM 部署成本；OCR 仅在 V2 需要减少录入时评估。
- 接入 `PrivateModelProvider`，复用同一接口、Schema、校验和反馈表。
- 与外部 AI 和 RuleOnly 结果对比。

阶段产出：私有化可行性报告、成本评估、效果对比。

### 阶段 6：可选 OCR 增强

目标：在 V1 推荐链路稳定后，用 OCR 减少人工录入和校验漏填字段。

- 对 PDF 图纸做 OCR。
- 提取标题栏、材质、表面处理、热处理、技术要求、公差备注。
- 保存 `drawing_text_snapshot`。
- OCR 结果只用于字段预填、漏填提醒和风险提示。
- OCR 识别结果必须由业务员确认后才能进入推荐主输入。

阶段产出：图纸文字摘要、OCR 准确率抽样结果、字段化提取规则。

### 阶段 7：反馈闭环

目标：让系统持续学习经验，而不是停留在一次性推荐。

- 保存 AI 建议与人工最终输入差异。
- 输出采纳率、修改率、拒绝率、按工艺的误差分布。
- 根据反馈优化相似度权重、规则阈值、prompt 和校验边界。
- 形成可训练样本。

阶段产出：反馈分析报表、高质量训练样本集。

### 阶段 8：工艺选择和工时预测模型

目标：当数据量足够后，让数值预测更稳定。

- 训练工艺选择模型：多标签分类，预测需要哪些具体工艺。
- 训练工时预测模型：回归模型，预测每道工艺工时。
- 输入包含材料、业务导入属性、CAD 特征和相似案例；历史人工确认工艺和工时作为训练标签，不作为新输入件的匹配条件。
- 模型输出仍经过 `AiQuoteValidationService` 校验。
- 大模型更多承担解释、复杂图纸理解和异常提示。

阶段产出：专门模型、离线评估报告、线上灰度策略。

## 15. 风险和控制

### 15.1 主要风险

- CAD 解析失败或不同格式兼容性差。
- 历史核价本身不一致，导致相似件推荐学习到错误经验。
- 工艺字典命名不规范，影响 AI 和规则匹配。
- V2 启用 OCR 后，OCR 识别错误可能导致字段预填或漏填提示不准确。
- 非工时费用经验性强，模型预测波动较大。
- 外部 AI 服务涉及图纸和客户数据合规风险。
- 用户过度信任 AI，跳过必要复核。

### 15.2 控制措施

- 初期只做草稿，不自动保存最终报价。
- 后端强校验工艺 ID、工时、费用项和范围。
- 展示相似案例、置信度和风险提示。
- 低置信结果必须人工确认。
- CAD 失败时自动降级到手工或相似件弱匹配；V2 OCR 失败不影响 V1 推荐链路和人工核价。
- 所有 AI 请求和结果只记录摘要，敏感内容脱敏或不落库。
- 定期抽样复盘 AI 建议与人工最终结果。

## 16. 后续讨论重点

下一步建议围绕以下问题继续细化：

1. 公司历史核价样本量是否足够，尤其是新件、相似件、复杂件的样本质量。
2. 当前图纸文件中 STEP/STP、PDF、DWG/DXF、原生 CAD 的占比。
3. CAD 解析优先做哪些特征，哪些特征必须人工确认。
4. 外部 AI 是否允许接入，允许发送哪些脱敏字段。
5. 私有化部署的成本和硬件边界。
6. AI 推荐结果是只辅助单件，还是未来要支持整单批量草稿。
7. 什么置信度和差异范围可以一键应用，什么情况必须强制人工复核。
